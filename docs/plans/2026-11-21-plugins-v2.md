# Handover: plugins v2

**Status**: 2026-11-21. For whoever builds plugins v2, after v1 has landed.
The owner will land a second plugin with v2; nothing here starts before v1 is
merged and has run on a host.

## Where things stand

- v1 is specified in `docs/specs/2026-11-21-plugins.md` and its three parts,
  `-security`, `-web` and `-hooks`. Read them first: v2 adds to them and must
  not loosen a v1 rule.
- The reference plugin is `tehas-app/tehas-plugin-floorplan` (Apache-2.0).
- The first design covered everything below in one spec. Six reviews, one
  per part, found every part not ready (pull request #2634, the comment
  "Review of the spec, six parts"). v1 kept what could be made sound at once.
  This handover keeps the rest, with what the reviews found, so v2 does not
  rediscover it.
- The first design's text is in the history of `docs/specs/`, at commit
  `2528c2d5` ("Spec for plugins, with Floorplan as the first (#2634)"), the
  version that was merged before the review. Its `-chats` and `-industry`
  parts were removed from the tree after it.

## What v2 is for

v1 lets a plugin show a view, read the code, call the model and report on a
pull request. v2 lets it do more in the factory's own surfaces, each behind
its own grant, without a v1 rule getting weaker:

| Surface | What it adds |
| --- | --- |
| Gates | A hook that can hold, at more stage points |
| Chats | Skills and tools for Obeya's and tehas-industry's chats |
| Outside | A view, and later a run, reaching other hosts through the factory |
| Factory data | A plugin reading the factory through the MCP server |
| Inspection | Every crossing through one check, kept for a mass review, quarantine |
| Menu | Plugins in a menu section of their own, more than one view, `open: page` |
| Kinds | A plugin with a server of its own (`kind: "service"`) |
| Model | A queue in front of the endpoint, more than one model |
| Secrets | A key a plugin's proxy requests carry, never the plugin |
| Industry | What industry builds to show and roll out plugins |

## The second plugin

Pick a second plugin that needs at least one v2 surface and is small: it is
the proof that the contract generalises. Two that fit:

- **A licence or dependency check** as a gate on `after:work`: reads
  `/product` at the head, no model, `fail` when the change adds a dependency
  under a licence the instance refuses. It proves gates without a view.
- **A product-docs skill** for Obeya: a skill and a `find-doc` tool that
  answer from an index the refresh builds, no model in the call. It proves
  chats.

Whichever it is: its own repository in tehas-app (`tehas-plugin-<name>`),
Apache-2.0 or closed to prove the licence rules, and its own argument lists in
`test/fixtures/argv/plugin-*`.

## Gates and more hook points

v1 has `hook:after:work`, report only, after the report, as a commit status.
v2 adds `gate:<point>` and points `before:work`, `before:plan`, `after:plan`,
`before:refresh`, `after:refresh`.

What the hooks review found, which v2 must answer:

1. **A hold must stop the merge, not swap a label.** pi-rukas opens the pull
   request inside the container (`console/cycle/src/work.rs:158`), so at any
   `after:` point it is already mergeable. Use the v1 status: a gate's `fail`
   posts `failure`, and the factory makes `tehas/plugin/<name>` a required
   check. Say plainly that without branch protection a gate is advisory.
2. **A refresh launders a hold.** The supervisor takes
   `needs-human-attention` off before a start (`supervise.rs:432`, `466-472`)
   and the report takes the awaiting-merge arm (`report.rs:1561-1571`). Keep
   the verdict per head commit; a cycle end whose head has no passing gate
   verdict never takes the awaiting-merge arm. v1 already runs the hook on
   refreshes, so the seam is there.
3. **Time.** A gate that must finish before the report runs inside the unit's
   `RuntimeMaxSec=8h` (`host/systemd/tehas-cycle@.service:24`), which leaves
   about an hour after `TEHAS_WORK_TIMEOUT`. Give gates a budget,
   `TEHAS_PLUGIN_GATES_BUDGET`, taken off the cycle's deadline in `work.rs`
   beside the handoff allowance, and refuse at load when timeout, grace,
   budget and report pass 8 hours.
4. **The seam.** Between `supervise()` and `apply::run`
   (`supervise.rs:473-490`). The report is a pure function of `Facts`
   (`report.rs:1-9`), so the verdict is a file `Facts` reads, on the
   `spec-block` park's pattern (`report.rs:2034`).
5. **The park reason.** `park_reason` is `a-z` and `-`, 40 characters
   (`console/store/src/verbs.rs:343`). Use `plugin-gate`, with the plugin's
   name in a field of its own; `tehas blockers` reads it.
6. **Fail closed, both ways.** A gate that crashes or times out holds. A held
   (quarantined) plugin's gate holds too, with reason `plugin-gate held`,
   until a person releases it or takes the grant away. The first design turned
   it into a note, which an inspector trip would use to switch a gate off.
7. **A way out.** `tehas plugin hook <name> <pr>` exists in v1; say that it
   re-runs a gate and what a person does to release a hold.
8. **The plan points** are posted by the dispatcher's poll, not pi-rukas
   (`host/docs/operating.md:1151-1153`); a container must not run in a poll.
   The seam is the end of `tehas-plan-<issue>.service`. "Update this issue"
   runs no container, and a plan with no open points starts a cycle with no
   tick: a gate's `fail` must turn that into a question.
9. **`before:work`** sits after the start check inside `tehas work`, where
   `tehas:running` is already on and the dispatcher waits 300 s for the start
   (`supervise.rs:130-133`). Name the refused end it leaves
   (`report.rs:1489-1494`).
10. Freeze, thaw, a host restart mid-gate, and outsource contractors: hook
    timeouts on the cycle's clock (`console/cycle/src/clock.rs`); a contractor
    leaves no workspace on the host, so the head is fetched as `finish` does.

## Skills and tools for chats

A plugin adds a skill (instructions) and tools to Obeya's chat and industry's
wizard and assistant. tehas lists the granted skills and runs a tool; the chat
hosts reach them through industry.

What the chats review found:

1. **A skill must not be system text.** Both hosts put everything in one
   system message (tehas-obeya `crates/obeya/src/turn.rs:83-149`; industry
   `crates/workshop/src/assistant.rs:640`). Make a skill untrusted reference
   text: the prompt lists its id and a one-line `about`; the text comes as a
   tool result marked `"untrusted": true, "source": "plugin:<name>"` when the
   model asks for it. A total cap across plugins, 8 KiB.
2. **A taint rule in the hosts.** In a turn whose context holds a plugin's
   skill or answer, write proposals (`propose_text`, `draft_ticket`,
   `propose_change`, a hold's `reason`) are refused, or shown with the
   plugin's label and the whole text, and links in the reply are not live.
   Those proposals write into tickets that cycles read.
3. **Arguments carry the person's data.** A tool's arguments can hold ticket
   text, the person's earlier chats, and in the wizard code and team memory,
   with no `product` grant. Cap them (2 KiB), refuse `params` schemas with
   unbounded strings, and show the person what was sent.
4. **A call keeps nothing.** Its stdout and stderr are discarded, its `/out`
   is a tmpfs thrown away, no chat payload is ever kept for review, and a
   crossing row for a call holds no login.
5. **`--login` proves nothing.** Whoever runs commands as the factory user
   names any login (`host/docs/api.md`: "getting to the machine is the
   caller's business"). State it as a filter for a person who lost access,
   not authentication. Ask industry for a gate word for calls that its
   millwright's pi session does not hold.
6. **Latency.** Obeya, workshop, SSH gate, `incus exec`, `tehas`, `docker
   run`, with 20-second timeouts on the way (industry
   `gate-client/src/lib.rs:48`, `backend.rs:171`). Tool `timeout` 1 to 10
   seconds, no `model` and no `/product` in a call in v2, an image built ahead,
   concurrency per person. A long-lived call container is a later kind.
7. **Shapes.** Answers at most 16 KiB (both hosts cut at 24,000 bytes,
   Obeya `turn.rs:31`); function names `plugin_<name>_<tool>`, 64 characters of
   `[a-zA-Z0-9_-]`; a `chats` selector per skill; the JSON of `skills --json`
   and `call --json` with schemas in `api/`; exit statuses per outcome;
   caching by pin.
8. What Obeya and industry each build is listed in the review's findings 6.

## The view reaching outside: `/_proxy/` and `net:`

A view asks its own name, `/_proxy/<host id>/<path>`, and the gate fetches
from a granted host. What the web review found:

- SSRF: connect to the checked address (no second lookup), check every A and
  AAAA, refuse IPv4-mapped and NAT64 IPv6, unique-local, CGNAT, `0.0.0.0/8`,
  multicast and the Docker bridge ranges; 443 only; no proxy from the
  environment; the key only to the granted origin, never after a redirect;
  normalise the path before the prefix check.
- Answers never become documents: `Content-Disposition: attachment` or serve
  only to `Sec-Fetch-Dest: empty` or `image`; drop all upstream headers but
  type and length; a bounded decompressor with the cap after decoding.
- Rate limits per login as well as per plugin.
- A `net` grant names the origin, not only an id, so a new pin cannot repoint
  it.
- The key a host needs is a secret in `~/.config/tehas/env`, never
  `instance.env` (`load.rs:8` refuses tokens there). Its name must not be
  ambiguous: plugin `a-b` with host `c` and plugin `a` with host `b-c` both
  give `A_B_C` under the first design's rule.
- Runs reaching outside go through the same proxy, with the same grants; the
  `tehas-egress` pattern (`console/mcp/src/egress.rs`) is the precedent.

## Factory data for plugins

`factory-read` and `factory-sessions`: an MCP key made for a plugin. MCP keys
are read from the environment at the server's start
(`host/docs/mcp-server.md:170`), so "made for the plugin" needs a mechanism:
a key file the server rereads, or a key per plugin in `~/.config/tehas/env`
and a restart. A run reaches the MCP server only through a socket, as the
model, since runs have no network.

## Inspection: crossings, mass review, quarantine

Every crossing (skill text, tool calls, model requests, proxy fetches, hook
verdicts, view pages at the swap) goes through one `inspect(crossing) ->
Verdict` in `console/core`: `allow`, `block`, `hold`. What the security
review found:

- `inspect` runs in at least five programs; it is a library, and `hold` needs
  a store flag every one of them and the edge reads.
- Rows per model request and per fetch flood the state store the dispatcher
  needs: a database of their own, a retention period, rate limits.
- Streamed answers cannot be inspected before delivery unless buffered; v1's
  socket answers whole, keep it so where inspection is on.
- Mask the kept copy only: `mask.rs:106` rewrites private addresses and would
  corrupt prompts.
- Kept payloads hold source code, chat arguments and logins: store under
  `~/tehas/state/`, mode 600, never through MCP, and industry's mass review
  takes rows only unless a factory opts in. Never keep a chat payload. A short
  payload's sha256 is guessable, so a row "holds no content" only with a keyed
  hash.
- An LLM prompt detector is one more step in `inspect`, inline or over a day's
  kept crossings. It is tehas's or industry's, never a plugin's.

## The menu, views and kinds

- Plugins take panels from the person's four in v1. v2: a list of their own,
  `live/plugins.json`, and a menu section on both front pages, with `open:
  dock` or `page`. `tehas panel` and the host bridge's `menu` stay as they are.
- More than one view per plugin, each its own path.
- `kind: "service"`: a plugin with a server of its own behind the gate, the
  Obeya way. It needs the gate to proxy to a container on a network the gate
  alone reaches, and every rule of the web part still applies.
- Widgets inside the dashboard's own pages would run a plugin's code on the
  dashboard's origin. Not without a design that isolates them.

## The model, again

- The cycles call the endpoint directly (`test/fixtures/argv/work-egress.5`),
  so v1 cannot put plugins behind them. A queue in front of the endpoint that
  both use, or a share of `tehas.slice`'s model capacity, is v2's.
- `model` in hooks and gates: only once a gate's wait cannot stop the line.
- More than one model, by a name the grant gives.
- Token figures across plugins and cycles in analytics, once #2277 keeps
  them for the proxy.

## Industry

v1: industry writes `TEHAS_PLUGINS` and the grant lines into the
`instance.env` it pushes; the settings repository's pull request is the
review. v2 is industry's own work, specified in tehas-industry:

- `[plugin.<name>]` in its settings, with the factories it goes to. A factory
  created later gets none without a person.
- Reading `tehas plugin --json` on each factory: wanted pin against reported,
  refusals, drift, retries per factory, never all-or-nothing.
- Holding a plugin everywhere: record who held it; industry releases only its
  own hold; a hold covers the name across pins.
- Its words: industry already has `factory adopt` and `factory hold` with
  other meanings, so tehas's verbs stay `plugin ...` and set lines.
- The first design's `tehas plugin adopt`, `state/plugins.json` and a ceiling
  in `instance.env` were dropped: industry writes that file itself, so a
  ceiling there limits nothing (industry `crates/settings/src/lib.rs:571`,
  `FACTORY_FILES`).

## Rules v2 keeps

- Every new surface is a new capability, a new row in the security part's
  table, a branch of the one pure function, and its own argument list in
  `test/fixtures/argv/`. Adding one never loosens one that is there.
- Grants name the commit.
- A refused plugin is skipped, never fatal to `tehas update`.
- Nothing a plugin wrote is a command to tehas, and nothing of a plugin
  reaches a cycle's agents.
- Every address behind the GitHub sign-in; no stray URL.
