# Toward v1.0.0

Notes toward the 1.0 release. Change this page as decisions are made.

Started 2026-11-16, at v0.30.6.

## What 1.0 means

- tehas as it runs today, with its dead and half-built parts taken out, its
  public surface written down and pinned by tests, and three new features
  built behind flags: outsourcing (#2270), the EGM spec pipe, and a working
  Protolab path.
- The features that stay work. 1.0 is not a campaign to prove every row of
  `host/docs/features.md` again.
- After 1.0, the contract changes only with a major version. Within 1.x a
  setting, label, command, exit status or schema field is only added.
- A correct contract comes before the date. Anything that could force a
  breaking change soon after 1.0 is settled before the first beta. When time
  runs short, features are cut, never contract questions.

## Removals

Everything below goes in an alpha. What is still in the tree at the first
beta is frozen.

- **The improvement loop.** Its program, units, prompt and settings, and the
  `cross-project` label. `tehas:improvement` stays, with a generic
  description, for the issues the review files.
- **Easy merge** and `TEHAS_EASY_MERGE`. Nothing starts it today, so the
  setting turns on a path no host can run. It may come back later behind a
  flag.
- **The `fixer` fields** of the factory API (`fixer`, `fixer-grant`). The
  `fixer` keys in other output are renamed.
- **Compatibility older than 0.30.** 1.0 opens a store from v0.30.0 (schema
  12) or newer. An older store is refused with a message that says to update
  to 0.30 first. The old importer, the early schema steps and the retired
  setting names go with it.
- **`TEHAS_CYCLE_REPORT`**, which has one allowed value and no reader.

A setting that is removed or renamed is refused with exit 78 and a message
that names the fix. `tehas update --check` lists each one before the update
changes anything.

## Features and flags

Every new feature lands behind a flag, off by default, until the release
that ships it. No update switches anything on: a flag is off unless the
instance sets it.

Two words, two meanings:

- **Feature**: what the release has. `tehas api --json` lists it in
  `features`. A word is only added in 1.x, never removed.
- **Flag**: what this instance has on. `tehas api --json` gives `flags`, an
  object from name to true or false.

A feature is either building or shipped:

- **Building**: in the code, but it cannot be switched on. Its settings and
  commands exit 78, and it adds no label, `--json` field or MCP tool. It is
  not part of the contract and may change: its rows in
  `api/settings-rules.json` (marked `"building": true`), its key in `flags`,
  its `--json` fields, commands and MCP tools may change or go until the
  release that ships it. Only shipped features' keys are guaranteed in
  `flags`.
- **Shipped**: an instance may switch it on. Its surface is part of the
  contract whether the flag is on or off.

Outsource, the spec pipe and the Protolab's external zip ship as shipped
only if each has its host proof by the first release candidate. One without
a proof ships as building and comes in a 1.x release.

## Order

Work happens in staged pre-releases, each a signed GitHub prerelease built
from one commit:

1. **Alphas** (`v1.0.0-alpha.N`). The removals, the renames of public names,
   the flags mechanism, the store schema at its 1.0 number, the contract
   page. New features land behind flags, building.
2. **Betas** (`v1.0.0-beta.N`). The freeze starts at the first beta: fixes,
   tests that pin the surface, docs, and a proven feature promoted from
   building to shipped. No removal and no change to a public name or shape.
   To leave the betas, nothing known may need a 2.0.
3. **Release candidates** (`v1.0.0-rc.N`). Fixes for faults the run finds,
   each with a test. A fix makes the next rc and the run starts again. The
   owner tags v1.0.0 on the commit of a clean run.

`tehas update` installs a prerelease only when it is named
(`tehas update --to v1.0.0-beta.1`). An ordinary update skips it.

## Merge trains

- One train branch per pre-release: `train/alpha.1`, `train/alpha.2`, and on.
- A topic pull request goes onto the open train, not onto main. It runs no
  CI of its own; it quotes `scripts/verify.sh --changed`.
- The train's pull request into main is the batch gate: CI runs on the
  combined revision against the current base.
- The owner merges the train to main as one merge and tags the pre-release.
- A pull request that breaks a batch leaves the train and goes to the next.

## The contract

One page, `host/docs/contract.md`, says what is public and what is internal.
Candidates for public:

- the `tehas` commands, their flags and exit statuses;
- the instance settings keys and what a missing one does;
- the labels and what each one does;
- the `--json` objects that have a schema in `api/`;
- the factory API and the MCP tools at v1;
- store and analytics migrations from 0.30.x;
- the update from 0.30.x, 0.31.x and 0.32.x by `tehas update`.

The rules for 1.x that go with it are under "The rules for 1.x" in
`host/docs/contract.md`.

`tehasbot` and the programs behind the commands are internal.

## The prototype on GitHub and on the dashboard

The Protolab is half built. 1.0 needs one path that works from end to end:
a zipped prototype and its ticket go onto GitHub, labelled so tehas sees
them, and show on the dashboard. The external zip sits behind the flag
`protolab-zip-url`.

What exists today:

- `tehasbot protolab` builds a page for each open issue whose latest
  `tehas:prototype` was applied by an allowed account, with the pinned
  label id. An attached zip is unpacked into the page, 10 MB a ticket.
- `live/protolab.json` lists them, and the business page shows a
  Prototypes stage while there are any.
- Nothing puts a prototype on GitHub. A person opens the issue, drags the
  zip into it in the browser, and applies the label by hand.

What 1.0 needs:

1. **One way to file it.** `tehas prototype file` opens the issue with the
   ticket text and the zip and applies `tehas:prototype` with the caller's
   own login. It refuses when the login is the bot's, since the Protolab
   drops a label the bot applied.
2. **A zip tehas can read.** The ticket may link the zip as a GitHub
   attachment or as an external URL. GitHub's API cannot upload an issue
   attachment, so the command gives an external URL. For an external URL:
   - the hosts it may come from are a setting, empty by default;
   - the ticket gives the zip's sha256 beside the URL, and a download with
     other bytes is refused;
   - the same limits as an attachment: size, file count, the unpacker.
3. **The ticket carries the spec**, as in the next section, so the same
   issue later moves from `tehas:prototype` to a start without being filed
   again.
4. **Proof on a host.** One prototype filed by the command, its page up,
   and the Prototypes stage showing it on the dashboard.

If filing by command does not make it, the Protolab ships as it works today
plus the external zip, and filing stays by hand.

## From an EGM spec to a pull request

The aim: a design spec written and reviewed with EGM (the Elephant-Goldfish
Model) in the prototype phase goes into tehas as the thing to build, and
every step up to the pull request can show it built that spec and not
something near it. It sits behind the flag `spec-pipe`.

What exists today:

- An issue can link a file such as `spec.md`. With files on, the cycle
  fetches it into its input, and the approval record keeps the attachment
  links with the sha256 of the approved title and body.
- Inside the cycle, pi-rukas checks the issue before it builds, checks the
  result against its plan contract, and reviews the patch. All of these
  read the issue body. None of them knows that one file is the approved
  spec.

What 1.0 needs, as steps:

1. **Mark the spec.** One line in the issue body: `Spec: <link>
   sha256:<hex>`. It rides on the attachments and the approval tehas has.
2. **Pin it at approval.** The approval record keeps the sha256 of the
   spec's bytes. A spec changed after the approval stops the start.
3. **Hand it to the cycle as the spec.** The cycle's input names the file
   as the approved spec. The part inside pi-rukas is an upstream issue;
   tehas fails closed on a runner that does not read it.
4. **The pull request answers to it.** The PR body names the spec and its
   sha256, and for each requirement says where it is met or why not.
5. **The check before the merge.** tehas marks a pull request whose block
   is missing or names another hash.
6. **Proof on a host.** One prototype, its spec, a start, and a pull
   request whose body accounts for every requirement, checked by a person.

## Outsource

Outsource (#2270, parts #2271 to #2278, spec PR #2279) runs cycles on
contractor hosts. It sits behind the flag `outsource`. In 1.0 it is for
trusted hosts only. If it is not on a train when the last alpha closes, or
its proof fails in a beta, it ships as building, and its settings, commands
and fields stay free to change until the release that ships it.

## Decisions

- 2026-11-16: aim for 1.0. Outsource is in. The features we keep count as
  working.
- 2026-11-16: 1.0 takes an EGM spec from the prototype phase and checks it
  all the way to the pull request.
- 2026-11-16: the Protolab gets a minimal working path: a zipped prototype
  and its ticket filed on GitHub, labelled, and shown on the dashboard.
  The zip may be a GitHub attachment or an external URL.
- 2026-11-16: every new feature is behind a flag, off by default, until the
  release that ships it. Outsource, the spec pipe and the Protolab's external
  zip may ship as building if they are not proven.
- 2026-11-16: removed in 1.0: the improvement loop and `cross-project`, easy
  merge, the `fixer` API fields, and compatibility older than 0.30.
- 2026-11-16: pre-releases go alpha, beta, rc, each a signed public
  prerelease. Work lands through merge trains, one per pre-release.
- 2026-11-16: `tehas chat` (#1880) is not in 1.0.
- 2026-11-18, proposed: the freeze started at v1.0.0-beta.1. No text says
  renames are allowed until the first beta.
- 2026-11-18, proposed: a building feature's surface is outside the contract:
  its settings rows in `api/settings-rules.json`, its key in `flags`, its
  `--json` fields (such as `contractors` in `tehas status --json` and
  `api/status.outsourced.json`), its commands and MCP tools may change or go
  until the release that ships it. Only shipped features' keys are guaranteed
  in `flags`.
- 2026-11-18, proposed: readers ignore fields they do not know. A schema in
  `api/` describes the release that ships it. Within 1.x a field, an enum
  value or an exit status may be added; an existing one keeps its meaning and
  is never removed. A reader treats an enum value it does not know as
  unknown, not as an error.
- 2026-11-18, proposed: the MCP protocol revisions the server accepts at 1.0
  stay accepted through 1.x; newer ones may be added.
- 2026-11-18, proposed: when pi-rukas renames a `PI_ENSEMBLE_*` input, tehas
  accepts both names through 1.x.
- 2026-11-18, proposed: the labels `tehas:lean` and `tehas:classic` and
  `TEHAS_DRIVER=lean` stay accepted through 1.x whatever lean becomes.
- 2026-11-18, proposed: supported update sources for 1.0 are 0.30.x, 0.31.x
  and 0.32.x (v0.32.0 is the current Latest release). A 0.30.x host can name
  only an rc or the release, not an alpha or a beta (v0.30.6's `tag_ok`).
- 2026-11-18, proposed: the contract's `tehas update` row names the built-in
  release repository and signing key, as the code and the rest of the manual
  do.
