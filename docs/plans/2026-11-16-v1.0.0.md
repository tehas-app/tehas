# Toward v1.0.0

An internal aim, not a schedule. No milestone or epic tracks it yet. This page
is where the notes live; change it as decisions are made.

Started 2026-11-16, at v0.30.6.

## What 1.0 means

- The features tehas has today work and stay. 1.0 is not a campaign to prove
  every row of `host/docs/features.md` again.
- Outsourcing (#2270) is part of 1.0.
- After 1.0, the contract below changes only with a major version.

## Order

1. **Outsource lands.** Epic #2270, parts #2271 to #2278, spec PR #2279. New
   feature work other than outsource waits until it is in.
2. **Freeze.** From then on main takes fixes, tests and docs until 1.0.
3. **The contract is written down and tested.** Candidates:
   - the instance settings keys and what a missing one does;
   - the `tehas` and `tehasbot` commands and their exit statuses;
   - the labels and what each one does;
   - state store migrations from any 0.30.x schema;
   - the factory API and the MCP tools at v1;
   - the update from 0.30.x by `tehas update`.
4. **A prototype's spec goes in, and the PR is checked against it.** See
   "From an EGM spec to a pull request" below.
5. **Clean up.**
   - Flaky tests: #2307, #2308.
   - Bugs: #1754 (a GitHub write sent twice), #2130, #1739 and #1740 (the cycle
     token's push).
   - The parked `tehas:question` findings: fix or close each one.
   - #51 (the cycle's container holds a token and has an open network) and #823
     (GitHub's bad minutes): fix before 1.0, or name them in Known limits.
6. **The manual says what is true.** `host/docs/features.md` drops stale lines
   such as "Nothing here has run for longer than a day" and gives outsource the
   status its host proof earns.
7. **Release candidates.** `v1.0.0-rc.N` runs on tehas-tehas and one more
   factory. The owner tags v1.0.0.

## From an EGM spec to a pull request

The aim: a design spec written and reviewed with EGM (the Elephant-Goldfish
Model) in the prototype phase goes into tehas as the thing to build, and
every step up to the pull request can show it built that spec and not
something near it.

What exists today:

- `tehas:prototype` gives an issue a Protolab page with its attached files.
- An issue can link a file such as `spec.md`. With files on, the cycle
  fetches it into its input, and the approval record keeps the attachment
  links with the sha256 of the approved title and body.
- Inside the cycle, pi-rukas checks the issue before it builds (the intent
  gate), checks the result against its plan contract, and reviews the patch
  in six lens passes. All of these read the issue body. None of them knows
  that one file is the spec the person approved.
- EGM's drift report compares documents with code, after the merge, outside
  a cycle. Pi is not an EGM host, so EGM itself does not run in a cycle.

What 1.0 needs, as steps:

1. **Mark the spec.** One way for an issue to say "this file is the
   approved spec", by a link or a path in the repository. Not a second
   input channel: it rides on the attachments and the approval tehas has.
2. **Pin it at approval.** The approval record keeps the sha256 of the
   spec's bytes, not only its link. A spec changed after the approval
   stops the start the same way a changed body does.
3. **Hand it to the cycle as the spec.** The cycle's input names the file
   as the approved spec, so the intent gate, the plan contract and the
   review read it as the requirement and not as one more attachment. The
   part inside pi-rukas is an upstream issue; tehas passes the file and
   says what it is.
4. **The pull request answers to it.** The PR body names the spec and its
   sha256, and for each requirement of the spec says where it is met or
   why not. A requirement left out is said, never dropped in silence.
5. **The check after the cycle.** Before the person merges, tehas checks
   that the PR names the approved spec's hash. After the merge, a drift
   check of the spec against the code can run outside the cycle; whether
   that is EGM's drift report by hand or an idle-time job is open.
6. **Proof on a host.** One real prototype, its EGM spec, a start, and a
   pull request whose body accounts for every requirement, checked by a
   person.

## Open questions

- How long the release candidates run, and what counts as a clean run.
- Whether the lean driver (#1099) and `tehas chat` (#1880) ship in 1.0 as
  experimental, off by default, or wait for 1.1.
- Which factory besides tehas-tehas runs the candidates.
- The spec's form: does tehas take EGM's design document as it is, or ask
  for numbered requirements so step 4 can name each one?
- Where the spec lives: an attachment on the issue, or a file in the
  product repository pinned by blob id, as the lab's `spec.md` is.

## Decisions

- 2026-11-16: aim for 1.0. Outsource is in. The features we have count as
  working. Keep it internal: notes here, no milestone or epic.
- 2026-11-16: 1.0 takes an EGM spec from the prototype phase and checks it
  all the way to the pull request.
