# Fixer, part 1: the factory's grant — implementation plan

**Spec:** issue #294, part 1. On 2026-10-17 the owner split the fixer in
two. tehas keeps what the factory accepts from the fixer's account: the rule
5 boundary. The loop that decides, with its prompt, its timer and the rules
for not just retrying, moved to tehas-industry (its spec, section "The
fixer"). The loop as first built here went to industry as a reference and
is not merged here.

**Goal:** the dispatcher takes `tehas:ready` from `TEHAS_FIXER_LOGIN` only
within a grant, and says why when it does not.

## Global constraints

- Platform files name no product and no host (rule 1).
- A malformed setting stops with 78 (rule 2). `lib/config.sh` stays free of
  side effects (rule 3).
- `libexec/work`'s mounts and environment do not change (rule 4). The
  fixer's comment reaches a cycle only through `retry-context.md` in the
  images directory that is already mounted where the instance gives images
  or files.
- The fixer is its own account, never the bot, never in
  `TEHAS_ALLOWED_LABELERS` (rule 5).
- No fixer token in tehas. The token belongs to whatever decides.

## The grant

A `tehas:ready` from the fixer starts a cycle only when all of these hold:

- the issue is not the control issue;
- a person in `TEHAS_ALLOWED_LABELERS` approved an earlier cycle
  (`state/cycles/<n>.approved.json`, or its `rests_on` when the last start
  was the fixer's);
- the body still has that approval's sha256, and nobody outside the list
  renamed or edited the issue since;
- the fixer has started fewer than `TEHAS_FIXER_MAX_RETRIES` (2) cycles
  since that approval.

Otherwise the label comes off and the issue says why. Concurrency, the cap
of waiting merges and the slice's room hold a fixer start as they hold any
other.

## Interfaces

Approval record of a fixer start:

```json
{"at": "...", "by": "<fixer login>", "how": "fixer", "body_sha256": "...", "links": [...],
 "rests_on": {"at": "...", "by": "<person>", "how": "label|retry-tick|outage-retry", "body_sha256": "..."},
 "fixer_starts": 1,
 "retry_context": [{"source": "fixer:<comment id>", "by": "<fixer login>", "at": "...", "text": "..."}]}
```

The fixer's comment goes into `retry_context` when it is the fixer's newest
on the issue, written in the ten minutes before its label and edited by
nobody after. It starts with:

```
<!-- tehas:fixer issue=<n> action=retry|change -->
```

History, `state/cycles/<n>.history.jsonl`, one line per ended cycle, the
last 50. Fields are only added:

```json
{"at": "...", "started": 0, "rc": 0, "status": "...", "step": "...", "cap": "...", "park_reason": "...",
 "failure_kind": "...", "failure_cause": "...", "provider": false, "parked": true, "pr": "...", "by": "...", "how": "..."}
```

Nothing in tehas reads it yet. `tehas history` (the factory API spec, PR
#296) will list it.

## Tasks

1. Settings and `lib/fixer.sh`: `TEHAS_FIXER_LOGIN`, `TEHAS_FIXER_MAX_RETRIES`,
   the grant. `test/config_test.sh`, `test/fixer_test.sh`.
2. The cycle's history line. `test/cycle_test.sh`.
3. The dispatcher's grant, the approval record, the fixer's comment in
   `retry_context`, `tehas:fixer-escalated` taken off on a start.
   `test/dispatch_test.sh`, `test/work_test.sh`.
4. A title changed since the approval ends the grant.
5. `install.sh` installs `lib/fixer.sh`; `tehas labels` makes
   `tehas:fixer-escalated`.
6. The manual: `operating.md` "The fixer's grant", `tools.md`, `features.md`
   (not yet seen on a host), `instances/example/instance.env`.

## Later parts, factory side only

- Part 2, stale pull requests: a fixer `tehas:ready` on an issue with an open
  pull request refreshes it and leaves one pull request, not two. The
  dispatcher's handling of an open pull request that closes the issue needs
  a fixer case.
- Part 3, ordering: the dispatcher honours `tehas:blocked` (no start while a
  named blocker is open) and `tehas:next` (after `tehas:urgent`), counting
  only the fixer's and allowed accounts' labels. `tehas labels` makes both.
- Part 4, planning answers: a planning turn takes a tick or a reply from the
  fixer within a cap per session, never two turns in a row, and never
  "End this planning session".

## Review focus

- A fixer record whose `rests_on` is missing, malformed or by an account no
  longer allowed: refused.
- An approval record that is a link: refused.
- The fixer's comment text: quoted in `retry-context.md`, under a head that
  says a model wrote it.
