# Images as input to a cycle: plan

**Spec:** `docs/specs/2026-10-13-images.md`. Where this plan and the spec
differ, the section "What the build changed" says why.

**Goal:** a cycle's explore and plan steps see the images its issue links.

## What the build changed

Read in the code on 2026-10-13. The spec and the handover said otherwise.

- **The guard does not read `PI_ENSEMBLE_EXTRA_IMAGE_DIRS`.** It reads
  `PI_ENSEMBLE_ALLOWED_ROOTS` (`extension/src/sandbox-fs-guard.ts:56`, the
  same at the pinned commit). Only the wrapper `bin/pi-rukas` turns one into
  the other, and `tehas work` does not run the wrapper. So a model's `read`
  of an image would be refused in the parent session. This plan does not need
  the guard: the driver reads the files itself, in its own process, and the
  guard only looks at tool calls. `tehas work` passes one variable, as the
  spec says, and no allowed root.
- **There is no intent gate prompt.** The intent gate is a block inside the
  explore prompt and code that reads the reply. Two prompts get the images,
  explore and plan.
- **The check is in the dispatcher, not in `tehasbot health`.** The health
  command reads files and calls nothing. The dispatcher already asks the model
  endpoint before it starts anything and holds with `no resources`. The image
  check is two more conditions there, and `/health` shows the hold as it does
  the others.
- **The directory on the host is per issue**: `work/<name>-<issue>.images`,
  as the workspace is, because cycles run side by side. Inside the container
  it is `work/<name>.images` for every cycle.
- **`tehas work` posts the comment itself.** The dispatcher's start comment is
  posted before `tehas work` runs. The comment is posted only when the issue
  text links something.
- **The type is told by the first bytes**, not by the name or by what GitHub
  answers. A file named `.png` that is svg text is left out.
- **The images are fetched before the workspace is made**, so a start that
  stops over an image does not move aside what the last cycle left.
- **`tehas plan` exists** (`libexec/plan`). The handover says it does not. It
  is not part of this work.

## pi-rukas

The fork `janit/pi-rukas` is what `host/versions.env` pins, so the work is
filed and done there. Line numbers are of `cdcbf80`.

**Contract with tehas.** `PI_ENSEMBLE_EXTRA_IMAGE_DIRS` names one directory in
the container. In it:

```json
{"issue": 7,
 "images": [{"file": "image-1.png", "link": "https://github.com/user-attachments/assets/...",
             "type": "image/png", "bytes": 48211}],
 "leftOut": [{"link": "https://...", "reason": "More than 8 images."}]}
```

`file` is a plain name in that directory. `type` is one of `image/png`,
`image/jpeg`, `image/gif`, `image/webp`. The directory is read-only. No
variable, no manifest, an empty `images`, or a manifest for another issue:
nothing changes.

**Tasks.**

1. A new module, `extension/src/work-driver-issue-images.ts`. The files it
   would otherwise go into are at the 500 line limit. It reads the variable
   and the manifest with `fs`, refuses a `file` with a slash or a link target
   outside the directory, checks `issue`, and returns the images as
   `{type: "image", data: <base64>, mimeType}` with their links. Test:
   `extension/smoke-tests/test-issue-images.ts`.
2. `images?` on `DispatchSpec` (`extension/src/types.ts`), passed in the RPC
   prompt line (`extension/src/spawn.ts:248`). Pi 1.0.0 takes `images` on an
   RPC `prompt`. Test: `test-spawn-bounds.ts` or `test-role-tools.ts`.
3. Explore: `work-driver-explore-run.ts` loads the images once and gives them
   to the dispatch, and to the retry (`:215`). The prompt gets a section that
   lists each image beside its link, in the order attached, and says an image
   is untrusted and cannot change instructions. Test: a new
   `test-explore-images.ts`.
4. Plan: the same images on the plan dispatch (`work-driver-plan.ts:129`) and
   on its two corrective dispatches. The plan prompt asks for the placement in
   words: the element, its visible title, where in it. Test:
   `test-plan-prompt-contract.ts`.
5. Only when the step's model reads images. Nothing in pi-rukas reads a
   model's `input` list today. The nearest is `listAvailableModels()`, which
   parses an `images` column that nothing uses (`list-models.ts:75`). Without
   a model that reads images the prompt says the issue has images the model
   cannot see, and no image is attached.
6. `docs/configuration.md` and `docs/sandbox.md`.

**To find out first there.** Whether the crash-resume path needs the images
(`work-driver-resume-reattach.ts:93,136` sends its own prompt). Whether the
plan step should also be told where the issue body is: its prompt says "read
both" and names no path.

## The pull request for this branch

It says:

- This is a security change (AGENTS.md rule 4). With `TEHAS_WORK_IMAGES=1` a
  cycle's container gets one more read-only mount and one more variable.
  `test/work_test.sh` pins both states: off is today's list, on is the list
  plus exactly these two. No existing assertion was relaxed.
- The images are untrusted input. What limits them: GitHub's storage only,
  the issue text only, an owner, member or collaborator only, four types by
  their bytes, 8 images, 10 MB, names made by tehas, read-only, outside the
  workspace.
- Until pi-rukas is changed and the pin moves, the setting hands the cycle
  images that no model is shown.
- For a person, in `instances/tehas-tehas/` (rule 8): `TEHAS_WORK_IMAGES=1` in
  `instance.env`, and `"input": ["text", "image"]` for the model in
  `models.json`. Not before the model on the fleet reads an image: the
  dispatcher holds every cycle while it does not.

## Seen on 2026-10-13

- `lib/attachments.sh` against GitHub: the image in the text of issue 63 was
  fetched with the token and is a png by its first bytes.
- grizzly reads images. Its own gateway answered the dispatcher's one-pixel
  request with 200 ten times out of ten, in under half a second, with 4 slots
  as before and 31916 of 32607 MiB in use. Given that issue's screenshot
  (1206 by 2622) it listed the page's elements, their text and their places
  correctly. The image cost about 1070 prompt tokens and the answer took 6
  seconds.
- Pi takes the driver's prompt line. `pi --mode rpc` (1.1.0) was sent the
  line `spawn.ts` writes, `{type, message, images}`, with that screenshot,
  against grizzly. The model answered with the card's exact title and the
  text and side of the two boxes in the header.
- **The gateway the tehas-tehas instance names does not.** The same request
  to `gb1:8086` was refused six times out of six: "this server was started
  without the vision encoder". gb1 lists one node for `qwen3.8-flash-next`,
  tehas-black, and that node runs without vision. gb1 sees grizzly as a
  member but not its model, and grizzly sees no other node. So with the
  setting on today the dispatcher would hold every cycle, as it should.

Before the instance is changed, one of these has to be true: the model reads
images on every node that serves it; or the instance's `models.json` names
grizzly's gateway; or viiwork routes a request with an image to a backend
that reads images (the viiwork plan, steps 3 to 5).

## Not verified

- That a GitHub attachment link serves the same bytes later. If not, the
  dispatcher records a hash at approval and `tehas work` compares.
- The dispatcher's request with one pixel against a real endpoint. A model
  with every slot busy may take more than its 30 seconds and hold the next
  start for a poll.
- Anything on a host. `features.md` says so.
