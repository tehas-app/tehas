# Solid 2 as the front end's base, from tehas v1.1.0

**Goal:** Solid 2 renders the pages, carries their async data and holds their
interface state. Native platform features stay where they do the job: custom
elements as the page's structure, `<dialog>`, `popover`, `<details>`, forms,
`:has()`, container queries, `Intl`, SVG. tehas v1.1.0 ships the base and moves
the plain dashboard onto it. tehas-industry (milestone 0.41 Kiinteä Kuha) and
tehas-obeya (milestone 0.2 Kiinteä Kärppä) follow on the kit that 1.1 ships.

**Timing:** v1.1.0 follows v1.0.0 closely. So 1.1 holds the base and one page,
the dashboard. The business page and the factory floor move in 1.2.

**Decision taken with the owner (19 Nov 2026):** adopt Solid 2
(https://docs.solidjs.com/). This replaces the 1.0 rule "no library in this
release" and the fallback named in the v1.0.0 notes (Preact with signals).

## Where things stand

- `host/docs/frontend.md` forbids any library and any npm. It names the
  island contract (`<name>.js`, `.model.js`, `.render.js`) and a kit at
  `host/fun/kit/`, `kit 1`.
- The kit does not exist yet: there is no `host/fun/kit/`. 1.1 builds it.
- No page has a custom element. The pages are static HTML and Caddy templates,
  with plain scripts that draw with `el()` from `fun/dom.js`. The dashboard is
  `docs/dashboard.frag`, `fun/dashboard-view.js` (21 KB), `fun/console-tabs.js`
  and `fun/host-bridge.js`.
- The byte ratchet (`console/ops/src/update/pages.rs`, `host/fun/pages.max`)
  already allows a library import in a `.render.js` file only.
- Node tests draw pages against a fake `document` (`test/live_fixtures_test.mjs`).
- tehas-lab vendors Solid 2.0.2 on an unmerged branch
  (`design-systems-and-samples`: `scripts/vendor-solid.sh`, `kit/vendor/solid.js`).
  It is an IIFE bundle of 112,425 bytes, 42,306 gzipped. Its approach is the
  starting point; its output is not the one tehas needs.
- Solid today: `solid-js` 2.0.3, `@solidjs/web` 2.0.3, `@solidjs/signals`
  2.0.3, `@solidjs/html` 2.0.1. 2.0.0 went stable on 16 Nov 2026. MIT.

## The split

| Owned by | What |
| --- | --- |
| The platform | The page's structure as custom elements in the light DOM; `<dialog>`, `popover`, `<details>`, forms, `:has()`, container queries, `Intl`, SVG; the themes as global CSS |
| Solid | Drawing each island (`render` into the element), async data (feeds as async memos, `isPending`, `<Loading>`, `<Errored>`), interface state (signals and stores shared by the islands of a page), actions (`action`, `createOptimistic`) |
| Pure modules | Each island's model, `(data, props, nowMs) -> model`: no DOM, no Solid, tested with `node --test` |

A custom element is the place a Solid root lives. `connectedCallback` mounts
it when the hydrate trigger fires, and `disconnectedCallback` calls the
disposer `render` returns. Solid draws inside it and nowhere else.

## Components of the base

### 1. The vendored library

No JavaScript build tool: no npm, no esbuild, no Vite. The step is Rust.

Measured on 19 Nov 2026: the published browser files cannot be served as they
are. `solid-js` `dist/solid.js` is 53,293 bytes, `@solidjs/web` `dist/web.js`
81,403 and `@solidjs/html` `dist/html.js` 20,123, but `@solidjs/signals`
`dist/prod/` is 44 modules and 729,998 bytes reachable from its index, mostly
comments. That is a 47-file import waterfall and about 880 KB raw. The lab's
esbuild bundle of the same code is 112,425 bytes (42,306 gzipped). None of the
files uses `eval` or `new Function`. `@solidjs/html` fills `<template>`
elements through `innerHTML` (with `trustedHTML`), which is fine for constant
template strings only.

So the tool bundles and minifies, in Rust:

- `tools/vendor-solid/`, a cargo project of its own, kept out of the
  workspace so the gate never compiles it. It depends on `rolldown` (1.3.x,
  the Rust bundler behind Vite, with oxc's minifier). A person runs it when the
  pins change. It needs the network, so it stays outside the gate.
- It downloads the pinned tarballs from the npm registry over HTTPS
  (`solid-js` 2.0.3, `@solidjs/signals` 2.0.3, `@solidjs/web` 2.0.3,
  `@solidjs/html` 2.0.1). It checks each against its pinned `sha512`
  integrity, unpacks them in a scratch folder, and resolves the `browser`
  production entries. No package code runs.
- It bundles one entry that re-exports the fixed list below into one
  minified ES module, `host/fun/kit/vendor/solid.js`. The licences go beside
  it, and its header names each version. Then it rewrites the kit's manifest
  line.
- The kit's Solid API surface is a fixed export list: signals, memos, stores,
  `For`, `Show`, `Loading`, `Errored`, `isPending`, `latest`, `action`,
  `createOptimistic`, `flush`, `onCleanup`, `untrack`, `render`, `html`. The
  ratchet test fails on an import of any other name. The first step measures
  what a page loads. The lab's 112 KB minified bundle is a reference, not a
  target.
- The kit's `MANIFEST` line holds its sha256 and size. A workspace test checks
  the file against it, so a hand edit fails the gate.
- Bumping Solid is its own pull request: the script's output, the manifest and
  the changelog.

### 2. Templates: `@solidjs/html`, no build step

- Components use the `html` tagged template, not JSX, so the files are served
  as they are and the gate needs no node build.
- JSX would need Solid's compiler, which today is Babel or Vite: a JavaScript
  build at install or in the gate. Not taken. If template cost shows up in
  measurements, look first for a Rust JSX transform for Solid (on oxc or swc)
  run by `tools/vendor-solid`, before any JavaScript tool.
- Rule for safety: text from `/live/` files is bound as an expression
  (`${() => m.title}`), never pasted into the template string. A lint in the
  ratchet test rejects `html` calls built with `+` or nested template literals.
- The Solid docs cover JSX only. The first step proves `html` with 2.0's
  `<Loading>`, `<For>` and stores in all four engines.

### 3. Loading and caching

- Modules import the library by one bare name, `solid`. Each page that
  loads an island gets an import map, and `console update assets` (Rust)
  writes it, naming the hashed file (`kit/vendor/solid.<hash>.js`). The file
  is then cached as immutable and every page shares one copy.
- `assets.rs` today hashes only the files named by tags. 1.1 also hashes the
  kit's modules and writes the import map. A module imported by a relative path
  stays as now: `no-cache`.
- The ratchet keeps the bare-import rule: only a `.render.js` file, and kit
  files that draw, may import `solid-js`.

### 4. The kit, `kit 1`

`host/fun/kit/`, shipped with tehas and copied whole by other programs at a
pinned tag:

| File | Holds |
| --- | --- |
| `vendor/solid.js` and the licences | The library, one minified module |
| `island.js` | The base for an island element: parses attributes, waits for the hydrate trigger (`load`, `visible`, `idle`, `interaction`), mounts and disposes the Solid root, dispatches `<element>:<verb>` events |
| `feed.js` | The feed store on Solid: one async source per `/live/` address per page, polled, paused while the page is hidden, keeping the last good value; read with `isPending` and `<Loading>` |
| `state.js` | Page state shared by islands: named stores created once per page |
| `parts.js` | Shared pieces drawn in Solid: time ago, empty state, busy sign, error with retry |
| `kit.css` | Kit rules in `@layer kit`, `display: block` or `contents` for each element |
| `MANIFEST` | `kit 1`, then one line per file |

The kit has not shipped yet, so Solid goes into `kit 1` itself. tehas-industry's
FE-14 and tehas-obeya then pull `kit 1` from the 1.1 tag.

### 5. The island contract, revised

Changes to `host/docs/frontend.md`:

- **Server HTML first stays.** Solid's `hydrate` only takes over HTML that
  Solid's own SSR wrote, so on mount `render` replaces the element's children.
  The server HTML stands until then, and should be the same shape so the page
  does not jump.
- **Data in:** attributes, a child JSON script, or `src="/live/<file>.json"`
  through `feed.js`. Islands never `fetch` on their own.
- **State:** islands of one page share state through `state.js` stores, not
  DOM events. DOM events `<element>:<verb>` stay the public contract, for the
  page's controller and for a host page.
- **Three files stay.** `.model.js` is pure and has no Solid. `.render.js` is
  the Solid component and the only file that imports `solid-js`. `<name>.js`
  is the element on `island.js`.
- **Adapter:** `mount(host, ctx)` becomes the Solid root. `update(model)`
  writes a store, and `unmount` is the disposer. The interface does not change,
  so a later library change is still one file per island.
- **Tiers:** native markup and plain elements stay where they are enough. A
  page with no island still loads no Solid.

### 6. Solid 2, not 1.x

Solid 2 is days old, and most examples a model has seen are 1.x. The manual
gets a short "Solid 2 in tehas" section: the APIs used, and the 1.x names that
must not appear. The ratchet test fails on these: `createResource`,
`startTransition`, `useTransition`, `batch`, `onMount`, `on(`, `Suspense`,
`ErrorBoundary`, `createMutable`, `produce`, `mergeProps`, `splitProps`,
`solid-js/web`, `solid-js/store`, `solid-js/html`. Also: props are read where
they are used, never destructured, and writes land on the next microtask
(`flush()` when a test needs it now).

### 7. Tests

- Models: `node --test`, unchanged.
- Render: Solid's `html` needs a real DOM, and the fake `document` of
  `live_fixtures_test.mjs` will not do. The gate cannot fetch jsdom or a
  browser. So:
  - the gate keeps the models, the ratchet, the manifest check and the
    1.x-name lint;
  - render tests run in a browser through tehas-e2e (Playwright, Chromium,
    with Firefox and WebKit before a release), against `test/fixtures/live/`;
  - `live_fixtures_test.mjs` keeps checking that each sample goes through the
    models.
- Whether render tests can go into the gate later (a vendored jsdom, or a
  browser in CI) is an open question.

### 8. Budgets

- The library is counted once, as `library solid <bytes>` in `pages.max`, and
  is left out of each page's script bytes. Each page pays for it once, and the
  manual's budget table names it.
- The island budget, 12 KB for the three files, stays.
- The dashboard's line is reset by the move and then held.

### 9. Browser baseline

The baseline stays at the last two majors of the four engines. The bundler's
target is set to match it, and the first step checks the output in each
engine.

### 10. Developer loop

- No build, so a file save and a reload is the loop.
- A preview page, `/dev/islands`, served only by the development docs server
  (`libexec/dev-login` setup). It draws each island from
  `test/fixtures/live/`, so you can work without a running factory.
- Types: a hand-written `kit/solid.d.ts` for the export list, and JSDoc in the
  kit, so tehas-obeya's `tsc` checks its islands against the kit.

### 11. Security and supply chain

- No change to a cycle's container (`sandbox.rs`): this is page code only.
- One library, pinned by version and registry integrity, bundled by Rust
  with no package code run, and each bump reviewed as a diff of the vendored
  files.
- No CDN. No `eval` and no `new Function` (the published files have none; the
  tool repeats the check on each bump).
