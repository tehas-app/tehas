Audit of tehas v1.0.0-rc.1 (tag on main at 58cad6e5) before v1.0.0.

- Scope: the core factory. outsource, spec-pipe, protolab-zip-url,
  prototype-file, lean and review are planned for 1.1. They are checked only
  for staying off in a release, and for whether their names in
  `host/docs/contract.md` "Names reserved for 1.1" can be added without a
  rename.
- Already fixed in rc.1, not reported again: #2542-#2548, #2551-#2557.
- Known and open: #2532, #2562, pi-rukas#2393, #51, #1742, #1791.
- Fixes go as pull requests onto `train/rc.2`.

## Ultrareview, 2026-11-19

`/code-review ultra` with no target. The working tree and the upstream range
were empty, so it reviewed `HEAD~1` only: 93311d38, "The features page
records the first update to a 1.0 beta on a host" (#2539). This was one row
of `host/docs/features.md`, not the release. Each finding was checked
against the file.

### 1. Important: the update path reads as proven on a host

`host/docs/features.md:164`, row "Update by release".

The only evidence is the versions `/health` reports on a factory that its
industry manager moved from v0.30.6 to v0.32.0 to v1.0.0-beta.7. It does not
say that `tehas update` ran, or that the `.sha256` check, the signature check,
the instance check or the `current` switch were seen. AGENTS.md: "do not mark
something proven that you have not seen work."

Fix: say how the factory was moved (by `tehas update --to` or by the
manager's own path) and what was seen of the checks, or describe it as a
version change seen in health only.

### 2. Important: the caveat on update sources was dropped

`host/docs/features.md:164`.

The change removed "The update from v0.30.x, v0.31.x or v0.32.x to this
release is not yet seen on a host" and put nothing in its place. What was
seen was 0.30.6 to 0.32.0 to 1.0.0-beta.7. Not seen: an update to rc.1 or
1.0.0, an update from v0.31.x, and an update from v0.30.x straight to an rc.
The plan names all three as supported sources.

Fix: keep a narrower caveat that names what is not yet seen.

### 3. Nit: the store row now disagrees

`host/docs/features.md:169`, row "The state store's database".

It still says the migration from the v0.30, v0.31.0 and v0.32.0 stores "is
not yet seen on a host", while the update row says the 0.30 migration was
seen as the factory coming up on it.

Fix: change both rows together, with the same limits (seen only as the
factory starting, and only to beta.7), or drop the claim from the update row.

### 4. Nit: older sentences in the update row are stale

`host/docs/features.md:164`.

"Seen once, 2026-10-21" is now the second sighting. The row still ends "an
update from one release of it to the next has not been seen", right after
it describes a factory moving across three console releases.

Fix: date the older sighting without "once". Reword or remove the last
sentence if the new sighting went through the console update.

### 5. Nit: the installed manual names a host

`host/docs/features.md:164`.

The row names the host koala, its factory tehas-lab and the manager industry
v0.36.2. This breaks hard rule 1: platform files name no host. The lint
passed only because no names list is present on the machine that ran it.

Fix: describe the sighting in general terms ("a lab factory managed by an
industry") and keep the host details in `docs/`.

### Lens: security. tehas v1.0.0-rc.1

Read-only audit of AGENTS.md hard rules 2, 4, 5 and 10 on main at 93311d38
(rc.1 is 58cad6e5; the one commit since touches host/docs/features.md only).
Two findings, both verified. Most of the surface was found sound; the list is

#### Findings

##### 1. medium: an edit by an account outside the list passes once an allowed account edits after it

- Where: `console/core/src/events.rs:243` (`edit_holds`),
  `console/dispatch/src/decide.rs:1881` (`unchanged_since`),
  `console/dispatch/src/finish.rs:213`, and the query at
  `console/dispatch/src/read/github.rs:40`.
- What is wrong: the hold on a body changed after the approval reads only
  GraphQL's `lastEditedAt` and `editor`, the last edit. Any earlier edit made
  after the label is not seen. Renames are read whole from the timeline, and
  the millwright's tick on a comment already reads `userContentEdits`
  (`read/github.rs:141`, `questions.rs:127`), so the issue body is the one
  text judged by its last editor alone. No hash covers this window: the body
  hash is recorded when the start is decided, not when the label is applied.
- Scenario: an outside account opens an issue. alice (allowed) applies
  `tehas:ready`. The issue waits for room, which can be hours. The author
  edits the body and adds instructions. alice, or any allowed account, then
  saves the body: a ticked task box or a typo fix is enough. `editor` is now
  alice, `edit_holds` answers None, the start is credited to alice's label,
  and the hash recorded is of the attacker's text. The cycle runs it with the
  bot's token and the model keys in its container.
- How verified: by reading. `edit_holds` returns `(!allowed(who)).then(..)`
  for the one `editor` it is given; the page asks for no edit history of the
  issue. `host/docs/tools-dispatch.md:390` says "nobody else has changed its
  title or body since", which the code does not hold. No issue found for it
  (searched `userContentEdits`, `lastEditedAt`, "last editor").
- Limit: it needs an allowed account to save the body after the hostile edit
  and before the start. Without that second edit the hold works.
- Contract-impacting: no. Internal; the manual's sentence becomes true.
- Fix: read `userContentEdits(last: N) { totalCount nodes { editedAt editor } }`
  for the issue and hold on any edit after the approval by an account outside
  the list, and when `totalCount` exceeds the nodes. To keep the queue page
  inside its budget, ask it only for an issue whose labels would start it.

##### 2. low: commands with no required settings run, call GitHub and write on a malformed instance

- Where: `console/src/commands.rs:394` (`required`), whose `_ => &[]` arm
  covers `tehas start`, `pause`, `drain`, `limit`, `order`, `panel`,
  `host-message`, `freeze` and `thaw`; `console/src/start.rs:262`.
- What is wrong: `console run` stops with 78 only for the settings `required`
  names. The load itself does not stop on a malformed `TEHAS_REPO`,
  `TEHAS_CONTROL_ISSUE` or `TEHAS_ALLOWED_LABELERS`. These commands name none,
  so they run. Hard rule 2 and the exit tables in `host/docs/contract.md`
  (start, limit, order: "78 The settings are missing or malformed; nothing is
  written"; pause, drain, freeze: 78) say otherwise. A missing `instance.env`
  and a building feature's switch do stop them with 78.
- Scenario, reproduced with the debug console, a store made by `store init`
  and a stubbed `gh`:
  - `TEHAS_REPO=bad`: `tehas start 5` ran `gh api repos/bad/issues/5`,
    recorded a host approval and exited 0. With `TEHAS_REPO=` it ran
    `gh api repos//issues/5`.
  - `TEHAS_ALLOWED_LABELERS="alice  bob"` or `TEHAS_CONTROL_ISSUE=x`:
    `tehas start 5` called gh and recorded the approval, exit 0.
  - With any of the three malformed: `tehas pause`, `drain`, `limit set
    --cycles 2`, `limit clear`, `order set --issues 5`, `panel set`,
    `host-message set` exited 0 and wrote their file or row.
  On a real host GitHub answers 404 for a malformed repository, so `start`
  ends 3 and not 78; no wrong repository is reached. The harm is the contract:
  a program that drives the factory by exit status never sees the documented
  78 from these commands.
- Contract-impacting: yes. The exit tables are frozen at 1.0. Decide before
  the tag.
- Fix: either give these commands their settings in `required` (at least
  `TEHAS_REPO` for `start`), or narrow the tables and rule 2's wording to
  "the settings a command needs". Letting `pause` and `drain` work on a broken
  instance is defensible; `start` calling GitHub with an unchecked
  `TEHAS_REPO` is not.

#### Checked and found sound

- Who applied the label: actor of the newest application, not label presence
  (`events.rs` `label_actor`); removal and re-application by another account
  is denied; unstamped events never authorise; same-second changes count as
  after unless the approver made them.
- Pagination: the queue reads the last 100 label events a page, and
  `dropped_events` falls back to the REST list with `--paginate` when a page
  disagrees with the labels.
- Allow list: exact-case whole-login match, so a wrong case denies; logins
  pinned to user ids in `state/account-ids` (`accounts.rs` `vouch`) cover
  renamed and re-registered accounts; the bot on the list stops the poll
  with 78.
- Check to start race: body and title sha256 recorded with the approval and
  compared by the cycle as it starts (`core/src/approval.rs` `hold`).
- Container (rule 4): `test/work_test.sh` pins the exact mounts and variable
  names; no Docker socket, no SSH keys, nothing from `~/.config/tehas`;
  cap-drop ALL, no-new-privileges; model keys limited to
  `TEHAS_MODEL_KEY_<NAME>`; cycle token narrowed to contents and pull requests
  write, issues read.
- Host git on a tree a container wrote: pinned to no hooks and no fsmonitor;
  planning turns clone fresh each turn.
- Issue relay (`cycle/src/relay.rs`): O_NOFOLLOW, 1 MiB, argv with no shell,
  fixed `--repo`, markers refused, 50 writes, edits only on issues it created.
- Attachments: link allow-list, names made by the program, token only to
  github.com on stdin, unpack in a child with no token; zip rules cover
  slip, links, counts and inflated size.
- Tokens (rule 10): bearers go to curl on stdin or a pipe, gh by environment,
  docker `-e` by name. None found in argv.
- Permissions: `state/` kept 0700 by install.sh and checked by health; token
  and key files 0600.
- MCP server: read-only mounts, read-only root, constant-time key check
  before the body, bounded reads, log names from a closed list, no symlinks.
- Docs server and router: static, read-only, capabilities dropped,
  `/live/` allow-listed, consoles off by default, templates check the path
  and Host. Front-end scripts use no innerHTML.
- Update: sha256 then minisign with the key built into the binary; VERSION
  and the top directory must equal the tag, so an old signed tarball cannot
  be served under a new tag; an older "newest" does not move the host back.
  `TEHAS_RELEASE_REPO` changes the source, not the key.
- Fail closed: with no `instance.env`, 35 commands tried all exited 78 or 64
  before any gh, docker or git call and wrote nothing (apart from finding 2).
- Building features: `TEHAS_LEAN=on` stopped every command tried with 78;
  `--driver lean` is refused, not run as classic.

### Lens: error handling. tehas v1.0.0-rc.1

Read only. Verified by reading the code and by running the debug build of
rc.1 (`console/target/debug/console`, `store`) against a throwaway HOME in
the scratchpad. No high or critical finding. Two medium, five low.

#### Findings

##### 1. Medium: the gate before the first copy does not predict a migration that fails

- Where: `install.sh:918-939` (`dispatch_hold`, the gate), `install.sh:946-951`
  (programs copied, the new `store` among them), `install.sh:1177-1196`
  (`store_db`, the real migration); `console/store/src/lib.rs:557-571`
  (`Verb::MigrateDry`); `console/store/src/verbs.rs:497-523` (`schema`);
  `console/ops/src/update/run.rs:189-209` (`refused`, `put_back`).
- What is wrong: `store migrate --dry-run` opens read only, reads
  `user_version` and asks `migrable`. It does not try the backup, the backup
  directory, the write open's `quick_check` or the steps. The real
  `migrate --backup` runs only after every file is copied. When it fails,
  install.sh exits 1 with "the files are installed, the database was left as
  it was", `refused()` is false, so `current` stays on the new release and
  nothing is put back. The installed store is now the new one, and every verb
  of it refuses the old schema with 78 ("run store migrate").
- Failure scenario: a 0.30/0.31/0.32 host (schema 12 to 17) updates to 1.0
  (schema 18). The backup cannot be written: the disk has no room for the two
  copies, or `state/backup` is a link to another volume. The gate passes, the
  programs are replaced, the migration is refused. Every poll then stops with
  78, a cycle still running cannot put its end on record
  (`cycle/src/apply.rs:853-873`), and every further `tehas update` fails the
  same way until the cause is fixed by hand. The previous version is not
  runnable: its files are only the `.prev` copies. The way back is
  `tehas update --to <old version>`, which nothing says.
- How verified: ran the rc.1 store on a fresh database with `state/backup` a
  link out of the home: `migrate --dry-run` exit 0, `migrate --backup` exit 78
  ("the backup goes in the state/ or state/backup/ of the store's home").
  Read the order of the steps in install.sh and `verbs::schema`.
- Contract-impacting: no (internal). It bears on the `tehas update` row
  ("from any 0.30.x, 0.31.x or 0.32.x release"), since that update is the one
  that changes the schema on every host.
- Fix: make the gate a real rehearsal before the first copy: settle the backup
  directory, write the backup, and run the steps on that copy. At least take
  the backup in the gate, so no room or a refused directory ends with
  "nothing was installed" and `current` put back. The full rehearsal may be
  for 1.x; the backup in the gate fits an rc.

##### 2. Medium: a write whose connection dropped after GitHub took it is sent again

- Where: `console/core/src/journal.rs:126-134` (`maybe_taken`), `:113-119`
  (the result word), `console/cycle/src/apply.rs:318-339` (`tried`).
- What is wrong: the fix of #1754 treats two answers as "GitHub may have taken
  it": a timeout and `HTTP 5xx`. A gh that exits non-zero with a transport
  error after the request went out (`read: connection reset by peer`,
  `unexpected EOF`, `EOF`, an HTTP/2 GOAWAY) matches neither, settles as
  `read-failed` and comes back as `Wrote::Failed`. `tried` sends a `Failed`
  write again with no read in between, up to `gh.tries` times. In a poll, a
  failed tell is not recorded and the next poll says it again. `gh_why` and
  `githubs_fault` already know these words; only `maybe_taken` does not.
- Failure scenario: the cycle's report posts its comment, GitHub commits it,
  and a proxy or NAT resets the connection before the answer arrives. gh
  exits 1 with "connection reset by peer". The report posts the same comment
  a second and a third time. This is the double write of #1754 through the
  one door it left open.
- How verified: by reading. The regex in `maybe_taken` is `HTTP 5[0-9]{2}\b`
  and the `Some(_)` arm tests nothing else; `tried`'s `Wrote::Failed` arm
  only stores the reason and loops. Not reproduced with a stub gh.
- Contract-impacting: no (internal).
- Fix: in `maybe_taken`, count a non-zero exit whose words say the connection
  broke after it was made (reset, closed, unexpected EOF, EOF) as unknown.
  `connection refused` and `no such host` stay failed: nothing was sent.

##### 3. Low: three public commands return a status outside their table when the reader goes away or a program is missing

- Where and what:
  - `console/src/run.rs:124-140` (`hand_to_dispatcher`): `tehas refresh`
    exits 127 or 126 when `libexec/tehas-dispatch` is missing or cannot run.
    The table has 0, 1, 3, 64, 78. `tehas work` and `tehas index` answer the
    same condition with 78 through `beside()` (`run.rs:199-209`).
  - `console/src/top.rs:366`: `tehas top --once | true` exits 1. In the table

  - `console/src/commands.rs:419-422`: `tehas help`, `tehas help <command>`

  - `console/src/order.rs:165`: `tehas order` with no state store exits 1.
    Its table gives 1 only for "the file could not be written or removed" and
    never names the store; `tehas history`, `tehas stop`, `tehas state` and
    `tehas dispatch` give 78 for a store that is not installed, and
    `tehas start` documents its 1.
- Failure scenario: a script with `set -o pipefail` runs
  `tehas top --once | head -5` and reads 1 as "no live directory"; a manager
  that maps statuses by the contract meets 127 from `tehas refresh` on a host
  whose install stopped partway.
- How verified: ran each against the rc.1 debug build with the reader closed
  (`{ sleep 0.15; tehas <cmd>; } | true`) and with no `tehas-dispatch` beside

##### 4. Low: `tehas stop` removes the issue's lock file while a starting cycle may wait on it

- Where: `console/ops/src/stop.rs:462-466` and `:536-549` (lock taken, file
  removed, lock dropped); `console/cycle/src/main.rs:507` (`tehasbot cycle`
  waits 5 s); `console/cycle/src/lock.rs:25-43` (`take` opens once and retries
  `try_lock` on the same descriptor, and never checks that the path still
  names the file it locked). `console/store/src/upkeep.rs:457-481`
  (`remove_held`) knows the problem, but its guard reads the file's mtime,
  and `take` opens with `append`, which does not touch it: the comment still
  describes bash's `exec 9>`.
- Failure scenario: a person clears the leftovers of #7 with `tehas stop 7`
  in the seconds a poll starts `tehas-cycle@7`. The unit opens `7.lock`,
  finds it held and waits. stop removes the file and lets go. The unit now
  holds a lock on a file with no name. Until `tehas work` below it takes a
  fresh lock at the path (`main.rs:548-553`, after the start is on record and
  GitHub was read), the dispatcher's probe, `tehasbot clean`'s `lock_free`
  and a `tehas work 7` by hand all see no cycle.
- How verified: by reading; the window is seconds and it mostly heals itself,
  which is why it is low. Not reproduced.
- Contract-impacting: no.
- Fix: in `lock::take`, after the lock is taken compare the descriptor's
  inode with the path's and open again when they differ. Then stop and the
  sweep may remove freely, and the stale mtime guard can go.

##### 5. Low: `switch` moves `current` and then reports that it did not

- Where: `console/ops/src/update/release.rs:709-731` (`switch`) and
  `:1075-1080` (its caller in `go`).
- What is wrong: `switch` renames the new link over `current`, then appends
  to `state/release-history`. When the append fails it returns false, and
  `go` says "current could not be pointed at <target>; nothing was installed"
  and returns 1. `current` does name the target by then, no `Undo` was
  planned, and install.sh never ran.
- Failure scenario: `state/release-history` cannot be written (owned by root
  after a by-hand step, or a full disk). `tehas update` exits 1 saying nothing
  changed; `tehas api` and the next update read the target as the version
  installed while every installed file is the old one. The next
  `tehas update` runs the target's install.sh, so it heals, but the message
  is false and `prune` never learns of the switch.
- How verified: by reading.
- Contract-impacting: no.
- Fix: append the history line before the rename, or treat a failed append as
  a warning and go on.

##### 6. Low: a malformed `TEHAS_ENERGY` or `TEHAS_MCP` in instance.env points at the wrong file

- Where: `console/core/src/settings/load.rs:645-666` (`host_values`).
- What is wrong: a host setting that fails its rule is always reported with

- Failure scenario: `TEHAS_ENERGY=solar` in `instance.env` stops every

- Contract-impacting: no (message only; the status is right).

##### 7. Low, for 1.x: nothing but the manual keeps a schema-changing update off a factory with cycles running

- Where: `install.sh:946` to `:1196`; `host/docs/operating.md:2451-2455`.
- What is wrong: between the copy of the new `store` and the migration, every
  store call of a running cycle is refused with 78, and after it the cycle's
  old code talks to the new store. The manual asks for a drain, under a
  heading for 0.30.x only, and calls this "the one update that asks for a
  drain". `tehas update` does not look for held cycle locks and says nothing.
  Any 1.x release that adds a schema step repeats it.
- Failure scenario: a 0.32 host runs a plain `tehas update` to 1.0 with a
  cycle about to end. Its `cycle-end` is refused for the whole of its five
  tries, the end is not on record, and the next poll treats a finished cycle

- How verified: by reading the order in install.sh, `verbs::schema` and
  `cycle/src/apply.rs:853-873`. Not reproduced.
- Contract-impacting: no.
- Fix: when the dry run says `from != to` and a cycle lock is held, have
  `tehas update` say so and stop unless the factory is drained; or migrate
  directly after the store is copied to shorten the window.

#### Checked and found sound

- Settings fail closed. Every public command was run with no `instance.env`
  and with a minimal one: 78 before any write, apart from the commands whose
  help says they need no settings (`status`, `top`, `github writes`). The
  only files a refused run left were lock files.
- Removed and renamed settings: `TEHAS_EASY_MERGE`, `TEHAS_CYCLE_REPORT`,
  `TEHAS_IMPROVE_*`, `TEHAS_CONCURRENCY`, `TEHAS_TICKET_CONCURRENCY`,
  `TEHAS_OWNER`, `TEHAS_BOT_LOGIN`, `TEHAS_FIXER_*` each stop with 78 and a
  line that names the new key or says to take the line out. `TEHAS_REVIEW`,
  `TEHAS_REVIEW_REPO`, `TEHAS_OUTSOURCE=on` and `TEHAS_DRIVER=lean` are
  refused with 78 and name the feature.
- Bad arguments give 64 in every command tried, before the settings where the
  table says so.
- Panics on untrusted input: every `unwrap`, `expect`, slice and index outside
  the tests in core, store, dispatch, cycle, ops, mcp and the console was
  read. Each is guarded (a shape check first), a constant regex, or an
  argument the parser already required. Garbage in `state/limit.json` and
  `live/health.json` (truncated JSON, wrong types, huge numbers, bytes that
  are no text) gave the documented answers, no panic.
- The store: each migration step is one immediate transaction with
  `meta.schema` and `user_version`; a failed step commits nothing; the foreign
  keys are checked before the commit of a rebuilt table; the backup is written
  before the first step and a partial copy is removed. A store newer or older
  than the binary is refused with 78 by every verb, never read as no rows.
  `verbs::write` rolls back on any error.
- The release switch: download, `.sha256`, signature with the built-in key and
  the unpack all happen before `current` moves; the unpack is staged and
  renamed; the link is replaced by a rename; an install.sh that says "nothing
  was installed" puts `current` and the image tag back. The update lock is a
  flock held on a descriptor, so a killed update leaves no stale lock.
- The dispatcher's start: the approval is recorded before the label, a failed
  mark withdraws it, a mark GitHub did not answer is read back, a unit that
  does not come up gets its approval taken back and the label replaced, and a
  `tehas:refreshing` or `tehas:running` left behind is cleared by
  `decide/clean.rs`. `start_on_record` handles a store that took the start
  after it timed out.
- Swallowed errors: outside the tests the only `let _ =` on a store or GitHub
  call is the journal's settle (`core/src/journal.rs:122`), which is safe by
  design: the row stays open and the next poll settles it by a read.
- Bounds: GitHub, store and Docker calls on the poll's and the cycle's paths
  go through `run_full` or `timeout` with a TERM and KILL grace. The few
  unbounded `docker` and `git` calls are in `tehasbot clean`, the previews and
  the update's prune, each under a unit's `TimeoutStartSec` or a person's
  terminal.
- `tehas state unpack` swaps directories with a put-back and names what it
  could not restore.

### Lens: type safety and data contracts (v1.0.0-rc.1)

Nine findings: none critical or high, four medium, five low. Read-only audit; nothing in the repo was changed.

Checks ran against the existing debug binaries in `console/target/debug` (`console`, `tehas-mcp`), with fixtures under `scratchpad/ts`. ##### 3. Medium: a `TEHAS_CYCLE_MIN_FREE` the load accepts can switch the dispatcher's disk floor off
- **Where:** `console/core/src/settings/rules.rs:570-573` and `:804-815` (`FreeDisk`, `mem_mb`) against `console/dispatch/src/settings.rs:99-101` and `console/core/src/slice.rs:327-345` (`bytes`).
- **What is wrong:** two parsers for one setting.

- **Fix:** have the dispatcher read `TEHAS_CYCLE_MIN_FREE_MB` as the other readers of the size settings do, or treat an unparsable value as a refusal (78), never as 0.

### Lens: performance and resource use (tehas v1.0.0-rc.1, 58cad6e5)

Read only. Nothing in the repository was changed. Measurements were made on a
synthetic store in the scratchpad (since removed) and with read-only `gh` calls
against tehas-app/tehas. No critical or high finding. Nothing here touches the
public contract.

#### Findings

##### 1. Medium: every write to the state store scans the whole database, and the database grows with every issue ever run

- Where: `console/store/src/db.rs:951-975` (`prepare`: `PRAGMA quick_check` on
  every `Purpose::Write` connection), reached from `console/store/src/verbs.rs:538-541`
  (`write` -> `db::lock`). Callers on a timer: `console/cycle/src/watch.rs:820-848`
  (`now_file`, one `store cycle-heartbeat` per running cycle every 10 s), plus
  every write verb of a poll (`poll-begin`, `poll-record`, journal, approvals).
- What is wrong: each store verb is its own process and its own connection, so
  "the first write of a run" (#1769) is in practice every write. `quick_check`
  reads every page. The file is not bounded: `store prune` never removes a
  `cycles` row (`upkeep.rs:14-17`, "A cycle's row is never removed"), so
  `issues`, `cycles`, `cycle_results.payload` (the runner's result kept whole),
  `cycle_settings` and `cycle_progress` stay for every issue ever run, and the
  100 heartbeats of each ended cycle stay 90 days (`upkeep.rs:383-389`).
- Failure scenario: a factory that has run 1,800 issues in 90 days (tehas-tehas
  is past issue #2500) holds about 60 MB. Every 10 s each running cycle pays a
  full scan of it; with 3 cycles that is about 26,000 full scans a day, and a
  poll that starts a cycle pays one per write verb. The cost rises linearly
  with the factory's age and never falls. Not seen to break anything: it is
  CPU and page reads that grow, about 2% of a core per running cycle at this
  size with finding 2.
- How verified: built a store with `store init`, filled it with 1,800 issues
  (100 heartbeats, one 8 KB result each) and 90 days of polls: 59.4 MB.
  `PRAGMA quick_check` with the system's optimised SQLite: 108 ms.
  `store cycle-heartbeat` (debug build): 0.50 s on that store against 0.01 s on
  an empty one.
- Contract: no. Internal.
- Fix: run the check where it pays: once per poll (`poll-begin`) and in
  `upkeep`, `migrate` and `check`, not in `cycle-heartbeat` and the other
  per-tick writes. For 1.x, let `prune` drop `cycle_results`/`cycle_progress`/
  `cycle_settings` of cycles ended more than N days ago.

##### 2. Low: `store publish` reads every heartbeat on record, every 10 s per running cycle

- Where: `console/store/src/live.rs:318-326` (`read`), called by
  `watch.rs:841` (each tick of each cycle), `cycle/src/after.rs:308` and the
  poll (`dispatch/src/poll.rs:1225`).
- What is wrong: the query joins all of `heartbeats` to `cycles` and keeps the
  newest row per issue. Nothing limits it to running cycles, so it scans the
  heartbeats of every cycle that ended in the last 90 days (up to 100 each) to
  find the few that run and the one last end.
- Failure scenario: same store as finding 1: 180,000 rows scanned per publish,
  from every running cycle's tick.
- How verified: the query on the 59 MB store: 80 ms with optimised SQLite;
  `store publish` (debug build) 0.34 s against 0.00 s on an empty store.
- Contract: no.
- Fix: drive the query from `cycles` (`ended_at IS NULL`, index
  `cycles_running`, plus the newest `endings` row), or trim an ended cycle's
  heartbeats to its last row in `cycle-end`.

##### 3. Low: the status reads up to 1,000 issues for the word list, at least every 5 minutes, inside the poll

- Where: `console/src/queue.rs:858-875` (`gh issue list --state all --limit
  1000 --json title,labels`, used only by `buzzwords`, `queue.rs:450-454`);
  run from `console/dispatch/src/poll.rs:42` (`STATUS_AGE = 300`),
  `poll.rs:768-770` (before the queue is read, under `dispatch.lock`) and again
  at the end of every poll that changed something (`poll.rs:513`, `:1237`).
- What is wrong: the header says "five GitHub calls", but this one is ten
  paged GraphQL requests on any repository with 1,000 issues of any state, to
  count words that change slowly. On a small queue it is the largest GitHub
  cost of the factory.
- Failure scenario: on tehas-app/tehas (44 open, about 2,500 in all) an idle
  hour is about 30 x 3 requests for the poll (2 queue pages + tidy) and
  12 x 16 for the status, 120 of them this read. Each status run adds about
  8 s before the poll reads the queue, so a start waits that long once every
  five minutes, and longer when GitHub is slow (each call has its own bound
  and retry).
- How verified: read the code; timed the same command against
  tehas-app/tehas: 8.0 s, 244 KB. The labelled search before it took 2.8 s.
- Contract: no, if `buzzwords` stays in `status.json`.
- Fix: read the word list at most once an hour (keep the previous
  `buzzwords` of `status.json` between reads, as the stale parts already do).

##### 4. Low: three long-lived logs are never cut

- Where: `console/store/src/upkeep.rs:588-593` (`LONG_LIVED` names four logs)
  against `host/systemd/tehas-preview.service:7`,
  `tehas-preview-sweep.service:7`, `tehas-protolab.service:7` and
  `logs/clean.log` (`tehasbot clean`).
- What is wrong: `logs/preview.log` and `logs/protolab.log` are appended every
  5 minutes and `logs/clean.log` every hour. None is in `LONG_LIVED` and none
  matches `old_log`, so nothing ever rolls or removes them.
  `host/docs/operating.md:1982` says they "stay".
- Failure scenario: slow growth without bound (a few lines per run, 288 runs a
  day each); a preview or protolab that fails every run with a long error
  grows faster. Years, not weeks, on a healthy host.
- How verified: read the units, `roll_logs` and `old_log`; no other code names
  these files for removal.
- Contract: no.
- Fix: add the three names to `LONG_LIVED`.

##### 5. Low, documented: a full copy of the store on every install, never removed

- Where: `console/store/src/lib.rs:673-690` (`migrate` copies even when the
  schema is current, twice when a step runs); `upkeep.rs:162-167` (`daily`
  matches only `tehas-<YYYYMMDD>.db`, so `tehas-<schema>-<time>.db` is never
  among the copies it trims).
- Failure scenario: each `install.sh` or `tehas update` leaves one or two
  copies of a store that finding 1 says keeps growing. A host updated weekly
  with a 60 MB store adds 3 to 6 GB a year in `state/backup/`.
- How verified: read the code; `host/docs/host.md:770-771` and
  `operating.md:2043` already say nothing removes them.
- Contract: no.
- Fix: for 1.x, keep the newest N (say 5) migration copies in `make_backup`.

##### 6. For 1.x: the poll's cost is linear in the open issues of the repository

- Where: `console/dispatch/src/read/github.rs:30` (`ISSUE_PAGE = 25`),
  `:233-316` (`queue`: every open issue, whole body, 100 timeline items, every
  poll, no page limit and no "changed since").
- What it costs: ceil(N/25) sequential `gh` processes before any decision,
  every 2 minutes. N = 1,000 open issues is 40 calls a poll, 1,200 an hour,
  and a poll of one to two minutes, so the timer runs back to back. The
  GraphQL points hold to about N = 4,000. The page size is load-bearing for
  correctness (the comment at `:24-29`), so this is not an rc fix.
- How verified: read the code. Not reproduced: no repository of that size at
  hand.
- Contract: no.
- Fix: for 1.x, a cheap first query (`issues(filterBy: {since})` or the
  labelled subset) and the full page only for issues that changed.

#### Checked and found sound

- Dispatcher reads: one batched `store batch` per poll (#941), comments,
  blockers and events read in aliased or parallel calls, not per issue. The
  REST re-read of a cut timeline needs more than 100 label events on an issue;
  the largest on tehas-app/tehas is 30.
- `poll-record` reads the tail of `github-writes.log` by seek, not the file.
- Store busy handling: writers wait 5 s, readers 1 s, 1 ms fair polling, WAL,
  short-lived connections, so no long reader pins the WAL. Reads run no
  `quick_check`.
- Store pruning: `upkeep` hourly prunes endings, settled actions and journal,
  polls, poll_cost, sweep_log and histories at 90 days; heartbeats capped at
  100 per issue; daily backups capped at 7.
- Analytics: prunes at 365 days after every write; publish skips unchanged
  files by fingerprint.
- Logs: per-cycle, plan, index and review logs go after 7 days; dispatch,
  review-timer, refresh and github-writes logs roll at 64 MiB; a preview's
  build log goes with the preview.
- Disk: `versions/` keeps the last three; `run/cycle-*` and `run/plan-*`
  hardlink copies of dead pids are swept by the next start; sandbox image tags
  and build cache are the cleaner's.
- MCP server: 32 connections, head 8 KiB, body and io deadlines, every file
  read by tail or under `READ_BOUND`, no database opened in the request path.
- Console tail: incremental by offset, bounded per pass.
- Timers: all oneshot with `OnUnitInactiveSec`, a `flock` on the dispatcher,
  bounded `TimeoutStartSec`; no overlapping runs.
- Cycle watch: 2 store processes per 10 s tick per cycle; the scratch walk is
  capped at 500,000 entries and only runs with `TEHAS_SCRATCH_DIR`.
