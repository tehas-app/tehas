# Spec: plugins, external features with views of their own

**Status**: Draft 2026-11-21, with the owner's decisions on where a plugin
runs, where it comes from and when it runs. Nothing is built.

## Purpose

Some features are not tehas's own but are worth showing beside the factory.
A **plugin** is such a feature: a program from a git repository that adds
menu items and views to a factory's dashboard.

A plugin uses the APIs tehas-industry already uses to add its features to a
factory: the factory API (`tehas ... --json`), the read-only MCP server,
`tehas panel` and the host bridge. tehas adds no plugin API of its own beyond
what a plugin needs to run on the host, and the host gives it nothing a
person did not grant (see "The security model").

The first plugin, and the reference implementation, is
[tehas-app/tehas-plugin-floorplan](https://github.com/tehas-app/tehas-plugin-floorplan).
It draws a [Floorplan](https://github.com/haydenschmitty/floorplan) map of
the factory's product repository and shows it as a view.

## The guarantees

1. **Off unless asked.** With no `TEHAS_PLUGINS` setting and nothing
   adopted from industry, no plugin is fetched, built or run, and there is no plugin unit, file or menu item.
2. **Pinned.** A plugin is named by a git URL and a full commit hash. tehas
   never follows a branch or a tag. A plugin changes on a host only when a
   person changes the pin and runs `install.sh` or `tehas update`.
3. **Fail closed.** A malformed plugin setting or manifest stops the command
   with 78 before it fetches, builds or runs anything.
4. **Outside the cycle.** A plugin never runs in a work cycle's container,
   and the cycle's container is given nothing new (hard rule 4).
5. **Read only.** A plugin never writes to the product checkout, GitHub or the
   state store. What it may change is its own output and its own menu items.
   A hook's verdict is posted by tehas, not by the plugin.
6. **Removable.** Taking a plugin out of `TEHAS_PLUGINS` and running
   `tehas update` removes its unit, its output and its menu items, and nothing
   else.
7. **It never blocks the line, unless granted a gate.** A plugin that
   fails, hangs or is missing holds no cycle, poll or refresh. Its failure is
   logged and shown on its own menu item. Only a `gate:<point>` a person
   granted may hold an issue, and only at that point.
8. **Signed in, always.** Every address of a plugin needs a GitHub
   sign-in with access to the factory's repository. See "Sign-in".
   A view's page loads and reaches nothing but its own name; the factory is
   its proxy. See "Talking to the outside".
9. **Nothing without a grant.** A plugin gets a locked-down container and
   nothing more until a person grants each capability it asks for. See
   "The security model".
10. **Any licence, closed source included.** A plugin contains no tehas code
   and tehas contains no plugin code. See "Licences".

Test: the existing suite passes unchanged with no plugins set.

## What v1 ships

v1 ships a few surfaces that are worth having at once, each behind its
grant, and names the rest without building them. A reserved name is refused
with 78 until a release ships it, so a plugin that asks for one fails clearly
and nothing is half there.

| Surface | v1 | Reserved for later |
| --- | --- | --- |
| Views | `view`: a static view and its menu item, widgets on the kit | A plugin with a server of its own (`kind: "service"`); widgets inside the dashboard's pages |
| Code | `product` at the default branch, and at the branch head in a hook | Other repositories; other refs |
| Model | `model:<budget>` through `tehas-proxy` | More than one model; embeddings |
| Outside | `net:<host id>` for the view, through the factory's proxy | A run reaching other hosts |
| Buttons | `action:<id>` that asks for a run | Actions with input |
| Stages | `hook:after:work` and `gate:after:work` | The `before:` points; `plan` and `refresh` |
| Chats | `skill:<id>`: instructions for Obeya's and industry's chats; `tool:<id>`: a tool those chats may call | Tools that offer buttons; skills for a cycle's agents |
| Inspection | Every crossing through `inspect`, recorded; `hold` and `release` | An LLM prompt detector, inline and as a mass review |
| Factory | Nothing | `factory-read`, `factory-sessions`; ticket notes as a declared output |
| Sign-in | GitHub, through the factory's App, for every address | Other identity providers |
| Industry | `adopt` and `drop` under the factory's ceiling | Industry's own plugins, with views of its own |
| Runs | `default-branch`, `on-demand` | Other events: a pull request opened, a schedule |

Room to grow, in v1 already:

- `kind`, `"batch"` in v1, so another kind is a new value, not a new
  contract.
- `requires`: the feature words of `tehas api` the plugin needs, for
  example `["plugins", "plugin-hooks"]`. A tehas without one refuses the
  plugin with 78 and names the word.
- Unknown fields in a manifest are refused, not ignored, so a newer manifest
  never runs half understood on an older tehas.
- Each new surface is a new capability: one row in the table, one branch of
  the pure function, one argument list in `test/fixtures/argv/`. Adding one
  never loosens one that is there.

## Settings

In the instance's `optional.env`:

```
# A plugin per line: <name> <git URL> <commit>.
TEHAS_PLUGINS="floorplan https://github.com/tehas-app/tehas-plugin-floorplan 0123456789abcdef0123456789abcdef01234567"
```

- `name`: `a-z`, `0-9` and `-`, 1 to 24 characters, unique.
- `git URL`: `https://` only. No user or password in it. The repository may
  be private: `install.sh` and `tehas update` fetch it as the host's user,
  with that user's own git credentials. The credentials never reach the
  plugin's container.
- `commit`: 40 hex characters.

`lib/config.sh` checks the shape and nothing else: it fetches nothing.

## The manifest

`tehas-plugin.json`, at the pinned commit:

```json
{
  "plugin": 1,
  "kind": "batch",
  "requires": ["plugins", "plugin-hooks"],
  "name": "floorplan",
  "label": "Floorplan",
  "license": "Apache-2.0",
  "build": "Dockerfile",
  "asks": ["view", "product", "model", "action:refresh", "hook:after:work",
           "skill:map", "tool:find-part"],
  "hooks": [{"at": "after:work", "mode": "hook", "timeout": 900}],
  "limits": {"memory": "2g", "cpus": 2, "pids": 256},
  "runs": ["default-branch", "on-demand"],
  "timeout": 3600,
  "ui": {"kit": 1},
  "actions": [
    {"id": "refresh", "label": "Refresh floorplan", "does": "run"}
  ],
  "views": [
    {"id": "map", "label": "Floorplan", "path": "/", "open": "page"}
  ],
  "skills": [
    {"id": "map", "file": "skills/map.md", "tools": ["find-part"]}
  ],
  "tools": [
    {"id": "find-part", "about": "Which part of the app a file or feature belongs to, and what it talks to", "params": "tools/find-part.schema.json", "timeout": 30}
  ]
}
```

| Field | Rule |
| --- | --- |
| `plugin` | The contract's version, `1`. Any other value: refused |
| `kind` | `batch`: runs that end. Other kinds are reserved |
| `requires` | Optional. Feature words of `tehas api` the plugin needs |
| `name` | Equals the name in `TEHAS_PLUGINS` |
| `label` | One line, 1 to 24 characters |
| `license` | Optional. An SPDX expression or `proprietary`, shown by `tehas plugin`. See "Licences" |
| `build` | A Dockerfile in the repository, built on the host into `tehas-plugin-<name>:<commit>` |
| `asks` | The capabilities it wants, from "Capabilities". Each may be `{"cap": "<name>", "optional": true}` |
| `limits` | Optional. Memory, CPUs and processes for a run, at most the instance's `TEHAS_PLUGIN_LIMITS` |
| `runs` | When it runs: `default-branch`, `on-demand`. At least one |
| `timeout` | Seconds, 60 to 14400. A run over it is stopped |
| `ui` | Optional. `{"kit": 1}`: the view's widgets are drawn in Solid 2 on the tehas kit, which tehas serves to the view. Absent: the view brings its own UI. See "Widgets in Solid" |
| `actions` | Optional, at most 4. A button a view may show. `does` is `run` in v1, the same as `tehas plugin run`. See "Actions" |
| `views` | At most 2. Each becomes a menu item |
| `views.id` | `a-z`, `0-9` and `-`, 1 to 16 characters |
| `views.path` | A path under the plugin's view name, starting with `/` |
| `views.open` | `dock` or `page`, as in the host bridge's menu |
| `net` | Optional, at most 8. `id`, `origin` (`https://` only), `paths` (prefixes). See "Talking to the outside" |
| `hooks` | Optional. `at` a point, `mode` `hook` or `gate`, `timeout` in seconds. Each needs its `hook:` or `gate:` grant |

| `skills` | Optional, at most 4. `id`, a Markdown `file` in the repository, and the `tools` it uses. See "Skills for chats" |
| `tools` | Optional, at most 8. `id`, `about` (one line, at most 200 characters), `params` (a JSON Schema file), `timeout` (1 to 60 seconds) |

A field not in this table is refused with 78.

`tehas-plugin.schema.json` in `api/` says the same, with a full and a bare
sample, as for the other contracts.

## When it runs

- **`default-branch`**: after the product's default branch moves. The check
  is one `git ls-remote` of the default branch on the plugin timer,
  `tehas-plugin.timer`, every 10 minutes, against the commit of the last good
  run. No model call while nothing moved.
- **`on-demand`**: `tehas plugin run <name>` starts a run now. It exits 3 if
  a run of that plugin is going.

One run per plugin at a time. Runs of different plugins may overlap.

## Commands

```
tehas plugin [--json]            # the plugins, their pins, last run and its result
tehas plugin run <name>          # start a run now
tehas plugin log <name>          # the last run's log
```

`tehas plugin --json` prints `{"api": 1, "plugins": [...]}`; `tehas api`
lists `plugins` once it ships. With `TEHAS_PLUGINS` unset, each verb exits
78.

The rules go in Rust, in a `plugin` module of `console/ops`, with the
manifest's reader in `console/core`. Bash only starts the unit.

## Licences

tehas is Apache-2.0, which already lets a closed program use it. The plugin
contract goes further: a plugin needs nothing of tehas's code at all, so no
licence of tehas reaches a plugin, and no plugin's licence reaches tehas.

- **The contract is an interface, not code.** A plugin is a separate program
  in its own container. It meets tehas only through the manifest, the
  container's mounts and environment, the files it leaves in `/out`, and the
  public commands and MCP tools. It links no tehas crate, imports no tehas
  script and is not built on a tehas image. tehas mounts nothing of
  `~/tehas` or of its own source into the container.
- **The contract's files are free to copy.** A plugin may want the schemas
  and samples, `api/tehas-plugin.schema.json` and the other `api/` objects it
  reads. `api/` is dedicated to the public domain under CC0-1.0, with its own
  `api/LICENSE`, so copying them carries no notice and no terms.
- **The kit is served, not copied.** A view with `ui.kit` loads the kit
  from tehas at run time. The plugin's repository and image hold none of
  it, so the kit's Apache-2.0 and Solid's MIT stay with tehas's copy.
- **Nothing else of the dashboard.** A view loads no other dashboard
  script, style or font. The pixel typeface in `host/fun/` is third-party
  work under its own terms.
- **tehas never distributes a plugin.** No plugin code goes into this
  repository, its releases, the sandbox image or `tehas state pack`. A plugin
  is fetched on the host from the repository the instance names, so its terms
  are between its author and the host's operator.
- **The manifest may name its licence**, `license`, an SPDX expression or
  `proprietary`, which `tehas plugin` shows. tehas reads nothing else from
  it.
- **The reference plugin is Apache-2.0**, as the rest of the tehas family,
  and keeps the licence and notice of the Floorplan it pins (MIT). Being
  open is its choice, not something the contract asks of a plugin.

## The reference plugin: Floorplan

`tehas-app/tehas-plugin-floorplan` holds:

- `tehas-plugin.json`: asks for `view`, `product`, `model` and
  `action:refresh`, runs on `default-branch` and `on-demand`, one view,
  `open: page`.
- A pin of Floorplan by commit, checked against its `CHECKSUMS.txt`.
- A driver: Floorplan's unattended mode (`FLOORPLAN_UNATTENDED=1`, `--json`)
  follows `skills/floorplan/workflow.json`. Floorplan's scripts do the
  mechanical work and call no model. The driver runs the model jobs against
  `TEHAS_PLUGIN_MODEL_URL` with the four tools the workflow allows
  (`read_file`, `list_files`, `grep`, `submit`), checks each answer against
  its schema, and masks secrets with Floorplan's `maskSecrets` before it
  writes.
- The run: copy the map's state from `/state`, refresh or make the map, then
  `serve.mjs --export` into `/out/map/`. The export leaves out `.cache/` and
  the host's paths.
- The view: one small page on the kit with a "Refresh floorplan" button
  (the `refresh` action), the time and commit of the last map, and the
  exported map in an iframe below.

- The hook, `after:work`: rebuild the map on the cycle's branch head from
  the default branch's map in `/state`, and leave as notes what the change
  added to Floorplan's Health check: a key in the code, an endpoint with no
  sign-in, an open Supabase table or Firebase rule, a Stripe webhook that
  can be faked. Notes only, never a gate, with the findings' places and no
  secret values. It shows a hook in action on a real change, and the
  findings never reach the view.

- The skill, `map`, and its tool, `find-part`: a chat asked "where does
  checkout live?" or "what does this ticket touch?" calls `find-part`, which
  reads the last map in `/state` and answers with the part, its files and
  what it talks to. No model call: the map is already written. A person
  writing a ticket in Obeya gets the parts it is likely to touch.

What the view has, from Floorplan's map: the parts, files, endpoints and
screens, and Recent work from the commits since the last map. It has no Ask
bar and no flow requests: those need Claude Code or Codex beside the map.

The Health check names where keys sit in the code. Even behind the
sign-in, that is more than every reader of the repository needs, so the
reference plugin leaves Health out of the export (`--include` without
`health`) and its findings go only into the hook's notes on the pull
request, which tehas posts. Turning it on in the view is a setting of the
plugin, off by default.

## Open points

1. Panels are at most 4. Should plugins have their own menu section with its
   own limit, so they do not take a person's panels?
2. A plugin that needs a server of its own (a view that answers requests)
   is left out of v1. It would follow Obeya's way: its own program behind
   the edge, reached only through the public APIs.
3. Should `TEHAS_PLUGIN_ACCESS` be one setting for the factory, or one per
   plugin? One for v1.
4. Does the driver live in the plugin repository, as above, or does tehas
   carry one driver for any Floorplan-like `workflow.json`? Recommended: the
   plugin's, so tehas stays plugin-agnostic.
