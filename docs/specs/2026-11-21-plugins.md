# Spec: plugins v1

**Status**: Draft 2026-11-21, rewritten the same day after a review of every
part against the code (the comment "Review of the spec, six parts" on pull
request #2634, which merged the first design). Owner's decisions: own unit and container, a pinned external
repository, GitHub sign-in on every address, the v1 scope below, and industry
writing plugins into the `instance.env` it already pushes. Nothing is built.

What v1 leaves out is in `docs/plans/2026-11-21-plugins-v2.md`, the handover
for plugins v2.

## Purpose

A **plugin** is a feature that is not tehas's own: a program from a git
repository, pinned by commit, that adds a view to a factory's dashboard and
may report on a cycle's pull request. It runs on the factory's host in a
container of its own and gets nothing a person did not grant.

The first plugin, and the reference, is
[tehas-app/tehas-plugin-floorplan](https://github.com/tehas-app/tehas-plugin-floorplan):
a [Floorplan](https://github.com/haydenschmitty/floorplan) map of the product,
refreshed when the default branch moves, and Floorplan's Health check on each
pull request a cycle leaves.

## The guarantees

1. **Off unless asked.** With `TEHAS_PLUGIN` off, no plugin is fetched,
   built or run, and there is no plugin unit, file, port or menu item.
2. **Pinned.** A plugin is a git URL and a full commit. Its grants name the
   same commit. A new commit runs only when a person, or industry's settings
   push, changes both lines and `tehas update` runs. `tehas plugin try`
   runs a local folder once for its author and is never a plugin of the
   factory (see "Writing a plugin").
3. **Fail closed.** A malformed plugin setting stops the settings load with
   78. A manifest, a Dockerfile or a build that breaks a rule makes that
   plugin refused, and nothing of it runs.
4. **A refused plugin is skipped, not fatal.** `tehas update` finishes the
   rest of the update, leaves the refused plugin off, says why, and exits 1
   at the end. `tehas plugin` shows the refusal.
5. **Outside the cycle.** A plugin never runs in a cycle's container and the
   cycle's container is given nothing new (hard rule 4). A hook runs after the
   cycle's report, in its own unit, and holds no slot, lock or label.
6. **Nothing without a grant**, and nothing a grant could give beyond the
   list in the security part.
7. **Signed in, always.** Every address of a plugin needs a GitHub sign-in
   with access to the factory's repository. A view loads nothing from another
   site.
8. **Writes only through tehas.** A plugin never writes to the product,
   GitHub or the state store. What a hook reports, tehas posts.
9. **Removable.** A plugin taken out of `TEHAS_PLUGINS` loses, at the next
   `tehas update`, its view, panel, images, state and timer. Its run rows in
   the state store stay, as history does.
10. **Any licence, closed source included.** See "Licences".

## What v1 ships

| Surface | In v1 |
| --- | --- |
| View | One static view per plugin, a panel in the dock, behind the sign-in, widgets on the kit |
| Code | `product`: the default branch's head, and a pull request's head in a hook |
| Model | `model:<tokens>`: chat completions through a socket made for the run |
| Button | `action:refresh`: asks for a run |
| Stage | `hook:after:work`: reports on a cycle's pull request as a commit status, its findings behind the sign-in |
| Runs | When the default branch moves, and on demand |

Everything else is reserved for v2 and refused by name with a word that says
so: `gate:`, other hook points, `skill:`, `tool:`, `net:`, `factory-read`,
`factory-sessions`, other `kind`s, more than one view.

## Terms

| Term | Meaning |
| --- | --- |
| plugin | A program from a pinned git repository |
| manifest | `tehas-plugin.json` at the root of the plugin's repository |
| run | One start of the plugin's image: `refresh` (default branch or on demand) or `hook` |
| view | The files a good refresh left, served behind the sign-in |
| grant | A capability a person allowed, for one plugin at one commit |

## Settings

The feature is `plugins` in `console/core/src/features.rs`, building in the
release that brings it, switch `TEHAS_PLUGIN`. Its settings, in
`instance.env`, checked by `console/core/src/settings/rules.rs`:

```
TEHAS_PLUGIN=on
TEHAS_PLUGINS="floorplan=https://github.com/tehas-app/tehas-plugin-floorplan@0123456789abcdef0123456789abcdef01234567"
TEHAS_PLUGIN_GRANTS_FLOORPLAN="0123456789abcdef0123456789abcdef01234567 view product model:2000000 action:refresh hook:after:work"
TEHAS_PLUGIN_ACCESS=write
```

| Setting | Rule |
| --- | --- |
| `TEHAS_PLUGINS` | Space-separated `<name>=<url>@<commit>`. Name `a-z` and `0-9`, 1 to 12 characters, a letter first, no `-`, unique, and not one of tehas-industry's secret words (`key`, `token`, `secret`, `private`, `password`, `passwd` and their plurals), which its settings check refuses as part of a variable's name. URL `https://`, no user, password, query or fragment. Commit 40 lower-case hex. At most 4 |
| `TEHAS_PLUGIN_GRANTS_<NAME>` | The plugin's commit, 40 lower-case hex, then its grants, space-separated. A commit other than the pin's grants nothing, and the plugin is refused with "the grants are for another commit". A grants line for a plugin not in `TEHAS_PLUGINS` is refused at load. `model:<tokens>` is 1 to 999999999; a bare `model` in a grant is refused |
| `TEHAS_PLUGIN_ACCESS` | `read`, `triage`, `write`, `maintain` or `admin`: the least permission on `TEHAS_REPO` that lets a person in. Required when any plugin is granted `view` or `action:`. No default. `read` and `triage` are refused while the repository is public (see the web part) |
| `TEHAS_PLUGIN_LIMITS` | Optional. `memory=<GiB> cpus=<n> disk=<GiB>`, all three, in that order, each 1 to 999: the most one run may have. Default `memory=2 cpus=2 disk=4` |
| `TEHAS_PLUGIN_MODEL_DAY` | Optional. Tokens a day for all plugins together. Default 5000000 |

The rules apply to every line given, also with `TEHAS_PLUGIN` off. A bad
line is 78 at load, like any setting. The load reads only the lines:
it fetches nothing and runs nothing (hard rule 3). Whether a pin's manifest
asks for what is granted is checked at `tehas update`, after the fetch.

Industry, for a factory it manages, writes these lines into the
`instance.env` it pushes, and its settings repository's pull request is the
review. tehas needs nothing more from industry.

A secret a plugin needs is reserved for v2. v1 plugins need none.

## The manifest

`tehas-plugin.json`, at the pinned commit:

```json
{
  "plugin": 1,
  "kind": "batch",
  "name": "floorplan",
  "label": "Floorplan",
  "license": "Apache-2.0",
  "build": "Dockerfile",
  "asks": ["view", "product", "model", "action:refresh", "hook:after:work"],
  "timeout": 3600,
  "ui": {"kit": 1},
  "view": {"label": "Floorplan"},
  "actions": [{"id": "refresh", "label": "Refresh floorplan"}],
  "hooks": [{"at": "after:work", "timeout": 600}]
}
```

| Field | Rule |
| --- | --- |
| `plugin` | `1`. Anything else: refused |
| `kind` | `batch`. Anything else: refused as v2 |
| `name` | Equals the name in `TEHAS_PLUGINS` |
| `label` | One line, 1 to 24 characters, control characters refused |
| `license` | Optional. 1 to 64 characters of `[A-Za-z0-9.+:() -]`: an SPDX expression or `proprietary`. Shown, never acted on |
| `build` | A path in the repository to a Dockerfile, at most 255 bytes, parts of `[A-Za-z0-9._-]`, none `.` or holding `..`. The build context is the repository at the commit |
| `asks` | At most 6, no duplicates. The capabilities it wants, by name without a value: `view`, `product`, `model`, `action:<id>`, `hook:after:work`. Each must be granted, or the plugin is refused; the grant gives the value, as `model:2000000` |
| `timeout` | Seconds for a refresh run, 60 to 14400 |
| `ui` | Optional. `{"kit": 1}`: the gate serves the kit to the view |
| `view` | Optional; needs `view`. `label`, 1 to 24 characters, the panel's label |
| `actions` | Optional, at most 2. `id` `a-z` and `-`, 1 to 16; `label` 1 to 24. Each needs `action:<id>`. An action asks for a refresh |
| `hooks` | Optional, at most 1. `at` is `after:work`; `timeout` 60 to 1800. Needs `hook:after:work` |

A field not in the table is refused, so a manifest made for a later tehas
never runs half read; `views`, or `view` as a list, is refused as v2. A
manifest is at most 64 KiB. The schema holds every rule but three, which are
the reader's alone: the name equal to the pin's, each action's own ask, and
unique action ids. `api/plugin-manifest.schema.json` holds the same rules,
with `api/plugin-manifest.full.json` and `.bare.json`, CC0-1.0 like the rest of
`api/` (see "Licences").

## Runs

- **Refresh, when the default branch moves.** `tehas-plugin.timer` runs
  `tehasbot plugin tick` every 10 minutes. It reads the head the poll already
  fetched into the product's mirror, no extra GitHub call, and starts a
  refresh of each plugin whose last attempt was at another head. A failed
  attempt is not tried again at the same head; a new head or `tehas plugin
  run` tries again. The first tick after a plugin is set up refreshes it.
- **Refresh, on demand.** `tehas plugin run <name>`, or a press of an action.
- **Hook.** After a cycle's report, see the hooks part.
- **Not while held back.** No refresh starts while the factory is paused,
  drained, read-only, or while `tehas update` or `tehas state pack` runs.
  The tick then does nothing and says why in its log.
- **One refresh of a plugin at a time.** A tick or a press while one runs
  does nothing and answers "running". Hooks have their own queue.
- **In the slice.** Every plugin container runs in `tehas.slice` and counts
  in admission by room (`host/docs/operating.md`, "Limits that hold work
  back"), so a plugin never takes room a cycle was promised.

A run is `tehas-plugin@<name>.service` for a refresh and
`tehas-plugin-hook@<name>-<pr>.service` for a hook, each starting one
container through the Rust program `tehas-plugin`. Each run is a row in the
state store, table `plugin_runs`: plugin, commit, kind, trigger, who pressed
(a login, or `timer` or `host`), head, start, end, result, tokens.

## Commands

| Command | What it does | Exits |
| --- | --- | --- |
| `tehas plugin [--json]` | Each plugin: pin, label, asks, grants, state (`unbuilt` before its first fetch, `building`, `ready`, `refused`), refusal, last run, tokens today | 0; 78 when the feature is off |
| `tehas plugin review <name> [<commit>] [--json]` | Fetches the commit (the pin by default) and prints what it asks, what each ask lets it do, what is granted, what changed since the pin, the Dockerfile's base images, and the grants line to write. Writes nothing but the fetched objects | 0; 1 fetch or read failed; 3 refused, with why; 64; 78 |
| `tehas plugin run <name>` | Asks for a refresh now | 0 asked; 3 one is running; 64; 78 |
| `tehas plugin hook <name> <pr>` | Runs the plugin's hook on that pull request's current head | 0 asked; 3 running or no such open bot pull request; 64; 78 |
| `tehas plugin log <name> [--hook <pr>]` | The last run's log, at most 1 MiB, as the plugin wrote it | 0; 3 none; 64; 78 |
| `tehasbot plugin tick` | The timer's step | 0 |

`tehas plugin --json` prints `{"api": 1, "plugins": [...]}`, with
`api/plugin.schema.json` and a sample, empty when none is set. `tehas api`
lists `plugins` in `features` once the feature ships.

Industry needs only `tehas plugin --json` and `tehas plugin review --json` to
show where a plugin runs and why a factory refused it.

## Writing a plugin

A plugin's author is often an agent. Three commands make the loop short,
before anything is pushed or pinned:

| Command | What it does | Exits |
| --- | --- | --- |
| `tehas plugin new <dir> [--name <name>]` | Writes a starter plugin into an empty folder: a `tehas-plugin.json` that asks only for `product`, a Dockerfile, a run script that writes one page on the kit to `/out`, a README, and a test that checks the manifest against `api/tehas-plugin.schema.json`. Needs no settings and runs wherever tehas's release unpacks, a laptop included. Runs no git command | 0; 1 the folder is not empty; 64 |
| `tehas plugin check <dir> [--json]` | Reads the manifest and the Dockerfile from a local folder and applies the rules `review` applies to a fetched commit: the schema, the build rules, each ask known and not reserved. Needs no settings and no network | 0; 3 refused, with why; 64 |
| `tehas plugin try <dir> --grants "<grants>" [--json]` | On a factory, as the tehas user: builds the folder and runs one refresh in the container a pinned plugin with those grants gets, and prints the path its `/out` was copied to. No view is served, no panel, timer or state is made, and nothing of it is left after the run but that copy and its log. Grants past what the factory's settings allow are refused | 0; 1 the build or the run failed; 3 refused; 64; 78 off |

`tehas plugin try` runs code that no one pinned. It is a person's command
on the host, as `tehas dev` is, and the container is the same one with the
same grants, so it gives the code nothing the folder's author could not
get by pinning it. It never adds the folder to `TEHAS_PLUGINS`.

The Start page of the manual says how to write one once the commands ship.

## Licences

tehas is Apache-2.0 and has no copyleft, so a closed program may use it. The
contract keeps more distance than that.

- A plugin is a separate program in its own container. It meets tehas through
  the manifest, its mounts and socket, the files it leaves in `/out`, and the
  commands above. It links no tehas crate, imports no tehas script, and is not
  built on a tehas image.
- A view that asks for the kit loads it from the gate at run time. It uses
  the kit's Apache-2.0 and Solid's MIT files without redistributing them, and
  neither licence puts a term on the plugin. A plugin may still copy the kit;
  Apache-2.0 allows that in closed code, with its notice.
- `api/` is dedicated to the public domain under CC0-1.0, with its own
  `api/LICENSE`, so a plugin may copy schemas and samples freely. `README.md`
  and `NOTICE` say so. The files in `api/` are the owner's and the factory
  bots' work.
- tehas never distributes a plugin. No plugin code is in this repository, its
  releases, the sandbox image or `tehas state pack`.
- The reference plugin is Apache-2.0 and keeps the MIT notice of the Floorplan
  it carries.

## The reference plugin: Floorplan

`tehas-app/tehas-plugin-floorplan` holds:

- The manifest above.
- Floorplan's skill scripts at a named upstream commit, copied into the
  repository with their MIT licence (zero dependencies), so the image builds
  with no network. `CHECKSUMS.txt` from upstream is kept beside them and
  checked by the repository's own test.
- A Dockerfile `FROM` a Node image by digest.
- A driver, in Node, that follows Floorplan's `workflow.json` in unattended
  mode (`FLOORPLAN_UNATTENDED=1`, `--json`). It runs the model jobs through the
  run's model socket with the four tools the workflow allows (`read_file`,
  `list_files`, `grep`, `submit`), checks each answer against its schema, and
  masks secrets with Floorplan's `maskSecrets` before it writes.

**A refresh**: copy `/product` to `/work/code` (Floorplan writes `floorplan/`
in the codebase's root), put the last map from `/state` in place, refresh or
make the map, write it back to `/state`, and export it with
`serve.mjs --export /out/map.html --include flows,notes,recent`. The view's
`/out/index.html` is a small page: the commit and time of the map, a
"Refresh floorplan" button that uses the kit's `press.js`, and `map.html` in
a frame. Health is left out of the view. The image is `node:22-bookworm` by
digest, since git is needed and the build has no network to add it.

**The hook**: copy the pull request's head to `/work/code`, the default
branch's map from `/state` (read only in a hook), rebuild with no model call,
and report what the change added to Floorplan's Health check: kinds of
finding, file and line, never a value. The verdict is `note` or `pass`, never
`fail` in v1.

What the view has: the parts, files, endpoints and screens, and Recent work.
No Ask bar and no flow requests: those need Claude Code or Codex beside the
map.

## Open points

1. Plugins take panels from the person's four. v1 refuses a fifth and says
   so. A menu section of their own is v2.
2. Whether Floorplan's maps are good enough on the factory's model is not
   known. The reference plugin's first step answers it before the rest is
   built (Work 1).

## Work

In order. Each is a pull request; a security change says so.

1. **The reference driver, by hand.** In `tehas-plugin-floorplan`: the
   driver against this repository and the factory's model, no tehas changes.
   It decides whether the rest is worth building.
2. **Settings and manifest.** The feature, the settings' rules, the manifest's
   reader and its schema, `tehas plugin` and `review`. `api/LICENSE`.
3. **The run.** `tehas-plugin`, the container as a pure function of manifest
   and grants in `sandbox.rs`, its argument lists, the build, `/out` and
   `/state`, the product export, the units and the timer. Security change.
4. **The model socket.** Security change.
5. **The gate.** `tehas-plugin-gate`, the edge routes, the sign-in, the
   policy, the kit, the action, the panel. The App's callback and secret in
   `tehas setup`. Security change.
6. **The hook.** The seam in `tehas-cycle`, the hook unit, the status and the
   findings page. The App's "Commit statuses: write". Security change.
7. **Writing a plugin.** `tehas plugin new` and `check`, which need only
   the schema, then `try`, which needs the run (3).
8. **The manual.** `host/docs/plugins.md`, `api.md`, `features.md` as
   building, the changelog fragment with its adopter action.
