# Events

**Status**: proposed, 2026-11-22. Step T11 of
`docs/plans/2026-11-21-coding-standard-v2.md`. Being built, step by step
as "The build" lists. It uses the
words of `docs/specs/2026-11-22-ports.md` and answers that spec's open item
"Events". Written from two drafts read by three reviewers; the shape of the
first, with what the reviewers asked to take from the second and every
defect they found that holds against the code fixed. Revised after a
consumer's review so that a consumer can see every event after the fact.

## Purpose

tehas tells nobody what a cycle did, except through one plugin hook,
`hook:after:work` (`console/cycle/src/hook.rs`), and through the factory
API, which a program polls and compares. This spec gives tehas one
vocabulary of events in the ports' words, a small in-process dispatcher in
the manner of Symfony's EventDispatcher, the JSON form a plugin, a page and
another program read, and the fields the factory API needs so that every
event can also be seen after the fact.

The consumer that runs many factories raises the same events itself, from
what it reads through the factory API between polls. So every event is pull
first: a fact the factory API prints, or prints after this step. Push is the
same fact, raised in the process that records it.

## Decided

1. **Pull first.** Every event has a witness: a read that shows the same
   fact later, with the same identity and the same values. tehas pushes
   nothing to another program in 2.0.
2. **Raised where the fact is recorded, after the record commits.** The
   payload is built from what the store wrote, never from the raiser's own
   view, so push carries what the witness then prints. A listener can never
   undo the fact or fail the raiser.
3. **One module, in `tehas-ports`.** `console/ports/src/events/`: the names,
   the payloads, the envelope, the dispatcher. std and serde alone, no
   effects, no clock, no supplier word, as the crate's rules say. The
   consumer vendors it with the crate at the tag, so both sides share the
   names, the types and the serde shape, not a copy of them.
4. **Synchronous, in the raiser's thread.** No queue, no threads, no
   runtime. A listener that must reach outside starts the work and returns,
   as the hook's seam does today (a request file and a unit started with
   `--no-block`).
5. **Notify and gate are two sides of a point.** The `after` side is a
   notify event: the fact happened, nothing waits. The `before` side of a
   few points is a gate: the act waits for an answer. Every raise point in
   2.0.0 is a notify event. The gate's contract is written now; the first
   gate is raised in 2.1.
6. **Names are `<subject>.<what-happened>`**, lower case, words joined by
   `-`, past tense, in the ports' words: `cycle.ended`, `change.offered`,
   `factory.limit-changed`. Never a supplier's word (no label, no pull
   request). The subjects `cycle`, `question`, `ticket`, `change` and
   `factory` are tehas's; a consumer's own events take a subject of its own.
7. **One fact, one name, one identity.** The pair (name, key) is unique. The
   key is made from the fact by the payload's own code, so tehas and a
   consumer that builds the event from a witness make the same key. The one
   exception, the clear of a limit, is said where `factory.limit-changed`
   is listed.
8. **The cycle has a stable id**, `<blueprint>-<attempt>`, such as `12-3`,
   printed by `tehas status --json` and `tehas history --json`. It is
   unique within one store, which `tehas api --json` names in `store`.
9. **Every start has exactly one history line**, and every work line has one
   end word from a closed set, `tehas_core::outcome::OUTCOMES` with
   `offered` in place of today's `pr`.
10. **Times in JSON are RFC 3339 strings** in whole seconds and UTC,
    `2026-11-22T13:20:00Z`, as the factory API prints them (`started` and
    `ended` in history, `since` in status, `askedAt` in question after
    T11.6). A payload holds the ports' `At` in Rust and writes it as that
    string at the JSON edge, so a consumer copies a witness's value instead
    of converting it.
11. **The plan's example names are replaced.** `cycle.after-work` is
    `change.offered`, granted `hook:after:change.offered`: the 1.x hook's
    point is "a cycle left a change for review", and naming it so keeps
    `cycle.ended` meaning every end. `ticket.approved` is `ticket.acted`
    with `act: "Approve"`, because `Act` may grow and an event per act would
    make each new act a contract change. The 2.1 surfaces spec's placeholder
    `hook:gate:cycle.before-work` is `hook:before:cycle.started=<policy>`.
    The owner can overrule any of the three.
12. **Plugins stay off in 2.0.0.** The dispatcher, the notify events, their
    schemas, the factory API's new fields, the kit's names and the renamed
    grant ship. No plugin runs; no page listens to a server stream until
    2.1.

## The words

| Word | Meaning |
| --- | --- |
| event | A fact tehas records once, named and typed, with a schema in `api/` |
| notify event | The `after` side: comes after the fact; nothing waits on it |
| gate | The `before` side: the act waits for every gate listener's answer |
| payload | The event's typed data: one Rust type and one schema per name and side |
| envelope | `api`, `event`, `when`, `key`, `at` and the payload as `data` |
| key | The event's identity within its name, made from the fact |
| witness | The read that shows the fact after it happened |
| listener | A function registered for one name and side, with a priority |
| stop | A listener's answer that the later listeners are not called |
| cycle id | `<blueprint>-<attempt>`, the identity of one cycle: `12-3` |
| end | The closed word a cycle ended with: `offered`, `merged`, `handoff`, `parked`, `failed`, `refused`, `stopped` |
| store | The id of one state store, made once when it is first laid: a factory moved by pack and unpack keeps it |
| source | The name of a factory, set on an envelope by a consumer that relays many factories' events |
| port shape | How a port type in a payload is written: the ports' own serde shape, which `tehas-ports` defines and the consumer vendors (`"Approve"`, `{"Number": 12}`). Times alone are RFC 3339 strings (Decided 10) |

The consumer copies this table as its terms.

## The cycle id and the end

What the code has today:

- **An attempt per issue.** `cycles.attempt` and `cycle_history.attempt`
  (`console/store/src/schema.sql`). A start takes one more than the greatest
  attempt in `cycles` and in `cycle_history` for its issue
  (`console/store/src/cycle.rs`), and history keeps the newest 50 rows of an
  issue, so the greatest survives. Neither `status` nor `history` prints it.
- **A write order.** Every history row, of a cycle or a planning turn, is
  given `seq`, one more than the greatest in either table, as it is written
  (`cycle_history_order` and `plan_history_order` in `schema.sql`). Only the
  trim of the 50 deletes a row.
- **A cursor that is not an id.** History's `cursor` is
  `<ended>-<issue>-<seq>`. `--after` compares only its `seq`
  (`Cursor::before` in `console/src/history.rs`) and lists in `seq` order,
  so it already pages by write order. The cursor of v0.13, `<ended>-<issue>`,
  is still taken and compared on its seconds and issue. A cursor names a
  line, not a cycle, and a running cycle has none.
- **An open outcome.** History's `outcome` is the store's status word (one
  of `tehas_core::outcome::STATUSES`); its schema takes any string of 1 to
  40 characters. History's `status` is the exit status, an integer.
- **A closed set elsewhere.** `OUTCOMES` is `pr`, `merged`, `handoff`,
  `parked`, `failed`, `refused`, `stopped`, decided by
  `console/analytics/src/run.rs` (`outcome`) from fields history has, and
  kept in the analytics' `runs.outcome` CHECK
  (`console/analytics/src/schema.sql`).
- **Lines missing.** A refused start and a cycle ended by `tehas stop`
  (`end_short`) and a lost cycle (the next start) write only `endings`, the
  publish's ten newest ends, never `cycle_history`.
- **One start time.** `running[].since` in `status` is the health file's
  `startedAt`, and history's `started` is `cycle_history.started_at`; both
  are `cycles.started_at` of the start (`console/store/src/live.rs`,
  `cycle.rs`). A row imported from the ledgers of v0.30 may have no
  `started_at`.
- **The trim is by end time.** History keeps an issue's 50 rows with the
  greatest `at`, not the greatest `seq`.

What T11 makes:

- **`cycle`**, the cycle id, pattern `^[1-9][0-9]{0,8}-[1-9][0-9]{0,8}$`,
  on each item of `running` in `status --json` and on each work line of
  `history --json`. A running cycle and its ended line carry the same id.
  It is unique within one store (see "The store"); a consumer of many
  factories qualifies it with the factory and its `store`. A plan line has
  none. `cursor` stays the paging key and is not an id: a consumer keys
  cycles on `cycle`, lines on `cursor`.
- **`running[].how` and `running[].by`**, the start's `cycles.how` and
  `cycles.started_by` in the words history prints, `by` left out for a
  cycle run by hand, so `cycle.started` is built from `status` with every
  field. `running[].since` equals the history line's `started` to the
  second, which a test pins.
- **Paging by write order.** `--after <cursor>` returns every line written
  after the cursor's line, whatever its `ended`. The order is `seq`, the
  write sequence; `ended` is not an order. The cursor keeps its shape,
  `<ended>-<issue>-<seq>`, because `tehas export` names directories by it
  and its schema pins it; its leading parts are read by no comparison. The
  v0.13 cursor is still taken as today and is given a three-part `next` on
  the first line it lists.
- **`recorded`**, on a work line whose write time is not its `ended`: the
  time the line was written. A lost line keeps `ended` as the best estimate,
  when it was last heard from, so it is backdated; `recorded` says when it
  was written, and its `seq` places it after every line written before it.
  `cycle_history` gains `recorded_at`, set on every row.
- **The trim is by `seq`.** History keeps an issue's 50 rows with the
  greatest `seq`, so a backdated line is never the one trimmed first, and
  `seq` is never given twice.
- **`started` is required on a work line.** The state-store step, T11.2,
  sets a missing `started_at` to the row's `at`, so a line from the v0.30
  ledgers prints `started` equal to `ended`; every line written since has
  the start's time. On work lines only: a plan line may leave it out. The
  rule is in the field's description in `api/history.schema.json` and
  pinned by Rust tests, since the schema checker, `test/schema.jq`, has
  no `if`/`then` to say it in the schema.
- **`end`**, on each work line: one word of `OUTCOMES`, an `enum` in the
  schema, decided by the table below. The set is exhaustive: a new word is a
  major change.
- **`offered` replaces `pr`** as the end word of a cycle that left an open
  change and did not park. It matches `change.offered` and names no
  supplier. A 2.0 rename with no alias: the analytics, history, the MCP
  server's outcome words and the event use one word for one fact (R1).
- **`change`**, on a work line that names a change: its number, from
  `cycle_history.pr`, so no consumer parses an address. The line's `pr`,
  the change's address, stays.
- **`signalled`**, on a work line, `true` when a signal stopped the cycle,
  left out otherwise. The 1.x hook skips such a cycle, and history must show
  it for `change.offered` to have a witness.
- **`outcome` and `status` keep their meaning**: the store's status word and
  the exit status. `end` is the word a program decides on.
- **One function decides the end**, `tehas_core::outcome::end`, moved from
  the analytics' `run::outcome`. History, the events and the analytics call
  it (R1).
- **One line per start.** A refused start, `tehas stop` and a lost cycle
  write their `cycle_history` row in the transaction that writes their
  `endings` row:
  - refused: `outcome` `refused`, `status` the exit status when the unit
    left one, `started` the start's time, `end` `refused`;
  - stopped: `outcome` `stopped`, `started` the start's time, `end`
    `stopped`;
  - lost: `outcome` `lost`, `ended` when it was last heard from, as
    `endings` already computes it, `recorded` the time of the start or poll
    that wrote it, `end` `failed`. The store ends a cycle as lost only
    when no process holds its lock and it has been quiet for `LOST_AFTER`
    (120 seconds); otherwise it refuses with `heard`, which the poll
    ignores. One race is left: a cycle already quiet for 120 seconds or
    more that a person stops with `tehas stop` can be ended as lost by the
    poll between the release of its lock and `--stopped`, a window that
    holds `docker rm -f`, up to 30 seconds. It is harmless: the page
    already showed the cycle lost, and `tehas stop` then says the record
    was already ended.

  `endings` stays the publish's short list of ends (`console/store/src/live.rs`
  reads it), written from the same end; history is the record. A store test
  pins that every `endings` row has its history line.
- A store test pins that an attempt is never given twice for an issue, also
  after history drops rows past the newest 50.

### The end word

`end` takes the first row that matches, top to bottom. The inputs are the
line's `outcome` (the status word), `status` (the exit status), `change`,
`parked` and `failureKind`. `cap`, `parkReason` and `signalled` decide no
end: `signalled` only keeps a change from being offered.

| # | When | End |
| --- | --- | --- |
| 1 | `outcome` is `merged` and `parked` is false | `merged` |
| 2 | `outcome` is `closed`, `interrupted` or `stopped`, and `parked` is false | `stopped` |
| 3 | `outcome` is `refused` | `refused` |
| 4 | `status` is 3, 4, 5, 40, 64 or 78 | `refused` |
| 5 | the line has a `change` and `parked` is false | `offered` |
| 6 | `outcome` is `handoff` | `handoff` |
| 7 | `outcome` is `killed`, `stalled`, `timeout`, `aborted`, `unknown`, `failed` or `lost`, or `failureKind` is set and is not `cap` | `failed` |
| 8 | any other line | `parked` |

`merged` means the change was merged within the cycle: the report saw it
merged and wrote `merged` with exit 0. A runner that claims `merged` when
no merged change is found is parked by the report (`merged-claimed` in
`console/cycle/src/report.rs`) with the word `merged` kept, so row 1 asks
that the line did not park; such a line ends by row 8. Rows 1, 2 and 5 ask
`parked` false, so `parked: true` never comes with `merged`, `stopped` or
`offered`: every parked line ends with a word of `STOPS`. A cycle tehas
stopped for its disk also has the status word `stopped`: when it parked, a
later row decides it.

One work line per word, the fields that decide it and `end`:

```json
{"cycle": "7-1", "outcome": "merged", "status": 0, "parked": false, "change": 9, "end": "merged"}
{"cycle": "12-4", "outcome": "closed", "status": 10, "parked": false, "end": "stopped"}
{"cycle": "14-2", "outcome": "refused", "status": 78, "parked": false, "end": "refused"}
{"cycle": "15-1", "outcome": "handoff", "status": 10, "parked": false, "change": 21, "end": "offered"}
{"cycle": "16-3", "outcome": "handoff", "status": 10, "parked": true, "change": 22, "end": "handoff"}
{"cycle": "12-3", "outcome": "failed", "status": 10, "failureKind": "verify-failed", "parked": true, "end": "failed"}
{"cycle": "18-1", "outcome": "running", "status": 10, "cap": "step-failed:develop", "failureKind": "cap", "parked": true, "end": "parked"}
```

Against today's `run::outcome` four ends change, each a fix with a
changelog line and a line of "Changed in 2.0": `stopped` from `tehas stop`
ends as `stopped` and `lost` as `failed` (both fell through to `parked`); a
parked `merged` line ends by row 8 (it was `merged`); a parked `closed` or
`interrupted` line ends by the later rows (it was `stopped`).

## The store

- **`store`**, in `tehas api --json`: an id made once when the state store
  is first laid, 32 lower-case hex digits from the host's random source,
  kept in the store's `meta` table. A store laid before T11 is given one by
  the state-store step, T11.2.
- **Pack and unpack carry it.** `tehas state pack` copies the whole store,
  `meta` with it, and `unpack` keeps the copy, so a moved factory keeps its
  `store`. The attempt counters move too: an attempt is read from `cycles`
  and `cycle_history`, which travel whole, so a moved factory never gives
  an attempt twice. `tehas state load` moves every table but `meta` today;
  T11 has it take the copy's `store` as well, since the copy's cycle ids
  come with it.
- **A cycle id is unique within one `store`.** A consumer keeps its seen set
  per factory and `store`, and empties it when `store` changes: a new store
  starts its attempts again, so `12-1` may be another cycle.

## The first list

All notify. "Raised by" is the process that records the fact.

| Event | Raised by, when | Key | Witness |
| --- | --- | --- | --- |
| `cycle.started` | `tehas-cycle`, once the start is on record | cycle id | a `cycle` first seen in `running` of `status --json` (`since` is its time, with `how` and `by`), or first seen on a work line of `history --json` for a cycle that started and ended between two polls |
| `cycle.parked` | the writer of the cycle's history line, when the line has `parked: true`; its end is then one of `STOPS` (`handoff`, `parked`, `failed`, `refused`), as "The end word" says | cycle id | such a work line |
| `question.asked` | the process that records the question: the cycle's report for a park, the planning turn's report for a plan | the question's id, the store's own number | a question first seen in `tehas question --json --after <id>` (every question after an id, answered ones included, new in T11) |
| `cycle.ended` | the writer of the cycle's history line: the report, a refused start, `tehas stop`, the next start or the poll for a lost cycle | cycle id | a work line of `history --json` |
| `change.offered` | `tehas-cycle`, after the end, when the line names a change, has no `signalled`, and its end is not `refused` or `merged` | cycle id | such a work line |
| `factory.limit-changed` | `tehas limit set` when it writes a limit other than the one there (another `cycles`, `plan` or `reason`; a new `until` alone is a renewal, not a change), `tehas limit clear` when there was a limit, and `tehas drain`, which writes `cycles` 0, `plan` off and `reason` `draining` | the limit's `set`, or with no `set` the time the change was observed, `observed` (see below) | `tehas limit --json` differs from the last limit the consumer knows (see below) |
| `ticket.acted` | `tehas-dispatch`, when it records an act of an allowed account: an approval (`approve`), the start of a planning session (`plan`, `refine`), a finish ask taken (`finish`) | `<ticket>@<act>@<at>` | the act, its account and time in the tickets port's history, checked against the allowed list |
| `ticket.closed` | `tehas-dispatch`, when the store records a ticket it has an opinion about as closed | `<ticket>@<at>` | `Closed` in the tickets port's history |
| `change.merged` | `tehas-dispatch`, when the store records a change it links to a blueprint as merged | the change's number | `Merged` in the code host port's activity |

- **Only an allowed account's act is an event** (AGENTS.md rule 5). An act
  by any other account is not recorded, so it is not raised.
- **`change.offered` keeps the 1.x hook's rule.** 1.x asks a hook when the
  cycle was not signalled, not refused, and named a change
  (`Ending` in `console/core/src/plugin/hook.rs`), and the plugin bridge
  then asks only for a change open at its head. The event carries the first
  part, the bridge keeps the second, as today. A merged change is not
  offered; 1.x skipped it at the open check, so no plugin sees a
  difference. A test runs every 1.x case through the event and the bridge
  and finds the same hooks asked.
- **`question.asked` carries `choices` while the store has them.** The
  field is optional: present while the store keeps the question's options.
  As T11.6 keeps them, a planning question's options are kept only while
  the issue waits on it, so `choices` is left out for a planning question
  the issue no longer waits on. A consumer that catches up needs no
  options to act on a question that is no longer waited on.
- **`question.comment` is printed, optional, never null.** `tehas question
  --json` prints `comment`, the id of the comment that asked the question,
  as `question.comment` and `questions[].comment`, where the store has one
  (T11.6). It is the code host's id, so no event carries it.
- **`cycle.parked` and `question.asked` are two events on purpose**: a cycle
  can park with no question (none could be posted), and a plan question has
  no cycle.
- **A key joins its parts with `@`**, which no part can hold: a ticket is
  its number or its key's text (`KeyText`, letters, digits and `-`), an
  act is its name as the ports write it (`Approve`), a time is RFC 3339:
  `12@Approve@2026-11-22T11:10:00Z`. `Key` is a checked type: no white
  space, at most 200 characters.
- **`factory.limit-changed` is keyed on `set`.** `tehas limit --json`
  prints `set`, the time the limit was written, kept in the limit file. The
  event's key and `at` are that `set`, so tehas, a consumer that ran
  `tehas limit set` or `tehas drain` (each prints the limit with its `set`)
  and a consumer that saw it in a poll make the same key. `set` writing the
  limit that is already there keeps its `set` and raises nothing. The same
  limit is the same `cycles`, `plan` and `reason`, so a write that only
  moves `until` is a renewal: it keeps `set` and raises nothing, and a
  program that renews a limit before it expires changes nothing a consumer
  compares.
- **A change with no `set` is keyed on `observed`.** `tehas limit clear`
  removes the file, so `tehas limit --json` then prints `state` `none` and
  no `set`; an unreadable limit, or one written before T11, has no `set`
  either. Such a change carries `observed`, the time it was observed, in
  place of `set`: tehas's own time for its clear, a consumer's poll time for
  what it sees in a poll. A payload has exactly one of `set` and
  `observed`, and its constructors take one; it is never keyed on a default
  time. This is the one key that is not shared (Decided 7).
- **A consumer compares, then raises.** It keeps the last limit it knows:
  the one its last poll read, or the one `tehas limit` or `tehas drain`
  printed when it ran them itself. It raises when a poll differs from that
  limit in `set`, `cycles`, `plan` or `reason`, or in whether there is a
  limit (`none`, `unreadable` or one). `until` and the change of `state`
  from `ok` to `expired` are not compared: an expiry is no event, since
  `until` already says when, and time passing changes nothing a person
  wrote. A hand edit of the limit file is an event to a poller and none to
  tehas, which raises only its own writes.

### Order

- **Within one cycle**, tehas raises `cycle.started`, then once the end is
  recorded `cycle.parked` (if it parked), `question.asked` (if it posted a
  question), `cycle.ended`, then `change.offered` (if it left one). A
  consumer that builds them from one history line and the questions list
  raises them in the same order.
- **Across processes** the only order is `at`. A consumer orders by `at`,
  then by the order above.
- **At most once from tehas, at least once from a consumer.** tehas raises
  once, at its record; a raiser that dies between the commit and the raise
  loses the push, and the witness still has the fact. A consumer that polls
  may see a fact twice; it drops a (name, key) pair it has seen for that
  factory and `store`.

### What a witness keeps

A witness shows a fact only while the store keeps it. A consumer that polls
less often than the store forgets reports the gap instead of guessing.

- **History keeps the newest 50 work lines and 50 plan lines of each
  issue**, by `seq` after T11 (`cycle.rs` and `plan.rs` trim today by `at`).
  `seq`, the last part of each line's `cursor`, is given one at a time
  across both tables and only the trim deletes a row, so in a read with no
  `--issue` a number missing between the consumer's cursor and a line it
  reads is a line trimmed before it read it.
  The consumer reports that gap; it does not raise events for the line.
- **Questions are not trimmed.** An answered question stays, with
  `answeredAt`. A question that is withdrawn before it is answered (its
  comment is gone, or its planning session's questions are withdrawn,
  `park.rs` and `plan.rs`) is kept too, with `withdrawnAt`, where today
  it is deleted. T11.2 makes that change, so every question id stays
  and a consumer that polls sees each `question.asked` once.
- **`status` shows only what runs now.** A cycle that started and ended
  between two polls is first seen in history.
- **The limit is one file.** Two writes between two polls show only the
  second.
- **The tickets port and the code host port** keep what the supplier keeps;
  their adapters page it (R6).

### What is not an event in 2.0

- **A cycle's steps.** `running[].progress` is driver-specific and may change
  in a minor release, and no read keeps every step after the fact.
- **Planning turns, a question answered, a pause, a hold.** Each needs a
  witness that keeps its time and its identity. `answeredAt` in
  `tehas question --json` is the start of one for a question answered; the
  event waits for its own spec.

Each is added later by expand (R9), with its witness.

## Payloads

Field names are camelCase, as the factory API's are after T11.6, which
renames the one snake_case field of a witness, `asked_at` of
`tehas question --json`, to `askedAt`: a 2.0 rename with no alias. (The
plugin commands' `manifest_sha256` and the like are no witness and are not
this spec's.) A field with no value is left out, never null; a `false` the
witness leaves out is left out too. `ticket` is left out when the ticket is
the blueprint, which is every setup in 2.0. `blueprint` is the number the
factory API calls `issue`; every other value is the witness's, copied.

**One wire convention: a port type keeps the ports' own shape.** Every port
type in a payload (`TicketKey`, `Act`, `Account`, `CloseReason`,
`QuestionKind`, and any other) is written as `tehas-ports`'s serde writes
it, the shape the consumer vendors with the crate (R1: one owner of each
shape). There is no second, lower-case form: an act is `"Approve"`, a
question's kind `"Park"`, a ticket `{"Number": 12}` or `{"Key": "OPS-12"}`,
an account `{"realm": "Tickets", "login": "alice", "id": "1001", "kind":
"Person"}` (`id` left out when the site gives none, never null), a close reason `"Done"`, `"NotPlanned"` or `{"Duplicate":
{"Number": 7}}`. The one exception is a time, an RFC 3339 string by
Decided 10. The events' own words (`end`, `how`, `state`, `when`) are this
spec's and are lower case.

- `api` is the events' contract version, 1.
- `at` is when the fact happened: a start's `started`, an end's `ended`, a
  question's `askedAt`, an act's time in the supplier's history, a limit's
  `set`. Never when it was raised, and never a lost line's `recorded`.
- `source`, optional, is the name of the factory the event is from. tehas
  leaves it out: an event of tehas is about the factory that raised it. A
  consumer that relays envelopes from many factories sets it, and changes
  nothing else; one that sees `source` on an envelope it relays keeps it.
  The identity of a relayed event is (`source`, name, key).

## The dispatcher

```rust
// events/mod.rs

#[non_exhaustive]
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug, Serialize, Deserialize)]
pub enum Name {
    #[serde(rename = "cycle.started")] CycleStarted,
    // ... one variant per row of "The first list"
    #[serde(other)] Unknown,
}
impl Name {
    pub const ALL: [Name; 9];
    /// "cycle.started" and so on: the one place each string is written.
    pub fn as_str(self) -> &'static str;
    /// Whether the point has a `before` side that is raised: false for
    /// every name in 2.0, until the first gate in 2.1.
    pub fn gate(self) -> bool;
}

pub enum When { After, Before }

/// One variant per name, the payload as `data`.
#[non_exhaustive]
#[derive(Serialize, Deserialize)]
#[serde(tag = "event", content = "data")]
pub enum Event {
    #[serde(rename = "cycle.started")] CycleStarted(CycleStarted),
    // ...
    /// A name this copy does not know, a known name whose `data` does not
    /// read (the ports' one read rule, `unknown::read_any`, on the tag
    /// `event`), or any event of an envelope whose `api` is not 1. Read,
    /// never raised; writing it is an error, never an envelope with no
    /// `event`.
    #[serde(untagged, deserialize_with = "...", serialize_with = "...")] Unknown,
}

/// A typed payload. The key is the payload's to make (Decided 7).
pub trait Payload: Serialize + Clone + Into<Event> + 'static {
    const NAME: Name;
    fn key(&self) -> Key;
    fn at(&self) -> At;
    fn peek(e: &Event) -> Option<&Self>;
}

pub struct Envelope { pub api: u32, pub source: Option<Source>, pub when: When,
                      pub key: Key, pub at: At,
                      #[serde(flatten)] pub event: Event }
/// A factory's name, as a consumer of many names it: lower-case letters,
/// digits and `-`, at most 64 characters. tehas never sets it.
pub struct Source(String);
/// Reads its event as `Unknown` when `api` is not 1. serde writes the
/// fields as `api`, `source`, `event`, `data`, `when`, `key`, `at`, since
/// `event` is flattened: compare envelopes as values, not as text.
impl Envelope {
    pub fn new<P: Payload>(p: P) -> Self;   // key and at from the payload, no source
    pub fn from(self, source: Source) -> Self;
}
```

```rust
// events/dispatch.rs

pub enum Heard { Go, Stop, Failed(String) }
pub struct Fault { pub listener: &'static str, pub why: String }
pub struct Raised { pub stopped_by: Option<&'static str>, pub faults: Vec<Fault> }

pub struct Builder { /* listeners by name, side and priority */ }
/// The log's priority, i16::MAX, reserved.
pub const LOG: i16 = i16::MAX;
impl Builder {
    pub fn new() -> Self;
    /// The log listener: it alone takes `LOG`, and cannot stop an event.
    pub fn log(&mut self, listener: &'static str,
               f: impl Fn(&Envelope) + Send + Sync + 'static) -> &mut Self;
    /// `on` and `on_any` panic at wiring when given `LOG`.
    pub fn on<P: Payload>(&mut self, listener: &'static str, priority: i16,
                          f: impl Fn(&P) -> Heard + Send + Sync + 'static) -> &mut Self;
    /// For the bridges that take every event as JSON: plugins, SSE.
    pub fn on_any(&mut self, listener: &'static str, priority: i16,
                  f: impl Fn(&Envelope) -> Heard + Send + Sync + 'static) -> &mut Self;
    pub fn build(self) -> Dispatcher;
}

/// Built once at a program's wiring, then read only: `Send + Sync`.
pub struct Dispatcher { /* ... */ }
impl Dispatcher {
    /// Calls the listeners of `p`'s name in order until one stops it.
    pub fn raise<P: Payload>(&self, p: P) -> Raised;
}
```

- **Registration only at wiring.** Each program's `main.rs` builds its
  dispatcher. There is no global dispatcher, no registration after `build`,
  no removal, no wildcard but `on_any`.
- **Priority** is an `i16`, 0 when nothing says otherwise. Higher runs first;
  equal priorities run in the order registered, as in Symfony. The
  `listener` id names it in a fault and a log line; a program's wiring test
  checks its ids are unique.
- **The log listener runs first**, at `LOG` (`i16::MAX`), which only
  `Builder::log` takes: `on` and `on_any` refuse it with a panic at wiring,
  so a stop never hides an event from the log. The log's function returns
  nothing, so it cannot stop one either. Every program that raises registers it: one
  line per event in its log.
- **Stop.** `Heard::Stop` ends the list for that raise. It never undoes the
  fact and never reaches the raiser. Only tehas's own in-process listeners
  may stop; a plugin bridge never answers `Stop`, so one plugin cannot hide
  an event from another.
- **Failures stay with the listener (R6).** A `Failed`, or a panic caught
  with `catch_unwind`, is a `Fault`, and the next listener is called. The
  dispatcher never retries and never times a listener out. `raise` returns
  the faults; the raiser logs each as one WARN line naming the event, its
  key and the listener. A raise never fails the raiser. Time limits,
  retries and budgets of a listener's outside work are its adapter's.
- **The payload is read only.** A listener gets `&P` or `&Envelope`. Nothing
  passes between listeners; a listener that needs another's result is one
  listener.
- **No raise inside a raise.** A listener has no handle on the dispatcher.
- `Name` and `Event` join the ports' enums that may grow, and `Word` gains
  `EventName`: an older vendored copy reads a new name as `Unknown`, reports
  it once through the `Notices` sink as the ports spec says, and calls no
  typed listener for it. `End`, `Stop` and `When` are exhaustive. Payload
  structs do not deny unknown fields: a minor release may add an optional
  one.
- **Times.** `events::rfc3339`, a serde helper with no clock, writes and
  reads `At` as an RFC 3339 string in whole seconds and UTC. Every `At` of a
  payload and the envelope uses it.

### Why it cannot drift

- `samples()` in `events` returns, for every name, one `after` envelope
  with every optional field set and one with none. It matches on `Name`
  with no wildcard, so a new name without samples does not compile.
  `gate_samples()` returns the same pair for each gate whose JSON ships,
  as an `Ask` (see "Gates").
- `console/tests/events_contract.rs` (the root package, which has
  `serde_json` and `common::schema_errors`):
  - writes each sample with `serde_json` and compares it byte for byte with
    its file in `api/`, so the samples are made by the code;
  - validates each against its schema;
  - reads each file back as an `Envelope` and writes it again unchanged, so a
    field the Rust drops fails;
  - checks that each schema's `properties` are exactly the keys of the full
    and bare samples, and that the bare sample's keys are exactly the
    schema's `required`, with the `required` of the one `oneOf` branch it
    takes (a limit change's `observed`);
  - checks that the envelope schema refuses a `data` of another name, a
    time with a fraction or an offset, a key of another shape, and a `when`
    `before` for a name with no gate, and that the page schema refuses any
    `before`;
  - takes `$ref`, `allOf`, `if`/`then` and `oneOf` apart itself and hands
    the rest of each schema to `test/schema.jq`, which knows none of them;
  - checks that `api/events.txt` is `Name::ALL`, one name per line, that each
    name has its files, and that the Events section of `host/docs/api.md`
    lists the same names.
- `test/kit_events_test.mjs` checks that `host/fun/kit/events.js` names
  exactly the lines of `api/events.txt`.
- A new check in `architecture.toml`, `event-names` (R1): a string literal
  that equals an event name, the pattern
  `"(cycle\.(started|parked|ended)|question\.asked|change\.(offered|merged)|ticket\.(acted|closed)|factory\.limit-changed)"`
  quotes included, in `console/**/*.rs`, allowed in
  `console/ports/src/events/**` alone, max 0. It matches nothing today. A
  new name joins the pattern in the pull request that adds it. Elsewhere
  code names `Name::CycleEnded`, never the string.

## Gates

A gate asks before tehas acts, and waits. The first, built in 2.1, is the
`before` side of `cycle.started`: raised by `tehas-cycle` after the start is
decided and before the cycle's container starts. Its payload, `StartAsk`:
`blueprint`, `ticket?`, `how`, `by?`, `approval` (the approval's time). Key
`<blueprint>@<approval>`. Its first listener is the plugin hook that gives a
cycle files (`2026-11-22-plugin-surfaces-2.1.md`, part 7).

| | Notify | Gate |
| --- | --- | --- |
| When | after the fact | before the act |
| Raised with | `raise`, returns `Raised` | `ask`, returns `Gated`: `Allow`, or `Refuse(why)` |
| A listener's answer | `Go`, `Stop` or `Failed` | `Allow` or `Refuse(why)`; the first refusal ends the round |
| A listener's failure or panic | a fault, the next runs | its policy |
| Witness | the first list | a refusal is a hold, listed in `held` of `status --json` with why `gate` and the listener's reason |

- **Time limit.** A plugin's manifest names it on the hook, 30 to 300
  seconds for a `before` hook (60 to 1,800 for an `after` hook, as today).
  The plugin bridge holds it (R6); the dispatcher never waits on a clock.
  Each listener of a gate has its own limit, and they run one after
  another, so a gate can wait as long as their sum. `tehas plugin review`
  shows each listener's limit and the sum for the gate.
- **Policy.** A person picks what no answer means, when the gate times out
  or the run fails: `hold` (a refusal, with why "no answer in N seconds") or
  `pass` (an allow, logged once). It is written on the grant:
  `hook:before:cycle.started=pass`. A `before` grant with no policy is
  refused with 78 (AGENTS.md rule 2): there is no default.
- **The answer** is `/out/_tehas/answer.json`,
  `{"api": 1, "answer": "allow" | "refuse", "why": "..."}`, the reason at
  most 140 characters, cleaned as a status description is.

In 2.0.0 the gate's JSON contract ships: `when` in the envelope, the schema
of `StartAsk` and of the answer. In `tehas-ports` they are `StartAsk`
(its key and its `at`, the approval, made through `GatePayload`),
`Ask<P>`, the envelope of a gate, which reads only with `when` `before`, its
own name and `api` 1, and `GateAnswer`, with `Verdict` `allow` or `refuse` and
`Why`, 1 to 140 characters with no control character (Rust's
`char::is_control`, U+0000 to U+001F and U+007F to U+009F, the set the
schema's pattern names), which a refusal must have. `GateAnswer` reads only
with `api` 1. `ask`, `Gated`, `Builder::gate` and the
raise point are added in 2.1 with their first user (R9).

## Schemas

New, written from `samples()` and `gate_samples()` by T11.7:

- `api/event.schema.json`, the envelope, tighter than "anything with these
  keys":
  - `api` const 1; `source` optional, pattern `^[a-z0-9-]{1,64}$`;
  - `event` an `enum` of the names in `api/events.txt`;
  - `when` an `enum` of `after` and `before`;
  - `key` a string, pattern `^[^\s]{1,200}$`, and per name the key's own
    shape: a cycle id for the `cycle.*` names and `change.offered`, a whole
    number for `question.asked` and `change.merged`, `<ticket>@<act>@<at>`
    and `<ticket>@<at>` for the ticket names, a time for
    `factory.limit-changed`;
  - `at` a whole-seconds UTC time, pattern
    `^[0-9]{4}-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])T([01][0-9]|2[0-3]):[0-5][0-9]:[0-5][0-9]Z$`,
    the same pattern on every time of every payload;
  - `data` checked by `event`: one `if`/`then` per name, `if` the `event`
    const and `when` `after`, `then` `data` `$ref` the name's schema, and
    one per gate for `when` `before`. A name with no `before` side refuses
    `when` `before`. The key's shape per name is in the same rules. A
    2020-12 validator reads them; `test/schema.jq` does not, so

    cannot drift").

## The factory API

Within API version 1 fields are only added (`host/docs/api.md`,
Principles); the renames of "Changed in 2.0" are the 2.0 contract's. T11
adds three feature words to `api/features.txt` and to `FEATURES` in
`console/src/api.rs`, the words a release ships. They are not entries of
`console/core/src/features.rs`, the registry of optional features that a
switch turns on:

- `cycle-ids`: `tehas api` prints `store`; `status` prints `cycle`, `how`
  and `by` on `running`; `history` prints `cycle`, `end`, `change`,
  `signalled` and `recorded`, requires `started` on a work line, pages by
  write order, and has a line for every start;
- `questions`: `tehas question --json` with no issue lists every waiting
  question, and with `--after <id>` every question whose number is greater
  than `<id>`, answered and withdrawn ones included, in number order
  (`--after 0` lists them all; no question is trimmed). Each has `id`,
  `issue`, `kind`, `cycle` (a park's), `askedAt`, `answeredAt` (an answered
  one's), `withdrawnAt` (a withdrawn one's) and `choices`, from the
  `questions` table. With an issue it prints what it prints today, with
  `askedAt`;
- `events`: the factory raises the events of this spec, and
  `tehas limit --json` prints `set`.

A consumer checks the word in `tehas api --json` before it reads the field.
On an older factory it keys a cycle by issue and start time and reads
`outcome` as it does now.

**A question's id is the store's own number.** Today it is not: the
`questions` table's `id` is the supplier's comment id
(`park.rs`, `plan.rs` insert the comment's id as `id`), and
`tehas question` and `tehas answer` print it. The build adds the store's
number: the state-store step, T11.2, rebuilds `questions` with `id` given in
order and never reused, and the comment's id in a column of its own.
`tehas question --json` prints it as `comment` on `question.comment` and
`questions[].comment`: optional, left out when the store has none, never
null. No event carries it (see above). Existing rows are numbered
in `posted_at` order. The answers that point at a question move with it.
`id` in `tehas question --json` and `tehas answer --json` is then the
store's number, a 2.0 change of meaning.

The cycle entries of `running.json` gain `attempt`, `how` and `by`, so
`status` can print them. The store's publish (`console/store/src/live.rs`)
writes `running.json`; the health file is built from it by `tehas-ops`
health (`console/ops/src/health.rs`), and `status` reads the health
file.

`host/docs/api.md` gains the fields in the tables of `tehas api`,
`tehas status`, `tehas history`, `tehas question`, `tehas answer` and
`tehas limit`, the paging rule and the retention of "What a witness keeps",
`tehas state` saying that pack, unpack and load carry `store`, and a section
"Events" with the words, the list, the envelope, the order and the witness
of each. T9 copies the list into the 2.0 contract.

## Plugins

- **The grant** is `hook:<when>:<event>`: `hook:after:<event>` for a notify
  event, `hook:before:<event>=<policy>` for a gate. Written for the plugin's
  commit, listed by `tehas plugin review`, and checked again on every
  install, enable and pin move, as grants are today. `Cap::HookAfterWork`
  becomes `Cap::Hook { when, name }` (`console/core/src/plugin/manifest.rs`,
  `review.rs`).
- **The manifest's hook** `at` is `<when>:<event>`, as 1.x's `after:work`
  is: `after:change.offered`.
- **In 2.0 one grant is taken**, `hook:after:change.offered`, which does what
  `hook:after:work` does today. `hook:after:work` is refused with no alias,
  saying the word is now `hook:after:change.offered`. Every other `hook:`
  word is refused as "not in this release" until 2.1.
- **The bridge** is an `on_any` listener in the plugin code, id
  `plugin-hooks`, priority 0. It keeps the events a plugin is granted, checks
  that the change is open at its head as 1.x does, writes the request and
  starts the unit. It replaces the call to `hook::ask` in
  `console/cycle/src/supervise.rs`. It is registered only while the feature
  `plugins` is on, which in 2.0 it is not.
- **The context** (`api/plugin-context.schema.json`, kind `hook`) keeps
  `trigger`, `commit`, `head` and `pr`, and gains `event`, the envelope.
  `tehas plugin hook` by hand is a person's run, not an event: its context
  has no `event`.
- **2.1** opens the other names, the gate, and `postMessage` to plugin
  frames: `{"type": "tehas:event", "event": <envelope>}`, sent only to the
  frame of a plugin granted `hook:after:<event>`.

## The front end

- **The kit owns the names.** `host/fun/kit/events.js`, beside `stream.js`
  and listed in the kit's `MANIFEST`, exports `events`, a page-level
  `EventTarget`, the list of names, and `raise(envelope)`, which dispatches
  a `CustomEvent` named `tehas:<event>` (`tehas:cycle.ended`) whose `detail`
  is the envelope, with `source` when the envelope has one. It does not
  bubble. An island's own events stay `<element>:<verb>` (`kit/island.js`);
  an element's name has a hyphen and no element is named `tehas`, so the two
  never meet. It ships in 2.0 with
  its test. tehas's own pages raise nothing on it until 2.1.
- **A consumer may raise on it in 2.0.** A consumer's page that learns a
  factory fact from its own stream may call `raise(envelope)` with an
  envelope that `api/event-page.schema.json` accepts, `source` set when its
  page shows many factories. `raise` checks the envelope's fields and the
  name, and refuses any `when` but `after`; it does not check each name's
  `data` or the shape of its key, which the schema does. What the consumer's stream carries to build the
  envelope is the consumer's own contract with its pages.
- **`tehas:` is only for the names in `api/events.txt`.** A consumer's own
  page events, which are not factory facts (a chat's line added, a draft
  changed), use the consumer's own namespace or `<element>:<verb>`
  (`acme-chat:line-added`), never `tehas:`.
- **Gates never reach a page.**
- **SSE, in 2.1.** Each message is `event: <name>`, `id: <name> <key>` (a
  key is unique only within its name), `data: <envelope>`, read by
  `stream()` of `kit/stream.js`. The stream keeps no replay: a page that
  reconnects reads the witnesses again. A consumer that merges the streams
  of many factories prefixes each id with the envelope's source,
  `id: <source> <name> <key>`, and sets `source` in the envelope.
- The other repositories of the trio use these names and this `detail`.

## The consumer that runs many factories

It **vendors**, with `tehas-ports` at the tag: `Name`, `Event`, the
payloads, `Envelope`, `Source`, `Key`, `CycleId`, `End`, `Stop`, `How`, the
`rfc3339` helper and the dispatcher, which it may use for its own
listeners.

It **copies**: the words table, the names and the grant words, the rule
`tehas:<event>` for its pages, the schemas and samples of `api/` into its
own contract tests, and the witness rules, keys, order and versions of this
spec.

It **raises** its first list from its polls:

| Event | From | Fields |
| --- | --- | --- |
| `cycle.started` | a `cycle` in `status` `running` it has not seen, or a work line in `history` whose `cycle` it has not seen | `cycle`, `issue` as `blueprint`, `since` or the line's `started` as `started` and `at`, `how`, `by`, from `running` or the line alike |
| `cycle.parked` | a new work line with `parked: true` | the line's `cap`, `parkReason`, `failureKind`, `failureCause`, `progress.step` as `step`, `provider`, `repeat`, `end` |

| `cycle.ended` | a new work line | `cycle`, `started`, `ended` as `at`, `recorded`, `end`, `outcome`, `status`, `parked`, `signalled`, `change` |
| `factory.limit-changed` | when it runs `tehas limit` or `tehas drain`, or a poll of `tehas limit --json` differs from the last limit it knows | the limit as printed, `set` as key and `at`; with no `set` (a clear, an unreadable or missing limit), its poll's time as `observed`, key and `at` |

A consumer that first sees a cycle in history raises `cycle.started` with
the line's `started` as `at`; every work line has one after T11. It dedupes
on (name, key) per factory and `store`, and compares `factory.limit-changed`
by the limit as "The first list" says. It reads history with the cursor it
kept and reports a gap in `seq` as "What a witness keeps" says.

**Which factory.** tehas never says which factory an envelope is from; the
consumer knows whom it polled. When it relays envelopes, to its pages, its
own listeners or another program, it sets `source` to the factory's name
and adds nothing else. The envelope it relays is still one the schema in
`api/` accepts.

## Versions

The envelope's `api` is 1. A new name, a new gate or a new optional field is
a minor change: an older copy reads `Unknown` or skips the field. Renaming
or removing a name or a field, a new required field, a new `End` or `Stop`
word, or a new meaning for a key is a major change, listed in
`host/docs/contract.md`.
