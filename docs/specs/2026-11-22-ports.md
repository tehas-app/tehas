# Spec: the ports, in tehas's terms

**Status**: proposed, 2026-11-22. Step T4 of
`docs/plans/2026-11-21-coding-standard-v2.md`. Nothing is built. Written
from three drafts read by three reviewers against R1, R2, R4, R6 and R7, and
against how little of the rest changes; the shape of the winning draft, with
what the reviewers asked to take from the other two. Revised four times the
same day after critiques: every file the architecture checks count has a
step, every write a `Write` with its settle rule, every floor a count,
every behaviour change a pull request of its own, and the session's
decisions are written in Decided.

## Purpose

tehas reaches GitHub from many places today: the dispatcher's reads in
`console/dispatch/src/read/`, the cycle's writes in
`console/cycle/src/apply.rs` and its relay, the console's commands, the
update's release reads in `console/ops/`, and the one trait in our terms,
`Forge` in `console/core/src/forge.rs`, which covers labels alone. GitHub's
paths, fields, statuses and page sizes are known in several crates (R1),
and a time limit or a rate limit is handled differently in each (R6).

This spec puts every one of those behind three ports in tehas's words, with
GitHub as their one adapter. The same ports are the shared set that a
consumer that runs many factories adopts instead of writing its own, so
its needs shape them as much as tehas's do.

## Decided

By the owner:

1. Three ports: **tickets** (the work level: epics, stories, approval,
   priority, release targets), **blueprints** (the issues a cycle works
   from: the technical design, the plan, the technical discussion) and the
   **code host** (changes, branches, checks, merges, tags, releases).
2. GitHub is the one adapter written in 2.0.0, and it answers all three.
3. Allowed setups: a code host (GitHub, GitLab or Bitbucket) always, with
   tickets from that code host or from Jira. Never Jira alone, so
   blueprints always come from the code host.
4. Approval is an act. Authorisation stays the account behind a change,
   checked against an allowed list, with its history (AGENTS.md rule 5).
5. Paging, retries, time limits and the points budget live in the adapter,
   which answers with a few named outcomes. No method takes a method, a
   path, a URL to call or untyped JSON (R2). The one link a port takes is a
   commit status's link for a person to open, a `WebLink` checked when made
   and never followed (see "Shared types"). General enough for two
   suppliers, GitHub and GitLab (Jira for tickets), no further.
6. The port definitions (traits, our types, outcomes, fakes, laws and the
   recorded samples) go in a crate of their own, `tehas-ports`, with no
   supplier in its code and no dependency beyond std and serde, so the
   consumer vendors its files at the tag (see Decided 26).
7. The security shims that decide whether a `gh` call writes stay separate
   unless the owner agrees otherwise (see Open).

By the session running the work, whose recommendations the owner made
decisions:

8. **T2's vocabulary.** The state words (the enum `State`, the acts, the
   choices and `MarkerKind`, the kinds of tehas's markers) live in
   `tehas-ports`, with no supplier word. The GitHub adapter owns the table
   from each word to its label string and marker text, checked by a test
   of the adapter against `host/labels.tsv`. Every label and marker string
   of the adapter is in that table, `console/github/src/table.rs`; the
   adapter's other code names a word, never its string. The `label-words`
   check then allows two places alone: `table.rs` and the adapter's tests
   under `console/github/tests/`. This departs from the plan's "a module
   in core" for T2: T2 may land in core first, and its module moves to
   `tehas-ports` (the words) and the adapter (the strings) at T4.1.
9. **The ports' version.** `tehas-ports` has no version of its own. It is
   vendored at tehas's tag, and `VERSION` names that tag. A change to the
   ports is expand, then contract (R9), with the surface listed in `api/`
   at T9, so a consumer sees a change before it vendors.
10. **Releases and tags stay in the code host port**, as the owner's split
    says: reading them, and making a release, uploading its files and
    publishing it.
11. **The relay keeps its `gh` words.** `console/cycle/src/relay.rs` parses
    the container's `gh` argument lists inside itself, as a write guard, and
    that parse is a written floor of `gh-argv`. So are the two shims, the
    console's (`host/shim/gh`, `console/src/gh_shim.rs`) and the sandbox's
    (`host/sandbox/gh-shim`).
12. **Identity and Board are part of the three ports, not new ports.**
    Identity answers for every realm: who acts, an account's standing,
    tokens, a person's sign-in. Board is a read joined across tickets,
    blueprints and the code host. Each has a trait of its own so the
    adapter owns its cost. This departs from the plan's T4, which names only
    the three; the owner can overrule it. The plan's T4 also put blockers in
    the blueprints port and tokens in the code host port: this spec puts
    blockers in Tickets, since they are work-level links that Jira holds,
    and tokens in Identity, since every realm mints its own. Both are
    departures the owner can overrule.
13. **A split setup composes two sites.** A `Site` serves one realm's
    supplier. A code host plus Jira is two sites, the code host's and the
    tickets', put together by `Split`, whose `Join` owns its handles and
    borrows none.
14. **Health.** The `Ledger` and `HealthState` replace
    `state/github-failures` (`console/core/src/github_fails.rs`). The
    factory API's `github` health check in `live/health.json` keeps its name
    and its shape in 2.0, fed from the Ledger. T9 lists any change to it.
15. **The Ledger is keyed by the budget's holder** on the supplier's host
    (Decided 36): the factory's account as the site budgets it (an
    installation, on GitHub), each person, each anonymous address. One
    holder running out stops that holder alone, on every project it
    serves.

By this spec:

16. Each port is a read trait and a write trait. The poll's read phase is
    given read handles alone, so by its type it cannot write.
17. A work cycle takes exactly one blueprint, never a ticket directly. A
    ticket with no blueprint gets one before work starts.
18. The link from a ticket to its blueprints is kept in tehas's state store,
    written only by tehas or from an act of an allowed account. Never a
    marker in a body. The link from a blueprint to its change is the code
    host's, read beside the cycle's own record.
19. Every account carries its realm (code host or tickets) and the
    supplier's stable id. Each realm has its own allowed list, by account
    id; nothing is inferred across them.
20. The journal records a typed `Write`, one row per request, not a `gh`
    argument list. A 1.x row still in flight is settled as unknown by a
    read.
21. The joined reads (the queue read, the change reads and their kin) are
    `Board`, so the adapter owns their cost. A split setup gets a pure
    default join.
22. One report per outage, across short processes: a pure health state
    machine over a typed ledger the caller gives the adapter.
23. One `Site` per project. A program that reads another project (tehas's
    own release project, a plugin's or a skill's repository) builds a site
    for it, with its own actor.
24. **T4 ends with written floors, not 0.** The plan's T4 is done when
    `github-rest` is 0. This spec ends it at 0 outside `console/github/`
    but for written floors, each with its file and count in Done: the write
    guards that stay (Decided 11), the site's CI in the release gate, the
    sandbox's files (rule 4), the factory API's field names and the front
    pages until T9, and tehas's own `--json` flag, which the pattern
    catches. The same holds for `label-words`, whose floors are the front
    pages and the write guards' own tests. This departs from the plan; the
    owner can overrule it by asking T4 to narrow the patterns instead.
25. **Planning always opens blueprints.** The planner's new items are made
    through the relay as `BlueprintWrites::open`, on every setup. Where
    ticket and blueprint are one item, each new blueprint is a ticket too,
    and the dispatcher's plan step makes it a part of the planned ticket
    (`TicketWrites::add_part`, today's `sub-issue-add`). On a split setup
    the plan step writes the `opened` link instead. In both, the plan step
    writes from the relay's record of what it opened; the relay writes no
    link and no part.

By the session, after the second critique:

33. **The adapter setting waits for the owner.** The plan's "The adapters"

By the session, after the third critique:

34. **`GitHub::new` keeps its callers through T4.2.** T4.2 lands the

    `GitHub::new` outside a `main.rs`, each allowed by name with its why.
    `console/ops/src/holds.rs` twice (`tehas resume` reads the control

35. **`tests-stub-gh` ends at a floor of 99.** `test/gh_fail_test.sh` tests
    `t_gh_fail` of the shell test library, not a behaviour of Rust code, and
    two floor tests still use that helper (`install_fresh_test.sh`,
    `shim_writes_retry_test.sh`). It stays, a written floor of 21. Decided
    31 says 99.
36. **Health and the budget are keyed by the budget's holder and the
    supplier's host, not by `SiteId`.** A `HostId` names one supplier's
    host as the adapter names it. One outage of a host gives one notice for
    every project on it, and a spent installation holds every project it
    serves. `SiteId` stays the key of tokens alone (see "One report").
37. **Markers travel apart from bodies.** A note's body never includes its
    markers. Markers are their own field on `Step`, `NewTicket`, `Ticket`,
    `Blueprint`, `NewBlueprint` and comments. An edit keeps the markers it
    is not told to change (`MarkerEdit`). `find_marked` reads every place a
    marker can be. The sum of a `TicketNote`, and of every body a settle
    rule compares, is over the body without markers.
38. **A narrow scope for an agent.** `Scope::Agent` writes tickets and
    changes and reads contents, and writes no contents: the token a
    consumer mints for its agent, never `Full`.
39. **Port enums that may grow are `#[non_exhaustive]`.** They are named in
    "Enums that may grow". A reader that meets a variant it does not know
    reads it as that enum's `Unknown` and reports it once. This is how R9
    holds across the vendored copy: a minor release adds a variant beside
    the old ones, and an older copy still reads.
40. **The trio's read is a gate.** T4.1, the first pull request that adds
    `tehas-ports`, merges only after the consumer's session has read this
    spec and answered in writing, and the plan's Log names that answer.
41. **Behaviour changes get pull requests of their own**, each before the
    move that needs it, never inside a refactor step: the claim split into
    `Mark` then `Assign`, the relay's conditional edit, the shim not
    retrying the adapter's rate-limited writes, the health check's `last`
    line, and the `refresh-begin` and `refresh-end` words. See "Behaviour
    changes, each a pull request of its own".
42. **Recorded samples are answers per operation.** A sample is keyed by
    the port operation and its input in our terms, not by the request.
    The laws check an adapter's answers against them, so two adapters that
    ask a site different questions are tied by what they answer. The
    consumer may add samples through a pull request to tehas. `Person`,
    `Anonymous` and `Deploy` get samples from the consumer's side, or are
    left as marked gaps until tehas has a transport for them.

## The ports at a glance

| Port | Read trait | Write trait | Holds |
| --- | --- | --- | --- |
| Tickets | `Tickets` | `TicketWrites` | acts, states, kinds, priority, blockers, parts, targets, assignees, the history of who changed what |
| Blueprints | `Blueprints` | `BlueprintWrites` | text, comments with their editors, edit histories, attachments |
| Code host | `CodeHost` | `CodeHostWrites` | changes, branches, files, checks, merges, tags, releases, the git remote |
| Identity, of every realm | `Identity` | none | who a handle acts as, an account by id or by login, an account's standing, whether it can be assigned, tokens, a person's sign-in |
| Board, across the three | `Board` | none | the joined reads: open work with the control ticket, one item whole, closed work, a target's work, open changes with what they close |

Identity and Board are parts of the three ports, not ports of their own
(Decided 12). Beside them, four small traits the caller implements and
gives the adapter: `Links` (tehas's store answers it), `Ledger` (the budget
and the health state, shared across processes), `Keyring` (person and
deploy credentials, held by the caller) and `TokenStore` (where minted
tokens are kept, so the adapter knows no file). `Site` is the adapter's
front for one realm: it makes the handles. `Split` puts two sites together.

## The crate

`console/ports/`, package `tehas-ports`, library only.

```toml
[package]
name = "tehas-ports"
edition = "2021"
publish = false

[dependencies]
serde = { version = "1", default-features = false, features = ["std", "derive"] }
```

Rules, each held by the architecture test:

- **std and serde alone.** No `serde_json`, so no `Value` can reach a port
  (R4). No workspace crate, no async runtime, no build script, no feature
  flags: a vendored copy has no features to get wrong.
- **No supplier in its code.** No supplier name, host, path, field, query,
  label string or status code, in code or in doc lines. The owned-names
  check lists the supplier words, `repos/`, `api.`, `graphql` and the label
  words as banned in `console/ports/src/**` and `console/ports/Cargo.toml`
  with a floor of 0 (R1). What each supplier does is written in the
  adapter's docs and in this spec, never in the code. The recorded samples
  in `console/ports/samples/<site>/` are data, read by no code of the
  crate. They hold the port's answers in our types, not the site's
  requests or bodies, so only their directory names a site (see "The
  fakes and the laws").
- **No effects.** No file, network, process, environment or clock. The
  fake keeps a clock of its own (R3).
- `#![forbid(unsafe_code)]`, `cargo fmt`, clippy clean.

Every data type (ids, records, marks, markers, outcomes, `Write`,
`Receipt`, ledger and health values) derives `Serialize` and
`Deserialize`, so a port value crosses the store, the journal and the
factory API in one shape. Not the traits, the handles, `Join`, `Split`,
`Caller` (a `&'static str`), `Secret` or `Token`; `MeterRow`, which holds a
`Caller`, is `Serialize` only.

### Enums that may grow

A port enum that a minor release may add to is `#[non_exhaustive]` and has
an `Unknown` variant (Decided 39). These are: `Mark`, `Act`, `State`, `Choice`,
`Kind`, `MarkerKind`, `Scope`, `Happened`, `ChangeHappened`, `Write`,
`WriteKind`, `Receipt`, `Refusal`, `Unread`, `Pool`, `NotMergeable`,
`Conclusion`, `Verdict`, `Health`, `PortName` and `Word`. The code below
writes `Unknown` out for `Scope`, `Write`, `Receipt`, `WriteKind`,
`PortName` and `Word`; the others have it the same way. Each is
serialised with a tag, so `#[serde(other)]` reads a tag it does not know as
`Unknown`.

- **Reading one.** A reader (an adapter, the journal's settle, a consumer
  reading the factory API or the journal with an older copy) that meets a
  variant it does not know reads it as `Unknown` and reports it once per
  process, as `Health::Unknown(Word)` through the `Notices` sink, where
  `Word` names the enum.
- **What `Unknown` means.** It fails closed, as `Unread` does. An unknown
  act is no act: it authorises nothing. An unknown state or marker holds
  the ticket. An unknown `Write` row stays unknown, is never sent and is
  left for a reader that knows it. An unknown `Refusal` or `Unread` is
  handled as the `Refused` or `Unread` it sits in.
- **Writing one.** `Unknown` is never written: a write that names it is
  `Refused(Invalid)` before any request.
- **Exhaustive on purpose.** `Outcome` (a new outcome is a major change),
  `Sent`, `Realm`, `Lost`, `Passing`, `TicketState`, `CloseReason`,
  `Mergeable`, `Overall` and `Actor`. A new variant of these is a major
  change of the ports.

So R9 holds across the vendored copy: a minor release adds a variant
beside the old ones, the consumer's older copy reads it as `Unknown`, and
the contract step that drops the old one waits for a major.

### Handles, threads and `&mut`

- `Site` is `Send + Sync` and takes `&self`. One site serves one realm of
  one project: a program that reads several projects (tehas's release
  project, a plugin's or a skill's repository, each factory's project for
  the consumer) makes one site for each. What must be shared across them
  (the budget, the health state) is in the `Ledger`, not in the site.
- A handle is made per pass (a poll, a cycle's report, a relay request, a
  console command) and takes `&mut self`, as `Forge` does today. It keeps
  what it read in that pass, its read retries and its reports, and forgets
  a read on its own write to the same thing, as the poll's `Calls` does
  now. Today's `Forge`, `Calls` and `RetryPolicy` move in without locks.
  A handle is `Send`, not `Sync`.
- The traits are synchronous: std alone cannot name a runtime, and tehas
  runs `gh` as a process. A caller on an async runtime calls a handle from
  its blocking pool.
- Making a handle can fail (`Got<Box<dyn ..>>`): a person whose credential
  the keyring no longer has is `SignedOut`, a write handle asked as
  `Anonymous` is `Forbidden`, a port the site does not serve is
  `Refused(Unsupported)`, before any request.
- A handle owns what it uses (it holds a shared part of its site, not a
  borrow), so a `Box<dyn Tickets + Send>` has no lifetime and `Join` can
  hold handles from two sites.

Who depends on whom (R8): every library crate depends on `tehas-ports` and
on no adapter. The adapter, a new crate `console/github/` (`tehas-github`),
depends on `tehas-ports`, `tehas-core`, `serde` and `serde_json`. From core
it takes the clock and, until T4.11, `Bounded` and `GhRunner`, which stay in
core while other crates still call them (Decided 27) and then move into the
adapter. Only a program's wiring (its `main.rs`) names `tehas-github`, to
build a `Site` from the settings, beside the five callers of `GitHub::new`
that stay allowed by name from T4.2 until they move (Decided 34). A test of any other crate uses
`tehas_ports::fake`, never the adapter.

The check that holds it is new in `architecture.toml` at T4.2:
`adapter-wiring` (R8), pattern `\btehas_github\b`, files
`console/**/*.rs`, allowed `console/github/**` and each program's
`src/main.rs`. It counts a `use` in a library module, a test or a module of
a program other than its `main.rs`, so a library crate cannot reach the
adapter even where its package also builds the program. A program whose
wiring needs more than `main.rs` names that one module in `allowed`, with a
`why`. It lands at a max of 5, today's callers of `GitHub::new` outside a
`main.rs` (Decided 34), each named with its why, and each move that takes
one off lowers the max: 0 at T4.11 at the latest.

**tehas's adapter and the consumer's.** `tehas-github` runs `gh` through the
console's shim for the factory's account and the operator. The plugin
gate's sign-in client (`Curl` in `core/src/access.rs`, `curl` over the
site's API and web hosts today) stays in core while the gate calls it, as
`Bounded` does, and moves into the adapter at T4.11, where it answers
`sign_in_link`, `signed_in` and a signed-in person's handles. An actor it
has no transport for (`Anonymous`, `Deploy`, until a tehas caller needs
one) is `Refused(Unsupported)` when its handle is asked, before any
request. The consumer does not take `tehas-github` (Decided 26): it keeps
its own GitHub adapter over its own HTTP clients, which serves every actor,
and passes the same laws against the same recorded samples.

Which adapters a host runs is the owner's call (Decided 33, Open). The proposal:
two settings in the instance directory (rule 1), `TEHAS_CODE_HOST` and
`TEHAS_TICKETS`, validated by `lib/config.sh` and core's settings. In 2.0
only `github` is accepted for either (`TEHAS_TICKETS=github` means the code
host's own tracker), and a missing setting means `github`, so no instance
changes on update. Any other value stops with 78 before any call (rule 2):
`jira` with "not built in this release". Blueprints have no setting: they
are always the code host's. Until the owner decides, T4 builds the wiring
as if both were `github`, and adds no setting.

## Shared types

```rust
// ids.rs

/// A ticket on the tickets supplier. On a code host's own tracker its
/// number; on a separate tracker its key, kept whole and never split.
pub enum TicketKey { Number(NonZeroU64), Key(KeyText) }
/// Checked when made: letters, digits, `-`, at most 64. Never parsed.
pub struct KeyText(String);

/// A blueprint's number on the code host. Never assumed equal to a ticket's.
pub struct BlueprintNo(NonZeroU64);
/// A change's number on the code host. Never assumed in the same number
/// space as a blueprint's.
pub struct ChangeNo(NonZeroU64);

/// What a number names where tickets, blueprints and changes share one
/// number space (a code host's own tracker). A caller asks; it never guesses.
pub enum Item { Ticket(TicketKey), Change(ChangeNo) }

/// An item in another project or on another site: named, never followed.
pub enum Ref<T> {
    Here(T),
    Elsewhere { project: ProjectName, item: ItemName },
}
/// A project and an item as their site names them, for display. A caller
/// never parses either.
pub struct ProjectName(String);
pub struct ItemName(String);

/// Opaque ids the adapter makes and reads back. Stored and compared only.
```

**Markers travel apart from bodies** (Decided 37). A body, a note's text, a

## The named outcomes

Every method answers a value or one `Outcome`. A site's status, error text
and field names never leave the adapter (R6).

```rust
// outcome.rs

pub type Got<T> = Result<T, Outcome>;
pub type Did = Result<(), Outcome>;

/// A list the adapter vouches is all there is.
pub struct Whole<T>(Vec<T>);

/// Exhaustive on purpose: a new outcome is a major change of the ports.
pub enum Outcome {
    /// Not there, or not visible to this actor.
    NotFound,
    /// A conditional write lost: read again, then decide.
    Conflict(Lost),
    /// The site will not take this write until an input changes. Remember
    /// it; do not retry.
    Refused(Refusal),
    /// This actor may not do this. Never widen the actor in reply.
    Forbidden,
    /// The credential is no longer good.
    SignedOut,
    /// The budget of this holder and pool is out until then. Calls of the
    /// same holder in the pool fail at once, with no request, until `until`.
    Spent { pool: Pool, until: At },
    /// A passing failure. For a write, whether it may have reached the site.
    Unavailable { why: Passing, sent: Sent },
    /// The answer could not be read whole. Fail closed: read as changed,
    /// held or unknown, never as empty.
    Unread(Unread),
}

/// `Gone` only for the thing a conditional write named (the comment, the
/// branch), deleted between the read and the write. A write to a thing
/// that was never there, or is not visible, is `NotFound`.
pub enum Lost { Changed, Gone, HeadMoved, Elsewhere }
/// `ReadOnly`: a read-only host's handle made no request (see "The write
/// guards").
pub enum Refusal { Invalid, Cycle, NotMergeable, Exists, Unsupported, ReadOnly }
/// Reads counted one per call; reads priced by how much they ask; searches;
/// writes. Which pool a call draws on is the adapter's.
pub enum Pool { Calls, Priced, Search, Writes }
pub enum Passing { Timeout, Unreachable, Server, Broken }
/// `Maybe`: the request went out and no answer came. The journal's
/// `Wrote::Unknown`: never sent again on this answer, a read settles it.
pub enum Sent { No, Maybe }
pub enum Unread { Cut, Inconsistent, TooLarge, Malformed }

impl Outcome {
    /// One fixed line in our words for the report. Never the site's text,
    /// which may name a host or carry a token.
    pub fn line(&self) -> &'static str;
}

/// A write of several parts, applied in order, that says how far it got.
pub struct Applied<P> { pub done: Vec<P>, pub stopped: Option<(P, Outcome)> }
```

**Already done is success.** Removing a mark that is not there, adding one
that is, linking what is linked, a tag on the same commit, a label that
exists: each is `Ok(())`. No caller repeats that rule.

**A batch read answers per item**: `Vec<(K, Got<T>)>`.

**Answers with no obvious outcome**, as the GitHub adapter reads them:

| GitHub answers | Outcome |
| --- | --- |
| 410, issues turned off or the issue deleted | `NotFound` for the item; `Facts.tracker_on` says which |
| 422 "not installed on all repositories" when a token is minted | `Forbidden`: the factory's account may not reach this project. Never retried with a wider scope |
| A query answer with data and errors | per item: an item whose node came whole is answered, an item named in an error is `Unread(Inconsistent)`. A list with any error in it is `Unread`, never a partial list as whole |
| 404 on a write to a comment or branch the caller read | `Conflict(Gone)`, as the table of `Lost` says; any other 404 is `NotFound` |
| 422 on a close as a duplicate | the adapter closes as not planned and writes the "Duplicate of" line, which is how the site records a duplicate it will not link; `Ok(())`. Read back as `Duplicate(key)` from that line. This is how the site holds the reason, not a decision |
| 422 on an assignee | `Refused(Invalid)`: the account cannot be assigned on this project |

**`Sent::Maybe` is settled in the adapter first.** After a time limit on a
write, the adapter reads where it can (the comment with its marker is
there, the mark is on), as `apply/reread.rs` does today, and answers
`Unavailable { sent: Maybe }` only when that read fails too.

What each caller does with each outcome:

| Outcome | Dispatcher | Cycle |
| --- | --- | --- |
| `NotFound` | the issue is gone or closed: no start | the issue closed under it: end the cycle as now |
| `Conflict` | read again next poll | the stamp or edit is left, with one line |
| `Refused` | held, with one line, not retried until the ticket changes | the write is left, with one line |
| `Refused(ReadOnly)` | the read-only line is logged and the poll goes on as if the write was made, as today; a write that would have made something (a note, a ticket, a blueprint, a change) leaves nothing to record, so the step stops there and the start record of `read_only` stands | the same; a report that would have stamped a change stamps nothing |
| `Forbidden` | one line; nothing widens | one line |
| `SignedOut` | the poll stops with one report | the report is kept for the end fault |
| `Spent` | the poll skips reads of that holder in that pool until then and says so once | waits within its bound, or keeps the write for the end |
| `Unavailable`, `sent: No` | the poll ends; the next poll is the retry | tried as the journal says, then one line |
| `Unavailable`, `sent: Maybe` | the journal row is unknown; a read settles it next poll | the same; nothing is sent twice |
| `Unread` | fail closed: the issue counts as changed or held | the same |

Acts, states, choices and a project's marks all go through `apply`, or
through the journal part by part: an approval is `Step { mark:
vec![Mark::Act(Act::Approve)], .. }`, a close is the step's `close`. A hold
or a block of today is a step whose note carries a `Marker`, with the marks
to take off: `Step { note, markers: vec![hold], unmark, .. }`, the marker
in its own field, never in the note's text. On a site with native
blockers, `wait_on` writes the link as well, and the marker stays the record of who asked and why. On a split
setup every ticket write above lands on the tickets site: its text, its
priority, its target and due date, its parts both ways, its assignee.

**An answer's tick is a write of its own.** The consumer's press is a note,
or, for an answer, a tick saved in the place of the note. A tick is a
conditional edit of a comment, which is the blueprints port's
(`BlueprintWrites::edit_comment`, `Write::EditComment`), so it is not a
part of a `Step`. The caller sends the tick first and the step after it,
with no note. How far the press got is the tick's `Did`, then the step's
`Applied`: a tick that lost (`Conflict(Changed)`) stops the press before
any mark moves.

**What `Kind::Epic` is on GitHub** (Decided 32). The `epic` label, as tehas
reads it today (`console/src/epics.rs`, `EPIC_LABEL`). `set_kind(Epic)`
writes the label and no issue type, and `set_kind` of another kind takes
the label off. `TicketDigest.kind` answers `Epic` when the label is on,
whatever the issue type says. The issue type is read as a hint for the
other kinds; where it says epic and the label is off, the two disagree,
the label wins, and the ticket is no epic. A consumer that marks epics by
type today writes them with `set_kind(Epic)`, which puts the label on.

**The claim and its assignee.** Today the dispatcher's claim puts the
running mark on and assigns `TEHAS_ASSIGNEE` in one `gh issue edit`, and
marks again without the assignee when GitHub refuses it
(`dispatch/src/apply/start.rs`). The claim becomes two rows,
`Write::Mark` then `Write::Assign`, in a behaviour change of its own (B5)
on today's path before T4.7, so T4.7's move changes no test. The mark goes first, so the claim
never fails on the assign; an `Assign` that answers `Refused(Invalid)` is
logged with today's warning line and the claim stands. This is one request
more per claim on GitHub. `tehas setup`'s check that the owner can be
assigned (`ops/src/setup.rs`, `repos/{repo}/assignees/{owner}`) becomes
`Identity::assignable`. `TEHAS_ASSIGNEE` stays a login in the settings and
is turned into an `AccountId` with `Identity::account_by_login`, as the
allowed list is (see Identity).

**The control ticket.** The factory-wide pause is a ticket of its own,
today's `TEHAS_CONTROL_ISSUE`, read today as `Snapshot.control_labels` and
`control_events`. It is a ticket in the tickets port: its marks and its
whole history are read by `Board::open_work` (`OpenWork.control`) and by
`Tickets::ticket` with `Depth::All`. The pause is `Act::Pause` on it, and
who applied it is read from its history, as now (rule 5). On a split setup
it is a ticket of the tickets site, and the setting holds a `TicketKey`.

point of `since`. The relay only edits items its own cycle opened, so a
conflict is rare.

**What a change closes, and other references.** A caller never writes
"closes #n" or `owner/name#n`. A change says what it closes with
`NewChange.closes`, which the GitHub adapter writes as one closing line per
blueprint after the body. An `edit_change` of the body reads the change's
`closes` first and writes the same lines again, so a stamp cannot drop
them. Any other reference in a body (a ticket, a blueprint, a change in
this project or another, an account) is the text `Cites::cite` gives, from
the handle the body is written through, so a split setup's ticket notes
name things as the tickets site does. The cycle's finish and the
consumer's bump fill `closes`; `Proposal.change` carries it.

credential, never a working tree. Releases and tags are the code host's

continuous integration, not a port, and stay a written floor as

the site. In tehas, `account_by_login` is how `TEHAS_ALLOWED_LABELERS`,

**Tokens, a security change (rule 4).** Minting moves from
`ops/src/github.rs` into the adapter, behind `Identity::token`. Keeping
tokens does not: the caller's `TokenStore` keeps them. This changes what
makes the files a container is given, so T4.10's pull request says it is a
security change.

- **Who writes the files a container gets.** The same programs as today,
  and no other: `tehasbot github-token` (asked by the console's shim, the
  poll and `tehas-cycle renew`), with `--cycle` for a cycle's token and
  `--session` for a planning turn's or a dev session's, and the renewer
  thread of the turn's or session's own process (`renew_session`). Each
  now calls `Identity::token` through tehas's `TokenStore`; no new program
  writes a token file, and the dispatcher, the cycle's container and any
  plugin write none.
- **Which file holds which scope.** tehas's `TokenStore` over `Home`
  writes the product's code host site alone to files, with today's modes
  and its lock: `Scope::Full` in `state/github/token` (with
  `token.expires`), `Scope::Cycle` in `state/github-cycle`,
  `Scope::Session` in `state/github-session`, `Kept::Grant` in

  in `state/github/lock` (30 seconds). `Scope::Read`, `Scope::Files` and
  `Scope::Agent` have no file today and get none: they are kept in the process's memory
  and are never written or mounted. A token of any other site (the release
  project, a plugin's or a skill's repository) is kept in memory too.
- **What a container is given does not change.** The token directory
  (`console/core/src/sandbox.rs`, mounted read only at
  `/run/tehas/github`) holds the `Scope::Cycle` token alone for a cycle and
  the `Scope::Session` token for a planning turn or a dev session, narrowed
  further on a read-only host as `narrowed` does now. The pins stay as
  they are and pass unchanged: the argument lists in `test/fixtures/argv/`,
  checked by `test/sandbox_argv_test.sh` and by the tests of
  `console/core/src/sandbox.rs` and `console/ops/src/mcp.rs`, and
  tehas-cycle's tests of what a container is given

  (`test/work_test.sh`, which AGENTS.md rule 4 still names, is gone; see

- **A refused token.** When the site refuses a kept token, the adapter
  calls `TokenStore::forget(site, None)`, which removes the token files
  and the two facts, as today's 401 does, so no other process reads the
  bad token until it expires. The next ask mints afresh. A file it cannot
  remove makes `forget` answer false, and the adapter raises one
  `Health::TokenNotDropped` notice for the handle; the call still answers
  `SignedOut`.
- **Tests.** A new test of tehas's `TokenStore` pins each scope and fact to
  its file and mode, pins that `Read`, `Files` and `Agent` write no file,
  and that
  two sites never share a file.

## The journal's write

`console/core/src/journal.rs` records what a write will do before it does
it (R3), for the dispatcher (`dispatch/src/apply.rs`) and the cycle
(`cycle/src/apply.rs`, `apply/reread.rs`) alike, and the store reads it
(`store/src/journal.rs`, `store/src/verbs.rs`). Today it records `gh`
arguments. Under the ports it records a `Write`: one variant for every
write method of every port, and no write method without one
(`TicketWrites::apply` is not a write of its own: it is its parts, see
below). Each variant
is one request to the site, so one row is one request, as a row is today,
but for the two noted below.

**No bytes in a row.** `Propose` and `Upload` name their files by sum
(`Sum`, a sha-256 and a length), and `send` takes the bytes from the
caller's `Blobs`. Every body is a `Body`, summed in the row. The journal
keeps no file and no body.

**When the bytes are gone.** A `Propose` or `Upload` row left unknown is
settled by sending it again, which needs its files. If the next pass's
`Blobs` does not hold a file the row names, `send` answers
`Refused(Invalid)` before any request, and the row stays unknown: it is
not closed and not sent. It is reported once, by its kind, in the pass's
reports. The next pass whose `Blobs` holds the files sends it again. A
caller that will never hold them again (a bump given up, a release
dropped) decides afresh from a read, as for any row found not sent, and
closes the row as not sent with that decision.

**The two variants of several requests.** `Prepare` (every mark of the
factory) and `Propose` (a branch, a commit, a change) are each several
requests. Both are idempotent by their inputs, so a row of either left
unknown is settled by sending the same write again, which a read would
otherwise have to piece together. `send` answers `Propose` with the
outcome of the part that stopped; how far it got (`Applied`) is given to
a caller of `CodeHostWrites::propose` directly, and the journal needs no
more, since sending again finishes the rest.

**A read-only host.** `Journal::send` asks `read_only()` first. On a
read-only host it writes the `read_only::line` of the write, records no
row and answers `Refused(ReadOnly)` without a request, as `refuse` skips a
write today. What the dispatcher and the cycle do with it is in the table
of outcomes.

read that fails leaves the row unknown for the next pass; a rule never
reads an absence from an `Unread`. Where a rule finds the write did not
land, the row is closed as not sent and the caller decides afresh from the
same read; nothing is replayed from the row.

A press's `Step` is not one row. The journal sends it part by part, in the
step's order, one row each: the note (`comment-post`), each mark taken off
(`label-remove`), each put on (`label-add`), the close (`issue-close`), as
the dispatcher writes them today. A part that answers `Unavailable { sent:
Maybe }` leaves its row unknown, and the parts after it are not sent in
this pass: the step stops there, as `Applied` says. The next pass reads the
ticket, settles the unknown row from that read by the kind's rule (the
note with its sum is there or not, the mark is on or not), and decides
again from the same read. What is left of the step is then decided afresh, never replayed from
the old step, so nothing is sent twice.

`Wrote::Unknown` is answered by `Unavailable { sent: Maybe }`, and is
settled by its kind's rule in the table above.

**Side by side (R9).** The journal's new path does not replace the old one
in one step:

- T4.4 adds `Journal::send(store, write: &Write, writes: &mut dyn Writes,
  files: &dyn Blobs)` beside today's `Journal::write(store, issue, kind,
  args, input, done_if)`. Both record into the same table; the store's
  `journal-record` takes `--write <json>` beside `--args <json>`, and
  `KINDS` gains the new words.
- The cycle (T4.5) and the dispatcher (T4.7) move their writes from
  `write` to `send`, call site by call site, each crate's tests first. Until
  the last one moves, the two paths run side by side: the dispatcher's
  settle (`apply/settle.rs`) and the cycle's (`apply/reread.rs`) read
  either kind of row, an argv row by its 1.x word and a `Write` row by its
  variant, and each settle has a test for both.
- `Journal::write` and its argv are removed in T4.7's last pull request,
  when nothing calls it. With it go `journal.rs`'s own reading of gh's
  error text: the rule that takes a time-out, a reset connection or a
  5xx as maybe sent (its 5 raw statuses), and the 3 test strings that name
  the site's API host. That rule moves into the adapter's runner beside
  `call::gh_why`, its tests into the adapter's sample tests, reading the
  site's answer and not gh's words. The store keeps reading argv rows
  until the next major.

**Rows in flight at upgrade.** The store's journal row gains a `write`
field beside the argv field (expand). A new row records the `Write`. A 1.x
row that holds argv and has no answer is read at the settle as unknown and
settled by the rule of its 1.x word's kind (`refresh-begin` as
`MarkChange`, `refresh-end` as `UnmarkChange`, `label-remove-only` as
`Unmark`), as an `Unknown` row is now, so an upgrade with rows in
flight loses nothing and sends nothing twice. The argv field is removed at
the next major (contract, R9).

The relay's contractor channel carries a `Write` as JSON instead of an
argument list, and the factory checks it against the same scope again.

**The relay's writes and what follows them.** The relay is not the
journal: it answers the container at once, as now. Its outbound calls
(`RelayWrite::Open`, `Edit`, `Comment`) go to `BlueprintWrites::open`,
`edit` and `comment` and are recorded in the cycle's record, with the
number and link of each blueprint it opened (`scope.created` today). The
relay writes no link row and no part. The dispatcher's plan step reads
that record after the turn and writes, through the journal, the
`AddPart` of each opened blueprint on a one-item site (Decided 25), or
the `opened` link row through the store's `link-record` on a split
setup.

**A relay open that may have landed, or was refused.** The adapter has
settled what it can before it answers (`Sent::Maybe` is settled in the
adapter first). What is left:

- `Unavailable { sent: Maybe }`: the relay settles at once by the rule of
  `OpenBlueprint` (a search for the title, a hit of ours read whole). Found,
  it is an open like any other: recorded with its number and link, and the
  container's `gh` is answered as for a made issue. Not found, or the read
  fails: the cycle's record holds the open as `unknown`, with its title and
  time, and the container's `gh` fails with one line that says the item
  may have been made and is not to be asked again. While an open is
  unknown, the relay refuses another open of the same title in that cycle
  with the same line, so a planner that retries makes no duplicate. After
  the turn, the plan step settles each unknown open by the same rule before
  it writes any part or link: one found is linked as an opened one, one not
  found is dropped from the record.
- `Refused(ReadOnly)`: nothing was made and the record holds nothing. The
  container's `gh` fails with the `read_only::line`, as the shim's refusal
  reads to it today. The plan step has nothing to link, and the start
  record of `read_only` stands.
- Any other outcome: nothing was made; the record holds nothing and the
  container's `gh` fails with the outcome's `line()`.

**The cycle's writes that build GitHub's words by hand** move with the
cycle (T4.5): `stamp_pull` in `cycle/src/apply.rs` edits the pull request's
body, which is `Write::EditChange`; its `trailers` and `cycle/src/stamp.rs`
build `https://github.com/{repo}.git` by hand, and `finish/plan.rs` and
`report.rs` build the remote and the pull request's address the same way.
Each takes `CodeHost::remote` or the `link` of a `Posted` or a digest.

## The fakes and the laws

In `tehas-ports/src/fake/`, std only, compiled always, used by both
consumers' tests (R7).

- **`World`**: an in-memory site. Tickets, blueprints, changes, comments
  with editors, tags, releases, accounts with ids and standing, targets,
  kinds, links, and a clock the test moves. A small builder keeps tests
  short: `World::new().ticket(7, |t| t.title("x").act(Act::Approve, "alice"))`.
- **Setups.** `World::same_item()` makes every ticket its own blueprint, as
  GitHub answers. `World::split()` keys tickets `PROJ-n`, numbers blueprints
  apart from them, and numbers changes apart from blueprints, as GitLab
  does, so a caller that confuses the three fails in tests even though
  GitHub would let it pass.
- **`FakeSite`**: a `Site` over a `World`. Every write is checked as a site
  would (a mark on a closed ticket, a merge at a moved head), applied, and
  recorded as `Wrote { by: Account, what: Write }`, so a test asserts
  `world.wrote()` in our words instead of a `gh` argument list. History it
  writes names the handle's account, so authorisation tests run through
  the fake. A read handle has no write method to call.
- **`Faulty<S: Site>`**: wraps any site and answers chosen calls with an
  outcome: `Faulty::new(site).on(Op::Board(BoardOp::OpenWork), Fault::Timeout).times(2)`.
  Faults: time out (with `sent` chosen, and the write applied or not, as
  the test says), unreachable, spent until a time, signed out, forbidden,
  refused, and odd answers (cut, inconsistent, too large, malformed, a
  repeated item, out of order). `Op` names every method of every port. It
  runs the same `health` machine as an adapter, so it raises the same
  notices.
- **`Notices`**: a sink that keeps what it was told, so a test asserts one
  report. **`MemoryLedger`**: a `Ledger` in memory, which a test can make
  fail. **`MemoryTokens`**: a `TokenStore` in memory that records each site
  and scope it was asked to keep or forget.

`laws.rs` holds the laws as functions over the traits:
`laws::tickets::removing_an_absent_mark_is_done`,
`laws::code_host::merge_at_a_moved_head_is_a_conflict`,
`laws::lists::past_the_bound_is_unread`, `laws::lists::last_n_is_never_cut`,
`laws::history::oldest_first`,
`laws::blueprints::an_edit_moves_the_revision`, and
`laws::search::words_never_widen`: words that spell the site's qualifiers
(another project, another kind of item, a mark) find only this project's
items of the port asked, and only by those words. The fake runs every law in
the crate's tests. A future adapter starts by passing the laws.

**The recorded samples, a contract test for any adapter** (Decided 26,
42). They live in `tehas-ports`, as data, in
`console/ports/samples/<site>/`, so the consumer vendors them with the
laws and the fakes. A sample is an answer per operation, keyed by the port
operation and its input in our terms, never by the request: the call (say
`Tickets::history` of ticket 7 with `Window::Whole`), the actor, the
state of the fixture project it was read from, and the answer the call
must give, all in our types. Two adapters that ask the site different
questions (tehas's through `gh`, the consumer's own REST and GraphQL
documents, tuned for its budget) are tied by what they answer, not by how
they ask.

- **How an adapter runs them.** Each adapter keeps its own recordings of
  the site, made against the same fixture project, beside its own tests
  (`tehas-github`'s under `console/github/tests/recorded/`, the
  consumer's in its own repository), and replays them through its own
  transport. The laws then check its answer to each sample's operation
  against the sample's answer. A recording no sample asks for is the
  adapter's own business; a sample whose operation an adapter cannot
  answer from its recordings fails its test.
- **Who adds samples.** tehas records them, with every token, host name
  of a person's machine and private name taken out. The consumer may add
  samples through a pull request to tehas, so they arrive in its next
  vendored copy and tehas's adapter must pass them too.
- **Actors tehas cannot run.** `Person`, `Anonymous` and `Deploy` have no
  transport in `tehas-github`. Their samples come from the consumer's side,
  through the same pull requests, or are left as marked gaps: a sample
  file that names the operation and actor and says `gap`, which the laws
  skip and list, until a transport exists. tehas's adapter answers those
  actors `Refused(Unsupported)` and passes a gap by doing so.

Only the adapters' recordings, their code and their tests name the site's
paths and fields; the samples hold our types alone, and no code of
`tehas-ports` reads them.

## The links

Three links: ticket to blueprint, blueprint to change, and through those
two, ticket to change. No supplier keeps the first; tehas does.

**Ticket to blueprint** is kept in the state store, in a table of its own:

```
links(ticket, blueprint, made_by, made_by_realm, made_at, how)
    how: same-item | opened | linked
```

Why the store and not a marker in the blueprint's body: the link decides
which ticket's approval lets a blueprint be worked. Anyone who can edit a
body could repoint a marker, so an account that may not approve could aim a
blueprint at an approved ticket. The link is written only by tehas (when it
opens a blueprint for a ticket) or from an act of an allowed account, and
its row names who made it, as approval does (rule 5). A blueprint's body
carries a line back to its ticket for people to read, a `Marker` of kind
`TicketOf`; nothing reads it to decide.

**How a link is made.** Three ways, each writing one row that names who
made it:

- `opened`: tehas opens a blueprint for a ticket and writes the row. For
  the one blueprint of an approved ticket with no plan, the dispatcher
  opens it through the journal and writes the row once the open's
  receipt names the blueprint. For planning, the relay opens the
  blueprints and the dispatcher's plan step writes a row for each from
  the cycle's record of what the relay opened (Decided 25). An open left
  unknown is settled by a read (`Blueprints::search` for its title and
  `TicketOf` marker) before any row is written.
- `linked`, by an act: an allowed account of the ticket realm writes a
  note on the ticket with a `Marker` of kind `Link` naming the blueprint,
  through the site as it would write any note (on a site with an action for
  it, the adapter reads that action as the same marker). The poll reads the
  marker, vouches its author and, from `Tickets::note_edits`, that no
  other account edited it (rule 5, as for a hold, whose marker is vouched
  the same way on either setup), and records the row through a new store
  verb,
  `link-record`. The row then stands: a later edit of the note changes
  nothing, and removing a link is the same act with `remove=1`.
- `linked`, by the operator: `tehas link <ticket> <blueprint>` on the host,
  which calls the same store verb with the operator as `made_by`.

`Links` stays read-only for the adapters; only the store writes rows.

```rust
// links.rs

    fn blueprints_of(&self, ticket: &TicketKey) -> Got<Vec<BlueprintNo>>;
    fn ticket_of(&self, blueprint: BlueprintNo) -> Got<Option<TicketKey>>;

/// Where ticket and blueprint are one item: the same number, both ways.

```

On every setup 2.0.0 runs, tickets come from the code host and `SameItem`
answers; the table is added empty. On a split setup the store answers. The
consumer that runs many factories uses `SameItem` too, and on a split setup
reads a factory's links through the factory API (a new read for T9), never
by guessing that two numbers match.

**What T4 builds, and what waits for a split setup.** T4 builds what every
setup 2.0.0 runs reaches, and the store's side of the links so a split
setup adds no migration:

- Built in T4: the `links` table, empty, and the store's `link-record`
  verb (T4.8); `Links` and `SameItem`; the realm column of
  `state/account-ids` (T4.8); the plan step's `AddPart` on a one-item site
  (T4.7).
- Waiting for a split setup, built with its tickets adapter: `tehas link`;
  the poll reading a `MarkerKind::Link` note and vouching it through
  `Tickets::note_edits`; the ticket realm's allowed list; the plan step's
  `opened` link rows and the `opened` row of an approved ticket's one
  blueprint; the store's answer to `Links`. Each is designed above so the
  ports need no change for it. The resilience test's split run covers the
  reads, writes and health of two sites, not these.

**Blueprint to change** is on the code host in every allowed setup. The site
records it (`ChangeDigest.closes`), and tehas records it as well: a cycle's
record names the change it opened. tehas decides from its own record; the
site's `closes` is read beside it, and a change that closes a blueprint
tehas did not record is someone else's, shown and not adopted. The branch
name `feature/issue-<n>` is tehas's convention, owned by one module of
core: the port returns the head branch and the caller applies its rule.

## The cycle and its blueprint

A work cycle takes exactly one blueprint, never a ticket directly.

- On every setup 2.0.0 runs, a ticket is its own blueprint: today's
  behaviour in new words.
- On a split setup, a ticket with no blueprint gets one before work starts.
  The act `Plan` runs a planning cycle that reads the ticket and opens
  blueprints through the relay, as planning opens sub-issues today; the
  dispatcher's plan step links each `opened` (Decided 25). An approved
  ticket with no plan asked gets one blueprint the factory opens with the
  ticket's title and text, linked `opened`.
- On a one-item site (every setup 2.0.0 runs), planning opens blueprints
  the same way, each one a ticket as well, and the plan step makes each a
  part of the planned ticket with `add_part`, as `sub-issue-add` does
  today. Each new item carries the approval the millwright carries to it
  now. Planning never calls `TicketWrites::file`.
- Approval is on the ticket. What it approves is the ticket's title and
  the blueprint text at the moment of the act: the approval row keeps the
  sum of the ticket's title (`title_sha256`, the title is the ticket's) and
  of each linked blueprint's body (`body_sha256` per blueprint), as it keeps
  the issue's today. Where ticket and blueprint are one item the two sums
  are the ones kept now. A blueprint edited later by an account outside the
  allowed list needs approving again. A blueprint linked after the
  approval needs one too.
- Why one blueprint: the container reads its issue through `gh` on the code
  host, the relay writes only to the cycle's own issue or one it opened, and
  a cycle's questions and markers are written where it works. A cycle that
  took a Jira ticket would need a Jira credential in the container, which
  rule 4 forbids.
- When the last blueprint of a ticket is closed by a merged change, the
  factory closes the ticket: one writer, decided in the pure code.

## Identity across suppliers

- Every `Account` names its realm, its folded login and, where the site
  gives one, its stable id. The vouch of `tehas_core::accounts` holds per
  realm: `state/account-ids` gains a realm column, so a rename cannot make
  one account pass for another.
- The settings keep giving logins. `ops/src/ids.rs` and `ops/src/setup.rs`
  fill `state/account-ids` from `TEHAS_ALLOWED_LABELERS` and
  `TEHAS_MILLWRIGHT_LOGIN` with `Identity::account_by_login` of the realm's
  site, instead of `GET users/<login>`; `NotFound` is today's missing
  login. Authorisation then compares account ids alone. No setting changes
  to ids.
- Authorisation stays the account behind the change, checked against an
  allowed list, with its history (rule 5), per realm. Today's
  `TEHAS_ALLOWED_LABELERS` is the code host's list. A split setup adds a
  list for the ticket realm, by account id. An act on a ticket counts by the
  ticket realm's list; an answer or an edit on a blueprint by the code
  host's. "No other account changed it since" is read in the history of the
  supplier that holds the thing. Neither list widens the other.
- One person with two accounts: no rule needs to know, so none is told by
  default. Where a rule needs "the same person" across realms, it reads a
  setting that groups each person's account ids. No entry is no match.
  Nothing is inferred from an e-mail or a display name, and the port never
  decides it.
- The dispatcher's read edge turns an `Account` into the login string the
  `Snapshot` holds, after the vouch, so `decide` reads the strings it reads
  now.

## Paging, retries, time limits and the budget

All of it is in the adapter. A caller gives a bound and gets a whole answer
or an outcome. What stays with the caller is how often to ask, which is
policy and tested in the pure code.

| What | Today | In the adapter |
| --- | --- | --- |
| Paging | `--paginate`, cursors and page counts in several crates | the adapter alone. It pages to the whole or one past the bound (`Unread(Cut)`). A repeated cursor, a total that does not add up, a node with no number: `Unread(Inconsistent)`, never a partial list as whole |
| A cut timeline | `dropped_events` finds an issue the page cut short; `rest_events` reads it again | inside the adapter: `Ticket.history` is whole or `Unread` |
| Comment edits | `fill_comment_edits` in chunks of `COMMENT_EDIT_CHUNK` 20, `edits_of` | inside `Blueprints::comment_edits`, `Tickets::note_edits` and the joined read |
| A call's time limit | `Bounded`, 30 s (`CALL_BOUND` in `ops/src/forge.rs`), TERM then KILL after 5 s; `GH_BOUND`, 120 s, in `core/src/call.rs` for the cycle, the journal and the console | one `Policy` value in the adapter, a read bound and a write bound. A pass gets a deadline when its handle is made (the poll's lock); a call past it answers `Unavailable(Timeout)` without running. `GH_BOUND` and `CALL_BOUND` go when their last caller moves |
| Read retries | `RetryPolicy` and `NOTES_MAX` in `read/run.rs`; `core/src/retry.rs`, the read-retry rule the poll, `tehasbot status` and tidy share, read from gh's words | the handle's, unchanged in amount: twice at most within the whole limit, `Unread(Inconsistent)` once. `retry.rs`'s rule moves into the adapter's runner, reading the site's answer, not gh's text |
| Write retries | none in Rust; the console's shim sends a rate-limited write once more after `TEHAS_GH_RETRY_WAIT` (60 s) | the adapter alone. Its runner turns the shim's retry off for its own calls (a new shim setting, `TEHAS_GH_RETRY=0`, pinned by the shim's tests, made on its own as B1 before T4.2), so a call never outlives the adapter's bound in the shim's wait. A rate-limited write answers `Spent`, held in the `Ledger`. A write is sent again only when it is idempotent by meaning (marks, links, targets, a tag, a status, `propose`) or the site refused it before acting, and only within the bound. A note, a comment, a new ticket, change or release is sent once. Every other `gh` on the host (an operator's, a plugin's) keeps the shim's retry |
| Rate limits | 403 or 429 read from gh's error words | the adapter reads its site's cost and holds what is left per host, holder and pool in the `Ledger`: the factory's account as the site budgets it (an installation), each person, each anonymous address. Once a holder's pool is spent, that holder's calls in it fail at once with no request, for every project it serves; other holders go on. Anonymous search is a pool apart from anonymous reads |
| Points | the page size is the guard | the joined read asks the site's cost beside it; the meter counts calls and points by caller name for every path, person and anonymous included |
| Caching | the poll's `Calls` per pass | per handle, cleared by the handle's own writes; conditional requests with validators kept by the adapter where its wiring gives it a directory; the change token of `changed`, which a push can later feed |
| Tokens | `ops/src/github.rs` mints and keeps them under `state/github/` | minting in the adapter, behind `Actor::Ours` and `Identity::token`; keeping in the caller's `TokenStore` (see Identity, "Tokens, a security change") |

A failure becomes an outcome where it enters, in one function of the
adapter (today's `forge::gh::why`, `run::why_words`, `call::gh_why`, and
`console/src/notice.rs`, which reads "HTTP 404/403/429" out of gh's text),
so no status leaves it.

### One report

Two layers, so tehas reports once with or without a shared ledger:

```rust
// report.rs: per pass
/// A caller's name for the meter: `"dispatch.poll"`, `"cycle.report"`.
pub struct Caller(&'static str);
/// Which port a report or a meter row is about.
pub enum PortName { Tickets, Blueprints, CodeHost, Identity, Board, Unknown }
pub struct Report { pub port: PortName, pub outcome: Outcome, pub calls: u32 }
pub trait Reports {
    /// The reports since the last take, each kind once with its count.
    fn take_reports(&mut self) -> Vec<Report>;
}

// ledger.rs: across processes, typed
/// One supplier's host, as the adapter names it: every project on it shares
/// its health, and every holder on it its budget. Not a project: that is
/// `SiteId`, which keys tokens alone.
pub struct HostId(String);
/// Whose budget a call spends. The adapter makes the ids. `Ours` is the
/// factory's account as the site budgets it: on GitHub the installation,
/// which serves every project it is installed on.
pub enum Holder {
    /// The factory's account, as the site budgets it.
    Ours(HolderId),
    Person(AccountId),
    /// A caller's address, kept as the adapter's sum of it.
    Anonymous(HolderId),
}
pub struct HolderId(String);
pub struct Budget { pub left: u32, pub resets: At }
pub enum HealthState {
    Healthy,
    Failing { since: At, why: Passing },
    Spent { pool: Pool, until: At },
    SignedOut { since: At },
}
/// A failed call, for the health check: when, the project it was for, and
/// its outcome, whose fixed line is `outcome.line()`. Read back whole by
/// another process.
pub struct Failure { pub at: At, pub site: SiteId, pub outcome: Outcome }
/// The ledger could not be read or written: its file is missing, locked
/// past its wait, or not whole.
pub struct LedgerDown;
/// Whose health a state is: the host's own (an outage: `Healthy` or
/// `Failing`), or one holder's on that host (`Healthy`, `Spent` or
/// `SignedOut`).
pub enum Whose { Host, Holder(Holder) }
pub trait Ledger: Send + Sync {
    fn budget(&self, host: &HostId, holder: &Holder, pool: Pool) -> Result<Option<Budget>, LedgerDown>;
    fn put_budget(&self, host: &HostId, holder: &Holder, pool: Pool, b: Budget) -> Result<(), LedgerDown>;
    fn health(&self, host: &HostId, whose: &Whose) -> Result<HealthState, LedgerDown>;
    /// Write `new` only if the state is still `expect`. True if written.
    fn swap_health(&self, host: &HostId, whose: &Whose, expect: &HealthState, new: &HealthState) -> Result<bool, LedgerDown>;
    /// Keep one failed call, with the project it was for; the ledger cuts
    /// what is older than `keep`.
    fn failed(&self, host: &HostId, f: Failure, keep: u32) -> Result<(), LedgerDown>;
    fn failures(&self, host: &HostId, since: At) -> Result<Vec<Failure>, LedgerDown>;
}

// health.rs: pure
/// The next state, and the notice due, if any. Only a change of state
/// raises one.
pub fn next(now: At, was: &HealthState, seen: &Result<(), Outcome>) -> (HealthState, Option<Notice>);
pub struct Notice { pub host: HostId, pub whose: Whose, pub realm: Realm, pub what: Health, pub at: At }
/// `TokenNotDropped`: a refused token could not be dropped from the
/// `TokenStore`, so another process may still read it until it expires.
/// `Unknown`: a value of a newer copy was read (see "Enums that may grow").
pub enum Health {
    Unavailable(Passing), Spent { pool: Pool, until: At }, SignedOut, Recovered,
    LedgerDown, TokenNotDropped, Unknown(Word),
}
/// The enums that may grow, by name, for `Health::Unknown`.
pub enum Word {
    Mark, Act, State, Choice, Kind, MarkerKind, Scope, Happened, ChangeHappened,
    Write, WriteKind, Receipt, Refusal, Unread, Pool, NotMergeable, Conclusion,
    Verdict, Health, PortName, Unknown,
}
pub trait Notices: Send + Sync { fn notice(&self, n: Notice); }
```

- A pass takes its handles' reports once at its end and logs them, as the
  poll prints its notes now.
- The adapter tells `health::next` each outcome; a notice is raised only
  when `swap_health` wins, so many short processes (every poll, every
  cycle) and many factories on one budget report an outage once and its
  end once (Decided 36). An outage (`Unavailable`) is the host's: one
  notice for every project on that host, whichever project's call saw it
  first. A spent pool and a sign-out are the holder's on that host: a
  spent installation holds every project it serves, and its calls for
  any of them fail at once with no request until `until`. A split setup's
  two hosts report apart; two projects on one host never do.
- **tehas's `Notices` sink.** Each notice is one fixed line, in our words,
  on the standard error of the process that raised it, which its unit's
  log keeps, as the poll's notes are kept today. A person sees the state
  in the `github` health check (`tehas status`, the console, the factory
  API's `live/health.json`), which reads the Ledger. T4 posts no host
  message (`ops/src/host_message.rs`) for a notice: that would be a
  behaviour change, proposed in Open. The consumer's sink is its own.
- tehas's ledger is one file under `state/`, made by `Home` (T5) and given
  to the adapter at wiring; the adapter knows no layout of `$TEHAS_HOME`.
  The consumer's ledger is its own, shared by its factories.
- **A ledger that fails fails toward reporting.** When `health` or
  `swap_health` answers `LedgerDown`, the adapter raises the notice its
  own outcome calls for, as if it had won the swap, and one notice more,
  `Health::LedgerDown`, once per handle: two processes may then report
  one outage twice, but an outage is never left unreported. A budget that
  cannot be read is taken as unknown: calls go on and the site's own
  answer decides. A failure that cannot be kept is lost from the health
  check alone. The health check reads `LedgerDown` as failing, never as
  healthy.

**The health check (Decided 14).** The Ledger replaces
`state/github-failures` and `core/src/github_fails.rs`. The factory API's
`github` check in `live/health.json`, written by `ops/src/health.rs` and
shown by `console/src/status.rs`, keeps its name and its shape in 2.0:
`failed` is the count of `Ledger::failures` on the code host's host over
the window (tehas's ledger is its own file, so these are this factory's
calls, as today's file holds), `windowSeconds` stays 600
(`github_fails::WINDOW`), the warning stays at 3 (`THRESHOLD`), and
`lastAt` and `last` are the newest failure's time and its outcome's fixed
line. A ledger that cannot be read shows the check as failing, with the
line that says so. The one change a reader sees is that `last` is our
line, not gh's words. That change is made on its own before T4.4 (B2 in
"Behaviour changes, each a pull request of its own"), and T9 lists it in
the contract. A tickets host of a
split setup gets a check of its own beside it, named at T9.

## The resilience test

T4 is not done until this test passes, in `console/dispatch/tests/` and
`console/cycle/tests/`, over `FakeSite` wrapped in `Faulty`, with a
`MemoryLedger` and a `Notices` sink shared by both. It covers what R6 asks:
a supplier that times out, refuses, forbids, signs out and answers oddly,
for each port: every cell of the table below is a case.

1. **Time out.** The joined read times out twice, then answers. The poll
   holds what it could not read, starts nothing on it, keeps deciding from
   the store, and the next poll proceeds. A cycle's report in the same
   window writes what it can, keeps the rest for the journal, and ends
   normally.
2. **Rate limit.** The factory's holder's `Priced` pool is spent until a
   time. Every call of that holder in it fails at once with no request (the
   fake counts none). The poll skips those reads until the time and says so
   once; the cycle keeps its writes in the `Writes` pool going. A person's
   read in the same pool, as another holder, still answers. A second
   project on the same host, read with the factory's holder, fails at once
   too: the installation is spent for every project it serves.
3. **Refused.** A blocker link answers `Refused(Cycle)` and a mark on a
   closed ticket `Refused(Invalid)`. The dispatcher holds the ticket with
   one line and does not write it again until the ticket changes; the cycle
   leaves the write with one line and ends normally.
4. **Forbidden.** A comment and a change's mark answer `Forbidden`. One
   line each; no handle is made with a wider actor, and the fake counts no
   call by any other actor.
5. **Signed out.** The factory's handle answers `SignedOut` on its first
   read. The poll stops with one report; the cycle keeps it for the end
   fault. A person's handle signed out calls `Keyring::signed_out` once.
6. **Odd answers.** A cut list, a repeated item, an out-of-order history
   and a malformed answer each read as `Unread`: the issue counts as changed
   or held, never as empty, and nothing starts on it.
7. **A write that may have landed.** A comment times out with `sent:
   Maybe`, applied in one run and not in the other, and the second part of
   a step does the same. Neither run sends either twice; the next pass
   settles each row by a read and decides what is left afresh.
8. **One report.** Across all of it, run as several short processes over
   the one ledger, and over two projects on one host, the `Notices` sink
   holds exactly one notice for the outage, one for the spent pool, one for
   the sign-out, and one recovery for each. Each pass's `take_reports` holds each kind once with its
   count. The `github` health check reads the failures from the ledger
   with the shape it has today.
9. **A ledger that fails.** The `MemoryLedger` is made to answer
   `LedgerDown` during an outage. The sink holds at least one notice for
   the outage and one `LedgerDown`, never none, and the health check
   reads failing.
10. **Read-only.** Over `ReadOnly<FakeSite>`, a claim, a note and a filed
    ticket each answer `Refused(ReadOnly)`: the fake counts no request, the
    journal holds no row, and the start record is kept.
11. **Still running.** Neither the dispatcher nor the cycle exits non-zero,
   panics or leaves a lock held, and the next pass after recovery decides
   as it would have.

## Answers to the consumer's questions

1. **One adapter crate per site, or one per port per site?** One per site,
   answering every port that site serves. The cheap form of the queue read
   crosses all three ports on GitHub, and only one crate that holds all
   three can ask it as one question; that is `Site::board` and
   `Board::open_changes`. A ticket-only site, when built, answers tickets
   and its identity alone; `Setup::Split` joins it to the code host's site
   with `Join`. The consumer writes its own GitHub adapter over its own
   HTTP clients and does not take `tehas-github` (Decided 26); the laws,
   the fakes and the recorded samples in `tehas-ports` are the contract
   both adapters pass.
2. **Raw records, or derived facts?** Raw, typed records: history events,
   comments with authors and editors, marks, changes. The rules (the newest
   counted approval, a marker's trust) stay in each consumer's pure code.
   The ports' only pure helper is the order of history, which the port
   promises; markers come typed (`Marker`), parsed by the adapter.
3. **Factory state as labels, or from the factory API?** Both, with one
   owner. The factory writes its states as marks so people see them on the
   site, and the tickets port reports them. Another program should decide
   from the factory API. A state mark written by any account but the
   factory's is not the factory's.
4. **Where do markers live?** As a port value, `Marker { kind, key, fields
   }`, in its own field beside a comment's, a note's or a body's text,
   never inside it, with the author and last editor beside it. An edit
   keeps the markers it is not told to change, and `find_marked` reads
   every place one can be (Decided 37). The
   adapter writes and reads it the way its site allows: text in our syntax
   on GitHub, from its table, and perhaps a comment property on Jira. A
   ticket marker (hold, blocked, link) goes in a ticket note; on a one-item
   site that is the item's comments (`WorkItem::ticket_comments`). The
   factory's own markers (question, handoff) go on the blueprint. The
   adapter parses a marker's syntax; it never decides what one means or
   whether to trust it. A consumer's own markers are
   `MarkerKind::Project(name)`.
5. **Close reasons and duplicates on a site without them?** The adapter
   records them its own way (a label, a note, a resolution) and reads them
   back as `CloseReason`. `Refused(Unsupported)` only for what a site
   cannot hold at all. No capability flags.
6. **A conditional comment edit: a promise or a capability?** A promise.
   `edit_comment` always takes a `Revision` and answers `Conflict` when it
   lost. Where the site cannot compare and write in one step, a window of a
   moment remains, stated by the adapter's contract test. A caller that
   cares reads again after. tehas stops needing it once T12 retires the
   tick boxes.
7. **The change check: in the port now?** Yes: `changed(since)` on each
   port with an opaque `ChangeToken`, so a push can feed it later without a
   change to the port.
8. **How is a person's session handed to the adapter?** As
   `Actor::Person(PersonKey)`. The caller keeps person credentials in
   memory and implements `Keyring`; the adapter asks it when it makes a
   handle, keeps the answer no longer than the handle, never writes it to
   the ledger, and calls `signed_out` when the site refuses it. A program
   that holds only a short-lived read token is given it as a `Token` from
   `Identity::token(Scope::Read)`, minted by the program that holds the
   factory's account, and opens handles as `Actor::Ours(Scope::Read)` from
   it alone. An operator's own tools act as `Actor::Operator`, and a deploy
   credential as `Actor::Deploy`.
9. **Cross-project blockers and parts?** Named as `Ref::Elsewhere`, never
   followed, and held, as now.
10. **The bump: one operation, or a sequence?** One:
    `CodeHostWrites::propose`, idempotent by its inputs, answering how far
    it got when it stops.
11. **Git transport and downloads?** Downloads and archives are in the code
    host port with size and time limits. Git stays git, with a remote and a
    credential from `CodeHost::remote`; the port gives no working tree.
12. **Does the port give the agent a CLI?** Not in 2.0.0. Agents keep the
    code host's CLI behind the sandbox shim and the relay. A ports CLI for
    agents is a later step, after plugins.
13. **Where is the ticket-to-blueprint link kept, and what does a cycle
    take?** In tehas's state store, written only by tehas or from an act of
    an allowed account, read through `Links`, and by other programs through
    the factory API. A cycle takes one blueprint, always; a ticket with
    none gets one first.
14. **Who moves the ticket on a split setup when its change merges?** The
    factory. Its pure code decides "every blueprint of this ticket is
    closed by a merged change" and writes the close. Not the adapter,
    which decides nothing, and not the consumer, so there is one writer.
    The close is idempotent, so a second writer does no harm.
15. **One person with a ticket-tracker account and a code-host account?**
    Each act is authorised by its own realm's allowed list, by stable
    account id. Where a rule needs "the same person", it reads a setting
    that groups the ids; nothing is inferred.

Facts to confirm against recorded samples, before any second adapter, kept
here and in the adapter's docs, never in `tehas-ports`:

- **GitLab numbering.** Issues and merge requests have their own per-project
  numbers (`iid`), apart from each other and from global ids. The types
  already keep them apart; confirm the adapter never crosses them.
- **Marks on a change.** tehas takes a pull request's label off through the
  issues path today, which only GitHub allows. GitLab labels a merge
  request on its own path; `mark_change` hides the difference.
- **History.** GitLab keeps label, state and milestone events in three
  lists; the adapter merges them by the history law. Confirm the order of
  two events in one second.
- **Editors.** Whether a GitLab note names its last editor, and whether a
  note's or a description's edits keep a history (`body_edits`,
  `comment_edits` may answer only the last edit).
- **Blockers and parts on the free tier.** Whether "blocked by" links,
  child items and epics are there without a paid tier; where they are
  not, the adapter records them with a marker and says so in its docs.
- **Checks.** Pipelines for checks: the state of a commit with several
  pipelines, and the mergeable state mapped to `Unknown` while the site
  computes it.
- **Close reasons.** GitLab has none native; a not-planned close is recorded
  with a label, a duplicate with its own action.
- **Protected tags** and the answer to a tag that exists elsewhere.
- **Jira.** The transition for each act and its actor in the changelog,
  fix versions as targets, the resolution as the close reason, and comment
  properties for markers.
- **Bitbucket.** Allowed as a code host, but not used to shape these ports.
  Its issues are weaker (no label history), so it may back only the code
  host port, with blueprints elsewhere, which the allowed setups do not
  yet allow. To settle before any Bitbucket work.
