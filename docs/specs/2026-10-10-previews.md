# Spec: a preview of every pull request, and one edge for previews and the Protolab

**Status**: Agreed 2026-10-10. The proxy in front of the host is set up and
checked; nothing in this repository is implemented yet.

## Purpose

A pull request can be read on GitHub and cannot be looked at. A reviewer of a
change to the dashboard or the manual has to check the branch out and start a
server to see it. tehas should do that: every open pull request gets a running
copy of the product at an address of its own, and the copy goes when the pull
request does.

The Protolab already publishes something per ticket. It gets the same kind of
address, and both are served by one edge, from one setting.

A preview serves. It runs no dispatcher, no timer and no cycle, holds no token
and can reach nothing.

## What was decided, and what was not chosen

| Question | Decision | Not chosen, and why |
| --- | --- | --- |
| The names | `uat-<pr>.<domain>` and `lab-<issue>.<domain>`, one level under the domain | `<pr>.uat.<domain>`: Cloudflare's free certificate covers one level. Two levels need a paid certificate, or a DNS token on the host and the host's address made public |
| Who routes a name | A router container that tehas installs, on one port. The proxy in front of the host forwards every such name to it with the Host header kept | tehas writing a site per preview into the front proxy: that ties the platform to a server it does not install |
| Which pull requests | Every open one whose head branch is in the product repository itself. Pushing a branch needs write access | A `tehas:preview` label by an allowed labeller: a click for every pull request, and the factory's own would have none until a person came by. A fork's pull request: its build would run a stranger's code on the host |
| What a preview is | An image built from `preview/Dockerfile` in the pull request's own commit, answering HTTP on port 8080 | A recipe in the instance directory: a pull request that changes how the product is served would be previewed wrongly. Static files only: the manual and the dashboard are Caddy templates |
| When a preview goes | At the next run after its pull request is merged or closed, and a second, separate check every three hours | The five minute run alone: it works from GitHub's list, and a run that fails half way leaves something behind that the next run does not look for |
| A full disk | No build under a floor of free space. The pull request, the dashboard and the health file say so | Building until Docker fails: the factory's own cycles share that disk |

## Settings

Four settings in `instance.env`, read and checked by `lib/config.sh`.

| Setting | Default | Meaning |
| --- | --- | --- |
| `TEHAS_DOMAIN` | none | The domain the names are made under, as `tehas.app`. Host name characters only, no scheme, no path |
| `TEHAS_PREVIEWS` | `0` | `1` builds previews. It needs `TEHAS_DOMAIN`; without it every command stops with exit 78 |
| `TEHAS_PREVIEW_MAX` | `5` | How many previews run at once. The newest pull requests win |
| `TEHAS_PREVIEW_MIN_FREE` | `5g` | Free space below which no preview is built |

`lib/config.sh` stops refusing `TEHAS_PREVIEWS`. It still refuses
`TEHAS_CLONES`. One function, `tehas_edge_name <kind> <number>`, makes a name
from the domain; nothing else puts a name together.

With `TEHAS_DOMAIN` set and `TEHAS_PROTOLAB_URL` not, the Protolab's address is
`https://lab.<domain>`. Without `TEHAS_DOMAIN` the Protolab is as it is today,
by path on port 8081, and there are no previews.

## The edge router

`host/edge/protolab.Caddyfile` and `protolab.compose.yaml` become
`router.Caddyfile` and `router.compose.yaml`. One Caddy container, still on
port 8081, with the hardening the Protolab's container has now. Its
configuration is a fixed file. Nothing writes it when a preview comes or goes.

| Host header | Answer |
| --- | --- |
| `lab-<n>.<anything>` | The files of `~/tehas/protolab/<n>/`, with the headers the Protolab sends today |
| `uat-<n>.<anything>` | A reverse proxy to the container `tehas-preview-<n>`, port 8080, found by Docker's own name lookup. With no such container, a plain 404 page that says there is no preview |
| anything else | The Protolab by path, as today: the list at `/`, a ticket at `/<n>/` |

`<n>` is digits only. Every answer under a `uat-` or `lab-` name carries
`X-Robots-Tag: noindex, nofollow`. The router matches on the first label, so
its file holds no domain and the platform rule holds.

The router is on two Docker networks: `tehas-edge`, which has the published
port, and `tehas-previews`, which is internal. A preview is on the second one
only. The router can reach it; it can reach nothing, not the internet and not
the model host. On 11 October 2026 this was tried with Docker 29.1.3 and was
not so: a container on a network made with `--internal` could not reach the
internet or the host's other addresses, but it reached every service the host
listens on at all addresses, the SSH server for one, through the gateway
address of the network's bridge. The network is therefore made isolated from
the host as well, with the option
`com.docker.network.bridge.gateway_mode_ipv4=isolated`: the host then has no
address on the bridge. With it the gateway and the internet did not answer,
and containers on the network still reached each other by name, which the
router needs. The option needs Docker 27.1 or later and is valid only with
`--internal`.

The same day a review found that this was still not enough, again with
Docker 29.1.3. The option is about IPv4 only: on a network made with `--ipv6`
as well, the host held a global IPv6 address on the bridge, and a container
on that network got the host's SSH banner through it. And the bridge driver
takes a `com.docker.network.bridge.*` option it does not know and shows it
when asked, so a Docker before 27.1 most likely makes the network, answers
that it is isolated, and gives the host an address. That was not tried on an
old Docker. So neither the network's name nor the option alone is believed.
The network is made with `--ipv6=false`, and a run builds nothing unless all
of these hold: the Docker server is 27.1 or later, by its first two numbers,
and a version that cannot be read fails; the network is internal; its driver
is `bridge`; it has no IPv6; and the option is `isolated`. The log names the
one that failed. `install.sh` checks the same by the same code, and does not
ask an older Docker to make the network. `install.sh` creates the network;
the compose file names it as external.

Each ticket of the Protolab gets an origin of its own this way. Today one
prototype's script is kept from another's by a sandbox header alone.

## `tehasbot preview`

A script in `libexec/`, on a timer every five minutes, like
`tehasbot protolab`. Deterministic, no model.

```
tehasbot preview            bring the previews in step with the pull requests
tehasbot preview --sweep    the three hour check, see below
```

| Exit | Meaning |
| --- | --- |
| 0 | Done, or GitHub or Docker did not answer. What runs is then left running |
| 1 | It cannot write under `~/tehas` |
| 64 | A wrong argument |
| 78 | The instance settings are invalid, or `TEHAS_PREVIEWS` is not 1 |

One run:

1. Measure free space (see Disk).
2. List the open pull requests, one call. Keep those whose
   `head.repo.full_name` is exactly `TEHAS_REPO`. A missing or different one is
   left out and counted.
3. Keep the newest `TEHAS_PREVIEW_MAX`. The rest are listed as "over the limit".
4. Remove every preview whose pull request is not in that set: the container,
   the image, the fetched ref and the state directory.
5. For each one kept: when the container's `tehas.sha` label is the head
   commit, leave it. Otherwise build and replace.
6. Write `live/previews.json`, and comment on a pull request when its preview's
   address or state is new.

Build and replace, for pull request `<n>` at commit `<sha>`:

- Fetch `<sha>` into a bare clone, `~/tehas/preview/repo.git`. No working tree
  is made.
- `git archive <sha> | docker build -f preview/Dockerfile -t tehas-preview:<n> -`,
  with a time limit of 15 minutes, no build arguments and no secrets. A commit
  with no `preview/Dockerfile` has no preview; that is a state, not an error.
- Remove the old container, start the new one under the same name, then
  remove the old image by id. Two containers cannot share the name the router
  looks up, so there are a few seconds of the router's 404. A failed build
  leaves the old preview serving.

The container is started with exactly these, and `test/preview_test.sh` pins
them the way `test/work_test.sh` pins a cycle's:

```
--name tehas-preview-<n>
--network tehas-previews
--read-only --tmpfs /tmp --tmpfs /config --tmpfs /data
--cap-drop ALL --cap-add NET_BIND_SERVICE --security-opt no-new-privileges:true
--memory 256m --cpus 1 --pids-limit 128
--restart unless-stopped
--label tehas.preview=<n> --label tehas.sha=<sha> --label tehas.repo=<TEHAS_REPO>
```

No volume, no published port, no `-e`, no Docker socket. The state of each
preview is a small file, `~/tehas/preview/<n>/state.json`: number, commit,
state, when, and the reason when it is not serving.

### States

| State | Meaning |
| --- | --- |
| `serving` | The container runs the head commit |
| `building` | Written before a build starts, so a run that dies says where |
| `no-recipe` | The commit has no `preview/Dockerfile` |
| `build-failed` | The build ended non-zero or ran out of time. The log is `~/tehas/logs/preview-<n>.log` |
| `no-space` | The host is under the floor. Nothing was built |
| `over-limit` | More open pull requests than `TEHAS_PREVIEW_MAX` |

### The comment

One comment per pull request, by the bot, edited in place and found by a hidden
marker in its text. It gives the address when the state is `serving`. For
`build-failed` and `no-space` it says the preview could not be created and why:
for `no-space`, how much is free and how much is needed. It is edited only when
the state or the commit changes, so a full disk does not produce a comment
every five minutes.

## Purging, and the three hour check

A merged or closed pull request is no longer in GitHub's list of open ones, so
step 4 of the next run removes its preview: at most five minutes later.

That depends on the list. `tehasbot preview --sweep` does not. It runs on a
timer of its own every three hours and starts from what is on the host:

1. Every container, running or stopped, with the label `tehas.preview`; every
   image tagged `tehas-preview:*`; every directory under `~/tehas/preview/`;
   every fetched ref in the bare clone.
2. For each number found, ask GitHub for that one pull request.
   - Open, head in the product repository: keep, and remove any image or
     container of it that is not the one serving.
   - Merged, closed, not found, or head elsewhere: remove everything of it.
   - No answer: keep. A sweep never removes on a failed call.
3. Remove what belongs to no number: a container or image carrying the label
   with a malformed number, or of another repository than `TEHAS_REPO`.
4. Write what it removed to `~/tehas/logs/preview.log`, one line each, and
   the count and time to `live/previews.json` as `lastSweep`.

A sweep that removes anything found something the five minute run missed. That
is a line in the log to read, not a failure. It takes the same lock as the
five minute run, so the two never work at once.

## Disk

Every run, before anything else, `tehasbot preview` reads the free space of two
places with `df`: the file system of `~/tehas`, and the one of Docker's data
directory (`docker info`). The smaller is the host's free space.

- Under `TEHAS_PREVIEW_MIN_FREE`, nothing is built. Previews already serving
  stay. Each pull request that needed a build gets the state `no-space`, a line
  in the log, and the comment above.
- Removal still runs under the floor. It is how space comes back.
- The figures go into `live/previews.json` as
  `disk: {freeBytes, minFreeBytes, low}` at every run, whether or not there is
  anything to build.

`tehasbot health` reads that file, as it reads the other files in `live/`. It
adds `checks.disk`, and when `low` is true the status is `warn` and the output
says "The host is low on disk: previews are not being built." A `fail` from a
cycle still wins. This is the first check of the host itself; the manual's
"Not built" line about a full disk is narrowed, not removed, because nothing
stops a cycle on a full disk yet.

## The Protolab

`libexec/protolab` keeps what it fetches and writes. Three things change:

- The front page links a ticket as `https://lab-<n>.<domain>/` when
  `TEHAS_DOMAIN` is set, and as `/<n>/` when not. The files on disk are the
  same in both cases; links inside a ticket's page are already relative.
- A ticket's page links back to the list by its full address when there is a
  domain.
- `live/protolab.json` carries each ticket's address, so the dashboard does not
  build one.

## What the two share

- The router container, its Caddyfile and its two networks.
- `TEHAS_DOMAIN` and `tehas_edge_name`.
- `lib/edge.sh`: the steps both commands take over a numbered set. A lock,
  `skip if unchanged` by a stamp, `put in place by rename`, `remove what is no
  longer wanted`, and writing a `live/` list through a `.new` file. The
  Protolab's own code for these moves there.
- The dashboard's reading of a `live/` list with an address per number.

## In this repository as a product

`preview/Dockerfile`, for a preview of tehas itself:

- From the Caddy image the docs server uses.
- The commit's `host/docs`, `host/fun` and `host/edge/docs.Caddyfile`.
- `preview/live/`: sample `status.json`, `running.json`, `health.json` and a
  short console log, so the dashboard and the game view show something with no
  factory behind them.
- `TEHAS_INDEXING=0`, no analytics.

It is a file of the product. The platform does not know what is in it.

## Installing

- `install.sh` installs the router files in place of the Protolab's, the
  `tehas-preview.service` and `.timer` (five minutes) and the
  `tehas-preview-sweep.service` and `.timer` (three hours), and
  `libexec/preview` and `lib/edge.sh`. It removes the old Protolab files and
  recreates the container under its new name.
- The follow-up id `protolab` becomes `edge`. `install.sh` still accepts
  `protolab` and says the new name.
- The preview timers are enabled by the operator, like the Protolab's, and
  only do anything with `TEHAS_PREVIEWS=1`.

## On the host, by a person

Two things are not done by a pull request. The second is done: it was carried
out and checked from outside on 2026-10-10, on Ubuntu 26.04 LTS.

1. `instances/tehas-tehas/instance.env` gets `TEHAS_DOMAIN=tehas.app` and
   `TEHAS_PREVIEWS=1`. A real instance is not edited by an agent; the lines go
   in the pull request text.
2. The proxy in front of the host sends `lab.<domain>`, `lab-*.<domain>` and
   `uat-*.<domain>` to port 8081 with the Host header kept. That proxy is not
   on the factory's host: as read on 2026-10-10, the host runs the docs server
   on its private address, port 8080, and nothing else listens. The router
   binds to the same private address, so the proxy reaches it the way it
   reaches the dashboard.

   For this instance the proxy is a Caddy 2.11 system service on another
   machine, with one Caddyfile and a site `tehas.app` that gets its own
   certificate. A new name needs a certificate there too, or Cloudflare cannot
   finish the handshake (status 525). The decision: a Cloudflare origin
   certificate for `*.tehas.app`, made once in Cloudflare's dashboard and put
   on that machine as two files. Then one site:

   ```
   *.tehas.app {
       tls /etc/caddy/certs/origin.pem /etc/caddy/certs/origin.key
       @edge header_regexp Host ^(lab|lab-[0-9]+|uat-[0-9]+)\.tehas\.app$
       handle @edge {
           reverse_proxy <the host's private address>:8081
       }
       handle {
           respond 404
       }
   }
   ```

   Caddy takes a wildcard as a whole label only, so the names are picked by
   the matcher. The sites `tehas.app` and `www.tehas.app` are more specific
   and are not touched. Caddy passes the Host header on as it is.

   Not chosen: certificates on demand, one from Let's Encrypt per name. It
   needs no step in Cloudflare, but the router would have to answer Caddy's
   question "may this name have a certificate", every pull request number
   would be in the public certificate logs, and the first visitor waits. Not
   chosen either: a wildcard from Let's Encrypt, which needs a DNS token and a
   Caddy built with a plugin.

   The order matters. The certificate files go in place first, then the site,
   then `caddy validate` and `systemctl reload caddy`. With the site and no
   files Caddy does not start, and a restart then takes down every site in
   that Caddyfile. That happened on 2026-10-10. A reload with a bad
   configuration keeps the old one serving; a restart does not.

   As checked afterwards: the domain and its `www` name answer as before,
   `lab.`, `lab-1.` and `uat-1.` answer 502 because nothing listens on port
   8081 yet, and `nothing.` and `uat-x.` answer 404.

   The manual gets a page of its own for this, see The manual.

As read on the same day the host has 29 GB free of 58 GB, with 16 GB of images
and 7 GB of build cache. The default floor of 5 GB leaves room for a cycle.
The Protolab's container is not running there; this change is its first
install on a host.

DNS and the certificate need nothing: the existing wildcard record and
Cloudflare's certificate cover one level.

## Security

This is a security change and the pull request says so.

- A cycle's container is given nothing new. `test/work_test.sh` is not touched.
- `docker build` runs the pull request's build steps on the host's Docker
  daemon, with network access. Only a branch in the product repository is
  built, and write access to that repository is what a cycle's token already
  has. A fork's pull request is never built, and the test for that is the one
  that must not be relaxed.
- The preview container has no secret, no mount and no network but the one
  it shares with the router and the other previews. That network is internal
  and the host has no address on it, IPv4 or IPv6, so a preview reaches
  neither the internet nor the host. A run checks this before it builds: the
  Docker version, the driver, IPv6 and the option, as of 11 October 2026.
  What is checked is how the network was made, not what a container on it
  reaches. Previews can reach each other. The build is given no
  token: the commit reaches it as an archive on standard input.
- `uat-<n>.<domain>` and the dashboard on `<domain>` are one site to a browser.
  A preview's script can set a cookie for the domain. Nothing on the dashboard
  logs in, so this is accepted. It has to be looked at again before the
  dashboard has accounts.
- A preview is public. A branch pushed to the repository is published within
  five minutes. The manual says so.

## Tests

Shell tests with `gh`, `docker`, `git` and `df` stubbed. No network, no image.

- `test/config_test.sh`: `TEHAS_DOMAIN` shapes; `TEHAS_PREVIEWS=1` without a
  domain is exit 78; `tehas_edge_name`; the derived Protolab address.
- `test/preview_test.sh`: the pinned `docker run` arguments; a fork's pull
  request is not built; a pull request with a null head repository is not
  built; unchanged commit makes no build; a new commit builds, then removes the
  old container and image; a failed build keeps the old preview; no recipe;
  the limit; a merged pull request is removed with its image, ref and
  directory; GitHub down removes nothing; under the floor nothing is built and
  removal still runs; the comment is written once per state.
- `test/preview_test.sh`, sweep: a container whose pull request is merged is
  removed; one that is open is kept; an unanswered call keeps; an image with
  no container is removed; a label of another repository is removed.
- `test/edge_test.sh`: the router's Caddyfile passes `caddy validate` when
  caddy is there, and is checked by pattern when not: digits only, noindex on
  both kinds of name, no domain in the file.
- `test/protolab_test.sh`: links with and without a domain; addresses in
  `protolab.json`.
- `test/install_test.sh`, `test/update_test.sh`: the renamed files and the
  `edge` follow-up.
- A case for `tehasbot health`: `checks.disk`, and `warn` when low.

### The page on publishing: `host/docs/edge.md`

A new page, "Previews and the Protolab on the internet", linked from the
layout's menu, `llms.txt` and the sitemap. It is the record of the steps taken
for the tehas-tehas instance, written so that another instance can follow
them. It says the steps were done on Ubuntu 26.04 LTS with Caddy 2.11 as a
system service, and what is and is not proven.

1. What is needed: a domain on Cloudflare with a proxied wildcard record, and
   a proxy in front of the host that reaches its private address.
2. Why the names are one level deep: how to see that a name resolves and that
   its certificate does not reach two levels, with the `dig` and `curl` lines.
3. Why the proxy needs a certificate of its own: status 525 and what it means.
4. Making the origin certificate in Cloudflare: where it is, which host names,
   that the private key is shown once, and the encryption mode it needs.
5. Putting the two files on the proxy's machine: the directory, the owner and
   the modes, and the two checks, with `openssl` and as the `caddy` user.
6. The site in the Caddyfile, with the reason for the matcher.
7. `caddy validate`, then `reload`. A warning box: files first, never
   `restart`, and what happened when the order was the other way round. How to
   get back: take the site out, validate, start.
8. The answers to expect, as a table: 200, 301, 502 before the router is
   installed, 404 for other names. What each one tells you.
9. The settings in `instance.env`, installing the router with `install.sh`,
   and enabling the three timers.
10. Checking a preview end to end, and where to look when one is not there
    (a link to Troubleshooting).
11. Limits: the origin certificate is trusted by Cloudflare only; a preview is
    public; the names share a site with the dashboard.

The private address of the host is written as a placeholder on this page, as
everywhere in the repository.

## Not in this

- A database copy per preview. `TEHAS_CLONES` stays refused.
- Previews of a fork's pull request, by label or otherwise.
- A preview that is woken by a request and stopped when idle.
- Pruning Docker's build cache. The sandbox image's layers are in it.
- Stopping a cycle on a full disk.
