# Spec: plugins v2

**Status**: Draft 2026-11-21. Builds on the v1 spec, `2026-11-21-plugins.md`
and its parts, which are not built yet either. Nothing here is built, and no
code of v2 starts before v1's run, socket, gate and hook have merged and run
on a host. Owner's decisions: the second plugin is
[tehas-app/tehas-plugin-mattpocock-skills](https://github.com/tehas-app/tehas-plugin-mattpocock-skills),
a chat interview that turns a rough ticket into a specification; a skill a
person has read and granted is instructions, not untrusted text; plugin
skills reach the chats only, never a cycle; the specifications a chat shapes
are kept in industry; v1, v2 and v3 ship in one release with no
compatibility between them, under one manifest version. v2 is what the
second plugin needs, built to be pleasant to use, and what the third
plugin's spec (`2026-11-21-plugins-v3.md`) builds on: more views, services,
fetches through tehas, and inspection. The rest of the handover waits for a
plugin that needs it (see "Later").

## Purpose

v1 lets a plugin show a view, read the code, call the model and report on a
pull request. v2 lets a plugin help in the factory's chats, with skills that
steer how a chat works with a person and tools a chat can call, and gives a
plugin more room: several views in a menu of their own, a server of its
own, fetches from granted origins, and one check on everything that
crosses. It never makes a v1 rule weaker.

## The rules v2 keeps

Every v1 guarantee holds as written. In addition:

1. **A surface is a capability.** Each new surface is a new row in the
   capability table below, a branch of the one pure function that makes a
   run's container, and its own argument list in `test/fixtures/argv/`.
   Adding one never loosens one that is there.
2. **Grants name the commit**, as in v1.
3. **A refused plugin is skipped**, never fatal to `tehas update`.
4. **Nothing a plugin wrote is a command to tehas.** A verdict, a tool's
   answer and a skill's text are data that tehas checks against a schema.
5. **Nothing of a plugin reaches a cycle's agents.** Not a skill, not a
   tool, not a comment. A cycle reads the filed issue's title and text, as
   today.
6. **The person presses.** Nothing a plugin shaped is written anywhere
   until the person presses the host's button for it, on a card that shows
   the whole text.

## What v2 ships

| Surface | Capability | Part |
| --- | --- | --- |
| Skills in chats | `skill:<id>` | chats |
| Tools in chats | `tool:<id>` | chats |
| A plugin that is text alone | no `build` in the manifest | this file |
| A menu section and more views | `menu`, `view:<id>` | menu |
| A plugin with a server | `serve`, with `kind: "service"` | menu |
| Fetches from granted origins | `net:<id>=<origin>` | outside |
| One check, holds | no capability: every plugin's crossings | inspection |

Each part says what each capability gives and what a person should
weigh, in the shape of the v1 security part's table. `tehas plugin review`
prints the same text.

## Settings

Unchanged from v1 but for these:

| Setting | Rule |
| --- | --- |
| `TEHAS_PLUGIN_GRANTS_<NAME>` | Takes the capabilities above |
| `TEHAS_PLUGIN_INSPECT` | `on` or `off`, default `off`: whether crossings leave rows (inspection part). The check and holds work either way |
| `TEHAS_PLUGIN_SKILLS_MAX` | Bytes of granted skill text across all plugins, 0 to 32768, default 8192 (chats part) |

## The manifest

One version, `"plugin": 1`, holds every field of v1, v2 and v3: they ship
together, so there is no older reader to stay compatible with. The fields v2
adds:

| Field | Rule | Part |
| --- | --- | --- |
| `kind` | `batch` or `service` | menu |
| `build` | Optional. With none, the plugin has no image and no runs: only text, such as skills. A manifest with no `build` that asks for a capability needing a run (`product`, `model`, `view`, `action:`, `hook:`, `gate:`, `tool:`, `net:`) is refused | this file |
| `timeout` | Required only with `build` | this file |
| `skills` | At most 8, each `id`, `about`, `path`, `chats` | chats |
| `tools` | At most 8, each `id`, `about`, `params`, `timeout`, `chats`. Needs `build` | chats |
| `views` | Replaces `view`. At most 4, each `id`, `label`, `path`, `open` | menu |
| `port`, `health` | With `kind: "service"` | menu |
| `net` | At most 4 origins, each `id`, `origin`, `paths`, `run` | outside |

`api/plugin-manifest.schema.json` takes the new fields, and the samples
gain one per new surface.

## Commands

| Command | What it does | Exits |
| --- | --- | --- |
| `tehas plugin skills [--chat <host>] [--json]` | The granted skills and tools of every ready plugin, for one chat host or all | 0; 78 off |
| `tehas plugin skill <name> <id>` | Prints a granted skill's text | 0; 3 not granted or not ready; 64; 78 |
| `tehas plugin call <name> <tool> --args-file <f> [--login <l>] [--json]` | Runs a granted tool once and prints its answer | 0; 1 the tool failed; 3 not granted, held or busy; 4 timed out; 64; 78 |
| `tehas plugin hold <name> [--reason <text>] [--by industry]` | Holds a plugin: nothing of it crosses | 0; 64; 78 |
| `tehas plugin release <name> [--by industry]` | Takes away a hold made by the same party | 0; 3 not held, or held by the other party; 64; 78 |
| `tehas plugin crossings [<name>] [--since <t>] [--json]` | Kept crossing rows | 0; 3 inspection off; 64; 78 |

`tehas plugin review` prints, in v2, the full text of every skill the
manifest names, so the person who writes the grant has read what it grants.

## The second plugin: tehas-plugin-mattpocock-skills

**What it is for.** A person writes a rough ticket in Obeya's chat or in
industry's wizard, and the chat interviews them until the ticket is a good
specification for a cycle: the problem, the solution, user stories, the seams
it is tested at, and what is out of scope. The plugin brings the method; the
chat host brings the person and the ticket.

**What it holds.**

- Skills adapted from [mattpocock/skills](https://github.com/mattpocock/skills)
  at a named upstream commit, with its MIT licence and a `NOTICE` that names
  the upstream and says the plugin is not affiliated with its author. The
  repository is Apache-2.0 and public.
- The adaptation is in the repository, with the upstream text beside it, so a
  reviewer sees each change. Upstream skills name a harness's Skill tool,
  sub-agents, `/setup-matt-pocock-skills` and publishing to an issue tracker.
  The adapted text names none of these: in a chat, the host's own proposal
  tool is the only way a draft leaves the turn.
- No tools, no model, no view, no `product`, and no `build`: the plugin has
  no image and never runs. tehas reads the skill files from the pinned
  commit, so no code of the plugin runs on the host at all.
- The skills fit the hosts' own steps: the interview is the wizard's "Shape"
  step, the specification its "Draft" step, inside the hosts' rules (one
  question at a time, buttons through `offer_choices`, a body ending in
  `## Acceptance criteria`, only the person files).

**The skills.**

| Id | From upstream | What it does in a chat |
| --- | --- | --- |
| `grill` | `productivity/grilling` | Interviews the person one question at a time, each with a recommended answer to press, looking up facts itself, until no decision is left assumed |
| `spec` | `engineering/to-spec` | Writes the agreed ticket as a specification: problem, solution, who it is for, decisions, out of scope, what to check in the code, acceptance criteria |
| `slice` | `engineering/to-tickets` | Splits an idea too big for one piece of work into pieces that each work end to end, each naming what it needs |
| `brief` | `engineering/triage`, `AGENT-BRIEF.md` | Checks a ticket against what a cycle needs to start, and says what is missing |

**Its manifest.**

```json
{
  "plugin": 1,
  "name": "specs",
  "label": "Spec interview",
  "license": "Apache-2.0 AND MIT",
  "asks": ["skill:grill", "skill:spec", "skill:slice", "skill:brief"],
  "skills": [
    {"id": "grill", "about": "Interview the person until the ticket has no open decision", "path": "skills/grill.md", "chats": ["obeya", "wizard"]},
    {"id": "spec", "about": "Write the agreed ticket as a specification", "path": "skills/spec.md", "chats": ["obeya", "wizard"]},
    {"id": "slice", "about": "Split a large specification into tickets that each fit one piece of work", "path": "skills/slice.md", "chats": ["obeya", "wizard"]},
    {"id": "brief", "about": "Say what a ticket lacks before the factory can build it", "path": "skills/brief.md", "chats": ["obeya", "wizard", "assistant"]}
  ]
}
```

The plugin's name in `TEHAS_PLUGINS` is `specs`: v1's names are at most 12
characters. The repository's name is free.

**The flow**, which the chats part walks through as the person sees it:
interview one question at a time with a recommended answer to press, read
the decisions back, check the ticket as a builder would read it, split it if
it is big, draft it as a card, and the person files it. Every version of the
draft is kept in industry with the skills that shaped it.

**What it proves.** That a skill, granted after its text was read, steers a
chat; that a draft it shaped reaches a ticket only through the host's
proposal, shown whole with the plugin's label; that the specs a chat shapes
are kept, versioned, where the person finds them again; that a plugin can be
text alone, with no image; and that a plugin may carry another licence's
text.

**Its own tests.** The repository checks each adapted skill names none of the
words above, stays under 2 KiB, and keeps the upstream commit and licence
beside it.


## Open points

1. Whether 2 KiB per skill and 8 KiB in all hold the interview's method
   without losing what makes it work. The plugin's first step answers it
   (Work 1).
2. How a person in the wizard picks a skill: by name, or the model picks from
   the list of `about` lines. The chats part allows both and leaves the choice
   to each host.
3. Whether the hosts should show the person which plugin shapes a chat
   before the first question, or only on the card. The chats part has the
   card; a line under the chat's title is each host's choice.

## Later

The handover, `docs/plans/2026-11-21-plugins-v2.md`, lists more surfaces
and what the reviews found about each. They wait until a plugin needs one,
so each is designed against a real use. Each stays refused by name, as v1
refuses them. What the code checks of this spec corrected in the handover:

- **Gates.** The seam is right (`console/cycle/src/supervise.rs:473-490`).
  The awaiting-merge arm is `report.rs:1552-1571`; the spec-block park reads
  the store's approval, not a file, and the file pattern to follow is
  `Facts::file` (`console/cycle/src/facts.rs:226-230`). The handoff
  allowance is `HANDOFF_SECONDS` in `console/core/src/sandbox.rs:72` and the
  deadline is made in `console/cycle/src/prepare.rs:166-168`, not in
  `work.rs`. Freeze and thaw are `freeze.rs`, not `clock.rs`. A refresh is a
  work cycle (`prepare.rs:527-542`), so a refresh point is a work point with
  `how = "refresh"`. The 40-character park reason is checked in
  `console/store/src/cycle.rs:233`. When the seam's code is scheduled is the
  owner's call: it changes the cycle's deadline and what the report reads.
- **Secrets and factory data.** MCP keys are environment variables read at
  start (`console/mcp/src/main.rs:43`), so a plugin key needs the key file
  the handover names.
- **The model queue, named models, `model` in hooks.** As the handover says.

## Work

In order, after v1's Work 2 to 6 have merged. Each is a pull request; a
security change says so.

1. **The skills, by hand.** In `tehas-plugin-mattpocock-skills`: the adapted
   skills, pasted into a chat on the factory's model with the host's own
   prompt, no tehas changes. It decides the sizes in open point 1 and is the
   first look at whether the interview is a pleasure to use.
2. **Manifest 2 and skills.** The manifest's second version, an optional
   `build`, `skill:` read from the pinned commit, `tehas plugin skills` and
   `skill`, `review` printing the text. Security change.
3. **Skills in the chats, and specs kept.** In tehas-industry: the wizard's
   `draft_versions` and what shaped each, the route that keeps Obeya's
   drafts, the skill section in the wizard and assistant. In tehas-obeya:
   the skill section, its prompt cap, the "Shaped with" card, sending drafts
   to industry.
4. **Tools.** `tool:`, `tehas plugin call`, the call's container and its
   argument list. Security change.
5. **Inspection and holds.** `inspect`, `hold`, `release`, the crossings
   database. Security change.
6. **Menu and views.** `live/plugins.json`, the menu section, `views`.
7. **Outside.** `fetch.rs`, `/_proxy/`, the run's socket. Security change.
8. **Services.** `serve`, the service unit and its network, the gate's
   proxy. Security change.
9. **The manual.** `host/docs/plugins.md`, `features.md`, the changelog
