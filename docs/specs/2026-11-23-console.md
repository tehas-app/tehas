# Spec: the console

**Status**: Draft 2026-11-23. For tehas 2.1, filed after the trio's 2.0
tag. Nothing is built. It uses 2.0's names and layout throughout.

The console is a person's own `tehas dev` session on the factory's host,
opened from Obeya and held by tehas while no browser is attached. This
file is the tehas feature: the holder, the purge, tombstones, the limit,
who may open one, the gate's way to the host and the commands. It is the
open point "The console's feature spec" of the plugin specification's
revision 1.6.0 (`2026-11-22-plugins-1.6.md`), which must be in
`docs/specs/` before that revision's Work 4.

What is not here, and where it is:

| Part | Where |
| --- | --- |
| The view: the terminal, its tabs, End, what it refuses of agent output | The plugin, `tehas-app/tehas-plugin-console`, `docs/spec.md` |
| The `full` view framed by Obeya, `TEHAS_PLUGIN_FRAMERS` | Plugin specification 1.6.0, part 1 |
| The gate's route `/_console/<id>`: the upgrade, its checks, the frames, the bounds | Plugin specification 1.6.0, part 2 |
| The Console button, the modal, Pin, Hide, the pinned row | tehas-obeya, prototype first |
| The route that tells Obeya who may open a console, and the settings push | tehas-industry |

## Why a feature and not a plugin

Every plugin is code in its own container, with no network, that never
reaches the host. The plugin rules give no plugin, in any version, a host
shell, an SSH key, the Docker socket, the host's network or a host path.
A console is an agent session on the host. So it is a tehas feature,
switched on in tehas's settings, and the plugin supplies only the page
that draws the terminal. tehas starts, holds, limits and ends consoles,
decides who may open one, and joins a browser to one through one route of
its gate. Nothing else starts or reaches a console.

## Terms

| Term | Meaning |
| --- | --- |
| console | One person's long-lived `tehas dev` session on a factory's host, held by tehas |
| name | A console's name: `gh-<login>`, or `gh-<login>-<n>` for the n-th, the login in lower case |
| holder | `tehas-console.service`, which keeps each console's tmux server while no browser is attached |
| attach | One browser's connection to a console, through the gate and SSH. A console has at most one at a time |
| tombstone | A console put away whole into one file, to resume later |

## What a console is

A console is `tehas dev <name> --author "<login> <noreply>"`, run detached,
with three things tehas adds:

1. **Named after the person.** The clone is `$TEHAS_HOME/dev/gh-<login>`,
   made fresh from the product checkout when the console starts. Unlike a
   `tehas dev` clone, which is never removed, a console's clone is purged
   when it ends. The `gh-` prefix keeps consoles apart from the clones of
   host accounts that type `tehas dev` themselves. Those are never touched.
2. **The person on the commits.** `--author` names the login and its GitHub
   no-reply address, stored beside the clone as `gh-<login>.author`. The
   push and the pull request stay the bot's, as in every `tehas dev`.
3. **Detached.** It runs in the holder's tmux session, not in the
   terminal that started it. `tehas dev` gains `--detach`, which runs the
   same container with `docker run -it` inside the console's tmux window
   instead of the caller's terminal.

Everything else is `tehas dev`'s, unchanged: the sandbox image, the
cycle's limits in `tehas.slice`, the egress limit when `TEHAS_EGRESS` is on,
the model keys by name, the narrowed bot token, the clone's lock at
`state/dev/<name>.lock`, and `<name>.state` with the person's memory, Pi
sessions, transcripts, code index and build output.

**Hard rule 4.** The console's container is `tehas dev`'s, which is a
cycle's container with a terminal: the same image, limits, mounts and
variables, pinned by `test/dev_test.sh` and `test/fixtures/argv/dev.1`. The
console adds no mount and no variable. `--detach` changes where the
terminal is, not what the container is given, and its argument list is
pinned beside `dev.1` as `console.1`, identical to it. The tmux servers,
the gate's SSH key and the tombstones are on the host and never mounted
into any container.

### Its terminals

Each console has a tmux server of its own, `tmux -L tehas-console-<name>`,
with its socket in `$TEHAS_HOME/console/run/`, a directory of mode 0700. One
server holds one session, `<name>`, so nothing a client of one console's
server does reaches another person's. The holder starts each server with
`prefix None`, every key of the root table unbound, no command prompt
bound, `set-clipboard off`, `allow-passthrough off` and `remain-on-exit on`.

| Window | Runs |
| --- | --- |
| `pi` | `tehas dev gh-<login> --detach --author "..."`: Pi with pi-rukas |
| `shell` | `docker exec -it tehas-dev-gh-<login> bash`, in the same container, started when the person asks for it |

The person moves between the two with the view's tabs (the `window` frame
of 1.6.0 part 2), never with tmux keys, so every key reaches the program.

**No host shell, ever.** Neither window runs a shell on the host. A
window's command is a tehas program, never `sh -c` and never a login shell,
and nothing `exec`s a shell when it ends. When `tehas dev` exits in the
`pi` window, tmux keeps the window, and the holder runs
`tehas console stopped <name>` in it. That program draws "Pi has stopped."
with Start Pi and End, reads only those two keys, and exits into nothing
else. The `shell` window's shell is in the sandbox container. A test kills
`tehas dev` in the `pi` window and checks that no shell process is left in
the console's tmux server.

### Its life

| Event | What happens |
| --- | --- |
| Open, none running | tehas starts the console and attaches |
| Open, one running | tehas attaches to it. The screen as it is now, and 10,000 lines of scrollback |
| Open, a purge not finished | Refused: "The last console is still being cleared." A console never starts on what an earlier one left |
| Open, a tombstone waiting | tehas resumes the console from it and attaches |
| The browser closes, sleeps or loses the network | The attach ends. The console runs on |
| A second browser opens it | The second attach takes over. The first is told "Opened in another window" and stops drawing |
| End | The console ends and is purged |
| Pi exits | The console does not end. The `pi` window runs `tehas console stopped` |
| The login is taken off the list | The attach ends at once. The console ends and is purged at the next `tehas update` |
| `tehas update`, or a planned stop of the holder | Each console is tombstoned first, and resumes on the person's next Open |
| The host stops without warning | Consoles end. Each is purged when the holder starts again, before any Open is answered |
| The factory is paused, drained or read only | Running consoles keep running. A new one does not start, and Open says why |

A console counts in admission by room for as long as it runs, as a
`tehas dev` session does. Before it starts, Open shows how many more
cycles the slice has room for, as `tehas dev` prints it.

## Purged when it ends

A console that ends, for any reason, leaves nothing of itself on the host.
"Ends" is End, a login taken off the list, the feature switched off, a host
that stopped without warning, or a tombstone past its days. A closed
browser, a hidden modal or a tombstone is not an end.

| What | Where |
| --- | --- |
| The tmux server, its scrollback and both windows | The holder |
| The container and its `/tmp` | `docker kill`, then `docker rm`, of `tehas-dev-gh-<login>` |
| The clone, with any uncommitted or unpushed work | `$TEHAS_HOME/dev/gh-<login>` |
| The author file | `$TEHAS_HOME/dev/gh-<login>.author` |
| The state: memory, Pi sessions, transcripts, the code index, the build output | `$TEHAS_HOME/dev/gh-<login>.state` |
| The issue's images, if any | `$TEHAS_HOME/dev/gh-<login>.images` |
| The clone's lock | `state/dev/gh-<login>.lock` |
| A tombstone and its manifest, if any | `$TEHAS_HOME/console/tombstones/gh-<login>.tar.zst` and `.json` |

- **One place decides the paths.** A pure function in
  `console/core/src/console/purge.rs` gives the list from the console's
  name, and a test pins it. The purge removes only those paths, follows no
  symlink, and refuses any path not under `$TEHAS_HOME/dev/gh-`,
  `state/dev/gh-` or `$TEHAS_HOME/console/tombstones/gh-`. It never names a
  host account's clone.
- **It holds the clone's lock** while it runs, the lock `tehasbot clean`
  asks for, so nothing else writes there meanwhile.
- **Fails closed.** A purge that cannot finish marks the console
  `purge-failed`, says why in `tehas console`, and refuses a new console
  for that login until it is done. The holder's start and `tehasbot clean`
  try it again. A login is never handed a clone a purge did not finish.
- **After a restart.** The holder's start runs `tehas console sweep`: every
  `gh-*` clone and state with no running console is purged before the gate
  answers an Open.
- **What is not the console's.** What the person pushed is on the product's
  branches and pull requests, as the bot's, and stays there. The purge
  never calls GitHub.
- **What stays.** One row per console in `console_sessions`, with counts
  only, and sshd's own log of each attach.

**What End would lose.** Before End, the view asks (the `lost` frame of
1.6.0 part 2). tehas counts uncommitted files and commits on no remote
branch by running git inside the console's container, never on the host:
agents have written the clone, its hooks and its git configuration, so the
host runs no git there, as `tehas dev` already says.

## Tombstones

A tombstone is a console put away whole: stopped, packed into one
compressed file, and resumed later as it was. It is not an end, so nothing
is purged. Its use is a planned stop: `tehas update`, a restart of the
holder, and `tehas console tombstone <name>` for the operator.

| Kept | Not kept |
| --- | --- |
| The clone with its `.git`, uncommitted files and unpushed commits | Running processes: Pi's turn in flight, the shell, anything started in either |
| The author file | The container's `/tmp` |
| The state: memory, Pi sessions, transcripts, the code index | The build output, `.state/target`: it is rebuilt and is most of the size |
| The issue's images | The scrollback. Pi shows its own conversation again when it resumes |

**Putting away**, by `tehas console tombstone`, which `tehas update` and
the holder's stop call for each running console:

1. An attached view is told "The factory is updating. Your console is saved
   and comes back when you open it again." and keys stop.
2. `docker stop` with 30 seconds' grace, so Pi writes its session and
   pi-rukas its work state, then `docker rm`. The tmux server ends.
3. tehas packs the kept paths into
   `$TEHAS_HOME/console/tombstones/gh-<login>.tar.zst.part`, mode 0600 in a
   directory of 0700, zstd level 3 on all cores, holding the clone's lock.
4. It reads the file back, checks its sha256 against what it wrote, and
   writes `gh-<login>.json` beside it:
   `{"tombstone": 1, "name", "login", "made", "tehas", "head", "bytes", "sha256"}`,
   with a schema in `api/console-tombstone.schema.json`. Only then is
   `.part` renamed and the console's files removed, through the purge's
   list of paths.
5. A tombstone that fails leaves the console's files where they were, in
   the state `tombstone-failed`, and the update goes on. Open then starts
   the console from those files. Work is never removed before a checked
   tombstone holds it.

**Resuming**, on the person's next Open, never on its own, so an update does
not start every console at once and take the cycles' room:

1. Before anything is unpacked, tehas checks the manifest, that the login is
   on the list now and is the gate's sign-in, and the file's sha256,
   holding the clone's lock. A failed check unpacks nothing.
2. It unpacks with tehas's own tar reader: regular files, directories and
   symlinks only; no absolute name, no `..`, no link that leads outside the
   console's paths, no device, fifo or hard link outside the archive, and
   every path under the console's own names. Anything else refuses the
   tombstone and keeps it for the operator, with the reason in
   `tehas console`.
3. It starts the console as a new one on those files.
4. It removes the tombstone and its manifest.

**Bounds.**

- A tombstone is sensitive: product code, uncommitted work and Pi's
  sessions. It is never mounted into a container and never read by the
  gate. Only the resume opens it.
- `TOMBSTONE_MAX_GIB`, 8, a constant: the most one tombstone may be,
  compressed. The pack stops at it, and the console is left as in step 5.
- `TOMBSTONE_KEEP_DAYS`, 30, a constant: `tehasbot clean` purges a
  tombstone older than that.
- A tombstone counts toward the person's limit. End on it purges it
  without resuming. So does a login taken off the list.
- `tehas disk` counts tombstones. A tombstone that would leave the disk
  under `TEHAS_CLEAN_MIN_FREE` is not made; the console is left as in
  step 5.
- **The update's hook.** `tehas update` is Rust in `console/ops/src/update/`.
  Where it calls `tehas console tombstone`, before it stops the units, is
  agreed with the update's owner before Work 5 is built.

## The limit per person

```rust
/// The most consoles one person may have on this factory.
/// A constant now; `TEHAS_CONSOLE_MAX` replaces it later.
pub const CONSOLES_PER_PERSON: u32 = 1;

/// Whether `login` may start one more console, given those running.
pub fn may_start(running: &[Console], login: &str, limit: u32) -> Admit
```

- `may_start` is pure, in `console/core/src/console/limit.rs`: no clock,
  network or files. It answers `Start`, or `Full { running }`. Open with
  `Full` attaches to the person's console instead of starting another.
- The names are a pure function beside it: `gh-<login>` for the first,
  `gh-<login>-<n>` after. The names, the lock and the view's list are built
  for several from the start, so a limit above 1 changes the constant and
  no other code. Every test runs with limits 1 and 3.
- `TEHAS_CONSOLE_MAX` is reserved: the settings load refuses it with
  "reserved for a later version" (78) until it ships.

## Who may open one

The feature `console` is a row of `console/core/src/features.rs`, stage
`building`, switch `TEHAS_CONSOLE` (`on`, `off`, `1`, `0`; default `off`),
with the settings `TEHAS_CONSOLE_LOGINS` and `TEHAS_CONSOLE_VIEW`. It needs
the feature `plugins`, since its view is a plugin's. Its program is the
holder; its unit `tehas-console.service`.

| Setting | Rule | When missing |
| --- | --- | --- |
| `TEHAS_CONSOLE` | on/off | `off`: no console, the route is 404, the button is not drawn |
| `TEHAS_CONSOLE_LOGINS` | Space-separated GitHub logins: `A-Z`, `a-z`, `0-9`, `-`, 1 to 39 characters, no `-` first or last, no `--`. Compared without case. Unique. At most 32 | No one may open a console |
| `TEHAS_CONSOLE_VIEW` | A plugin's name, as `TEHAS_PLUGINS` names it | `console` |
| `TEHAS_CONSOLE_MAX` | Reserved | Refused with 78 when set |

Each row goes into `api/settings-rules.json` with `"building": true`. A
malformed value is 78 at the settings load, as for every setting.

- **The sign-in comes first.** The person signs in to the gate as for every
  plugin address, with `TEHAS_PLUGIN_ACCESS`. The list narrows that; it
  never lets in someone the sign-in would not.
- **The login is the gate's,** from its GitHub sign-in, never from the page.
  It is checked against the list on every attach and reconnect, not only at
  the start.
- **When the list changes.** At the next `tehas update`, which restarts the
  gate: every console socket whose login is off the list closes, and
  `attach-from-gate` refuses its reattach. The console is then ended and
  purged.
- **Never public.** The list is in `instance.env`, never in `live/`, the
  host bridge or an event.

What a person should weigh before adding a login: the console runs code in
the sandbox with the bot's narrowed token, the model keys by name and the
sandbox's network. Whoever is on the list can push branches and open pull
requests as the bot, and spend model time outside the plugin budget. It is
the access a host account in the group `tehas` has through `tehas dev`.

## The gate to the host: SSH

The gate reaches a console over SSH to the host's own sshd on `127.0.0.1`,
as the tehas user, with a key that can do one thing.

- **The key.** `tehas setup`, and `tehas update` on a host that has none,
  makes an Ed25519 key for the gate, `~/.ssh/tehas-console/gate_ed25519`,
  mode 0600 in a directory of 0700. It is outside `~/.config/tehas` and
  `$TEHAS_HOME`, read only by the gate, and never mounted into any
  container. Its public half goes into the tehas user's `authorized_keys`
  as
  `restrict,pty,from="127.0.0.1,::1",command="tehas console attach-from-gate" ssh-ed25519 ...`.
  `restrict` takes away forwarding, agents and X11; `pty` gives a terminal;
  `from` keeps the key to the host itself.
- **The host key** of sshd is pinned in `~/.ssh/tehas-console/known_hosts`
  when the key is made. The gate refuses any other.
- **The forced command.** The gate passes the login and the console's name,
  and nothing else, in `SSH_ORIGINAL_COMMAND`, as `<login> <name>`.
  `tehas console attach-from-gate` checks the login's form, that it is on
  `TEHAS_CONSOLE_LOGINS` now, that the name is one the login's limit allows
  and that it runs. Only then does it run
  `tmux -L tehas-console-<name> attach -t <name>`. Any other word, a second
  argument, a shell character or a name not the login's exits 3 with no
  output: the command worked and the answer is no. It never starts a
  console, runs a shell or passes anything to one.
- **Starting** is `tehas console start <login>`, which the gate calls as the
  tehas user, under the same checks.
- No key, agent or token is ever in a page, a log or a command line.
- A host with no sshd, or where the key cannot be written: `tehas update`
  says why and leaves the feature off, and the button is not drawn.

**Why SSH, when the gate is on the same host.** The gate could run
`tmux attach` under a pty itself. SSH gives two things that path does not:
sshd's own record of each attach, outside tehas, and the forced command as
a second check that does not trust the gate process. A gate that is taken
over still reaches only `attach-from-gate`, which checks the list and the
name again.

## What is kept

Counts, not content. A table `console_sessions` in the state store, added
by a migration after 2.0's schema 29: the login, the console's name, the
start, the end, how it ended (`end`, `pi-exit`, `host`, `removed`,
`tombstone`), the attaches, the bytes in and out, and each tombstone and
resume with its time and size. Never a keystroke, a screen or scrollback.
Scrollback lives only in tmux's memory. The bash of `tehas console` never
writes SQL: the store's own verbs do, as for every table.

## The commands

All under `tehas console`, in Rust, in `console/ops/src/console/` with the
logic in `console/core/src/console/`. The bash ceiling does not rise.

| Command | Public | Does |
| --- | --- | --- |
| `tehas console [--json]` | yes | Lists the consoles: name, login, state (`running`, `stopped`, `tombstone`, `purge-failed`, `tombstone-failed`), started, last attach, and the reason of a failed state |
| `tehas console start <login>` | yes | Starts the login's console, or resumes its tombstone. The gate calls it on Open |
| `tehas console end <name>` | yes | Ends and purges a console or a tombstone |
| `tehas console tombstone <name>` | yes | Puts a running console away |
| `tehas console attach-from-gate` | internal | sshd's forced command, above |
| `tehas console stopped <name>` | internal | What the `pi` window runs after Pi exits |
| `tehas console sweep` | internal | The holder's start and `tehasbot clean`: purges what no running console owns |

`tehas console --json` prints `{"api": 1, "consoles": [...]}`, with a schema
and samples in `api/console.schema.json`. Industry reads it to tell Obeya
whether a person has a console and may open one. Each public row goes into
`api/commands.txt` with its exit table in the contract:

| Status | When |
| --- | --- |
| 0 | Done |
| 1 | A docker, tmux, file or store call failed; nothing was half removed |
| 3 | The answer is no: the limit is full, a purge is unfinished, the login is not on the list, the factory takes no new console |
| 64 | A bad argument |
| 78 | Settings missing or malformed, or the feature is off |

## Security changes

Each says so in its pull request.

- The holder: a host service that runs `tehas dev` sessions for people with
  no host account.
- The gate's SSH key and its `authorized_keys` line, and the forced command.
- The purge: it removes files on the host.
- Tombstones: product code and sessions packed on disk, and the tar reader
  that unpacks them.
- The route `/_console/<id>` (plugin specification 1.6.0, part 2).

## Work

After plugins are on in a release and 1.6.0's parts 1 and 2 are built.
Each step is a pull request, in this order.

1. **The limit and the names.** `console/core/src/console/limit.rs`:
   `CONSOLES_PER_PERSON`, `may_start`, the names, with tests at limits 1
   and 3.
2. **Settings and the feature.** The `console` row of `features.rs`; the
   four settings in `api/settings-rules.json` and their rules; tests for
   each rule.
3. **The holder.** `tehas dev --detach`; `tehas-console.service`;
   `tehas console`, `start`, `end`, `stopped`; `console_sessions` and its
   migration; `api/console.schema.json`; `test/fixtures/argv/console.1`,
   identical to `dev.1`. The test that no host shell is left. Security
   change.
4. **The purge.** `purge.rs`, the paths as a pure function with its test,
   the removal under the clone's lock, `purge-failed`, `tehas console sweep`
   at the holder's start and as a step of `tehasbot clean`
   (`console/ops/src/clean.rs`), and the counts End shows. Tests that a
   purge leaves no file of the console and never touches a host account's
   clone. Security change.
5. **Tombstones.** The kept paths as a pure function, the pack with its
   read-back, the manifest and its schema, the resume with tehas's tar
   reader and a case per kind of entry, the update's hook, the holder's
   stop, the age purge in `tehasbot clean`. Tests that a failed tombstone
   removes nothing and that a resumed console has every kept file.
   Security change.
6. **SSH.** The gate's key, its `authorized_keys` line and the pinned host
   key, in `tehas setup` and the update; `tehas console attach-from-gate`
   with a test for each refusal. Security change.
7. **The gate's route.** 1.6.0 part 2, against a stub sshd. Security change.
8. **Industry.** The route for Obeya and the settings push.
9. **Obeya.** The build of its prototype, replaying its scenario.
10. **On a host.** One login on the list. See a console start, survive a
    closed browser, come back with its screen, push a branch as the bot
    with the person as author, be tombstoned by an update and resume, and
    end. Write what was seen into `host/docs/features.md`, and the manual's
    page for the console.

## Open points

1. **Events.** Industry learns of a console's end to take Obeya's row out.
   T11's names would be `console.started` and `console.ended` (with `how`),
   on a new subject `console`, tehas's own. Neither may carry the login in
   a payload a plugin can be granted. Left until industry's route is
   designed; the route alone (a poll of `tehas console --json`) may be
   enough.
2. **Idle consoles.** A console runs until it is ended. Whether one ends
   after some days with no attach is left until consoles have run on a
   host. If so, it is a second constant beside the limit.
3. **Consoles across factories.** The limit is per factory. A limit across
   industry is industry's, later.
4. **Uploads.** Files from the browser into the clone are not in this
   version. The person uses git, or `--issue`.
5. **pi-durable.** Considered and not chosen for tombstones: it makes a
   conversation durable, not a clone, and Pi does not run on it. Worth
   another look if pi-rukas moves onto it.
