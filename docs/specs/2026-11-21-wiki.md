# Spec: the product wiki

**Status**: Draft 2026-11-21, with the owner's decisions the same day (see
"Decided"). Nothing is built.

## Purpose

A person or an agent new to a product reads the code to learn it, every time.
The commit history and the releases say why the code is the way it is, but
nobody reads 2,000 commits.

The factory builds a wiki of the product for them: interlinked Markdown pages
written and kept up by the model, from the code at the head of the default
branch, the version tags and the commit history. It follows the LLM wiki
pattern Andrej Karpathy described: raw sources that are never edited, a wiki
the model owns and updates page by page, and a schema file that tells the
model how the wiki is kept. Each build starts from the last one and changes
what the new commits touched, so knowledge piles up instead of being derived
again on every read.

The wiki has its own page on the factory's site, `/wiki`. It shows the wiki as
HTML, when it was built, from which commit and release, and how far it is
behind main. A button there asks for a new build, and a nightly timer builds
it once a day.

## Decided

1. A page of its own, `/wiki`, shows the wiki as HTML (owner, 2026-11-21).
2. The page has a refresh button and says when the wiki was last updated.
3. A nightly build keeps it current without anyone asking.
4. A build runs in the background. The button returns at once and the page
   links the new build when it is done.
5. The link to a build names its date and commit: `/wiki/2026-11-21-68ffab1d/`.
6. The page says how far the build is behind the current main: the number of
   commits and the age, in days, or in months once it is 60 days or more.
7. The main dashboard links the current build.
8. Spec first. The build follows in its own pull requests once this merges.
9. **Access is the dashboard's GitHub login.** No page of the dashboard, or
   of the pages around it, is for a visitor who has not signed in. The wiki
   and its button take the same login as every other page; tehas adds no
   sign-in of its own and no way around the one in front of it.
10. **A path under the dashboard's name**, `/wiki/`, not a name of its own.
11. **Slow and cheap on the host, no limit on the model.** The host's part
    runs on few cores at the lowest priority. The model gets no time or token
    cap for now. A build does not wait for the queue.
12. **No copy in the product's repository.** The wiki is built from the
    repository and kept in the factory. A sync to another repository may
    come later; not now.
13. **Freeform.** Beyond `index.md`, `log.md` and the schema, the model picks
    the pages.

## The guarantees

1. **Off by default.** `TEHAS_WIKI=on` in the instance turns it on. With it
   off, nothing is built, `/wiki` says the feature is off and the timer does
   nothing.
2. **The code is the truth.** The wiki is a reading aid. Every page names the
   commit it was last checked against, and the page says how far behind main
   that is. Nothing in tehas acts on the wiki's text: no gate, no dispatch
   decision, no prompt of a cycle reads it in this spec.
3. **The sandbox is not widened for cycles.** The build's model runs in a
   container of its own kind, made in `console/core/src/sandbox.rs` and
   pinned by an argument list in `test/fixtures/argv/`. It gets a read-only
   copy of the product at one commit, the raw sources, its own output
   directory and the model proxy. It gets no GitHub token, no push, no Docker
   socket, no SSH key and nothing from `~/.config/tehas`. Adding the kind is a
   security change, and its pull request says so.
4. **No write path on the site.** The docs server stays read-only. A refresh
   reaches the factory the way industry's other asks do: as a `tehas`
   command on the host (see "Asking for a build").
5. **Model text is untrusted.** The host renders the Markdown to HTML in Rust
   with raw HTML escaped, serves it with no script and a strict CSP, and
   checks every page before a build is published.
6. **A failed build changes nothing.** The current build stays current. The
   page says the build failed and why.
7. **No secrets.** A commit message or file that matches a credential pattern
   is left out of the raw sources whole, not redacted, and the log names the
   commit.
8. **Read-only instances work.** A build writes nothing to GitHub.

## Access

The site has no sign-in of its own. On a host that industry fronts, its
proxy signs a visitor in with GitHub and lets them through when their account
can read the product's repository (tehas-industry's
`docs/specs/2026-10-17-industry.md`, "Dashboards and the login"). The wiki is
under the dashboard's name, so that one check covers it.

- tehas serves `/wiki` and `/wiki/<id>/` like the rest of the dashboard and
  adds no route of its own that skips the proxy.
- The page's button is a link the host bridge gives
  ([the host bridge](/api#the-host-bridge)), to a page of the host site where
  the signed-in person confirms. With no host bridge there is no button; a
  person on the host runs `tehas wiki build`.
- A factory that industry marks public serves its dashboard, and so its wiki,
  without the login. Decision 9 says no page should be public, so that setting
  is industry's to change (see "Industry's part").

## What a build is made of

### The raw sources

The host collects them in Rust before the model runs, into
`~/tehas/wiki/<id>.raw/`, read-only to the container:

| File | What |
| --- | --- |
| `head.json` | The commit, its date, the latest tag it contains and the commits since that tag, as `git describe` reads it |
| `tags.json` | Every version tag: name, date, commit, commits since the tag before |
| `log.jsonl` | One line per commit since the last build (all of them on the first): hash, date, subject, body. No author email. Trailers are dropped |
| `changed.json` | The paths changed since the last build, and the pages whose `sources` name any of them |
| `changelog.md` | The product's `CHANGELOG.md` at the commit, where there is one |

The code itself is the read-only copy of the product at the commit, made the
way a cycle's clone is made from `~/tehas/repos/<product>`.

### The wiki

The model writes the build's directory, `~/tehas/wiki/<id>/`, which starts as
a copy of the current build. Three files are fixed; the rest is the model's:

| Page | What |
| --- | --- |
| `SCHEMA.md` | How this wiki is kept: front matter, naming, linking, what goes in `log.md`, and pages it may want (an overview, the architecture, a page per part, per concept, per decision, per release, a timeline, a glossary). tehas ships it in `host/wiki/SCHEMA.md`; a product may replace it with `.pi/wiki-schema.md` |
| `index.md` | Every page, with one line each. The model updates it on every build |
| `log.md` | Append-only, one entry per build: the date, the commit, the range read, the pages added, changed and removed |

Every page but `log.md` starts with front matter. `sources` is optional and
lets the next build find the pages a change touched:

```
---
title: The dispatcher
sources: [console/dispatch/]
verified_at: 68ffab1d
---
```

### The run

1. **Plan, on the host.** Read the head of the default branch, `H`, and the
   current build's commit, `B`. With `H` equal to `B` and no `--full`, stop:
   up to date. Else collect the raw sources for `B..H`. The first build, a
   `--full` build and a build where `B` is no longer an ancestor of `H` (a
   rewritten history) read the whole history.
2. **Write, in the container.** The model reads `SCHEMA.md`, the raw sources
   and the code, and updates what the change touched, `index.md` and
   `log.md`. On a full build it may touch every page. No time or token cap
   (decision 11); the analytics record the run as kind `wiki`.
3. **Check, on the host.** In Rust, each a pure function with tests: front
   matter is there and valid; every `verified_at` of a changed page is `H`;
   every link resolves; no page is an orphan; `index.md` lists every page and
   no other; `log.md` has exactly one new entry and the earlier ones are byte
   for byte as they were; no page passes a size cap; no secret pattern. A
   failure fails the build.
4. **Render, on the host.** Markdown to HTML with pulldown-cmark, raw HTML
   escaped, into the build directory beside the Markdown, with one fixed
   layout and stylesheet from `host/wiki/`. Links between pages point at
   the HTML.
5. **Publish.** Write to `<id>.new`, rename to `<id>`, point `current` at it,
   rewrite `live/wiki.json`. Keep the last ten builds and the last build of
   each release tag; remove the rest and their raw sources.

The build id is the date of the build and the first eight hex of `H`:
`2026-11-21-68ffab1d`. Two builds of one commit on one day are one build: the
second replaces the first.

### Room on the host

The unit, `tehas-wiki.service`, runs at `Nice=19`, `CPUWeight=idle` and
`IOSchedulingClass=idle`, and its container gets `TEHAS_WIKI_CPUS` CPUs
(the example instance says `1`), so cycles always come first. It does not
take a cycle slot and does not wait for the queue. It is one build at a time.
The model's calls go through the proxy like a cycle's and are not held back.

## The page

`/wiki` is a page of the factory's site, an island on `/live/wiki.json` like
the dashboard's sections:

```
Wiki                                                   [Refresh]
Built 2026-11-21 03:04 from 68ffab1d (v1.2.0-beta.2 +5)
5 commits and 2 days behind main (main is 7c1e09a2, 2026-11-23)
Next nightly build 2026-11-24 03:00

  Open the wiki: /wiki/2026-11-21-68ffab1d/

Earlier builds
  2026-11-20-0ce91d7e  v1.2.0-beta.2 +3   12 pages changed
  2026-11-19-...
```

- "Behind main" is the commits in `B..main` and the days between the commit
  dates of `B` and of main's head; 60 days or more is shown in months.
  Nothing behind reads "up to date with main".
- While a build runs, the page says "building since 03:00, asked by the
  nightly timer" (or "by <login>"), and links the current build. When it
  finishes, the page links the new one without a reload.
- A failed build shows its reason and when; the current build stays linked.
- The button shows only when the host bridge gives its link.
- With `TEHAS_WIKI` off, the page says so and has no button.

The current build itself is served under `/wiki/<id>/`: the rendered pages,
with `index.html` the wiki's index. Each page shows its own header line:
build id, `verified_at`, and the link back to `/wiki`.

The dashboard's top line gets one link, "wiki", to the current build, with the
build id as its title. It is hidden when there is no build.

### live/wiki.json

Written by the build and by the status pass, read by the page, the dashboard
and `tehas status --json` (`wiki`), and named in "Files under live/":

```json
{
  "enabled": true,
  "state": "idle",
  "current": {
    "id": "2026-11-21-68ffab1d",
    "commit": "68ffab1d...",
    "commitDate": "2026-11-21T15:31:53+02:00",
    "describe": "v1.2.0-beta.2-5-g68ffab1d",
    "builtAt": "2026-11-21T03:04:10Z",
    "pages": 41,
    "url": "/wiki/2026-11-21-68ffab1d/"
  },
  "main": { "commit": "7c1e09a2...", "commitDate": "2026-11-23T10:12:00+02:00" },
  "behind": { "commits": 5, "days": 2 },
  "running": null,
  "asked": null,
  "next": "2026-11-24T03:00:00+02:00",
  "lastFailure": null,
  "builds": [ { "id": "...", "describe": "...", "changed": 12 } ]
}
```

`state` is `off`, `idle`, `asked` or `building`. The status pass reads the
product checkout the dispatcher keeps fast-forwarded and runs no model, so
`behind` stays true between builds. It runs every five minutes.

## Asking for a build

Three ways, one queue:

| Who | How |
| --- | --- |
| The nightly timer | `tehas-wiki.timer`, at `TEHAS_WIKI_AT` (instance setting, example `03:00`) |
| A person on the host | `tehas wiki build [--full] [--json]`; `tehas wiki` prints the state, `--json` the object above |
| A person on the page | The button, through the host site, which runs `tehas wiki build --by <login> --json` on the host |

`tehas wiki build` writes the ask, `~/tehas/state/wiki/ask`, with when and
who, and returns at once. A path unit, `tehas-wiki.path`, starts the build.
An ask while a build runs is kept as one ask for after it. An ask when main
has not moved since the current build answers `"upToDate": true` and starts
nothing, unless it is `--full`.

Like `tehas start`, the command runs as the factory's user and is trusted as
the host. `--by` is a name for the record and the page, not a check: the host
site has already checked the person.

## Industry's part

Not built by this spec, and specified in tehas-industry:

- The bridge's answer gains `wiki.refresh`, the link the button opens, for a
  factory with `wiki` in its `features`.
- The host site's page for it: the signed-in person, who can read the
  repository, confirms with a POST under the host site's session and CSRF
  rules, and the workshop runs `tehas wiki build --by <login> --json` through
  the factory API.
- `public: true` gives way to decision 9: the dashboard, and so `/wiki`,
  takes the login on every factory.

## Order of work

1. **The page without a model.** The crate's pure rules, the status pass,
   `live/wiki.json`, the page, the dashboard link and the routes, proven with
   a build directory a test writes by hand. Tests: `behind` on fixture
   repositories (a straight line, a merge, a rewritten history, 59 and 60
   days), the id, retention, every check.
2. **The build.** The container kind, the collect, the run, the render, the
   nightly timer and `tehas wiki build`. Proven on the tehas-tehas instance
   on the tehas repository.
3. **The button.** `wiki.refresh` and the host site's page, in
   tehas-industry.
4. **Later, not in this spec.** A sync of the wiki to another repository; a
   search index of the wiki through vipune, in a store of its own, for
   agents; giving a cycle the wiki as hypotheses; sending generic lessons to
   yokoten. Each needs its own spec and a measure first.

## What vipune and yokoten teach

Both were read for this spec on 2026-11-21: vipune at its last commit of
2026-11-03, tehas-yokoten at 2026-11-19.

| Lesson | From | Here |
| --- | --- | --- |
| A derived index falls out of step without anyone seeing it | vipune's FTS index (#208), `doctor fts` | `index.md` is checked against the pages on every build |
| Two write paths drift apart | vipune #238, #258, #271 | One publish function writes a build; the button, the timer and the command only ask |
| A fallback hides a failure | vipune removed mock embeddings (#147) | A failed build fails; nothing is published half done |
| Supersede, do not delete | vipune's statuses, yokoten's `newer` pointer and tombstones | Builds stay addressable by id; `log.md` says what replaced what |
| Name provenance by pointers | yokoten names a commit by hash, never quotes | `verified_at` and `sources` on pages; the raw sources keep hashes, not authors |
| Idempotent asks | yokoten's `idem` key | One build per commit and day; an ask on an unmoved main starts nothing |
| Drop a secret whole, do not redact | vipune's hook extract | Guarantee 7 |
| Pin the project key, do not infer it | vipune #158, #199 (ssh and https remotes) | The product comes from the instance's `TEHAS_REPO`, never from a remote |
| Docs drift from code; "the code is the truth" | yokoten's 29,600 lines of specs and their "differences" sections; vipune #112, #129, #306 | Guarantee 2 and the "behind main" line |
| Knowledge that reaches cycles unchecked does harm | yokoten's dev-loop trial stops after 3 wrong records reach a merge | No cycle reads the wiki in this spec |
| A model reads a loose spec its own way | yokoten's handover: ask agents to list their readings | `SCHEMA.md` is the model's contract, and the checks hold it |
| Measure before building more | yokoten's horizontal expansion: "the machinery has the right shape, and it does not deliver yet" | Search and cycle use wait for a measure (step 4) |
| A wiki is not a yokoten kind | yokoten's rule "counts and facts, not content" refuses paths, versions and hashes | The wiki lives in tehas state. Yokoten may later receive generic lessons through `share` |
| Chunk before embedding | vipune's 512-token limit (#92) | For step 4: split pages by heading |
