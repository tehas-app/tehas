# Spec: a read-only MCP server for a factory

**Status**: Agreed with the owner 2026-10-20. Nothing is built.

## Purpose

Agents outside this project, such as Hermes or OpenClaw agents, want to ask a
factory how it is doing: is it working, what is in line, what finished, how
the last ten days went. Today the only way in for a program is a shell on the
factory machine (`tehas status --json` and the rest of [the factory
API](../../host/docs/api.md)). Giving an outside agent a shell gives it far
more than status.

This spec adds an MCP server that answers those questions over HTTPS, public
like the dashboard, behind a list of API keys.

## The rule this rests on

**The MCP server shows nothing that the factory's public site does not
already serve.** The baseline (the owner's call, 2026-10-20) is every file the
docs server publishes under `/live/` and at `/health`, whether or not a page
draws it: issue numbers, titles, links, stages, statuses, steps, times, counts,
the ten-day aggregates, and the running cycles' console as published (already
masked for tokens, passwords and private addresses). No issue bodies, no
comments, no code beyond what the console shows, no logs, no settings, nothing
from GitHub that those files do not hold. A factory may work on a private repository; this rule is what keeps
the MCP server safe for one.

It is enforced by construction, not by care:

1. **It reads only the published files.** Its only input is
   `~/tehas/live/`, mounted read-only, the same directory the docs server
   publishes at `/live/`. It never reads `~/tehas/state/`, `~/tehas/logs/`,
   the instance directory or `~/.config/tehas/`, and calls no GitHub, Docker,
   git or model endpoint. It cannot leak what it was never given.
2. **It names every field it returns.** Each tool copies an allowlist of keys
   from the files below and drops everything else, the way `tehasbot top`
   cuts `top.json` to the keys the pages draw. A key added to a live file
   later is not served until someone adds it here, with a test.
3. **The console as published, no more.** `running.json` carries each
   running cycle's console, the agents' commands and the start of each
   result, masked by `tehasbot` before it is written. The MCP server serves
   that masked text as it is and never reads the raw logs behind it.
4. **Read only.** There is no tool that changes anything. Pause, resume,
   limit, drain, labels and retries stay with a person on the host.

## Goals

1. An agent that supports MCP 2026-07-28, or 2025-11-25 (see Protocol), over Streamable HTTP can connect with
   a URL and a key and list and call the tools, with no other setup.
2. Status as fresh as the dashboard's: what the dispatcher's last poll wrote,
   with that poll's time.
3. Simple config: switched on and given keys in the host's environment, off by
   default.
4. Fails closed: switched on with no keys, or with a key that is too short, it
   does not start (exit 78), and a request with no key or a wrong key gets 401
   and nothing else.

## Non-goals

- Writing anything. A later version may add actions behind separate keys; not
  this one.
- OAuth, dynamic client registration or per-key scopes. Every key sees the
  same thing.
- MCP revisions before 2025-11-25.
- Plain REST. A REST view over the same handlers can come later if a caller
  needs it.
- MCP resources, prompts, subscriptions (`subscriptions/listen`), tasks,
  sampling, elicitation. Tools only.
- Data the dashboard does not have: issue bodies, per-issue labels other than
  the stage, cost or token totals per issue.

## Anti-goals

These would make it a failure even if it works:

- Any text from a private repository beyond what tehas.app shows.
- A key, a host name or a private address in a response, a log line or an
  error.
- A way for a caller to make the factory do anything, or to make the server
  read a path it chooses.
- The factory, the docs server or the dashboard depending on the MCP server.
  It can be down and nothing else notices.

## Protocol

MCP revision **2026-07-28**, final and current since 28 July 2026:
<https://modelcontextprotocol.io/specification/2026-07-28>, with its
[changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog).
Streamable HTTP, stateless:

- One endpoint, `POST /mcp`, JSON-RPC. No sessions, no `Mcp-Session-Id`, no
  GET stream.
- `server/discover`: the supported version (`2026-07-28` only), capabilities
  (`tools` only), server info (name `tehas`, the tehas version).
- `tools/list` and `tools/call`. Results carry `resultType: "complete"`;
  `tools/list` carries `ttlMs` and `cacheScope: "private"`. Tools are listed
  in a fixed order.
- Each request's `_meta` protocol version is checked; another version gets
  `UnsupportedProtocolVersionError` naming the versions served.
- **Fallback for 2025-11-25 clients** (my call, until Hermes and OpenClaw are
  confirmed on 2026-07-28; neither says which version it speaks today): a
  request that starts with `initialize` is served the 2025-11-25 way, as the
  2026-07-28 text's section on backward compatibility describes, with the same
  tools and the same keys. It holds no session state the server must keep;
  drop it once both agents speak 2026-07-28. The
  `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers are checked
  against the body as the transport requires.
- Each tool has an `outputSchema` and returns `structuredContent`, plus the
  same JSON as text content for clients that read only text.

## Tools

Every result carries `"api": 1` and the time of the file it came from, like
the factory API, and the rules of [the factory API](../../host/docs/api.md)
apply: fields are only added within version 1, a field without a value is left
out, a client accepts fields it does not know.

| Tool | From | Returns |
| --- | --- | --- |
| `factory_status` | `health.json`, `status.json`, `demand.json`, `platform.json` | Overall state (pass, warn, fail) and why; paused or not; stale (no poll for ten minutes); the queue counts (in line, building, in review, stopped); the running cycles as issue, step, status, started; demand waiting and oldest; the tehas commit and how far it is behind |
| `factory_issues` | `status.json`, `health.json` | The issues the dashboard lists, by stage (queued, running, awaiting, stopped, completed): number, title, link, stage and its times. Planning: the count from `status.json` and the issue numbers from `health.json` `checks.plans`, with no titles, because `status.json` has none for them (my call). Optional argument `stage` to ask for one |
| `factory_endings` | `endings.json`, `health.json` | The last cycles that ended: issue, status, step, started and updated, and which failed |
| `factory_console` | `running.json`, `console-<issue>.txt` | For one running cycle, by issue number: issue, step, status, its status text, and the last 64 KB of its console file as published (argument `bytes` to ask for less). `running.json` names the file; the server opens it only when the name is exactly `console-<digits>.txt` and the digits are that cycle's issue, never a path from the caller |
| `factory_stats` | `analytics.json` | The ten-day report as the dashboard shows it: runs by outcome, cycle and lead time, first pass yield, handoff rate, availability, machine time, energy when published, the daily rows |

A tool whose file is missing, unreadable or not the expected shape returns a
tool error that says which file and why, not a partial answer, and not a
protocol error. `factory_stats` with analytics off says so.

The exact keys each tool copies are the builder's to list, from the files as
they are on tehas-tehas today; every key in that list must be one the
dashboard shows.

## Keys and config

In `~/.config/tehas/env`, where the host's other secrets are, never in the
instance directory (it is in a repository):

```
TEHAS_MCP=1
TEHAS_MCP_KEYS="<key> <key>"
```

- `TEHAS_MCP` unset or `0`: the server is not started, and `install.sh` leaves
  its unit off. `1`: it is.
- `TEHAS_MCP_KEYS`: keys separated by spaces. Each at least 32 characters of
  `A-Za-z0-9_-`. With `TEHAS_MCP=1`, an empty list or one bad key stops the
  server with exit 78 and a line naming the setting, not the key.
- A caller sends `Authorization: Bearer <key>`. The key is compared in
  constant time against each key on the list. No key, an unknown key or
  another scheme: 401 with `WWW-Authenticate: Bearer` and an empty body.
- A key is never written to a log. The access log names a key by the first 8
  hex characters of its sha256, so an owner can tell callers apart and
  remove one.
- Changing the list takes effect when the unit restarts; `tehas update`
  restarts it.
- `lib/config.sh` keeps `TEHAS_MCP` and `TEHAS_MCP_KEYS` when `tehas_load`
  clears other names, as it does for the host's other secrets.
- A helper prints a new key: `tehas mcp key` (32 random bytes, base64url). It
  writes nothing; the owner puts the key in the env file.

## Exposure

The MCP server is exactly as reachable as the factory's dashboard, never more
(my call). It binds `TEHAS_HOST_ADDR` as the docs server does, loopback when
unset. On a factory whose dashboard is only on a private network, the MCP
server is too: the rule "nothing the dashboard does not show" is about the
public dashboard, so the manual says to put `/mcp` on a public proxy only
where the dashboard is already public there. The server cannot tell, so this
is a sentence in the manual, not a check.

## How it runs

My calls, open to the builder where marked:

- **A Rust program**, like the console and the analytics tool: one binary,
  built by `install.sh`, `cargo fmt` and `cargo clippy` clean, its tests
  beside its source and in the gate.
- **Its own container**, started by its own user unit
  (`tehas-mcp.service`, `RestartPreventExitStatus=78` so a bad key list does
  not restart in a loop; switched off, the unit stops the container), locked
  down like the docs server's container: read-only root,
  `~/tehas/live` mounted read-only and nothing else of the host, all
  capabilities dropped, `no-new-privileges`, a memory limit, no network but
  its published port. The keys reach it as an environment variable, not a
  mount. Whether the binary runs in a minimal image or in the docs server's
  network is the builder's call.
- **Its port** on `TEHAS_HOST_ADDR`, next to the docs server's 8080 and the
  router's 8081; 8082 unless the builder finds it taken. Like those, it binds
  the loopback address when `TEHAS_HOST_ADDR` is unset.
- **Public through the same proxy as the dashboard.** tehas.app is served by
  a Caddy reverse proxy on another machine; that proxy routes `/mcp` to this
  port. It is not in this repository. The manual says what to add to it, and
  the PR says that a person must add it.
- **Limits.** Request bodies over 64 KB are refused; responses are small by
  construction. Rate limiting per address is the proxy's job and the manual
  says so.

## Tests

Shell tests and Rust tests, no network and no image, as `AGENTS.md` asks:

- Fails closed: on with no keys, a short key or a key with other characters,
  exit 78; off, not started.
- Auth: no header, wrong key, other scheme, a key with a trailing space: 401
  and an empty body; a listed key: 200.
- Protocol: `server/discover` answers; a request with another or no version
  gets `UnsupportedProtocolVersionError`; `resultType`, `ttlMs` and
  `cacheScope` present; tools in a fixed order.
- **The rule:** live fixtures that carry extra keys (a `body`, a made-up key)
  and the test that no tool returns them; `console` and `statusText` only
  from `factory_console`.
  A test that lists every key each tool can return, so adding one is a visible
  change.
- No path from a request reaches the file system: a tool argument with `..`
  or `/` is refused.
- Missing and malformed live files give a tool error naming the file.
- `test/work_test.sh`-style pinning of the container's mounts and environment:
  only `~/tehas/live` read-only, only the keys.

## Manual

- A page `host/docs/mcp.md`: what it is, the rule, how to switch it on, how
  to make a key, what to add to the public proxy, how a Hermes or OpenClaw
  agent connects, and each tool's fields.
- A row in `host/docs/features.md`, marked as tested, not proven, until an
  outside agent has connected to tehas-tehas through tehas.app.
- `host/docs/api.md` links it: the commands are still the API on the host;
  the MCP server is the read-only view from outside.

## Proof

Proven when an agent outside the tailnet, with a key, lists the tools on
`https://tehas.app/mcp` and calls each one on tehas-tehas, and a request
without a key gets 401.

## Left to the builder

- The exact allowlist of keys per tool, from the live files.
- The container image, the port if 8082 is taken, and the crate layout.
- The text of tool descriptions, short and plain, written for an agent.
