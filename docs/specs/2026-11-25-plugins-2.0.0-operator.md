## Terms

- **Plugin**: an addition to core. The owner, 2026-11-24: "the plugin
  architecture defines additions added to the core". It's what a builder
  writes, and what a factory pins, vets and turns on. The name stays
  (decision 25).
- **Operator**: the tehas service that runs plugins, "the entity operating
  plugins (tools) to control the factory machinery".
- **Tool**: only a function a plugin offers to the chats through
  `tool:<id>`, which a model calls. So the operator runs plugins, and a
  plugin may offer tools. "Tool" is never used for a plugin itself.
- **Adapter plugin**: a plugin of kind `adapter`, a class of its own with
  its own guarantees (part 10). It answers tehas's
  ports (tickets, blueprints, the code host, identity, the board) for one
  supplier (part 10). It's the rubric's adapter, the only module that knows
  a supplier, moved out of core. The built-in adapter is the crate in core
  that does the same today (`console/github`).
- **Module**: a unit of code. In core it means what the architecture rubric
  means (`docs/architecture-rubric.md`: deep modules, tests at a module's
  interface, the adapter as the only module that knows a supplier). In a
  plugin it means an ES module (a JavaScript file in `dist/`) or a
  WebAssembly module (`dist/wasm/<name>.wasm`), as in `run.module` and
  `wasm.load`. "Module" is never used for a plugin itself (decision 25).

## Why

Under 1.x a plugin is a Docker image, built on the host from the plugin's own
Dockerfile, and each run is a container with all of Node inside it. Plugin
code runs at build time, as root, for plugins that are off as well. Each
plugin carries its own image: about 200 KB of plugin code on a 1.2 GB base.
The container is the only fence around a whole platform.

Under 2.0.0 a plugin is files. A run is a JavaScript engine instance inside
WebAssembly, run by the operator. What a plugin can reach is the set of
functions tehas hands it, one for each grant, and nothing else exists inside
the engine.

## 1. The operator and the engine

- **The operator** (`tehas-operator`) is a Rust program in tehas that embeds
  wasmtime and runs every plugin. It runs as one long-lived service under
  systemd sandboxing, or in one hardened container: no network, a read-only
  root, every capability dropped. It runs as a system user of its own
  (10.5). Its unit hides the login user's home and shows only what it
  needs, read-only (10.5, "What the units see"), and it loads no
  environment file of the core. Where part 1.2 names a systemd setting,
  the container uses its equivalent (`--restart=on-failure`, `--memory`,
  `--cpus`). That's one outer boundary for all plugins,
  not a container for each.
- **The engine: StarlingMonkey, built with componentize-js in
  `--script-only` mode** (decision 27, on the spike's evidence in part 9).
  - **What it is.** SpiderMonkey in WebAssembly, as a component.
    componentize-js (Bytecode Alliance, 0.23.0) ships its own StarlingMonkey
    build. With `--script-only`, it makes one engine component for the
    `tehas:plugin` world, and each plugin's `dist/` JS is loaded into it as
    text at run time. No plugin is ever compiled into it.
  - **Imports.** The engine imports the `tehas:plugin` interfaces plus
    `wasi:random`, `wasi:clocks` and `wasi:io/poll`, and nothing else.
    WASI-Virt removes standard input and output. There's no filesystem,
    socket, HTTP or environment import (checked with `wasm-tools component
    wit`).
  - **Random and clocks stay on**, answered by the operator: fresh for each
    run. Turning them off freezes `Date.now()` and `crypto.getRandomValues()`
    into the snapshot, so every run would see the same values.
  - **Built once by tehas, pinned by digest.** componentize-js builds aren't
    bit-reproducible: two identical builds gave different hashes. So tehas's
    release workflow builds the engine once for each componentize-js
    release, publishes it, and names it by digest. That is building from a
    pinned Bytecode Alliance release, not compiling SpiderMonkey, and it
    never touches a plugin. The release workflow is a gate file.
  - **Why not the StarlingMonkey v0.5.2 release as is.** It has no custom
    imports, so the host API would have to travel over a WASI interface. In
    `cli/run` mode its event loop never runs, and WASI-Virt breaks its
    `incoming-handler` export. The smallest import set that still boots
    leaves no channel to the host.
  - Its web standard APIs (`TextEncoder`, `URL`, `crypto.subtle`) replace
    Node's `crypto` (part 5).
  - **starlingmonkey-ng** has no release, tag or package yet, so it wasn't
    tested. Look again when it ships.
  - **Not chosen: QuickJS-ng** on the `javy` crate. It was smaller and
    leaner (1.25 MB, 1.25 MiB per run), but Javy's published runtime can't
    take host functions. tehas would have to write and maintain its own
    engine crate, with no ES module loader and no typed world.
- **Start-up caches (operator-internal):**
  - Cranelift compiles each module ahead of time, and the operator keeps the
    result (`.cwasm`, keyed by module hash, wasmtime version and CPU).
  - The engine starts from a snapshot taken when componentize-js builds it,
    so the operator adds no snapshot step. Snapshotting a plugin's own
    loaded code (with Wizer, now `wasmtime wizer`) is a later option.

  The `.cwasm` is a cache of the approved bytes. What's vetted and hashed is never
  replaced.
- **No precompiled code from a plugin (H5).** Deserializing precompiled
  bytes can run arbitrary code (wasmtime documents this), so the operator
  compiles every module itself:
  - the `.cwasm` cache is written and read only by the operator, in its own
    data directory, which no plugin path reaches;
  - each entry's sha256 is recorded when it's written and checked before
    it's deserialized. A mismatch drops the entry, and the module is
    compiled again;
  - a `.cwasm` in `dist/` is refused at vetting (part 3).
- **One instance for each run.** Nothing is shared between two runs or two
  plugins.
- **No WASI file or socket access** for the engine. Clocks and random come
  from the operator. All other I/O goes through the `tehas` API (part 5).
- **Limits per run.**
  - Memory, through wasmtime's resource limiter.
  - Time, through epoch interruption, which replaces `docker kill`.
  - Fuel as a backstop.
  - Output size in `/out` and `/state`, as now.
  - **A deadline on every host call (H2).** Epoch and fuel interrupt
    WebAssembly, not a host function that blocks (wasmtime documents this).
    So each host function has its own deadline, enforced in Rust (part
    1.4). A call past its deadline fails with a named error, and the run
    goes on or ends on its own limits.
  - **Budgets on host calls and reads (H3):** the number of host calls,
    the bytes read through `fs.*` and `git.*`, and the model tokens. A spent
    budget fails the call, not the operator.

  A run that passes a limit is trapped, and the last good view stays.
- **Language.** ES2023 modules. The entry is `dist/driver/main.js`, and it
  exports `run(ctx)`. A driver imports the host API as `tehas`.
  - **Drivers are synchronous in 2.1.** The standard's §6 leaves it to the
    host whether `run` may return a promise; a host that can't settle one
    refuses a run that returns one, with a named error. The spike's
    `--script-only` export
    is synchronous: microtasks run, but a promise `run` returns hasn't
    settled when it returns. So `run` returns its result, not a promise,
    and a run that returns a promise is refused with a named error. Async
    drivers come only once the engine's async exports are proven by a
    check of part 9 (WASI 0.3, or componentize-js's async support).
  - **`ctx` is an object** in the API. The WIT may carry it serialized; the
    engine's glue hands `run` the parsed object, under the host's
    `plugin-context` schema.
  - **`ctx.trigger`** names why the run started: `clock` (for `every:` and
    `clock:`), `press` (a view's press, 6.3) or `once` (a run by hand). A
    later minor may add values, and a driver treats one it doesn't know as
    unknown.

  There are no timers beyond `await`. A plugin that needs to wait asks for
  `every:` or `clock:` (decision 33), as in `clock:mon-fri@06:00` or
  `clock:daily@06:00,18:00`. The word matches the trigger these runs
  record (`clock`). `at` stays only the manifest key of a hook point or a
  gate point.
- **`runtime`** in the manifest is reserved and accepts only `"starlingmonkey"` in
  2.0.0.

### 1.1 WebAssembly modules

- **A plugin is JavaScript or TypeScript, plus WebAssembly modules if it
  wants them.** Modules go in `dist/wasm/<name>.wasm`, committed as built.
  The builder may use any toolchain (Rust, C, Zig, Go, AssemblyScript, ...).
  tehas never compiles one. The manifest lists each module by name.
- **Drivers and views.** A driver's modules run in the operator, under the
  rules below. A view's modules run in the browser, under part 6.1
  (decision 26). The same audit applies to both.
- **The target.** Our own Rust modules target `wasm32-unknown-unknown`, so
  they import nothing. The null WASI preview 1 below is allowed for other
  toolchains that emit it, and a module built for `wasm32-wasip1` passes
  only if its imports stay within that list.
- **No `unsafe` in our own Rust** (tehas's rule). A module passes scalars,
  or uses the copy functions of the host's own helper crate for the
  calling convention below, so no plugin writes `unsafe` by hand.
- **Calling.** `tehas.wasm.load("<name>")` returns the module's exports.
  Numbers pass straight through. Bytes are copied by the operator, using the
  module's exported `memory` and `alloc(len)`, with a `(ptr, len)` argument
  and a result packed as `ptr << 32 | len`. Each module is its own wasmtime
  instance, with no memory shared with the engine, another module or another
  run.
- **Imports: pure compute only.** A module may import nothing, or only what
  common toolchains emit for a program that does no I/O:
  - `env.abort` (AssemblyScript), which traps;
  - a null WASI preview 1:
    - no preopened directories and no sockets;
    - `fd_write` to 1 and 2 goes to `log`, escaped like any plugin output
      (part 1.2);
    - `random_get` comes from the operator;
    - `clock_time_get` is monotonic only;
    - `proc_exit` traps;
    - environment and arguments are empty;
    - every other call returns `ENOSYS`.

  Any other import is refused. A module can't reach files, the model, git
  or any other grant. Only the JS holds grants.
- **Limits.**
  - 8 MiB for each module, with a total cap for each plugin.
  - Its memory counts in the run's memory cap.
  - Fuel and epoch interruption cover its time.
  - wasmtime's default features (SIMD, bulk memory, multi-value, reference
    types) are allowed. Threads, shared memory and memory64 are refused.
  - Core modules only, except an adapter built as one component (10.1).
    For ordinary plugins the component model comes later.
- **Audit, in three layers:**
  1. *The binary, at every deploy.*
     - A module must keep its name section, and a stripped module is
       refused.
     - The check records its imports, exports, maximum memory, function
       count and data segments, and flags strings in its data that look
       like URLs, keys or paths.
     - The checks use the **wasm-tools** crates: `wasmparser` to validate and
       list imports, exports and sections, and `wasmprinter` for the
       disassembly that `tehas plugin review` shows (a viewer, not build
       tooling).
  2. *A rebuild from source, during vetting and never on a host.*
     - The manifest may name a module's source in `src/` and a recipe: a
       toolchain container pinned by digest, plus the build command.
     - An auditor rebuilds it. A matching hash shows as "rebuilt from
       source: matches", and anything else as "binary only".
     - Deployment never requires a rebuild.
  3. *Behaviour, always.* The plugin's tests exercise each module. A module
     has no I/O, so its whole effect is what it returns.

  Our own plugins must reach "rebuilt from source: matches" (part 4). For a
  third-party plugin, the approver decides whether "binary only" is
  acceptable.
- **When to use one.** For hot loops in a single plugin, such as guard's
  pattern scan or floorplan's codebase scan. Heavy work on data that starts
  in the browser (images, media, files the user picks) runs in the view's
  own module, on the client (part 6.1), not in the operator. A hot path that several plugins
  share goes to core as a host function, through a plugin surface request.

### 1.2 Failure containment

A bad plugin must never take down core, and should cost other plugins as
little as possible (decision 30).

- **Core is outside the blast radius.** The gate, the dashboard and the
  factory's machinery never run plugin code. If the operator dies, plugins
  stop and core carries on: views show their last good output, and the
  dashboard marks plugins as unavailable.
- **A run's failure is the run's.** A trap, a thrown error or a passed limit
  ends that instance only. The last good output stays, and the run is
  recorded with its reason.
- **Gates and phases with no answer: hold** (decision 32, "make the safe
  choice"). No answer is never `allow`.
  - If a gate gets no answer, because the operator is down or the run
    failed or timed out, tehas holds the act, whatever the grant's policy.
  - The grant's `pass` or `hold` policy applies only to an answer that came
    back. A held phase past `max_age` follows its policy, because it was
    answered.
  - A phase already entered stays held, and tehas asks again on the next
    tick once the operator is back.
  - A person's lift (`tehas phase lift`) always works, with the operator
    down or not.
  - The `held[]` item's `text` says "plugin <name> unavailable", and the
    operator's crash loop alert (below) names the held issues.
  - The cost: while the operator is down, a factory with a
    `before:cycle.started` gate starts nothing until the operator is back
    or a person lifts the hold. That's taken over letting work pass a gate
    nobody checked.
- **The operator's own code can't be crashed from a plugin.**
  - Every host function runs under `catch_unwind`. A panic becomes an error
    for that run, is logged, and the run ends. The operator keeps going.
  - Every host function has a fuzz target (part 9), fed with what a plugin
    can send.
  - Host functions are bounded: a cap on each argument and result size, a
    deadline on each call (H2) and budgets per run (H3).
  - systemd restarts the operator if it exits (`Restart=on-failure`, with a
    start limit). A crash loop alerts the factory's owners and leaves core
    running.
- **Runs can't starve each other.**
  - At most one run of each plugin at a time. A trigger that comes during a
    run is merged into one queued run.
  - A run starts only when its memory cap fits in what's left of the
    operator's memory budget, so concurrency follows the caps, not the
    typical run (9 MiB for hoststats, 63 MiB for guard's scan, part 9).
    Runs that don't fit wait in a queue, with fair turns between plugins.
  - The operator's systemd unit has its own `MemoryMax` and `CPUQuota`, so
    the operator as a whole can't starve core either.
  - A plugin whose runs keep failing or timing out is backed off, and after
    a set number of failures in a row it's paused, with an alert. An admin
    resumes it.
- **Disk.** Each plugin has a total quota for `/state`, besides the size cap
  on each run's `/out`. A write past it fails in the run. The whole
  operator's data sits on its own quota, so plugins can't fill the disk core
  needs.
- **The model.** `model:<tokens>` is a budget for each run. A budget for each
  plugin and factory per day caps the total. A spent budget fails the call,
  not the run.
- **The engine and wasmtime.** An escape from the sandbox would land in the
  operator's sandbox, not in core: no network, a read-only root, no
  capabilities. wasmtime and the engine are kept current. A wasmtime
  security release is a patch release of tehas.
- **Views.** A view's frame is a sandbox with an opaque origin (H8, part
  6). It's still served from a name under the dashboard's site, so it may
  share the dashboard's browser process. `<tehas-plugin-view>` watches its
  frame, and one that stops answering is unloaded with a "this view stopped
  responding" state. Heavy view work runs in a worker (part 6.1).
- **Plugin output is untrusted data (H4).** Everything a plugin returns
  (`log()` lines, findings, verdict text, a gate's `why`, the review
  summary) is escaped and bounded by the host before anyone sees it:
  - terminal control sequences and other C0 and C1 controls are stripped
    before a terminal shows it (wasmtime's security guidance names this);
  - Markdown and HTML are escaped before a pull request comment or the
    dashboard shows it. Links show only as plain text or point to the
    plugin's own view;
  - each field has a length cap, and so does the total for each run (part
    1.4).
- **No secrets out (H7).** The host scans what a run returns (findings,
  verdict text, `/out` files it will publish) for secret patterns (tokens,
  private key blocks, the host's own credentials) and redacts them before
  publishing, recording that it did. H1 makes this rare; H7 catches what H1
  misses.
- **Tested.** The operator's tests include a plugin that panics a host
  function, one that loops, one that allocates without end, one that fills
  `/state`, and one that triggers itself in a storm. Core and the other
  plugins must keep running through each.

### 1.3 Scaling

One operator is enough for throughput: a typical run costs about 3 ms and
9 MiB (part 9), and runs come from branch moves, schedules and chats, a few times
a minute for each factory. More operators are for isolation first
(decision 31).

- **One operator for each factory instance.** Several factories on one host
  each get their own operator, with its own system user
  (`tehas-op-<instance>`, 10.5), systemd unit, limits, queue, quotas
  and data. A bad plugin on one factory can't touch another's runs.
- **A separate operator tier for third-party plugins (optional).** A factory
  may run third-party plugins in a second operator, apart from our own
  signed plugins, as its own user (`tehas-op-<instance>-3p`), so
  an escape from that sandbox reaches nothing of ours.
  Both operators run the same engine under the same rules.
- **Rules that keep more operators possible later:**
  - A run is stateless: a fresh instance, so any operator of the factory
    can take any run.
  - A plugin reaches files, state, git and the model only through the host
    functions, so the storage behind them can move without changing a
    plugin.
  - Each plugin of a factory belongs to one operator at a time. That keeps
    one run per plugin (part 1.2) and the `/state` quota without
    distributed locks.
  - Core hands runs to its operator over a defined channel, a local socket
    with a queue behind it, and never calls into it in process. Adding an
    operator is routing, not a redesign.
  - The `.cwasm` cache stays on each host, keyed by CPU.
- **Not now: operators on other hosts.** The `product` and `history` grants
  read the narrow view that core prepares on the factory's host (part 5),
  and the model goes through a local socket. A remote operator would need
  a copy of that view, or those calls forwarded back to the factory's
  host. That's built only when it's needed.

### 1.5 Hardening

The owner, 2026-11-25 (decisions 42 to 44), asked for a review that treats
every `.wasm` as untrusted code, on the host and in the browser. Revision 4
already held: no network, environment, WASI files or sockets; one small WIT
world with a grant check on every call and size caps; memory, epoch time
and fuel per run; the operator as a hardened service; vetting of the exact
`dist/` bytes by hash; core modules only, except an adapter built as one
component (10.1), with no threads or shared
memory; views on an origin of their own. Revision 5 adds:

| Item | Rule | Where |
| --- | --- | --- |
| H1 | A narrow repository view: tracked files at the commit, with secrets left out | 5 |
| H2 | A deadline on every host call | 1, 1.4 |
| H3 | Budgets on host calls and reads | 1, 1.4 |
| H4 | Plugin output is untrusted data: escaped and capped | 1.2, 1.4 |
| H5 | No precompiled code from a plugin | 1, 3 |
| H6 | A versioned interface: `tehas:plugin@2.0.0` | 5 |
| H7 | No secrets out: what a run returns is scanned and redacted | 1.2 |
| H8 | The view's frame is a sandbox with an opaque origin | 6 |
| H9 | WebAssembly in the browser is third-party code in a box | 6.1 |
| H10 | Devices by two keys: reserved, not built in 2.1 | 6 |
| H11 | The adapter's network: `http.request`, granted to adapters alone; declared origins, H2 deadlines, a budget and caps, every request recorded; the credential never enters the engine | 10.3 |

The generic rules go into tehas-standard's v3 plugin standard too.

## 2. Layout, and who builds

```
tehas-plugin.json   the manifest; its paths point into dist/
src/                source: .ts, .tsx, .jsx, .js, tests, and each module's source
dist/driver/        deployable driver JS; main.js exports run(ctx)
dist/view/          deployable view JS, HTML and CSS
dist/vendor/<lib>/  bundled third-party libraries, verified against upstream (part 3)
dist/wasm/          built WebAssembly modules (part 1.1)
dist/test/          built tests, run by tehas plugin test
skills/             skill files, as in 1.x
tehas.toml          the standard the repository follows, at its root
```

- **A root `tehas.toml`** names the standard the repository follows
  (`[standard]`, with its `url` and `version`) and the toolchains it uses
  (`[platform]`). It's binding for our own plugins, adapters included, and
  recommended for third-party ones.

- **Builds are the plugin builder's job.** The builder picks the tools (tsc,
  esbuild, Babel with Solid's preset, cargo, ...) and commits `dist/` at the
  pinned commit. tehas ships no build command and no transform.
- **tehas deploys `dist/` and nothing else.** It never transforms code, and
  it doesn't compare `dist/` with `src/`. `src/` is kept so people can read
  the source. What tehas checks, vets and runs is `dist/`.
- **TypeScript** is the builder's affair. tehas ships `tehas.d.ts` (part 5),
  and the kit ships `kit.d.ts` and `solid.d.ts` (part 6), so a TypeScript
  builder gets accurate types. Type checking runs in the builder's CI.
- **Tests** are built into `dist/test/`. `tehas plugin test` runs them in the
  engine with a small `test()`/`assert` API and fake host functions. A
  builder can also run their plugin under Node, for a debugger: through
  **jco**, which runs components in Node, or against the same fakes. The
  engine run is the one that counts.

### 2.1 A note for coding standard v3

Coding standard v3 (tehas-docs `wiki/decisions/coding-standard-v3.md`) is
still written for containers. The plugins lead drafted these changes for
the operator. They go into v3's next revision, not into this spec's rules:
- **R11, the kit**, plus verified `dist/vendor/` libraries (part 3).
- **R12, typed scripts.** TypeScript or JSDoc in `src/`, checked against
  the generated `tehas.d.ts` (part 5). `dist/` is readable, not minified,
  with no `eval` (part 3).
- **Solid JSX** is allowed in `src/` for views (part 6).
- **Drivers import only `tehas`**, besides their own `dist/` files
  (part 3).
- **xterm** stops being v3's named exception (console's terminal) and
  becomes a verified vendor library (part 3).

### 2.2 The manifest: `tehas-plugin.json`

Every field, under a closed schema in `api/` (the standard's §4). An
unknown field is refused.

| Field | Value | Needed | What |
| --- | --- | --- | --- |
| `plugin` | `2` | always | the spec's major |
| `spec` | a revision, such as `"2.0.0-r5"` | always | the spec revision the plugin was built against, so its tags can state it |
| `name` | a letter and up to 11 letters or digits | always | the plugin's name (the contract's rule) |
| `label` | text | always | what people see |
| `kind` | `"plugin"` or `"adapter"` | no; `"plugin"` | part 10 for `adapter` |
| `runtime` | `"starlingmonkey"`; `"component"` for an adapter only | no; `"starlingmonkey"` | part 1, 10.1 |
| `timeout` | seconds, at most 600 | with a driver | the time for one run |
| `asks` | grant names | always, may be empty | what it asks (part 5) |
| `driver` | a path | with a driver; `dist/driver/main.js` | the entry that exports `run(ctx)` |
| `actions` | id to `{label, args}`, `args` a JSON schema | no | the presses a view may send (6.3); `label` is what a confirm names, and a draft's confirm shows its exact title and body |
| `views` | `[{id, entry, open}]` | no | each view, its entry in `dist/view/`, and `dock`, `page` or `full` |
| `skills` | paths under `skills/` | no | skill files |
| `hooks` | `[{at, entry}]` | no | each hook or gate point, `at` as `hook:<when>:<event>` |
| `wasm` | name to `{path, source, recipe}` | no | the driver's modules (1.1) |
| `view_wasm` | name to `{path, source, recipe}` | no | the view's modules (6.1) |
| `vendor` | library to `{version, upstream, files}` | no | verified libraries, each file's sha256 (part 3) |
| `solid` | a `solid-js` version | with a compiled view | the version its compiled JSX expects (part 6) |
| `origins` | id to `{url, credential}` | an adapter only | 10.1 |
| `adapter` | `{world, component, realms, ports, credential}` | an adapter only | 10.1 |

There's no `license` field yet, because the licence is undecided. The
standard lists it, and it comes when that's decided.

## 3. Vetting `dist/` before enabling

- **Nothing runs until `dist/` is vetted.** At `tehas update`, a new or moved
  pin is fetched, checked and held as `pending`. It isn't run, served or
  offered until it's approved: automatically for our own plugins (part 4),
  by a person for everyone else. A plugin that's turned on keeps running its
  last approved commit until the new one is approved.
- **Automatic checks on `dist/`:**
  - **Parse:** JS is ES modules that the engine parses.
  - **Imports:**
    - a driver imports only its own `dist/` files and the `tehas` API,
      never a `node:` module or a package;
    - a view imports only its own `dist/view/` files, the gate's kit and its
      verified `dist/vendor/` libraries;
    - there are no outside URLs and no source maps.
  - **Readable JS in the plugin's own code:**
    - no line over 1,000 characters;
    - no packed or mangled code;
    - no `eval` or `new Function`.

    Measured on 2026-11-24: hand-written lines reach 617 characters (model
    prompts, security-rule regexes). A 300-character limit would have
    refused 9 of 14 plugins.
  - **Bundled third-party libraries are verified, not read.**
    - They go in `dist/vendor/<lib>/`. The manifest names each with its
      version, its upstream source (an npm tarball or a git commit) and a
      sha256 for each file.
    - The check fetches upstream and compares bytes. A library that matches
      is a known public release and is exempt from the readable-JS and
      `eval` rules. One that doesn't match is refused.
    - A file the plugin has patched counts as its own code.
    - Verified libraries count toward their own, larger size cap.
    - Today's cases: console's xterm.js (it already carries `SHA256SUMS` and
      `VERSIONS`), and floorplan's upstream Floorplan 0.11.0 (it already
      carries `CHECKSUMS.txt` and `PATCHES.txt`) with its `elk.bundled.js`
      (elkjs, 1.6 MB minified, EPL-2.0).
  - **Grant fit.** Every `tehas.*` function `dist/` calls must be covered by
    the manifest's grants.
  - **Modules** pass part 1.1's import, size and name-section rules. A
    view's modules pass part 6.1's import rule too (H9).
  - **Only known files (H5).** A `dist/` holding a `.cwasm`, a native
    library, or any file that isn't JS, HTML, CSS, a core `.wasm` or
    a listed vendor file is refused. The
    plugins lead decides before V3 whether a view's images and fonts join
    the list.
  - **The interface's version (H6).** A module that imports a function
    newer than the host's `tehas:plugin` is refused, naming the version it
    needs.
  - **Size caps** for `dist/view/`, `dist/view/wasm/`, `dist/vendor/` and
    `dist/wasm/`.
  - **Tests** pass.
- **A person's approval (third-party plugins).** `tehas plugin review`
  shows:
  - the grants;
  - all of `dist/`, or for a moved pin, the diff since the last approved
    commit;
  - each verified library with its upstream;
  - each module's facts and disassembly, marked as compiled code nobody can
    read;
  - a link to `src/`.

  Approval records the commit, the `dist/` hash and the approver by account
  id, as 1.10 does. Through industry it's given on the plugin page.
- **The approval is tied to the hash.** If `dist/` at the commit doesn't
  hash to what was approved, the plugin is refused. tehas runs exactly the
  approved bytes, so what was vetted is what runs.

## 4. Our own plugins: automatic trust through the signed vetted list

- **No manual step.** Our own plugins, the core plugins on tehas-plugins,
  are trusted after an automatic audit and need no person's approval.
- **The audit pipeline.** `vet.yml` in tehas-plugins (set up with the Bytecode
  Alliance's `actions` for wasmtime and wasm-tools) runs on each new commit
  to a core plugin's protected `main`:
  1. Run every automatic check of part 3 on `dist/`, including verifying
     the bundled libraries against upstream.
  2. Rebuild each WebAssembly module from its recipe. It must match:
     "binary only" fails for a core plugin.
  3. Run the tests in `tehas-operator`, then do one real run under the
     plugin's grants against a fixture factory. This replaces "ran on a
     host".
  4. Write the entry, bump the list's `serial`, sign and publish.

  If a step fails, the entry stays at its last vetted commit, and the
  pipeline opens an issue in the plugin's repository.
- **The entry** in `tehas-plugins/plugins.json`:
  ```json
  "vetted": {
    "repo": "tehas-app/tehas-plugin-review",
    "commit": "<sha>",
    "dist_sha256": "<hash of dist/>",
    "manifest_sha256": "<sha256>",
    "vendor": {"<lib>": {"version": "<v>", "upstream": "<url>", "matches": true}},
    "wasm": {"<name>": {"sha256": "<sha256>", "rebuilt": true}},
    "grants": ["view", "menu", "product", "history", "model", "every", "action:run", "record", "keep", "issue:draft"],
    "state": "vetted",
    "at": "<time>", "by": "vet.yml"
  }
  ```
  `state` is one of:
  - `building`: listed, with no commit through `vet.yml` yet;
  - `vetted`: the commit passed, and hosts may auto-approve it;
  - `refused`: kept off, with a reason (pageticket);
  - `revoked`: was vetted, now withdrawn (below).
- **Auto-approval on a host.** At `tehas update`, a pin whose repo, commit
  and `dist/` hash equal a vetted entry is approved. The approval is
  recorded as by the list, with its serial and signature.
  - It covers the code vetting of part 3 only.
  - **Turning a plugin on stays per factory**, as in 1.10 and on industry's
    plugin page. It's one admin click, and for one of our own plugins that
    click also gives it the grants of its vetted entry (decision 28). There's
    no separate grant approval.
  - **Except grants on a person's path** (the plugins lead's narrowing of
    decision 28). The click never gives a grant that holds or acts on a
    person's path. Each of these needs the admin's own grant:
    - `hook:before:<event>=<policy>`: the policy is the admin's choice, and
      a gate grant with no policy is refused;
    - `phase:<id>` (1.8), whose policy is `pass` or `hold`;
    - `answer:<kind>` (1.8);
    - `issue:advisory`, guard's (the plugins lead's decision of
      2026-11-25), waiting for the owner's OK, decided in guard's pull
      request. A run may file one issue in the factory's backlog for an
      advisory finding. The issue holds only public facts: the package, the
      advisory id and link, the installed and fixed versions. Details of
      secrets or review findings stay on the host. There's one open issue
      for each package and advisory, and a daily cap. The factory builds it
      as an ordinary cycle through its gates, and a person merges (hard
      rule 5);
    - `device:<feature>` (H10, part 6), reserved.

    `tehas plugin review` and industry's plugin page list them apart, as
    "needs your grant".
  - **Growth waits for the admin.** The grants given at that click are
    recorded on the factory. When a later vetted commit asks for a grant
    outside that set, the factory keeps running the last commit that fits
    and asks the admin. The plugin moves on once the admin gives the new
    grant. So a commit can't widen what it may do on a factory by itself.
  - A narrower later commit runs at once, and the factory keeps the grants
    it gave until the admin takes them back.
  - Third-party plugins: the admin approves the code and gives each grant,
    as in part 3. Its manifest's `origins` are only a request: each is
    granted only when the person approves it by name at turn-on (5.1).
- **Signing: Sigstore keyless.**
  - The pipeline signs through GitHub's OIDC, with the identity pinned to
    `tehas-app/tehas-plugins/.github/workflows/vet.yml@refs/heads/main`.
  - There's no long-lived key, and every signature lands in Sigstore's
    public transparency log.
  - tehas's release carries the allowed identity in `api/plugins-signers`,
    a gate file.
  - A host trusts the list only through its signature
    (`plugins.json.sig`), never through where it fetched the list from.
- **Rollback and freeze protection:**
  - The list carries an increasing `serial` and an `expires` date.
  - A host refuses a serial lower than the highest it has accepted.
  - An expired or unsigned list turns auto-approval off. Pins then wait for
    a person, and what's already approved keeps running.
  - **The adapter on an expired list** keeps running its last approved
    commit, and `tehas status` warns that the list has expired. The factory
    holds the adapter only when its commit is revoked or the list is
    unsigned (10.7).
  - **A release's default entry** for the adapter (10.8) carries its list's
    `serial` and `expires`. The host takes it only when that serial is at
    least the highest it has accepted, never over a newer entry.
- **Revocation.** `"state": "revoked"` for a commit, with a reason, set by
  the pipeline or by a person in an emergency. A host that runs a revoked
  commit turns it off at its next update, keeps its state and alerts the
  factory's owners. Industry pushes a revoked list at once.
- **What the trust rests on:**
  - branch protection on each core plugin's `main`, plus the Bytecode
    Alliance's **approved-contributors** Action, which closes pull requests
    from authors who aren't on an allowlist (agents' sloppy pull requests
    included);
  - branch protection on `vet.yml`, a gate file;
  - the strictness of the automatic audit.

  A commit that reaches a core plugin's `main` and passes the audit reaches
  every factory that pins it. That's the cost of having no manual step.
- **Third-party plugins** never get list trust. They always go through part
  3's approval by a person. Adding one is the admin's act and the admin's
  risk (decision 21).
- **Fetching.** A host fetches the list and its signature at `tehas update`.
  With industry, industry fetches and pushes them.
- **Fetching plugin repositories.**
  - A factory fetches over https with no credentials.
  - A public repository fetches as is. Verified on 2026-11-24: hoststats was
    made public as the verification plugin (decision 20), and a fetch with
    no credentials returns its `HEAD`, `4ac3c1c`.
  - A private repository fails the same fetch, so no factory can fetch the
    other plugins today.
  - For private repositories, a lent read token, as the plugins lead proposed on
    2026-11-24 and the owner accepted (decision 29):
    - a lent read token in `TEHAS_PLUGIN_FETCH_TOKEN_FILE`, outside the
      instance directory, read only at fetch time;
    - sent as a header through `GIT_CONFIG_*`, never on a command line, in a
      config, an image or a log;
    - scoped to a URL prefix, with `http.followRedirects=false`.
  - **A private pin with no token fails that plugin only** (decision 35).
    `tehas update` never exits non-zero because one plugin couldn't be
    fetched, and its frozen exit table stays as it is.
    - `tehas update`: the plugin keeps its last approved commit, or stays
      not installed. The update reports `fetch: no-token`, or `fetch:
      failed` for any other error, and exits as it would with no plugins.
    - `tehas plugin --json`: a `fetch` field on the plugin's entry, with
      the same word.
    - `tehas plugin review <name>`, a command about that plugin alone,
      exits 78 when the remote asks for credentials and no
      `TEHAS_PLUGIN_FETCH_TOKEN_FILE` prefix covers the URL. It exits 1 for
      any other fetch failure.
    - A malformed token setting is still malformed settings: 78 for every
      command (hard rule 2). That's a file named but unreadable, or
      readable by group or world, or a bad prefix.

    This matches 1.10's "not granted is not an update failure".

    The host check below still has to pass before any factory relies on
    it.
  - The host check is `tehas plugin review hoststats --json` on a
    tehas-factory 2.1 build. A tehas-factory 2.0 build refuses plugin
    settings with 78. It checks the fetch path on a real host. It's separate
    from `vet.yml`'s fixture run, which is what moves an entry from
    `building` to `vetted`. tehas-plugins#6 lists hoststats as `building`.

## 5. The host API: the `tehas:plugin` WIT world

- **The interface is written once, in WIT**, as the world `tehas:plugin` in
  tehas's `api/` (CC0 like the rest of `api/`).
  - **It's versioned (H6):** the package is `tehas:plugin@2.0.0`, and the
    manifest's `"plugin": 2` names its major. The host functions are on
    tehas's surface list, so a later minor only adds to them.
  - The operator's Rust side is generated from it (wasmtime's component
    bindgen and wit-bindgen).
  - **`tehas.d.ts` is generated from it** (`jco guest-types`), so the types
    builders see can't drift from what the operator provides. The kit's
    hand-written `.d.ts` files have already drifted, which is the problem
    this avoids.
- **A grant opens a group of imports.** The engine is built once for the
  whole world, so every import is linked. The operator refuses a call its
  grants don't cover: it throws "not granted" before any work is done
  (spike). The check is in Rust, in each host function.
- **No `u64` in the WIT.** `jco` maps it to `bigint`. Sizes, counts and times
  use `u32` or `f64`.

| Function | Grant | Replaces in 1.x | Used by |
| --- | --- | --- | --- |
| `fs.read`, `fs.list`, `fs.stat` | any input grant (`product`, `history`, `files`, `cycles`, `issues`, `pages`, `live:`, `feed:`, `feed:advisories`, `industry:logs`) | `node:fs` reads of mounts | every plugin with a driver |
| `fs.write`, `fs.remove` | `/out` always; `/state` with `keep` | `node:fs` writes | every plugin with a driver |
| `fs.read`, `fs.list`, `fs.stat` on `/state` | `keep`: the plugin's own `/state` only | `node:fs` reads | plugins that keep state |
| `git.head`, `git.diff`, `git.show`, `git.tree`, `git.blob`, `git.isAncestor`, `git.defaultBranch`, `git.status`, `git.log`, `git.files` | `product` or `history` | running `git` (`diff`, `show`, `ls-tree`, `cat-file`, `rev-parse`, `merge-base`, `symbolic-ref`, `status`, `log`, `ls-files`, `check-ignore`) | review, wiki, guard, goldfish, floorplan |
| `model.chat(req)` | `model:<tokens>`; images with `model:images` | `http.request` to `/run/tehas/model.sock` | floorplan, given, goldfish, guard, review, rsi, wiki |

- **Paths** keep the 1.x mount names (`/work`, `/out`, `/state`, `/product`,
  ...), held by the operator. There are no links and no `..`, and a path
  outside a granted root is refused.
- **A narrow repository view (H1).** Read-only still lets a plugin read and
  disclose a secret. So `product` and `history` give the plugin a prepared
  view, not the clone:
  - tracked files at the commit only, never untracked or ignored files;
  - left out by default: `.env` and `.env.*`; private keys (`*.pem`,
    `*.key`, `id_rsa*`, `id_ed25519*`); credential and token files
    (`credentials*`, `*.p12`, `*.keystore`, `.npmrc`, `.pypirc`, `.netrc`);
    and `.git/` itself. A repository may add paths in a `[plugin]` table of
    its root `tehas.toml`, and never remove the defaults;
  - symlinks are resolved while the view is prepared. One that points
    outside the view, or at a path left out, is left out too;
  - `fs.*` and `git.*` see the same view: `git.blob` and `git.show` refuse
    a path left out.
- **git** is answered by the operator from the narrow view that core
  prepares from the factory's clone (H1), never from the clone itself:
  read only, fixed operations, no git binary and no config read. Core
  writes the view into a directory the operator's user can read, and the
  operator answers `git.*`, `product` and `history` from that view only. Plugins today
  pass `safe.directory=*` and `core.hooksPath=/dev/null` to keep a git binary
  safe. With no binary, that risk goes away.
- **`run.module`** runs one `dist/` entry of the same plugin in a fresh
  instance, with the given `argv` and `env`, under the run's grants and
  limits. It returns `{stdout, code}`, and `process.exit` ends that
  instance. It's for command-line code a plugin bundles, such as floorplan's
  upstream scripts.
- **`ctx`**, the argument to `run(ctx)`, is an object (part 1) and carries
  what `/run/context.json` carried, with `trigger`.
- **`feed:advisories`, a new input.** tehas fetches advisory data for the
  product's locked packages, as it does for the other `feed:` inputs, and
  writes it for the plugin to read with `fs.read`. The plugin has no
  network. It comes with guard's pull request. From the release of the
  managing system that drops its patrol until guard's advisories check
  lands on a factory, no patrol runs. That's a known
  gap, not a failure.
- Every host function checks its grant and its paths in Rust, and each has a
  fuzz target.
- **A gate's answer is a shape, not a file** (N2). A gate listener's run
  returns an object of the shape `api/gate-answer.schema.json` gives
  (`{"api": 1, "answer": "allow" | "refuse", "why"}`). The operator checks
  it against the schema and hands it to tehas. There's no
  `/out/_tehas/answer.json` path (#3187). A return that doesn't fit the
  schema is no answer, so the gate holds (part 1.2).
- **The Kept libraries** (the table "Kept for the 2.1 plugins" in
  `docs/architecture.md`) split by where they run (decision 36: "key
  reusable services can stay in the core"). A port removes its library code

  - The kept-for-2.1 marker of a moved crate comes off, and the crate

### 5.1 Destinations, for every kind

One format serves every plugin that reaches outside the host: adapters now,
and `net:` and annex plants later (decision 53). In the standard's words
(§6): a manifest's origins are exact, with no pattern, and vetting signs
them; in the host's configuration, and only there, the one pattern is a
leftmost `*.` label; for an adapter the configuration only narrows; for
other code a host lets reach the network it may also widen, as an explicit
choice the host records and shows in its status; and widening never adds a
credential.

- **The manifest only asks; the default is no destinations** (decision
  64). The manifest's `origins` is a request, listing exact origins:
  `https`, a lowercase A-label host, no port, no path, no wildcard. A glob
  in a manifest is refused at vetting. Nothing is granted from the
  manifest alone:
  - for our own plugins, the signed vetted entry is the grant (10.1);
  - for a third-party plugin, the origins are granted only when the person
    approves each by name when turning it on, as `tehas plugin review`
    shows them (part 4).
- **A body policy for each destination.** Each origin entry lists its
  allowed `methods` and its `body`, `none` or `bounded(<bytes>)`. A
  destination added by widening defaults to `GET` and `HEAD` with no
  body.
- **The person configures destinations on the host, per plugin.**
  `TEHAS_PLUGIN_ORIGINS_<NAME>`, new and marked building, is a space-
  separated list of origins for the plugin `<name>`. Unset means the
  plugin's vetted origins, as they are.
- **Globs only in host configuration.** The one form is a leftmost `*.`
  label, as in `https://*.example.com`. Never a bare `*`, never a glob in
  the scheme or the port, and never a glob whose rest is a public suffix
  (`https://*.com` and `https://*.co.uk` are refused).
  - Public suffixes are read from a copy of the Public Suffix List pinned in
    the release by its upstream commit and sha256, both sections, ICANN
    and private. It changes only by a pull request that moves the pin.
  - The settings load checks the value's form and stops with 78 on a bad
    one (hard rule 3: it reads no list and makes no call). The programs
    check globs against the pinned list before any request, and stop with
    78 on a public-suffix glob.
- **Matching** is on the IDNA-normalised host, compared whole, and a glob
  matches exactly one or more labels to the left of its rest. The address
  checks of 10.3 still run on every connection.
- **Adapters: the host may only narrow.** For an adapter,
  `TEHAS_PLUGIN_ORIGINS_<NAME>` must be a subset of its vetted origins. An
  origin with no routes in the vetted entry can't be added, so widening an
  adapter stops with 78.
- **Ordinary plugins (once `net:` exists) and annex plants: the host may
  widen.** An origin the person adds beyond the vetted ones is their
  explicit choice. It's recorded with who set it and when, and `tehas
  status` shows each plugin's added origins. Widening never adds a
  credential to an origin: an added origin is reached with no credential.
- **One source for both sides** (decision 62: "the same origin
  configuration should match server and client comms of plugin code").
  A plugin's destinations are its manifest's `origins` plus the person's
  `TEHAS_PLUGIN_ORIGINS_<NAME>`, and nothing else. They govern its
  server-side requests (an adapter's `http.request`, and a driver's once
  `net:` exists) and its view's proxied requests (6.4) alike. A view has
  no list of its own. Narrowing and widening apply to both sides at once:
  an origin narrowed away is closed for the view too.
- **One checker: the request gate.** The same host code vets every request
  from every side. It runs the destination match, 10.3's path and URL
  rules and header allow-lists, the address checks, the pinned TLS and no
  0-RTT (5.2, 5.3), the caps after decompression, and the request ids and
  records (5.4), in one record format. The adapter host and the view's
  proxy both call it. 10.3 and 6.4 refer to it, and don't restate it.
- **The parent is always allowed** (decision 63: "the hosting parent
  should always be allowed"). The reserved origin id `parent` is the app
  the plugin runs in: the factory's dashboard, a managing system, Obeya or
  an annex.
  - It needs no manifest entry, and the person's host configuration can't
    narrow it away. A manifest may not declare an origin named `parent`.
  - The parent decides what's exposed. Each hosting app publishes its
    plugin-facing route list: for the factory, the factory API's read
    routes and the surfaces; for any other, the hosting app's
    plugin-facing routes. A route not on the list is refused. "Always
    allowed" is the destination, not every endpoint.
  - On the client side, the kit's `fetch` shim maps a same-origin or
    relative URL (`fetch("/api/...")`) to `parent`, through the same proxy
    and the same request gate (6.4).
  - On the server side, a driver or an adapter reaches the parent through
    the core's sockets (its host functions and surfaces), never by
    network. That's the same `parent` destination.
  - The person's session cookie never travels. Reads on exposed routes are
    allowed under the parent's own rules, with the request gate attaching
    the parent's auth for that load. Writes need 6.3's host-drawn confirm,
    and act as the person who pressed.
- **One egress host.** Every outbound request, from an adapter, from a
  driver under `net:` and from a view through 6.4's proxy, leaves through
  one process running as its own user: the adapter host (10.5), which this
  spec keeps calling by that name. The request gate runs there. The plugin
  gate only relays a view's request to it over its socket, and never
  connects out itself; the operator has no network at all.
- **No inherited proxy settings.** Both units clear and ignore
  `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` and `ALL_PROXY`, in upper and
  lower case, and the HTTP client is built with proxy detection off.
- **TLS identity.** The host connects to the address that passed the
  address checks, and uses the approved hostname for SNI and for the
  certificate check. The scheme is `https` only. On the wasmtime side there
  is no `wasi:sockets`, no `wasi:sockets/ip-name-lookup`, and
  wasmtime-wasi-http's default outgoing send is never linked: only the
  host's own `http.request` exists.
- **Per instance.** Grants, tokens, keys and budgets are scoped to one
  factory instance on a shared host.
- **Only the credential differs by side:**

  | Side | Credential kinds it may attach |
  | --- | --- |
  | an adapter's `http.request` | per route, as the vetted entry says (10.3) |
  | a driver under `net:` | none in 2.x |
  | a view, through the proxy | only `github-read`, on `api.github.com` (6.4) |
  | any side, to `parent` | the parent's own auth for that load or call, never the session cookie; writes only after a confirm |

- **Laws:** a glob in a manifest is refused; `*` and `https://*.com` in the
  setting are refused; an adapter widened by the setting is refused; a
  widened origin of an ordinary plugin shows in `tehas status`, with no
  credential attached; an origin allowed for one side is allowed for the
  other, with the same narrowing; a narrowed origin refuses both the
  driver's and the view's request; the view's and the adapter's requests
  share one record format; setting the proxy variables changes nothing;
  a component that imports `wasi:sockets`, `ip-name-lookup` or the default
  outgoing send is refused at vetting and at instantiation; nothing is
  granted from a manifest alone, and a third-party origin waits for the
  person's approval by name; a method or body outside an origin's policy
  is refused, and a widened origin takes only `GET` and `HEAD` with no
  body; a grant of instance A is unusable from instance B; an unexposed
  parent route is refused; a parent
  write without a confirm is refused; `parent` can't be narrowed or
  declared; a cookie never travels to the parent through the proxy.

### 5.2 Destinations can't be spoofed

The owner: "can we ensure destinations can't be spoofed via some
/etc/hosts hack" (decision 55).

- **TLS is always verified,** against the CA roots tehas ships
  (`webpki-roots`, pinned in each release), never the system trust store.
  A locally added CA isn't trusted. No setting turns verification off.
- **Names are the host's.** The plugin API has no DNS: an adapter hands
  the host a request (an origin id, a method, a path, a body), and the host
  vets it against the routes and makes it, or refuses it (decision 56). How
  the host resolves names is internal. What makes a spoofed name harmless
  is the guards here and the address checks of 10.3, which run on every
  new connection.
- **On the upstream path** the factory connects only to the pinned
  upstream, so no supplier name is looked up there.
- **The upstream's key is pinned.** `TEHAS_ADAPTER_UPSTREAM_SPKI`, new and
  marked building, is a set of sha256 hashes of the upstream certificate's
  subject public key, the current one and the next, beside
  `TEHAS_ADAPTER_UPSTREAM`. A key in neither holds the adapter with the
  named cause `upstream key mismatch` (10.7). An upstream set without it
  stops with 78.
  - **Rotation order:** the managing system adds the next key's hash to
    the setting; then the upstream starts serving the next key; then, once
    no connection uses the old one, the old hash is taken out. A step out
    of that order holds, and never fails open.
- **Peer keys are recorded.** Each connection records the SHA-256 hash of
  the peer certificate's public key. A change for an origin that takes the
  credential shows as a warning in `tehas status`, not a hold, because CAs
  rotate keys.
- **Out of scope: root on the host.** Root can change anything here. The
  login user can't change the units or the bundled roots.
- **Laws:**
  - an origin resolved to a server whose certificate is for another name
    is refused, and no credential is sent;
  - a locally added CA isn't trusted;
  - an `/etc/hosts` entry or a DNS answer that points an origin elsewhere
    ends in a refused TLS handshake or a refused address, and the
    credential is never sent;
  - an upstream key mismatch holds the adapter.

### 5.3 Communications hardening

The owner chose all four groups (decision 57). In the standard's words
(§14): a plugin process that needs no network gets none, by kernel rule,
and the `http.request` server sends only to the TLS port; TLS 1.3, or 1.2
with AEAD only, with no 0-RTT, and mutual TLS to an upstream with a client
certificate per host bound to its key; body caps count bytes after
decompression, and only `gzip` or `identity` are accepted. The systemd and
nftables settings below are this host's own.

- **TLS.**
  - TLS 1.3, or TLS 1.2 with AEAD cipher suites only.
  - No renegotiation.
  - No 0-RTT early data in either direction, because a replayed write
    could repeat. This holds for the adapter host's outbound connections
    and for the upstream.
  - Laws: a server that offers only TLS 1.1, or a TLS 1.2 suite that isn't
    AEAD, is refused; a renegotiation is refused; no request is sent as
    early data, and early data offered by a server isn't accepted.
- **Mutual TLS to the upstream.**
  - Each factory has its own client certificate. Its key is generated on
    the host and never leaves it, and the managing system binds the
    factory's key to it.
  - The upstream key header (`Tehas-Upstream-Key`, 10.4) stays, but it's
    useless without the certificate.
  - The certificate and key are versioned, so a rotation has two valid at
    once.
  - New settings, marked building: `TEHAS_ADAPTER_UPSTREAM_CERT` and
    `TEHAS_ADAPTER_UPSTREAM_CERT_KEY`, the paths of the certificate and
    its key. The key reaches only the adapter host's user, through
    `LoadCredential=`. A missing or unreadable one stops with 78.
  - Laws: a connection to the upstream without the client certificate is
    refused by the upstream, even with the key header; during a rotation
    both versions are accepted; the key is readable by no user but the
    adapter host's.
- **systemd and nftables fences,** installed by `bootstrap.sh root`.
  - Both units: `NoNewPrivileges=yes`, `ProtectSystem=strict`,
    `PrivateTmp=yes`, an empty `CapabilityBoundingSet=`,
    `RestrictNamespaces=yes`, `LockPersonality=yes`,
    `SystemCallFilter=@system-service` and `LimitCORE=0`.
  - The operator: `RestrictAddressFamilies=AF_UNIX` and
    `IPAddressDeny=any`, so the kernel guarantees it has no network.
  - The adapter host: `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`.
  - An nftables rule on the `tehas-ad-<instance>` uid (`meta skuid`): on
    the direct path it may connect out only on TCP port 443; on the
    upstream path only to the pinned upstream address and port. As defence
    in depth beyond the address checks, the rule also refuses at the
    network layer loopback, private, link-local, the shared address space
    of RFC 6598, IPv6 unique local, multicast and metadata addresses, and
    the host's own internal ranges.
  - Tests: the operator can't open an inet socket; the adapter host's user
    can't reach port 80 or 22.
- **HTTP and decompression.**
  - HTTP/1.1 or HTTP/2 over TLS only: no h2c, no HTTP/1.0, no `Upgrade`.
  - HTTP/2 has limits on concurrent streams, on the header list's size and
    on the frame size.
  - An answer's `Content-Encoding` is `gzip` or `identity` only. Any other
    is refused.
  - Body caps count the bytes after decompression, and the stream is cut
    when the cap is reached.
  - Laws: a gzip bomb (a small body that inflates past the cap) is cut at
    the cap and refused as `Unread(TooLarge)`; an `Upgrade` or h2c answer is
    refused; an encoding other than `gzip` or `identity` is refused.

### 5.4 Request ids and idempotency

The owner: "any other verification, request ids for idempotency or
something similar" (decision 58).

- **A request id for each port call.** Core issues `Tehas-Request-Id`, 128
  random bits, for each port call. It travels from core to the adapter
  host, to the upstream, and to what the upstream runs behind its URL, and
  every hop records it beside the supplier's own request id
  (`X-GitHub-Request-Id`). It's a header the host sets: the adapter can't
  set it, and reads it only for its own call.
- **An idempotency key for each write intent.** Core derives the
  `Idempotency-Key` from the write's intent (the port method, its target
  and the sha256 of what it writes), and persists it in the state store
  before the first send. Every retry reuses it, across calls and
  restarts. The upstream keeps each key with its final answer (a 2xx or a
  definitive 4xx, never a 5xx or a time-out) for 24 hours, and for a repeat
  it returns the stored answer without sending the request again. A key
  reused with a different request body is refused. On the direct path
  there's no store, so the marker and the hold below apply.
- **What counts as sent.** For a write, any failure after the first byte
  leaves the host's socket is `Sent::Maybe`: the adapter host crashing
  mid-write, a 5xx or a reset after forwarding, an upstream time-out. Only
  a failure proven to have happened before sending is `Sent::No`.
- **`Sent::Maybe` settled by marker.** A write that creates an object (a
  pull request, an issue, a comment, a release) carries its key in a
  tehas marker in the object's text.
  - It fits the ports' marker rules: it's a new kind of the ports'
    `MarkerKind`, which may grow (an older reader reads it as `Unknown`),
    and its text form is a row of the adapter's table, written and read by
    the adapter alone (`console/github/src/markers.rs`, `table.rs`).
  - Only a wrapped marker of this kind, in this object's own text, counts.
    A quoted or fenced one, a bare one and another item's one are no
    marker, as the ports' rules already say.
  - Found means sent, and the write is never sent again.
  - Not found leaves the write **held**, with the named cause `write not
    settled`, as the ports' outcomes say: `Sent::Maybe` is never sent again
    on that answer. The host reads again each pass within the settle
    window (10.9). It sends again only under the same idempotency key, once
    the upstream says that key is dead, or when a person releases it.
- **Answers checked against the request.** A write succeeds only if the
  object the answer returns matches what was asked: the repository, the
  kind, the number where one was named, and the sha256 of the title and
  body sent. A mismatch is a failure, never a success. A mismatch after a
  2xx is `Sent::Maybe` (`Unread(Inconsistent)`, sent), and is never sent
  again.
- **Frames in order.** The local socket's frames carry a sequence number
  for each connection (10.10), and a duplicate or out-of-order frame is
  refused.
- **Laws:**
  - a repeated key on the upstream path returns the stored outcome, with no
    second request;
  - a key reused with a different body is refused;
  - `Sent::Maybe` with the marker present settles as sent;
  - a crash mid-write, a 5xx or reset after forwarding, and an upstream
    time-out are each `Sent::Maybe`, and only a failure before sending is
    `Sent::No`;
  - an unsettled `Sent::Maybe` stays held and isn't sent again until the
    upstream says its key is dead or a person releases it;
  - a retry after a restart reuses the persisted key;
  - the upstream never stores a 5xx or a time-out as a key's answer;
  - a mismatch after a 2xx is `Sent::Maybe` and isn't sent again;
  - an answer for another object is a failure;
  - a duplicated frame is refused.

## 6. Views

- **Isolation is the security boundary.** Views are served by the gate at
  `plugin-<name>.<domain>` behind the sign-in, with the per-document CSP
  built from hashes and the `Permissions-Policy`, as now. Revision 5 adds
  the sandboxed frame (H8, below).
- **The view's frame is a sandbox (H8).** `<tehas-plugin-view>` frames the
  view in an `<iframe sandbox="allow-scripts">`, without
  `allow-same-origin`:
  - the view gets an opaque origin: no cookies, no storage, no session to
    borrow;
  - no `allow-popups`, `allow-forms`, `allow-top-navigation`,
    `allow-downloads` or `allow-modals`;
  - a `Permissions-Policy` that denies every device and powerful feature
    (camera, microphone, geolocation, clipboard, payment, USB, serial, HID,
    display capture, fullscreen), except what H10 opens;
  - the view's CSP is `default-src 'none'`, scripts and styles from the
    gate by hash, and `connect-src` only the host's proxy prefix (6.4);
  - its only channel is `postMessage` with the host element, over one
    `MessageChannel` port (6.3). The host sends the granted feeds. The view
    sends presses, which the host checks against the plugin's grants before
    acting. A view sends no result of its own: a press's result comes from
    the driver, as `answer` (6.3). Revision 5 drops revision-4 wording that
    said the view sends "presses and results".

  The cost: the kit's `feed.js` and `press.js` gain a `postMessage`
  transport. Scripts and workers fetched from the opaque origin (a view's
  `.wasm` comes over the port, 6.1)
  need CORS from the gate (`Access-Control-Allow-Origin: null` for exactly
  those files). Those requests carry no cookie, so the gate serves a view's
  files under a path minted for each signed-in load, never to a bare URL
  (owner question in the pull request). A spike comes first (part 9): a
  view on the kit, a feed, a press, and a jSquash codec in a worker, under
  H8 and H9, in Chromium, Firefox and Safari.
- **Devices by two keys (H10), reserved.** Decision 44: "maybe they can
  prompt the user if they want to". 2.1 builds none of it; the words are
  reserved so that no other surface takes them. A device stays denied
  unless both keys say yes:
  - **the admin's key:** the manifest asks `device:<feature>` (`camera`,
    `microphone`, `geolocation`, `clipboard-write`, `display-capture`), and
    an admin gives the grant by hand. Turning a plugin on never gives it
    (part 4);
  - **the person's key:** the host element then delegates exactly that
    feature to the frame (`allow="camera"`, and the same name in the
    frame's `Permissions-Policy`), and the browser shows its own prompt,
    which the person answers as for any site;
  - the host element shows a lasting sign while a device is in use, naming
    the plugin, and the person can stop it there;
  - a device's data stays in the browser, unless the plugin also has a
    grant to hand a result to the host (`attach:<kind>`, a plugin surface
    request);
  - whether a browser delegates a device to an opaque-origin frame is part
    of H8's spike. Where one doesn't, that device isn't offered there.
- **The web component wrapper.** In the dashboard, a core-owned
  `<tehas-plugin-view name="…">` custom element wraps the plugin's frame. It
  owns:
  - its size;
  - the loading, failed and off states;
  - theme tokens, through a narrow `postMessage` contract;
  - removing the view when the plugin is turned off.

  Plugin code never runs in the dashboard's origin. A shadow root isn't a
  security boundary, so mounting plugin components into core pages is
  refused.
- **Inside its origin**, a view is static HTML, or its entry defines exactly
  one custom element.
  Solid 2 from the gate's kit draws it, using the kit's island contract in
  the light DOM.
- **JSX.**
  - Builders may write Solid JSX (`.jsx`, `.tsx`) in `src/`. Solid's `html`
    templates work with no compile at all.
  - The builder compiles with Solid 2's compiler into `dist/view/`:
    `@solidjs/compiler` 2.0.x (Oxc) or `@solidjs/babel-plugin` 2.0.x, DOM
    mode, ESM. Both give the same imports (spike). There's no
    `babel-preset-solid` 2.x release; its newest 2.x is a release candidate.
  - The manifest names the `solid-js` version the output expects (today
    2.0.3), not the compiler's version, and tehas refuses one the kit doesn't
    carry.
  - Compiled output imports Solid's runtime helpers from `@solidjs/web` and
    the author's own names from `solid-js`. The gate's page maps both to the
    kit's Solid with an inline import map, allowed by its sha256 in the CSP
    (verified in Chromium 159; Firefox and Safari still to check).
  - Vetting (part 3) checks every `@solidjs/web` and `solid-js` import in
    `dist/view/` against the kit's export list, so a newer compiler's new
    helper is refused at vetting, not at view load.
  - 2.0 compiler facts for builder docs: `on:`/`attr:` are removed; a
    fragment nested in an element is refused; a custom element's value is an
    attribute unless written `prop:name`.
- **Kit change (core).** The kit's Solid exports only `html`, `render`, the
  signal and store functions and the control-flow components. Compiled JSX
  also needs these 14 (spike, both compilers):
  - `template`, `insert`, `createComponent`, `delegateEvents`;
  - `spread`, `effect`, `memo`, `mergeProps`, `ref`;
  - `setAttribute`, `className`, `setStyleProperty`;
  - `heldRead`, `readShallow`.

  `tools/vendor-solid` exports them from `@solidjs/web`. Cost: +589 bytes
  raw, +210 gzip (123,689 to 124,278); `pages.max` becomes
  `library solid 124278`. `Dynamic` and `Portal` stay out (+5.9 KB raw for
  little glue value). Before freezing the list, compile a wider corpus (SVG
  `class`, dynamic `style` strings, `Repeat`, `Reveal`). Views don't
  hydrate gate HTML, so `hydratable` output is refused. Exporting
  `mergeProps` needs a carve-out in the ratchet that bans that 1.x name in
  `host/fun`.
- **Types.** The kit's `solid.d.ts` alone can't type `.tsx` (49 errors: no
  `JSX` namespace, no `@solidjs/web/jsx-runtime`). Builders add
  `@solidjs/web` at the kit's version as a type-only devDependency, and
  `solid.d.ts` gains `export type Element` and typed `For`, `Show`,
  `Switch`, `Match`, `Loading` and `Errored`. With that, `tsc --strict`
  passes and catches real errors (spike). These are front-end decisions for
  tehas; they change the kit's MANIFEST and byte limit.
- **Size.** `dist/view/` has a byte cap, like core's `pages.max`. Verified
  libraries count toward their own cap.

### 6.1 Heavy work in the browser, in WebAssembly

Decision 26: heavy work offered by a view runs on the client where possible,
in WebAssembly built from C or Rust.

- **Where it runs.**
  - Data that starts in the browser runs in the view's module, on the
    client. That covers a picked or pasted image, a file the user is about
    to upload, a canvas or a recording. Examples: image compression, resizing
    and format conversion (JPEG, PNG, WebP, AVIF), hashing, diffing,
    parsing, PDF rendering and text extraction.
  - Data that is already on the host (repository files, run output) stays
    with the driver and its modules in the operator (part 1.1). It isn't
    shipped to the browser to be worked on.
  - "Where possible" fails in three cases. Then the work goes to the driver,
    or to core through a plugin surface request:
    - the work needs a grant (files, git, the model);
    - the result must be trusted by the host;
    - the browser can't do it within the view's limits.
- **Why.** The work costs the user's machine, not the factory host's. The
  host never decodes untrusted media, and the bytes go up once, already
  compressed. It also keeps the operator's caps small.
- **Layout.** A view's modules go in `dist/view/wasm/<name>.wasm`, with the
  JS that loads them in `dist/view/`. The manifest lists each one as a view
  module.
- **Tooling.** The builder picks it, and tehas consumes only the output
  (decision 8):
  - Rust: `wasm-bindgen` (with `wasm-pack`), or a plain `cdylib` with a few
    hand-written exports.
  - C and C++: Emscripten, or clang with wasi-sdk for code that does no I/O.
  - Ready-made codecs: the Squoosh codecs (mozjpeg, oxipng, libwebp, libavif,
    resize) as packaged by jSquash, and `image`/`photon` in Rust. A packaged
    codec is a verified library in `dist/vendor/`: its hash is checked
    against upstream, and it counts toward the vendor cap (part 3).
  - A vendored `.wasm` is still a view module. The manifest lists it, and it
    turns on `'wasm-unsafe-eval'`. Its upstream hash stands in for the name
    section and the rebuild, as a verified library's does for the
    readable-code rule. The import rule and the no-threads rule still
    apply.
- **CSP.** Only a view that lists view modules gets `'wasm-unsafe-eval'`
  added to its `script-src`. That keyword allows compiling WebAssembly and
  nothing else: no `eval`, no inline script. Under H8 the frame has an
  opaque origin, so `'self'` names nothing:
  - `connect-src` names only the host's proxy prefix for the load (6.4);
  - the host element sends each vetted module's bytes over the view's
    port, in a `module` message (6.3), and the view compiles them with
    `WebAssembly.compile`. So a module and its JS can't send data
    anywhere.

  Revision 4 said `connect-src 'self'`, and revision 5 opened the module's
  path, which revision 6 closes: modules come over the port. The spike checks this.
- **WebAssembly in the browser is third-party code in a box (H9).**
  - **Pure compute only**, the server's rule. Its imports are memory and a
    short allow-list of glue helpers: for `wasm-bindgen`,
    `__wbindgen_throw` and the string and memory helpers; for Emscripten,
    `emscripten_resize_heap` and a null `fd_write`. Any import that binds a
    web API (`__wbg_*` from `web-sys` or `js-sys`, fetch, DOM, storage,
    WebSocket) is refused at vetting.
  - **Always in a dedicated module worker** (`new Worker(url, {type:
    "module"})`, from `dist/view/`), never on the view's main thread: no
    DOM, bytes in and out through `postMessage`. Import maps don't apply in
    workers, so worker code doesn't import the kit.
  - **The worker's own CSP.** The gate serves worker scripts with
    `default-src 'none'; script-src` the plugin's own `view/` path and
    `'wasm-unsafe-eval'`, and `connect-src 'none'`. The view hands the
    worker a module's bytes by `postMessage`, so the worker fetches
    nothing and sends nothing.
  - Inside H8's frame, so the worker inherits the opaque origin.
  - A vendored codec (jSquash, Squoosh) is verified by its upstream hash,
    and still meets the import rule and runs in the same box.
- **Rules**, the same audit as part 1.1:
  - name section required;
  - imports recorded, and every import must be satisfied by the plugin's
    own vetted JS (the `wasm-bindgen` or Emscripten glue), within H9's
    allow-list. The glue is plugin JS under the readable-code rules, or
    part of a verified library;
  - threads and shared memory refused, because they need
    `SharedArrayBuffer` and cross-origin isolation headers on the gate;
  - SIMD allowed;
  - our own plugins must reach "rebuilt from source: matches" (part 4).
- **Limits.**
  - 8 MiB per module, and `dist/view/wasm/` has its own cap (part 3).
  - A view module can't gain any grant. All it reaches is what the view's
    JS hands it.
  - A run that is too heavy or too slow is the user's tab's problem, not
    the host's. The view shows progress, and a cancel that ends the worker.
- **Spike.** Not covered by part 9's first spike. Add one check: compress a
  picked image with jSquash's mozjpeg and WebP codecs in a worker, under the
  view CSP plus `'wasm-unsafe-eval'`, in Chromium and Firefox, and record
  the module sizes and timings.

The example plugin (tehas-app/tehas-plugin-example#1), the template every

- **The viewer's login. DECIDED** (decision 54): by the roadmap manager
  under the owner's grant, 2026-11-25, for the owner's review

- **The manifest's name.** The brief said `manifest.json`. This spec's name
  is `tehas-plugin.json` (2.2), and it holds.

### 6.3 The view's channel, presses and the kit

A view in its sandboxed frame (H8) talks only by `postMessage` to its
`<tehas-plugin-view>` host element. In the standard's words (§14's frame
item): every message is typed and versioned and checked against the host's
schema in its `api/`, and one that fails is dropped; a press names one of
the manifest's `actions`, carries a single-use nonce and arguments under
that action's schema, and its answer goes only to the frame load that
pressed, never into the output other viewers see. A frame is known by its
port, never its origin: the host element transfers a fresh
`MessageChannel` port for each load, and a new load revokes the old port
and its nonces. A press that acts as the person needs a confirm drawn in
the host element's own page, outside the frame, naming the action's
manifest label. Messages have caps on their bytes and on their number per
load, and one press is in flight at a time, with the numbers set by the
host (below). Each message is an object with `type` and `v` (the channel's
version, `1`).

| `type` | From | Fields | What |
| --- | --- | --- | --- |
| `port` | host | `v`, and exactly one transferred `MessagePort` | the first message of each load; the channel's port (below) |
| `ready` | view | `v` | the view has loaded and listens |
| `output` | host | `v`, `run` (its id and time), `files` (path to text), `next` (a nonce) | the last run's output, pushed by the host on `ready` and after each run |
| `press` | view | `v`, `action` (an id of the manifest's `actions`), `nonce`, `args` (an object under the action's schema) | a button press, with the single-use nonce of 6.2 |
| `answer` | host | `v`, `nonce`, `result` or `error`, `next` (a nonce) | the result of that press, sent only to that frame load |
| `error` | host | `v`, `code`, `text` | a message dropped or a press refused, by a named code |
| `module` | host | `v`, `name`, `bytes` | a vetted view module's bytes (6.1) |

- **The handshake.** The host's first message to each load is
  `{type: "port", v: 1}`, with exactly one transferred `MessagePort`. The
  view accepts only the first such message from its parent, and drops
  anything that comes before it, and any later `port` message. Every other
  message travels on that port.
- **One port per load.** On each load of the frame, the host element makes
  a `MessageChannel` and transfers one of its ports to the frame, in the
  `port` message. All
  traffic uses that port, and the kit accepts messages only on it. A
  message's origin can't tell frames apart, because a sandboxed frame's
  origin is the opaque `"null"`, the same for every view. So the host
  tells frames apart by their port, and treats every `load` event as a new
  load: it revokes the old port and every nonce issued on it.
- **Nonces.** The host issues each nonce, single-use, in `output` and
  `answer` (`next`), bound to the session and to that port.
- **Limits**, this host's numbers. A message is at most 64 KiB, a load
  sends at most 20 messages a second and 2,000 in all, and one press is in flight at a time. A message past
  a limit is dropped, and the host sends `error` with its code
  (`too-large`, `too-many`, `busy`).
- **Text stays text.** The host element never puts text from a view's
  message into its own DOM except as `textContent`.
- **A press that uses the person's credential needs a confirm first.** An
  action that uses a person's token directly runs only after a confirm
  that the host element draws in its own page, outside the frame, naming
  the action's `label` from the manifest. A law: a press of such an action
  with no confirm is refused.
- **A draft is filed under a person's name only after a confirm shown after
  the run.** When a pressed run leaves a draft (`issue:draft`), the host
  element draws a confirm in its own page, outside the frame, after the
  run. It shows the plugin's name and the exact title and body that will
  be filed. The person confirms or discards it, and nothing is filed
  without the confirm.
  - A draft from a run with no pressing person (`ctx.trigger` `clock` or
    `once`) is refused. It never falls back to the factory's token.
  - Laws: a draft from a press with no post-run confirm is not filed; a
    draft from a `clock` or `once` run is refused.
- **A press runs once and answers.** A press runs the driver's named action
  once, with `ctx.trigger` `press`, within the run's limits, and returns
  its result as `answer` to the pressing frame load only. A press's result
  is never the shared last good output, as 6.2's viewer rule says, and it's
  escaped and capped as part 1.2 says.
- **The kit on a plugin's origin.** The gate serves the kit's `island.js`
  and `kit.css` at the fixed paths `_kit/island.js` and `_kit/kit.css`
  under the per-load path of H8 (part 6).
- **The theme tokens.** Their one owner is the set every theme file sets,
  `host/fun/theme-*.css`, held equal by `test/theme_test.sh`. The host
  element sends those tokens' values for the current theme, light or dark,
  and the kit's `kit.css` uses them (`--bad`, `--text-faint`,
  `--text-quiet`, `--type-small` today).

### 6.4 A view's network: normal HTTPS, always through the host's proxy

The owner: "can we limit client side https access to be via the proxy
too? via the web component or some other encapsulation", then "requests
should be normal https, but be proxied" (decision 60).

- **Normal HTTPS, to the proxy only.** The browser makes real HTTPS
  requests, but only to the host's proxy:
  `https://<dashboard>/_proxy/<load-token>/<origin-id>/<path>`. The frame's
  CSP sets `connect-src`, and `img-src`, `media-src` and `font-src` beyond
  the per-load file path, to exactly that prefix and nothing else. The
  browser blocks any other destination.
- **The kit's `fetch` shim.** Authors write
  `fetch("https://api.example.com/x")`. The shim maps the URL to an origin
  id through the manifest's `origins`, and a same-origin or relative URL
  to `parent` (5.1), rewrites it to the proxy path, and
  calls the browser's own `fetch`. An unmapped URL throws a named error.
  Code that goes around the shim meets the CSP. There's no
  `XMLHttpRequest` or WebSocket shim in 2.x, and the CSP blocks both.
- **The load token.** It's minted for each load of the frame, scoped to the
  plugin, that load and its allowed origins, and short-lived. It's revoked
  on reload, or when the load's port is revoked (6.3), and it's never in a
  cookie. The frame sends `Referrer-Policy: no-referrer`, and its opaque
  origin means no cookie travels.
- **The proxy calls the request gate** (5.1), the same checker the adapter
  host calls, on the plugin's one list of destinations. What the proxy adds
  for a view: no `Cookie` or `Authorization` from the view and no
  `Set-Cookie` back, records that never keep the path's load-token
  segment, and a rate and concurrency cap for each load.

  The plugin gate relays the request over its socket to the adapter host,
  the one egress host (5.1), which runs the request gate and forwards
  through the upstream when one is set, and directly otherwise. The plugin
  gate never connects out, and the operator has no network.
- **No credentials for a view,** with one exception below. A view reaches
  only origins whose `credential` is false. Attaching any other credential
  for a view is out of 2.x without a new decision.
- **Answers are streamed,** with the answer-header allow-list and the caps
  enforced while streaming.
- **The grant is `net:`.** This re-scopes tehas-factory#2761 to this
  design. It's specified now and built when a plugin needs it: it floats.
  The GitHub adapter doesn't depend on it.

#### GitHub GraphQL reads from a view

The owner: "the client might want to do some direct graphql requests to
github and that should be fine" (decision 61). This is the one exception
to "no credentials for a view".

- **The view credential.** The vetted entry marks `api.github.com` with
  `view_credential: "github-read"`. No other origin may carry a view
  credential in 2.x. The proxy attaches the factory's installation token,
  minted read-only (`contents`, `issues`, `pull_requests` and `metadata`
  read) and narrowed to the instance's one repository, so GitHub itself
  lets only that repository, and public data, be read. The token never
  reaches the browser, and no record keeps it.
- **Free-form reads only.** A view may send its own GraphQL to
  `https://api.github.com/graphql` through the shim. The proxy parses each
  document and requires exactly one operation, of type `query`. Mutations
  and subscriptions are refused, and there's no batching.
  - A depth limit.
  - A cost cap. The proxy first asks GitHub for the query's cost with
    `rateLimit(dryRun: true) { cost }`, and refuses a query over the cap
    without running it.
  - A budget of requests and of cost for each load.
- **REST under this credential** is limited to `GET` on the routes the
  vetted entry lists for views.
- **Writes from a view** go only through vetted persisted operations named
  in the manifest's `actions` (6.3), never free-form. Each needs the
  person-acting confirm the host draws, showing what will change, and acts
  as the person who pressed.

#### Laws

- a direct fetch from the frame is blocked;
- an unmapped URL is refused;
- an origin that takes the credential is refused, `api.github.com`'s
  view credential aside;
- a private address is refused;
- an expired load token, or another load's, is refused;
- a `Set-Cookie` never reaches the frame;
- a load token in a record is redacted;
- a free-form mutation from a view is refused;
- a query over the cost cap is refused;
- reading another private repository fails, because GitHub refuses it
  under the narrowed token;
- the token never appears in the frame or in a record;
- a persisted write from a view without a confirm is refused.

## 10. Adapter plugins

An adapter plugin answers tehas's ports for one supplier: tickets,
blueprints, the code host, identity and the board, the joined reads. It's
the second kind of plugin. The GitHub adapter is the first: it leaves core
in 2.1, and it's the one plugin 2.1 requires at launch (decisions 41 and
50, tehas-factory#3321). The other parts of this spec hold for an adapter,
except where this part says otherwise.

**Adapters are a class of their own, with their own guarantees** (decision
51, the standard's §2a):
- **Our own only.** An adapter plugin is on the signed vetted list. The host
  refuses a third-party plugin of `kind: "adapter"`.
- **Called, never acting.** It runs on the host's path only when the core
  calls it through the port, and does only what that call asks. It has no
  schedule, hook, view, tool or gate of its own, and never decides to
  write.
- **Not under the plugins switch.** `TEHAS_PLUGIN`, `TEHAS_PLUGINS_OFF` and
  the turn-on click don't govern it, so a factory with plugins off still
  reaches GitHub. `TEHAS_ADAPTER` chooses it (10.1).
- **The core's hands.** The standard's guarantees 1, 4, 5 and 8 bind
  ordinary plugins. An adapter runs as part of a cycle when the core calls
  it, though never inside the cycle's container (10.5), and it carries out
  the core's writes to the code host, and only those.
- **Down is the port's failure.** A refused or unreachable adapter fails the
  core's call, as an adapter does (R6), never skipped in silence (10.7).
- **Approval stays a person's** (guarantee 9) for every plugin. A merge is
  the core's rule, behind a person's gate, and no plugin, adapter or not,
  has a merge grant.
- Pinned and vetted, fail closed, contained, and the hardening of 1.5 hold
  in full.

### 10.1 The kind and its manifest

- **`"kind": "adapter"`**, the standard's own value of `kind` (its §4). A
  manifest without `kind` is an ordinary plugin. An adapter has no driver
  entry, view, skill, hook, gate, tool or schedule.
- **JavaScript or one component** (the standard's §2a and §8):
  - **JavaScript in the engine** (`"runtime": "starlingmonkey"`), like any
    plugin: effects in one shell module that makes the `tehas.http` calls
    (R13), decisions in pure modules, heavy pure work in `dist/wasm/` core
    modules through `wasm.load`.
  - **One Rust component** (`"runtime": "component"`), in `dist/wasm/` and
    named in the manifest, in place of a driver in the engine. The GitHub
    adapter may be this: `console/github` as one Rust crate, with `gh` and
    curl replaced by `http.request`. Its imports are exactly the adapter
    world's (10.2), listed from the binary, and any other import, a WASI
    interface beyond random and the clocks included, is refused at
    vetting. Inside it, R3 and R13 hold: decisions in pure modules, the
    `http.request` calls in one shell module.
  - `wasm.load` and the engine's JavaScript exports apply only on the
    JavaScript path. A component exports the world's functions itself and
    loads no other module.
  - Part 1.1's audit applies to every core module, inside a component too.
    Our own adapters must be "rebuilt from source: matches", so the recipe
    pins the Rust toolchain and remaps paths so the build reproduces.
- **The manifest:**
  ```json
  {
    "plugin": 2,
    "name": "github",
    "label": "GitHub",
    "kind": "adapter",
    "runtime": "component",
    "asks": ["http"],
    "origins": {
      "api": {"url": "https://api.github.com", "credential": true,
              "methods": ["GET", "POST", "PATCH", "PUT", "DELETE"], "body": "bounded(8388608)"},
      "web": {"url": "https://github.com", "credential": false,
              "methods": ["GET"], "body": "none"},
      "assets": {"url": "https://release-assets.githubusercontent.com", "credential": false,
                 "methods": ["GET"], "body": "none"},
      "objects": {"url": "https://objects.githubusercontent.com", "credential": false,
                  "methods": ["GET"], "body": "none"}
    },
    "adapter": {
      "world": "tehas:adapter@2.0.0",
      "component": "dist/wasm/adapter.wasm",
      "realms": ["code-host", "tickets"],
      "ports": ["tickets", "ticket-writes", "blueprints", "blueprint-writes",
                "code-host", "code-host-writes", "identity", "board"],
      "credential": "github"
    }
  }
  ```
  - `origins` (the standard's field) are the only places it may reach,
    narrowed on the host as 5.1 says, never widened. The
    four above are the hosts `console/github/src/curl.rs` allows today.
    `credential` says whether an origin takes the credential at all.
  - **Vetting refuses an origin** that isn't `https`, or that has a port,
    user information, a path, a query, an IP literal or a trailing dot, or
    whose host isn't a lowercase A-label.
  - `http` (the standard's grant) is given to an adapter alone and refused
    to any other plugin.
  - `adapter` is tehas's own field. `credential` names only the kind of
    credential it needs. The host maps the kind to what it has configured
    (10.4). The manifest never holds a credential.
- **The vetted entry** of an adapter carries its origins, each with its
  `credential` flag, its credential kind and its **route table**. A host
  allows an origin only when both the manifest and the signed entry name it
  with the same flag.
  - **The route table** lists, for each port method, the HTTP methods and
    path templates it may send, the origin of each, and the credential kind
    the host attaches (the factory's, the person's, or none). For example
    `code-host-writes.merge`: `PUT /repos/{owner}/{repo}/pulls/{n}/merge` on
    `api`, the factory's credential.
  - **The repository is the host's.** The host fills `{owner}` and `{repo}`
    from the instance's repository setting (`TEHAS_REPO`). The adapter
    fills only the other variables.
  - Each variable fills one path segment and matches `[A-Za-z0-9._-]+`,
    raw and percent-decoded. A template has no wildcard.
  - Writes with the widest reach are allowed only inside the core's own
    calls for them: a merge only inside the core's merge, a default-branch
    ref update only inside its push, a release only inside its release
    call, and a label write only inside its mark calls.
  - The table is vetted with the code (part 4). A route a commit adds is a
    grant increase and waits for the admin, as part 4 says.
  - The gh relay's verb list, the commands a cycle may send through
    `host/shim/gh`, stays core's and is unchanged.
- **Choosing the adapter** is the admin's act, never the turn-on click of
  part 4, and never the plugins' switch. A new setting, `TEHAS_ADAPTER`,
  marked building:
  - unset: `builtin` until the contract step, then the release's default
    entry, or a newer signed one (10.8);
  - `builtin` is the built-in adapter, while it stays (10.8);
  - `plugin:<name>@<commit>` is a full commit the signed list vets.

  The settings load checks only the value's form (hard rule 3: it reads no
  list and makes no call). Whether the adapter is vetted, and whether its
  world's major is one the host has, is checked by the programs, and only
  the commands that call the code host stop with 78 (10.7).

### 10.2 The `tehas:adapter` world

- **Made from `console/ports`** (`tehas-ports`, `VERSION` `v2.0.0`), with
  one owner for each type (R1). A task in `console/xtask` writes the WIT
  from the crate, and the gate fails when the WIT in `api/` differs. No
  type is written twice by hand.
- **The world.** `tehas:adapter@2.0.0` is the adapter's world, written the
  same way as `tehas:plugin` (the standard's §6). On the JavaScript path the
  engine is built for it once; a component implements it itself.
  - **Exports**, what the adapter implements: `site`
    (`realms`, `meter`, `mark-name`, `marker-text`, `until`), and one
    resource for each handle the `Site` trait makes: `tickets`,
    `ticket-writes`, `blueprints`, `blueprint-writes`, `code-host`,
    `code-host-writes`, `identity` and `board`, with the traits' methods. A
    port the adapter doesn't serve answers `Refused(Unsupported)`, as the
    trait says. `board` may be left out: the host then answers it with the
    ports' default join (`Join`) over the other handles.
  - **Imports**, what the host provides, and nothing else: `http.request`
    (10.3) and `log`, plus `wasm.load` on the JavaScript path only; `ledger` and
    `notices`, the ports' `Ledger` (budgets and health shared across
    processes, answered from the host's state store) and `Notices`. The
    adapter's ledger writes are scoped to its own pools, bounded and
    monotonic, and its notices are fixed codes, never free text; and the
    engine's own random and clocks. No files, git, model, sockets,
    environment or arguments, checked with `wasm-tools component wit` as
    part 1 does.
- **Types follow the ports' rules for growth.** A WIT record is closed, so
  a field the ports add is a minor of the world. An adapter built against
  an older minor still loads, and the host fills the new field with the
  value `new` gives it. An enum that may grow carries `unknown`, and a
  reader fails closed on it, as the ports do. `Outcome` is exhaustive in
  the ports, so a new outcome is a major of the world. Part 5's rule holds:
  no `u64`. A number that may pass 2^32 crosses as its decimal string.
- **No secret crosses into the engine.** `Secret`, `Token` and
  `GitCredential` are resources the host owns. The adapter can pass one
  on or return one, never read it.
  - `Identity::token` and `token_over` stay `Refused(Unsupported)`, as
    `console/github` answers them today. Core mints the installation token,
    as now.
  - `signed_in` returns the account and a secret handle. The host keeps the
    secret in its keyring.
  - `CodeHost::remote` returns the URL. The host fills in the credential.
    A cycle's container gets its credential from core as it does today:
    nothing of the adapter reaches the container (hard rule 4).
- **The shim checks every answer.** Wrong but valid answers are the
  adapter's most likely fault, so the shim holds each one to the world
  before a caller sees it:
  - an answer that doesn't read is `Unread`, never empty;
  - a list is whole only with the ports' proof of its paging (`Whole`, or a
    `Took` whose `more` is settled), never because it ended;
  - a field a minor adds, whose default value could read as success,
    allow or sent, is a major change of the world, not a minor;
  - no destructive act of the dispatcher (a cancel, the tidy, taking a
    label off) follows from an absence alone. It needs a positive answer.

  A law covers each: a malformed answer reads as `Unread`; a cut list
  without its proof isn't whole; the world's check refuses such a minor
  field; and the dispatcher's tests do nothing destructive when the
  adapter answers with nothing.
- **The laws and the fakes run against an adapter plugin.** A shim in the
  host implements the ports' traits over an adapter's instance, so every law of
  `console/ports/src/laws.rs` runs on it unchanged. It runs against the
  adapter's recorded samples (`console/ports/samples/github/`), replayed
  through a fake `http`. An adapter plugin that fails a law the built-in
  adapter passes isn't approved. `vet.yml` runs the laws for our own
  adapters, and `tehas plugin check` runs them too.

### 10.3 The `http.request` grant

Decided by the owner (decision 47: "ok make it work"). Hardening item H11.
The rules below are the ones the request gate runs for every side (5.1);
this part is where they're written, and the adapter host calls the gate.

- **An adapter-only grant.** `http.request(req)` needs the grant `http`,
  which only an adapter is given (the standard's §5 and §6). `req` holds
  the origin id, method, path, query, headers and body. The adapter calls
  it as `tehas.http` from its shell module (R13). An ordinary plugin has no
  network, and `net:` (#2761) is specified for views in 6.4 and floats: it's
  built when a plugin needs it. It's R14's one exception to
  "no other I/O inside the engine".
- **The credential never enters the engine** (10.4).
- **Every call has a deadline** (H2), within the request budget and caps
  below.
- **Bound to the port call in flight.** The host knows which port method
  it called. It refuses a request outside that method's routes (10.1), and
  any request made while no port call is in flight.
- **The host picks the credential,** from the route of the port call in
  flight, never from the adapter. A person's credential, or a handle to
  it, is valid only inside the port call that received it.
- **The URL is built by the host:**
  - a path is a route's template filled by the host and the adapter
    (10.1). It matches `^/[!-~]*$`, and it holds no `?`, `#`, `\`, `%2F`,
    `%5C` (in either case), `//` anywhere, or a dot segment, in its raw or
    its percent-decoded form. The query is a field of its own;
  - the host takes a parsed URL from the origin, sets the path and the
    query on it, parses the result again, and requires its scheme, host and
    port to equal the origin's;
  - so a request can't name another host, a port, user information or an
    address literal.
- **Headers by allow-list.**
  - A request may carry `Accept`, `Content-Type`, `If-None-Match`,
    `X-GitHub-Api-Version` and the extras the vetted entry names. Vetting
    refuses an extra that's on the refused list below, so an extra can
    never open one. `Host`,
    `Proxy-*`, `Forwarded`, `X-Forwarded-*`, `Connection`,
    `Transfer-Encoding`, `Content-Length`, `Authorization`, `Cookie` and
    `Tehas-Upstream-Key`, `Tehas-Request-Id` and `Idempotency-Key` are
    refused, and so is any value holding CR, LF or NUL.
  - An answer's headers reach the engine by allow-list too: `Content-Type`,
    `Content-Length`, `ETag`, `Last-Modified`, `Link`, `Retry-After`,
    `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`,
    `X-RateLimit-Resource` and `X-GitHub-Request-Id`. No other does, and
    `Set-Cookie`, `WWW-Authenticate` and `Location` never do.
- **Redirects.**
  - A redirect off the allowed origins is refused, and so is one from
    `https` to `http`.
  - One to an allowed origin is followed by the host, at most twice, as
    `curl.rs` does today, and only to a path on a route of the port call in
    flight. On the upstream path it's followed as
    `<upstream>/<class>/<host><path>` (10.4). The credential is dropped unless
    the target is the same origin and that origin's `credential` is true. A
    body is never sent again.
- **Addresses.** The host resolves an origin's name once for each
  connection and connects to the address it checked, and checks again on
  every redirect. It refuses loopback, private, link-local and tailnet
  addresses; IPv4-mapped IPv6; `0.0.0.0/8`; the shared address space of
  RFC 6598; NAT64's well-known prefix (RFC 6052); 6to4 (RFC 3056); IPv6
  unique local addresses (RFC 4193); multicast; and cloud metadata
  addresses. The upstream (10.4) is the one name exempt.
- **GraphQL carries only vetted persisted operations.** In the standard's
  words (§2a): a route is an HTTP method and a path template, or a
  persisted GraphQL operation, its name and the sha256 of its exact
  document; the adapter sends a name and variables, never a document; a
  mutation appears only in a write method's routes; the host fills in the
  target; and the credential SHOULD be narrowed to the port call's
  permissions and its one target. The built-in
  adapter uses `gh api graphql` widely (`ticket.rs`, `port/board.rs`,
  `port/blueprints/edits.rs`, `port/code_host.rs`, `releases.rs`,
  `port/identity.rs`), so `POST /graphql` is fenced like the routes:
  - the vetted entry lists, for each port method, the operations it may
    send, by name and by the sha256 of each one's exact document text;
  - the adapter sends an operation's name and its variables, never a
    document. The host looks the document up by name, checks its hash, and
    refuses an unknown name or a hash that doesn't match;
  - the host injects `owner` and `name`, and any repository id, from
    `TEHAS_REPO` into the variables. The adapter can't set them, and a
    variable named like a repository locator (`owner`, `name`, `repo`,
    `repository`, `repositoryId`, `nameWithOwner` and the like) is refused;
  - mutations appear only in write methods' lists. The merge, ref,
    release, review and label mutations (`mergePullRequest`,
    `enablePullRequestAutoMerge`, `updateRef`, `createRef`, `deleteRef`,
    `createRelease`, `addPullRequestReview`, `addLabelsToLabelable`,
    `removeLabelsFromLabelable` and their kin) appear only in the core's
    merge, push, release, review and mark calls;
  - a person's token is used only for operations whose document names no
    repository but the injected one;
  - **one operation, of the right type.** Vetting parses each document and
    requires exactly one operation in it: a `query` for a read method, and
    a `mutation` only for a write method. A `subscription` is refused. The host checks the parsed type
    again when it sends. No batching and no arrays: the host builds the
    body itself from one operation's name and its variables. Aliases and
    fragments are allowed;
  - **node IDs belong to the repository.**
    - At vetting, every ID position is typed from GitHub's schema with its
      object kind (a pull request, an issue, a label, a labelable, a
      review's subject), IDs nested in `input:` objects included.
    - The host accepts an ID only where it came back in this call's
      answers on an object whose own `repository`, or its parent's for a
      nested object, equals `TEHAS_REPO`, or where the core passed it.
      An ID merely seen in an answer about this repository isn't enough.
    - Any other ID is resolved before sending, with
      `node(id){... on <kind>{repository{nameWithOwner}}}`. That lookup is
      its own vetted query, sent with the narrowed installation token and
      counted in the budget. It's refused on `null` or a wrong kind, and
      unless the name equals `TEHAS_REPO`, compared without regard to
      case.
- **Secrets in answers.** The fields of an answer that carry a secret are
  named per route in the vetted entry, and the host cuts them out before
  the engine sees the body. At run time the host also scans each answer
  for the bytes of the secrets it has configured, and refuses an answer
  that holds one.
- **A request budget, paging limits, body and time caps** (10.9).
  - Each failure comes back as a named error, which the adapter maps to the
    ports' outcomes, as `console/github` does today: a time-out is
    `Unavailable` with whether it was sent, a body past its cap is
    `Unread(TooLarge)`, a spent budget is `Spent`. A named error never
    carries a URL's query or a header value.
  - Retries are the adapter's, within the budget (R6).
  - A write port call reserves its requests up front, or is refused whole
    before it sends anything.
  - After an answer of `Sent::Maybe`, any further non-idempotent request
    on the same route is refused in that port call. A read settles it, as
    the ports say.
- **The host's configured upstream** (10.4) is allowed besides the
  origins. It stays generic: a URL and a key, naming no system behind it.
- **Every request is recorded** (the standard's §14: origin, method, path,
  status, size, time): its time, the plugin and the instance, the port
  call it served, the destination id, the method and path without its
  query, the resolved and the connected IP, the decision with its reason,
  the status, the bytes each way and the time it took. Never its credential, a header value or a body. The
  records are kept in the state store for 7 days and shown by `tehas
  plugin log <name>`. The adapter's `log` lines are redacted as H7 says.
- **Tested,** one law or test for each rule:
  - a request outside the port call's routes, and one with no call in
    flight, are refused;
  - the credential follows the route, never the adapter, and a person's
    handle used in a later call is refused;
  - a merge, a default-branch push, a release and a label write outside
    the core's own calls are refused;
  - paths holding `?`, `#`, `\`, `%2F`, `%5C`, `//` anywhere, or `.` or
    `..` segments, raw or encoded, are refused, and no path changes the
    origin after the second parse;
  - a `{repo}` the adapter tries to fill, or a variable that names another
    repository, is refused: every request names the instance's repository;
  - a redirect to a path on no route of the call in flight is refused;
  - an extra header that's on the refused list fails vetting;
  - an unknown GraphQL operation, or one whose document's hash differs, is
    refused;
  - a merge mutation sent from a read call is refused;
  - another repository's `owner` and `name` in the variables are refused;
  - a foreign `pullRequestId`, `labelableId` or `subjectId`, and a
    `node(id:)` read of another repository, are refused;
  - an ID taken from `closingIssuesReferences` that belongs to another
    repository, fed to a mutation, is refused;
  - a `subscription` is refused;
  - a document with two operations, a `mutation` in a read method's list,
    a batched or array body, and a send whose parsed type differs from the
    vetted one are refused, while aliases and fragments pass;
  - each refused header and each CR, LF or NUL value is refused, and the
    refused answer headers never reach the engine;
  - a redirect to another origin, to `http`, or to a credential-less
    origin carries no credential and no body;
  - a name that resolves to each refused address range, first or on a
    redirect, is refused;
  - an answer holding a configured secret is refused, and a cut field never
    reaches the engine;
  - a write call that can't reserve its requests sends nothing, and any
    further non-idempotent request on the same route after `Sent::Maybe`
    is refused;
  - no record, error or log line holds a query, a header value or a
    secret.

### 10.4 The credential, and the upstream

**The credential stays on the factory's host** (decision 48: "the token is
configured in the infrastructure, on the factory's host, never in the
plugin"). On the direct path, the rule:

- It stays where the host's configuration keeps it today: the GitHub App's
  key `~/.config/tehas/github-app.pem`, `TEHAS_GITHUB_APP_ID`, the sign-in
  client's `github-app.client-id` and `github-app.client-secret`, and the
  installation token that `tehasbot github-token` mints from them
  (`console/ops/src/github.rs`). There's no new place to store a secret.
- **The adapter host never reads the App's key or the client secret.**
  Core mints the installation token, and core makes a person's sign-in
  code exchange. The adapter host gets only short-lived tokens, and
  attaches them to each request.
- **Narrowed to the caller and the one repository.** Core mints each
  caller's installation token with `repositories` narrowed to the
  instance's one, and `permissions` narrowed to that caller's port set
  (10.5): `contents`, `issues` and `pull_requests` read-only for the MCP
  server and the plugin gate. Today `App::mint` in
  `console/ops/src/github.rs` is called with `narrow` None, which asks for
  everything the installation has. Core changes that call to pass the
  narrowing.
- **Tokens travel with the port call.** Core passes each token over the
  caller's checked socket (10.5) with the port call it's for, as a handle
  with its expiry. A person's token travels the same way, with the call
  that serves that person (10.3).
  - A person's token is used only for these fixed calls, and 10.3's rule
    for node IDs binds every request that carries it. Today they're
    `ticket-writes.open` for `issue:draft`, and identity's read of the
    viewer. A new one is a change to this spec.
  - Every token handle, installation tokens included, is dropped when its
    call ends. A later call can never use it.
  - When fewer than 10 minutes are left, the adapter host asks core for a
    new one before it sends. Renewal happens only inside a call, over that
    caller's own socket.
  - A token that expires during a call ends that call as `Unavailable`,
    not sent. It's never retried with the stale token.
  - `LoadCredential=` carries only the upstream key (below), never a
    supplier token.
- The plugin, its manifest, its repository, its `dist/`, the signed list
  and the operator's plugin state never contain it. The manifest names only
  the kind (`"credential": "github"`), and the host maps the kind to its
  configured credential.
- Rotating the token is a host action. The plugin needs no change and no
  new vetting.
- A missing or malformed credential stops the commands that call the code
  host with 78 before any request (hard rule 2, and 10.7). The factory
  holds, and says which setting is missing.
- A cycle's container still gets nothing from `~/.config/tehas` (hard
  rule 4).
- **Tested:** a fixture adapter that asks every import for the token,
  sends its own `Authorization` header, and looks for an environment gets
  nothing: no environment import links, the header is refused, `token`
  stays `Refused(Unsupported)`, and no answer the adapter sees holds the
  configured token's bytes. A law of the adapter's tests, run on every
  adapter. A second test: the adapter host's unit has no read access to
  `github-app.pem` or the client secret.

**The upstream: a generic proxy, or direct** (decisions 49 and 52).

- **The factory sees a generic upstream:** a proxy URL and a key. With an
  upstream set, the upstream attaches the supplier's credential, and the
  factory holds no supplier token.
- **A managing system may set that upstream,** and for a factory it
  manages, that upstream is the default. What the managing system runs
  behind the URL is its own spec, not this one.
- **Direct.** A standalone factory goes direct. Its host then attaches its
  own configured credential, by the rule above.
- **The protocol to the upstream:**
  - the host sends `<upstream>/<class>/<host><path>`, with the query:
    `<host>` is the full approved origin's host, never a plugin-chosen id
    alone, and `<class>` is the credential class the host sets, `adapter`,
    `github-read` or `none`. It never sends a full target URL, and never
    uses `CONNECT`;
  - traffic that isn't an adapter's never takes the class `adapter`, so an
    origin a third-party plugin names like the adapter's gets no
    credential;
  - the key goes in one header the host sets, `Tehas-Upstream-Key`. The
    adapter can never set it: it's on 10.3's refused list;
  - the upstream follows no redirect with a credential off the origin. A
    redirect it returns is handled by the host as 10.3 says;
  - the upstream's address is resolved and pinned when the adapter host
    starts, and its name is the one exempt from 10.3's refused addresses.
- **The settings,** new and marked building:
  - `TEHAS_ADAPTER_UPSTREAM`: `direct`, or an `https` URL;
  - `TEHAS_ADAPTER_UPSTREAM_KEY`: the key for that URL, kept where the
    model keys are (`TEHAS_MODEL_KEY_<NAME>`), so there's no new place for a
    secret. It reaches only the adapter host, through `LoadCredential=`,
    never through an environment file. Neither the operator nor a cycle is
    given it.

  A missing or malformed value, or a missing key or credential for the
  path chosen, stops the commands that call the code host with 78 (hard
  rule 2). There's no fallback from the upstream to direct or back, silent
  or otherwise.
- **The plugin can't tell which path is in use.** The origin list, the
  routes, the budget, the caps and the records apply on both, in the
  factory's host. The standard's §14 fences `http.request` the same way on
  both: a deadline, a request budget for each run, a page limit, body and
  time caps, and every request recorded.
- **If the upstream is down,** the factory holds and says so (10.7). That's
  accepted: the factory has no other credential to use.

### 10.5 Where the network lives: the adapter host

**Decided in this revision: egress lives in the adapter host**
(the program `tehas-adapter`, run as `tehas-ad-<instance>` under a
system unit of its own), and the operator keeps no network.

- **Rejected: network access in the operator for adapter runs only.**
  Part 1's promise is that an escape from the engine lands in a sandbox
  with no network, a read-only root and no capabilities. A process either
  has sockets or doesn't: the operator can't have the network for an
  adapter's run and not for the plugin run beside it. An engine escape in
  any plugin would then reach the network, and on the direct path the
  factory's credential.
- **The trust boundary.**
  - The standard's §14, first host item: the processes that run plugins
    (the operator, the adapter host) each run as an OS user of their own,
    never the core's, and reach the core only through its sockets. Here
    each is a dedicated system user that bootstrap creates (below).
  - The core programs keep the login user, as installed today under
    `systemctl --user`. A compromised core program already holds the login
    user's files, the App's key among them, so a uid between two core
    programs would add nothing.
  - The operator's user can reach none of the adapter host's sockets.
- **One socket per caller, no confused deputy.** Callers are separated by
  socket path. Each instance has its own socket directory and its own
  group, and each caller has a socket of its own there. On each connection
  the adapter host checks with `SO_PEERCRED` that the peer is the login
  user and holds that instance's group, so a socket serves one instance
  only. Each socket
  serves a fixed set of port methods, so a program that uses only its own
  socket, such as the MCP server or the plugin gate, can't be made to act
  with another caller's ports:

  | Caller | Ports |
  | --- | --- |
  | the dispatcher (`tehas-dispatch`) | reads and writes |
  | the cycle supervisor (`tehas-cycle`) | reads and writes |
  | the console (`console`), which serves the commands and the plugins' code host (below) | reads and writes |
  | the MCP server (`tehas-mcp`) | reads only |
  | the plugin gate (`tehas-plugin-gate`) | identity and access only, and the relay of views' proxied requests (6.4) |

- **The plugins' code host is served by the console.** An ordinary plugin
  never reaches the adapter. The console makes these
  fixed calls for it, before or after a run, never during one:
  - the `issues` and `cycles` inputs: `tickets.list`, `tickets.ticket` and
    `blueprints.blueprint`, written for the run to read with `fs.read`;
  - `issue:draft`: `ticket-writes.open`, as the signed-in person who
    pressed, from the run's record, only once that person confirmed the
    exact title and body after the run (6.3). A draft from a `clock` or
    `once` run is refused;
  - `issue:advisory`: `ticket-writes.open` as the factory, under its own
    caps (part 4).

  Who pressed, for `issue:draft` and any other call that acts as a person,
  comes from the plugin gate's session record, which the operator's user
  can't write, never from the run. These calls send only a title and a
  body: no labels, assignees or milestone.

  The plugin runner, under the operator's user, reaches the code host only
  through the console, never the adapter host's socket. That's how 10.6's
  callers fit the operator's refused user.
- **A 2.1 change to the host and bootstrap.**
  - **Users per instance.** `bootstrap.sh root` creates, for each factory
    instance (`<instance>` is the instance directory's name), the system
    users `tehas-op-<instance>` and `tehas-ad-<instance>`,
    `tehas-op-<instance>-3p` for the third-party tier of 1.3, so 1.3's
    promises hold, and `tehas-vx-<instance>`, the egress user for views
    (below).
  - **The names are checked first.** `useradd` takes at most 32
    characters. The longest name, `tehas-op-<instance>-3p`, adds 12
    characters to the instance name (`tehas-vx-<instance>` adds 9), so an
    instance name is at most 20 characters. Bootstrap refuses, before it
    writes anything, an instance name that doesn't match
    `^[a-z][a-z0-9-]*$` or is longer. A test gives it a name with a newline
    and one with sudoers syntax, and both are refused.
  - It installs their system units in `/etc/systemd/system`,
    `tehas-op-<instance>.service`, `tehas-op-<instance>-3p.service` and
    `tehas-ad-<instance>.service`, with `User=` set, and makes the sockets'
    directory with the login user's group.
  - **No root from the rule.** It installs a rule that lets the login user
    start, stop and restart exactly these units, and nothing else: either
    sudoers lines that are each one full literal command with no wildcard
    (`/usr/bin/systemctl restart tehas-op-<instance>.service`, one line
    per verb and unit), or a polkit rule that compares
    `action.lookup("unit")` exactly and allows only the verbs `start`,
    `stop` and `restart`, never `edit`, `set-property` or `daemon-reload`.
  - **One path for the programs.** The units run the programs from
    `~/tehas/libexec`, as installed today. That directory, and the path to
    it, are readable and executable by these users, and by nothing they
    can write.
  - `install.sh` stops treating these as user units. It puts the programs
    in `~/tehas/libexec` as now, restarts the units through that rule, and
    no longer enables them under `systemctl --user`, as `first_install`
    does today for the other units. If the system units are missing, it
    says to run bootstrap as root and leaves `TEHAS_ADAPTER` on `builtin`.
  - **Adopter action:** before updating to 2.1, run `sudo ./bootstrap.sh
    root <user>` again. It creates `tehas-op-<instance>`,
    `tehas-op-<instance>-3p` and `tehas-ad-<instance>` for each instance,
    their units and the rule. It refuses an instance whose name doesn't fit
    the rule above, and says so.
- **It has only what adapters need:** outgoing HTTPS; the tokens that come
  with each call; the upstream key, by `LoadCredential=`; the ledger, read
  and written through a call that core owns, never the state store's file.
- **Views leave through an egress user of their own.** A view's proxied
  requests (6.4) are relayed to a separate egress process run as
  `tehas-vx-<instance>`, never to the adapter host. It holds no write
  token and no adapter upstream key. Its own client certificate is scoped
  by the upstream to the classes `none` and `github-read`. It runs the same
  request gate (5.1), with 5.3's fences.
- **Its settings come with each call.** Core passes the adapter setting,
  the upstream URL and the call's token with each call. `TEHAS_REPO` comes
  from the egress host's own instance unit, and a call that names a
  different repository is refused.
  Core places the adapter's vetted `dist/` and the signed list in a
  directory the adapter's user can read. The adapter's unit loads no
  environment file.
- **What the units see.** Both units, the operator's and the adapter
  host's:
  - `ProtectHome=tmpfs` (or `TemporaryFileSystem=` over the home), so the
    login user's home is empty to them;
  - `BindReadOnlyPaths=` for only the programs in `~/tehas/libexec`, the
    vetted `dist/`, and, for the operator, the views and the narrow
    repository view;
  - `InaccessiblePaths=` for `~/.config/tehas` and `~/tehas/state/`, in
    case a bind ever reaches them.

  A test for each unit tries to read `~/.config/tehas`, the state store
  and `github-app.pem` as the unit runs, and fails, and checks that the
  vetted `dist/` isn't writable by the unit's user.
- **Nothing else.** No product clone, no model
  socket, no plugin's `/state`, no listening socket but its local one. The
  rest of part 1's sandbox holds: a read-only root, capabilities dropped,
  its own `MemoryMax` and `CPUQuota`. It's part 1.3's separate tier, used
  for adapters.
- **Kernel egress.** With an upstream set, `IPAddressAllow=` and the
  nftables rule name the upstream's addresses alone, and everything else
  is denied. A small root-owned updater that bootstrap installs refreshes
  that allow set: it re-resolves the upstream's name under 10.3's address
  checks, or takes a CIDR set given with the setting. A change it can't
  accept holds the adapter with the cause `upstream address changed`. On the
  direct path, the origins are names whose addresses move, so the kernel
  can't hold the unit to them. An nftables rule still lets the adapter
  host's user connect out only on TCP port 443 (5.3), and 10.3's checks in
  the host are the fence on which host it reaches.
- **No core egress exception.** On the upstream path, core's own mint
  calls and `tehas update`'s fetch of plugins also go out through the
  adapter host, on core-only routes of its socket.
- **A cycle's push credential, on the upstream path.** For a managed
  factory, the upstream mints the cycle's push credential, narrowed to
  contents write, the one repository and the cycle's lifetime. Core asks
  for it through a core-only route on the adapter host, and hands it to the
  cycle as it does today. The cycle container's own network is outside
  this spec, and unchanged (hard rule 4).
- **The cycle's container gains nothing** (hard rule 4). An adapter runs as
  part of a cycle when the supervisor calls it (the standard's §2a), but in
  the adapter host beside the supervisor, never inside the container. No
  socket, mount or variable of it is given to the container. The
  supervisor asks it from outside, as it asks `console/github` today.
- **Not a command.** `tehas-adapter` is installed in `~/tehas/libexec`,
  never on `PATH`, so it's no part under the contract's rule for the
  commands of other parts.
- Both run the same wasmtime and the same vetting. Adapters never run in
  the operator, and ordinary plugins never run in the adapter host.

### 10.6 How the callers take their ports

- **Today** the dispatcher (`console/dispatch`), the cycle supervisor
  (`console/cycle`), the console and the plugin runner build
  `tehas_github::GitHubSite` in their wiring. The MCP server
  (`console/mcp`) builds the forge type `tehas_github::GitHub`, and the
  plugin gate (`console/plugin-gate`) the access check
  `tehas_github::Access`. Those two aren't on the ports' `Site` yet, so
  they move onto the ports' identity and tickets first.
- **The plugin runner** stops building a site of its own: its code-host
  calls move to the console's fixed calls (10.5), so the operator's uid
  never connects to the adapter host. Each caller then takes only its own
  socket's ports.
- **Expand.** A core crate implements `tehas_ports::Site` over the adapter
  host's local socket. The adapter host runs from `~/tehas/libexec` as
  `tehas-ad-<instance>` (10.5). Each caller's wiring, the one place
  `architecture.toml`'s `adapter-wiring` check allows, picks by
  `TEHAS_ADAPTER`: `builtin` builds `GitHubSite` as now, and the plugin's
  value builds the socket's site. Unset builds `GitHubSite` until the
  contract step, and the socket's site, on the release's default entry or
  a newer signed one, after it. Above the wiring nothing changes, and the
  callers' tests run on the fakes as now.
- **Until every caller honours `TEHAS_ADAPTER`,** a caller that doesn't yet
  stops with 78 on a `plugin:` value, so no factory runs half on one
  adapter and half on another.
- **A pass is one instance.** A caller makes handles for a pass. The
  adapter host gives each pass a fresh instance of the adapter and drops
  it at the end, so nothing is shared between two passes or two callers.
  What lasts between passes lives in the ledger.
- **Each caller moves alone,** in its own pull request (R10), and keeps its
  tests (tehas-factory#3325).

### 10.7 When the adapter is down

The factory holds and says why. It never falls back to a wider set and
never answers allow (hard rule 2, decision 47).

- **The causes:** the adapter host down; the adapter trapped or past its
  limits; a world that doesn't load; a spent budget; the upstream down;
  the adapter's commit revoked, or the list unsigned; `adapter busy`;
  `records full`; `client certificate expired`; `mint failed`; `upstream
  key mismatch`; `upstream address changed`; `write not settled`. Each comes back to the caller as an outcome the ports already
  have (`Unavailable` with `Unreachable` and not sent, or `Spent`), and
  names its cause. The callers' fail-closed rules then hold as they are:
  - the dispatcher starts nothing, and its poll says why;
  - authorisation reads no label events, so it authorises nobody (hard
    rule 5);
  - a gate holds (part 1.2);
  - the plugin gate signs nobody in and lets no press through;
  - the MCP server answers the tool with its error.
- **An expired list is no hold** (part 4): the last approved adapter keeps
  running, and `tehas status` warns that the list has expired.
- **The words people see stay the contract's.** The fixed lines of
  `checks.github.last` in the health check and of the `github` line of
  `tehas status` (`GitHub's rate limit was reached`, `GitHub could not be
  reached` and the rest) stay exactly as they are. A cause with no line of
  its own maps to `a call to GitHub failed`. The cause itself goes in a new
  field, `checks.github.cause`, and in an `adapter` line of its own in
  `tehas status`, both only added.
- The host raises one notice for each change of state, through the ports'
  health machine, so `tehas status` and the dashboard say "adapter <name>
  unavailable" once, not on every pass.
- **No fallback.** With the plugin chosen, the built-in adapter is never
  used when the plugin is down, and nothing falls back to anonymous reads.
  The same holds between the two upstreams (10.4).
- **"Holds" means it tries again by itself.** A held caller retries on
  each pass, with no person needed, until the cause clears.
- **Deadlines nest.** Each port call carries its caller's deadline down
  the socket and on to the upstream, in a `Tehas-Deadline` header the host
  sets. Each hop takes what remains, minus a margin, and the upstream stops
  at it. A download gets a caller deadline of its own (10.9).
- **Slots and queues.** Each caller's socket has reserved slots and a queue
  of its own, the dispatcher's first. A call that finds no slot within its
  deadline ends with the cause `adapter busy`.
- **Records first.** Records are capped by size. A request whose record
  can't be written is refused before it's sent, with the cause `records
  full`.
- **Tokens and certificates.** A token's time is measured on a monotonic
  clock from its mint. Core caches the narrowed tokens for each caller. The
  adapter host's unit has `Restart=on-failure`. `tehas status` warns 14
  days before the client certificate expires.
- **No lockout.** Only the commands that call the code host stop with 78
  when the adapter can't be used. Today they're the dispatcher and the
  cycle supervisor, `tehas dispatch`, `tehas plan`, `tehas labels`, `tehas
  refresh`, `tehas github check`, `tehas github writes` and `tehas plugin`.
  A test of `console/src/front.rs` holds the list to the commands whose
  wiring builds a site. `tehas status`, `tehas update` and
  `tehas setup` still run: they say why, and `update` and `setup` are how
  it's repaired. A running service that finds the adapter down holds and
  says so, with no restart loop.
- A write whose answer is `Sent::Maybe` is never sent again by the host. A
  read settles it, as the ports say.

### 10.8 Expand, then contract

- **Expand, in 2.1.** `TEHAS_ADAPTER`, marked building, with `builtin` the
  default. The built-in adapter stays.
- **The proof.** The plugin passes every law and the recorded samples, it's
  on the signed list, and a factory runs on it on a host: a full cycle from
  an issue to a reviewed pull request, and an update from 2.0 to 2.1 that
  goes through (#3327).
- **The release ships a default vetted-list entry** for the GitHub adapter
  (the standard's §2a), not a pin. The entry is signed like any other and
  names a full commit, the `dist/` hash, the origins with their
  `credential` flags and the routes. A newer signed entry from the list may
  replace it between releases, so the adapter keeps guarantee 2: it's on
  its own schedule, not the release's.
- **`tehas update` checks the host first.** Before it stops anything, it
  checks that the system users, their units and the unit rule exist, and
  refuses if they don't, naming `sudo ./bootstrap.sh root <user>`.
  `install.sh` never writes `TEHAS_ADAPTER`.
- **`tehas update` fetches and vets the adapter before it stops anything.**
  `update` fetches the adapter over https with no credential from the
  signed entry's repo at its commit, and checks the `dist/` hash. On the
  upstream path the fetch goes through the adapter host's core-only route
  (10.5), still with no credential. It stops the old services only once the
  new adapter's `dist/` is fetched and matches its entry. If it can't, the
  factory keeps running what it had, and the update holds and says why.
- **Offline, and the newest entry.** A release's own default entry stays
  valid for that release, whatever its `expires`, so a factory that can't
  reach the list still runs. Among the entries it has, the host picks the
  newest whose world minor it supports.
- **Rolling back to 2.0.** 2.0 needs a direct credential configured as 2.0
  had it, the 2.1 settings (`TEHAS_ADAPTER`, the upstream's and the
  origins' settings) taken out, and the system units of 10.5 stopped.
  2.0 refuses the 2.1 settings, so the rollback stops with 78 and names
  them until they're gone.
- **Contract.** Then `console/github` leaves the workspace. `TEHAS_ADAPTER`
  unset means the release's default entry, or a newer signed one. From
  then on `builtin` stops with 78, naming the setting to change. It's never
  mapped to the plugin in silence. The contract already lists the GitHub
  adapter as internal, so this changes nothing in it.
- If the proof isn't green by 2.1's cut-line review, 2.1 ships the plugin
  beside the built-in adapter, and the contract step moves to 2.2.
- After the contract step every factory fetches the adapter plugin. Its
  repository is then public, as hoststats's is, or the private fetch
  (decision 29, #3304) is built first (owner question in the pull
  request).

### 10.9 Performance and limits

- **The dispatcher's poll goes through the adapter plugin.** Its time is mostly
  the network's. The adapter adds an instance for each pass (the
  engine and modules precompiled, so no compile at run time) and a copy of each
  answer across the boundary. Both are measured in part 9 before the
  expand step lands. The poll's own budget (`TEHAS_POLL_BUDGET`, by default
  `cpu=5,wall=30,writes=0`) still binds, with the adapter host's time
  counted in it.
- **The caps**, proposals until the plugins lead and tehas core tune them:

  | Limit | Default | Owner |
  | --- | --- | --- |
  | Time for one request | 20 s, as `console/github` uses today | tehas core |
  | Time for a release file's download, redirects in | 600 s, as today | tehas core |
  | One answer's body | 16 MiB; a file, an attachment or a release file streams to the caller up to the port call's own `limit` | tehas core |
  | One request's body | 8 MiB | tehas core |
  | Requests for one port call (the paging limit) | 100; past it the call ends `Unread(Cut)` | plugins lead |
  | Requests for one pass (the request budget) | 1,000 | plugins lead |
  | Redirects one request may follow | 2, as today | tehas core |
  | Memory of one instance | 64 MiB | plugins lead |
  | Instances at once in the adapter host | 8, one request at a time in each | tehas core |
  | Request records kept | 7 days | tehas core |
  | The settle window for an unsettled write (5.4) | 10 minutes, read again each pass | tehas core |
  | Deadlines, nested (10.7) | the dispatcher's poll 30 s (`TEHAS_POLL_BUDGET`'s wall); one port call within the poll's remainder; one request at most 20 s and within the call's remainder; a margin of 1 s at each hop | tehas core |
  | A download's own caller deadline | 600 s | tehas core |
  | Reserved slots per caller socket | dispatcher 4, cycle supervisor 2, console 1, MCP server 1, plugin gate 1 | tehas core |
  | Request records' size cap | 256 MiB per instance | tehas core |

  The supplier's own rate limits stay with the ledger's pools, as the
  ports keep them today.

### 10.10 Obligations for the implementing pull requests

Each of these is a law or a test that the pull request building its part
adds. None is optional.

- **The view's port only.** The host element listens only on the
  `MessageChannel` port it transferred (6.3), and ignores the window's
  `message` events. A test sends a window message and sees it ignored.
- **Sockets refuse the wrong user.** The operator's and the adapter host's
  users get `EACCES` on every socket they aren't meant for, the adapter
  host's caller sockets among them. A test tries each one as each user.
- **Hidden paths.** Every `InaccessiblePaths=` entry takes the `-` prefix,
  so a missing path doesn't fail the unit. The narrow view, the vetted
  `dist/`, the plugins' `/state` and the `.cwasm` cache live outside
  `~/.config/tehas` and `~/tehas/state/`, and each unit names their paths.
- **No sign-in in an adapter.** `signed_in` answers `Refused(Unsupported)`
  on an adapter plugin. Core makes the sign-in exchange (10.4).
- **The upstream path.** The upstream's own spec pins the narrowing of the
  credential it attaches. The host still keeps its route checks and its
  `TEHAS_REPO` checks on that path.
- **Queries and searches.** Each route lists the query keys it allows, and
  the host refuses any other. A GraphQL variable that carries a search
  string is typed in the vetted entry and limited in length and in what it
  may name.
- **Title and body only.** The console's `issue:draft` call sends only a
  title and a body, as a law.
- **Residual risk, accepted in writing.** On the direct path, the kernel
  holds the adapter host's user to TCP port 443 (5.3) but not to the
  origins' addresses, which move (10.5). That narrower remainder is
  accepted as residual risk. The address checks of 10.3 run on every new
  connection, redirects included, with a test.
- **The local socket protocol.** Each socket of the adapter host uses
  length-prefixed frames with a size cap, a protocol version, a sequence
  number for each connection (5.4), read deadlines and a rate limit for
  each socket.
- **Tokens leave no trace.** A token is zeroed after use, and is never
  written to a log, a crash report or a temporary file that swap can back.
- **Rotation without an outage.** The upstream key and the client
  certificate are versioned, so a new one is valid before the old one
  stops (5.3).

#### The hostile test kit

A fake supplier and a fake upstream that attack. Every law in this spec
runs against them in CI. They cover:
- redirects off the origin, and from `https` to `http`;
- DNS or hosts answers pointing elsewhere, certificates for another name,
  and a locally added CA;
- gzip bombs, oversized and slow answers, and HTTP/2 floods;
- foreign node IDs, documents with two operations, and a mutation in a
  read;
- replayed idempotency keys, and each `Sent::Maybe` outcome;
- duplicated and reordered frames;
- tokens that expire during a call, and a budget spent during a write;
- an upstream key mismatch;
- the system proxy variables set;
- a grant, token or key of one instance reused from another;
- a DNS answer that changes between lookups, an IPv4-mapped IPv6 answer,
  and metadata addresses.

#### Fuzz targets

One `cargo-fuzz` target for each parser on the path: the URL and path
builder; the header filters; the GraphQL document validator and ID typer;
the local socket's frame decoder; the view message decoder; the origin and
glob matcher. Each runs a fixed corpus in CI, and longer runs nightly.

### 10.11 Backlog, out of 2.1

- **Inbound webhooks.** If tehas ever receives one: verify
  `X-Hub-Signature-256`, check freshness, drop a repeated delivery id, and
  cap the body.
- **Certificate revocation checks** for the origins and the upstream.

## 11. Threat model

For the adapter path, the view channel and the operator (decision 59: "this
is our opportunity to make this rock solid"). A threat whose row names no
test is marked **OPEN**, so the gap shows; each OPEN row is a law its
implementing pull request adds.

### 11.1 Assets

- the installation token, and the App's key it's minted from;
- a person's token;
- the upstream key and the factory's client certificate and key;
- the repository: its code, issues, pull requests, labels and releases;
- the person's identity and login;
- the host's files: `~/.config/tehas`, the state store, the clone.

### 11.2 Adversaries

- a hostile ordinary plugin;
- a compromised adapter commit, signed onto the list;
- a malicious issue or pull request body, flowing through the model into
  a plugin or the adapter;
- a network attacker: DNS, the hosts file, a certificate for another name,
  a tampered answer;
- a spoofed or compromised upstream;
- a sibling plugin's view in the same dashboard;
- a reader of logs and records.

### 11.3 Trust boundaries

From the inside out:
1. **The plugin and the engine.** Plugin code runs in a WebAssembly
   instance and reaches only the host functions its grants open (parts 1
   and 5). An adapter's code is the same, with `http.request` its one way
   out (10.3).
2. **The operator's user** (`tehas-op-<instance>`, `-3p` for third-party
   plugins). No network by the kernel, no socket of the adapter host, no
   view of the home but its bound paths (1, 5.3, 10.5).
3. **The adapter host's user** (`tehas-ad-<instance>`). Outbound HTTPS only,
   held by nftables to 443 or to the upstream; short-lived tokens with each
   call; no App key, no state store (10.4, 10.5, 5.3).
4. **The core login user.** The core programs, which hold the App key and
   the state store, and reach the adapter host only through their own
   sockets (10.5).
5. **The upstream**, reached with mutual TLS, a pinned key and the upstream
   key (5.2, 5.3).
6. **The supplier** (GitHub), reached over verified TLS, directly or
   through the upstream.

The browser side: the dashboard's page, the host element in it, and each
view's sandboxed frame with an opaque origin, joined only by one
`MessageChannel` port per load (6, 6.3).

### 11.5 The limit that stays

A plugin may still send what it can read to a destination it was granted.
No check here can tell a legitimate request from one that carries data out
to a granted destination. So the destination grants, and keeping each
plugin's operations narrow, are the main data-protection decision a person
makes when turning a plugin on.

### 11.6 Out of scope

- root on the host;
- the supplier itself;
- a compromised CA in the pinned bundle.
