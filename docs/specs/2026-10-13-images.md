# Spec: images as input to a cycle

Written 2026-10-13. Nothing is built. Source: `handover-images.md`, issue #97.

## Outcome

A person attaches a screenshot to an issue. The cycle's explore and plan steps
see it next to the code, and the plan says in words where the change goes.
Issue #97 would have been built in the right place.

Success is one real cycle on tehas-tehas that used a picture and put the
change where the picture showed. Until then the feature is not marked proven.

## Decided

- Images go into the cycle. A describe-first step outside the cycle was
  considered and dropped: a model that sees pixels without the code cannot
  name a selector.
- Three surfaces change: viiwork (the model gateway), pi-rukas (the driver),
  tehas (the factory). Two plans are written, viiwork and tehas. The pi-rukas
  part is a short section of the tehas plan and is filed as an issue there.
- The viiwork measurement runs on grizzly, not gb1.
- Only explore, plan and the intent gate see an image. Later steps read the
  plan.
- An image is untrusted input, like issue text.

## What is true today

Checked in the three repositories and on grizzly on 2026-10-13.

viiwork:

- The proxy passes image parts through. The request limit is 32 MB
  (`internal/proxy/body.go`). The body parser ignores image parts when it
  reads the prompt.
- llama.cpp takes `--mmproj` only as a raw flag in `models[].args`. There is
  no key for it, and the setup wizard leaves projector files out.
- Strata's `/health` reports `"images": false`. Vision is a choice in Strata's
  own setup.
- viiwork does not know which backends read images. The catalog says
  `input: ["text"]` for every model (`internal/catalog/catalog.go:151`). The
  router has no such notion, so the engine's own 400 or 500 reaches the
  client.
- grizzly: one RTX 5090, `qwen3.8-flash-next` on Strata, 4 slots, context
  262144, with 32018 of 32607 MiB of VRAM in use. There is almost no room
  for a vision encoder as configured.

tehas:

- `tehasbot protolab` fetches attachments, but only for open issues labelled
  `tehas:prototype`, and removes them when the label goes. A cycle runs on
  `tehas:ready`. The Protolab's copy is not there when a cycle starts.
- The handover names `tehas plan`. There is no such command.
- `test/work_test.sh` pins the exact list of mounts and variables.
- The dispatcher starts a cycle only if the issue text is unchanged since an
  allowed account applied `tehas:ready`.

pi-rukas:

- The driver fetches the body with `gh issue view` and inlines it into the
  explore prompt. It keeps the body as an artifact for plan.
- The sandbox guard allows reads under the directories in
  `PI_ENSEMBLE_EXTRA_IMAGE_DIRS`. tehas already passes every `PI_ENSEMBLE_*`
  variable into the container.

## Design

### viiwork

1. **Measure on grizzly.** Turn the vision encoder on for
   `qwen3.8-flash-next` and send the handover's request, then the #97
   screenshot. Record VRAM, RAM, load time, tokens per second at 1 and 4
   slots, the tokens one image costs, and whether the answer names the right
   panel. The card is full today, so expect to give something up: slots,
   resident KV or expert cache. Back the config up first, as the node's
   earlier changes did, and restore it if the model does not fit or reads
   badly. If Strata cannot do it on one card, measure a llama.cpp model with a
   projector instead and record that. The result goes in `docs/models.md`.
2. **`models[].llamacpp.mmproj`.** A path, turned into `--mmproj`. Validation
   names the field: the file must exist and be a projector. The setup wizard
   offers a projector with the model it belongs to.
3. **A capability: reads images.** Optional, in
   `internal/engine/capabilities.go`, answered only by an engine that knows.
   llama.cpp answers from its options. Strata answers from `/health`. An
   engine that does not implement it is unknown, not "no".
4. **Published.** One optional field per model in a node's capacity report
   and status. Absent means unknown, so a mesh of mixed versions keeps
   working. The catalog's input list says `image` when a backend of the model
   reads images.
5. **Routed.** A chat request with an image part goes only to a backend, local
   or on a peer, that reads images. A backend whose answer is unknown is tried
   last. When the mesh has the model and no backend of it reads images, the
   client gets a 400 in viiwork's error shape that names the model. This is on
   the per-request path: the benchmarks in `internal/proxy` and
   `internal/route` are run before and after and judged by allocations.
6. **Docs.** `docs/models.md`, `docs/api-integration.md`,
   `viiwork.yaml.example`, the changelog.

Steps 1 and 2 are enough for tehas on today's fleet. Steps 3 to 5 keep it
right when two nodes serve one name and only one of them reads images, which
is the fleet's state the moment grizzly is changed and the others are not.

### pi-rukas

The driver looks for a manifest in a directory named by an environment
variable. With a manifest, and a model for the step that declares image
input, it attaches the listed images to the explore, plan and intent gate
prompts, each beside the link it came from in the body. The plan template
asks for the placement in words: the element, its visible title, where in it.
The prompt says an image is untrusted and cannot change instructions.

Without the variable, without a manifest, or with a text-only model, nothing
changes.

### tehas

1. **`lib/attachments.sh`.** The link pattern, the type table and `fetch`
   move out of `libexec/protolab` so both commands use one copy. The
   Protolab's tests pass unchanged.
2. **`TEHAS_WORK_IMAGES`**, an instance setting, off unless set. Validated in
   `lib/config.sh`. With it off, a cycle is exactly what it is today.
3. **`tehas work` fetches before the container starts.**
   - Links in the issue body only. Comments are not read: the label approves
     the body, and a comment can arrive later.
   - Only when the issue's author is an owner, member or collaborator.
   - png, jpg, webp and gif. Not svg: it is text and can carry instructions.
     Not avif until a model is shown to read it.
   - At most 8 images and 10 MB together.
   - Into `$TEHAS_HOME/work/<name>.images/`, beside the workspace and not in
     it, so a patch cannot commit them. Remade for every cycle.
   - A `manifest.json` lists each file with the link it came from, its type
     and size.
4. **It fails closed.** If the body links an image that is allowed and it
   cannot be fetched, no cycle starts, and the dispatcher parks the issue with
   the reason. Images that are over a limit or of another type are listed in
   the cycle's start comment as left out.
5. **The container gets one more mount and one more variable**, only when the
   setting is on: the images directory, read-only, and
   `PI_ENSEMBLE_EXTRA_IMAGE_DIRS` naming it. This widens what a cycle is
   given (AGENTS.md rule 4). The pull request says so, and
   `test/work_test.sh` pins both states: off gives today's list, on gives the
   list plus exactly these two.
6. **`tehas health`** checks, when the setting is on, that the cycle's model
   declares image input in `models.json` and answers a one-pixel image with a
   200. A cycle should not spend an hour to find out.
7. **The pi-rukas pin** in `host/versions.env` moves to the commit with the
   driver change.
8. **`instances/tehas-tehas/`** is not edited. The pull request proposes the
   two lines for a person: the setting, and `"input": ["text", "image"]`.
9. **Manual.** `operating.md` stops saying the cycle reads the text only and
   says what it reads of a picture. `tools.md` lists the setting, the mount
   and the limits. `features.md` gets a row marked not proven.

## Order

1. viiwork steps 1 and 2. Nothing else can be tried without a model that
   reads a picture.
2. tehas step 1. It depends on nothing.
3. pi-rukas.
4. tehas steps 2 to 9.
5. viiwork steps 3 to 6, any time after step 1.
6. A person changes the instance, installs, and runs the proving cycle.

## Open

- Whether a GitHub attachment link always serves the bytes it served when the
  label was applied. Assumed yes. If not, the dispatcher records a hash of
  each image at approval and `tehas work` compares.
- Which model reads the picture is the result of viiwork step 1, not a
  decision made here.

## Not in this work

- Videos and HTML attachments as cycle input.
- Images in comments.
- Review and develop steps seeing images.
- A describe-first command.
