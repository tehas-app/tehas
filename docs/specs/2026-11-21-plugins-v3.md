# Spec: plugins v3, and the third plugin

**Version**: part of the plugin specification 1.0.0, `2026-11-21-plugins-1.0.0.md`.

**Status**: Draft 2026-11-21. Builds on the v1 spec (`2026-11-21-plugins.md`
and its parts) and the v2 spec (`2026-11-21-plugins-v2.md` and its parts).
Nothing is built. Owner's decisions:

- The third plugin makes a ticket from an image or a page. It is the last of
  the three plugins that ship first, after Floorplan and the spec interview.
- It depends on the spec interview plugin (`specs`, from
  tehas-app/tehas-plugin-mattpocock-skills). So plugins may depend on
  plugins.
- v1, v2 and v3 land in one release. Nothing needs to stay compatible
  between them, so this part may change v1 and v2 where the third plugin
  needs it.
- When this part is done, the plugin specification is stamped 1.0.0. A later
  change of scope is a revision of 1.0.0, not a v4.

The interactive prototype of the third plugin's screens is
`2026-11-21-plugins-v3-pageticket.html` beside this file. Open it in a
browser; it runs on a built-in example.

## Purpose

v1 gives a plugin a view, the code, the model and a hook. v2 gives it the
chats, gates, the outside and more views. v3 adds what a plugin needs to
work with a person on one piece of the product and hand the result to the
factory as a ticket: a full-screen view, a chat of its own that knows the
source, uploads, kept files, a record in the state store, a drafted issue,
and another plugin's skills.

## One release, one manifest

Because v1, v2 and v3 ship together:

1. **One manifest version.** `"plugin": 1` reads every field of v1, v2 and
   v3, as the v2 spec already says. v3 adds fields to it and no version.
2. **One capability table.** The v1 security part's table, v2's parts and
   this part's rows are one table in the manual, `host/docs/plugins.md`.
   `tehas plugin review` prints from it.
3. **Limits from the last version that set them.** At most 8 plugins (v2).
   The rest as below.
4. **"Reserved for v2" goes, one surface at a time.** The manifest reader
   accepts a field or capability only once the code that enforces it has
   merged. Until then it stays refused by name, as the reader on main
   refuses it now (`console/core/src/plugin/manifest.rs`). The release
   ships no surface half built. At release, a capability is either in the
   table or refused as unknown, and refusals name the capability, never a
   version.

## New in v3

### Capabilities

| Capability | What it gives | What a person should weigh |
| --- | --- | --- |
| `needs:<name>` | The plugin runs only when the named plugin is ready, and gets what that plugin offers to dependants (its skills, so far) | Granting it does not grant the other plugin anything. Each keeps its own grants |
| `chat` | A chat of the plugin's own in its view, served by its `service`, with the factory's model | What the person types goes to the model, with what the plugin adds |
| `session:<minutes>` | The chat's container gets a read-only checkout of the default branch's head for the session, at most that many minutes | The plugin reads the product's source while a person chats, not only on a refresh |
| `upload:<MiB>` | A person may upload files to the view, at most that size each | What a person uploads reaches the plugin's container |
| `keep:<MiB>` | Files the plugin keeps between runs and sessions, at most that much in all, served at `/_frame/` and `/_keep/` behind the sign-in | Kept files can hold copies of the product's pages |
| `record` | tehas writes rows for the plugin in the state store's `plugin_records` table | The rows name issues and files. They are history, as runs are |
| `issue:draft` | The plugin may propose an issue; a person reviews and files it from the view | The person files it under their own login. The plugin never files, never labels |
| `model:images` | Image parts in model requests (see Changes to v1) | Images of the product's pages go to the model |

### Manifest fields

| Field | Rule |
| --- | --- |
| `needs` | Optional, at most 2. Each `name` (a plugin name) and `skills` (ids the dependency offers, at least 1). Needs `needs:<name>` |
| `records` | Optional, at most 4. Each `kind`, `a-z` and `-`, 1 to 16. Needs `record` |
| `views[].open` | `dock` (default), `page` or `full`. A plugin that asks for `chat` needs at least one view that is `page` or `full` |
| `upload` | Optional. `types`: 1 or more of `image/png`, `image/jpeg`, `image/webp`, `text/html`. Needs `upload:` |

### Dependencies

```json
"needs": [{"name": "specs", "skills": ["grill", "spec", "brief"]}]
```

| Rule | Text |
| --- | --- |
| What a dependency is | A name in `TEHAS_PLUGINS`. Not a URL, not a commit. The person pins each plugin on its own line, as now |
| Grant | `needs:<name>` in the dependant's grant line. The dependency's own grant line is unchanged and must grant the named skills to the `plugin` chat |
| Order | `tehas update` builds dependencies first. A plugin whose dependency is refused, off or missing is refused with "needs `<name>`, which is `<state>`" |
| Cycles | A cycle of `needs` refuses every plugin in it, naming the cycle |
| Depth | One level. A plugin that is needed needs nothing. More is a revision |
| Skills | The dependant's chat gets the granted skill texts of the dependency, read from the dependency's pinned commit, inside the same `TEHAS_PLUGIN_SKILLS_MAX` |
| Removal | Taking out a needed plugin refuses its dependants at the next update, with the same message. Nothing is removed silently |
| Review | `tehas plugin review <name>` shows each dependency's pin, state and the skill texts the dependant will get |

### The plugin's chat

- The view asks its own `service` for each turn. The service calls the model
  through the socket, with the dependency's skills in the instructions,
  labelled with their source, as the chats part does.
- With `session:<minutes>`, tehas starts the chat's container with the
  checkout mounted read-only at `/product`, as a refresh gets it. The
  session ends at its minutes, at 30 minutes without a message, or when the
  person closes the view.
- A turn that changes a kept file is a new version of it. tehas keeps every
  version until the record is closed.

### Records

A new table in `state/tehas.db`, the store that holds the order of ready
issues:

```
plugin_records(plugin, id, kind, issue, files_sha256, created, by, closed)
```

The plugin asks tehas, through its socket, to write or close a record.
tehas checks the plugin is granted `record`, that `id` is `a-z`, `0-9` and
`-` up to 32, and that `kind` is one the manifest names. `tehas plugin
records [<name>] [--json]` lists them. The dashboard's order view shows a
record's link beside the issue it names.

### Drafted issues, and the prototype reaching a cycle

1. The plugin proposes an issue: title, body, and the kept files it links.
2. The view shows the draft to the person, who may edit it, then presses
   "File". tehas files it as that person through the factory's App, with the
   person named as author, and writes `issue` on the record.
3. tehas copies the linked kept files to `state/plugin-files/<plugin>/<id>/`,
   read-only, and writes their sha256 on the record. The issue body carries
   one line, `tehas-files: <plugin>/<id> <sha256>`.
4. A person applies the label. Nothing else starts work (hard rule 5).
5. When the cycle starts, the supervisor puts those files into the cycle's
   given files, beside the issue's attachments, with their sha256 in
   `manifest.json`. A mismatch stops the cycle before the container starts.
   This is a security change to what a cycle is given (hard rule 4): it is
   files in the folder a cycle already gets, never a new mount, variable or
   socket, and `test/fixtures/argv/` does not change.

## The third plugin: tehas-plugin-pageticket

Name `pageticket`, label "Page ticket", Apache-2.0, `kind: "service"`.

### What it does

1. **Start.** A person gives an image (how it should look), a page address,
   or both, or uploads a page's HTML.
2. **Capture.** For an address, a headless browser in the plugin's container
   opens it at a fixed viewport, waits for the network to settle, freezes the
   rendered DOM, inlines CSS, images and fonts as `data:` URIs, and removes
   scripts, `on*` attributes, `javascript:` links, frames and `<base>`. The
   result is one standalone HTML file. An uploaded HTML file is cleaned the
   same way. With only an image, the model drafts the HTML from it.
3. **Compare.** With an image and a page, both are rendered to images at the
   same width, broken into components (background, blocks, pieces), matched
   by place, size and look, and each difference is listed as missing, extra,
   changed, resized or moved.
4. **Chat.** A full-screen view: the chat on the left, narrow; the prototype
   on the right, scaled with CSS to show the whole page. The chat knows the
   source through `session:`. A request changes the prototype by small
   find-and-replace edits, never a full rewrite, so it stays inside the
   model's output cap. Each edit makes a new version and the frame reloads.
   When a change touches a shared part (a component used by other pages),
   the chat asks: all pages, or only this page. The answer goes into the
   notes.
5. **Hand off.** The last version and a `notes.md` are the spec: what
   changes, why, in which source file, and for which pages. The `specs`
   skills shape the notes (`spec`) and say what the ticket still lacks
   (`brief`). The plugin drafts the issue; a person files and labels it.

### Manifest

```json
{
  "plugin": 1,
  "kind": "service",
  "name": "pageticket",
  "label": "Page ticket",
  "license": "Apache-2.0",
  "build": "Dockerfile",
  "asks": ["serve", "view", "chat", "session", "upload", "keep", "record",
           "issue:draft", "model", "model:images", "net:app", "needs:specs"],
  "timeout": 900,
  "views": [{"id": "pages", "label": "Page tickets", "path": "index.html", "open": "full"}],
  "net": [{"id": "app", "origin": "https://app.example", "paths": ["/"], "run": true}],
  "needs": [{"name": "specs", "skills": ["grill", "spec", "brief"]}],
  "records": [{"kind": "prototype"}],
  "upload": {"types": ["image/png", "image/jpeg", "image/webp", "text/html"]}
}
```

A grant line, for the tehas-tehas instance:

```
TEHAS_PLUGIN_GRANTS_PAGETICKET="<commit> serve view chat session:30 upload:10 keep:200 record issue:draft model:2000000 model:images net:app=https://app.example needs:specs"
```

### Files it keeps

```
<id>/v1.html … v<n>.html   versions of the prototype
<id>/notes.md              the notes
<id>/image.png             the person's image, if any
<id>/compare.json          the last comparison
```

### What each part uses

| Part | Capability |
| --- | --- |
| Start screen, workspace | `view` with `open: full`, `serve` |
| Upload of an image or HTML | `upload:` |
| Capture of an address | `net:<origin>` with `run`, the headless browser in the image |
| Draft from an image | `model`, `model:images` |
| Compare | Nothing: code in the container |
| Chat that knows the source | `chat`, `session:`, `model`, `needs:specs` |
| Prototype in a frame | `keep:`, served at `/_frame/` |
| Record | `record` |
| Ticket | `issue:draft`; a person files and labels |

## The stamp: plugin specification 1.0.0

`2026-11-21-plugins-1.0.0.md` lists the files of the specification, stamps
them 1.0.0 and holds the revisions table. Every file names it under its
title. A change of scope after the stamp is a revision there, not a v4.

## Open points

1. Whether `session:` mounts the checkout or the plugin asks for files one by
   one. A mount is simpler; a file request is easier to inspect.
2. Whether the drafted issue is filed as the person through the App's user
   token, or by the App with the person named in the body. The label rule
   holds either way.
3. Whether one level of `needs` is enough for the first release.
4. The capture's wait rule: network idle, a fixed delay, or both.
