# Spec: tehas-dev, a manual session on the factory host

**Status**: Agreed 2026-10-10. Implemented in the same pull request.

**Since**: the command is `tehas dev` and its script is `libexec/dev`, after
`docs/specs/2026-10-10-consolidate-cli.md` gave the host one `tehas` command.
The text below keeps the names it was agreed under; the container is still
`tehas-dev-<name>`.

**Since 2026-10-11**: a session can be started from a person's own account.
See "From another account" at the end, which replaces the first row of the
decisions table.

## Purpose

The host that runs the factory should also be a place to work by hand. A
person logs in as the tehas user, types one command, and is in an interactive
Pi session with pi-rukas, in the sandbox, in a clone of the product, on the
factory's models. No configuration beyond what the factory already has.

Before this, the manual said to apply `tehas:pause` and run pi-rukas "through
its own wrapper in a clone of your own". That left four gaps:

- There is no clone to work in. The product checkout is never given to a
  container, and the cycle's workspace is removed before every cycle.
- git in the wrapper's container has no credential helper, so a session can
  commit and cannot push.
- The wrapper forwards the whole host environment and mounts `~/.config/gh`.
  A cycle's container gets the token and the `PI_ENSEMBLE_*` settings only.
- Commits carry the bot's name whoever typed them.

## What was decided, and what was not chosen

| Question | Decision | Not chosen, and why |
| --- | --- | --- |
| Which Unix account | The tehas user. Everything a session needs is already in its shell | Each developer's own account: the settings, `models.json`, the image and the commands are all in one home, the image is built for one user id, and Docker needs a root-granted group. That is configuration per developer |
| Which tree | A clone of its own under `~/tehas/dev/<name>`, made by the command and kept | The product checkout: the dispatcher runs git in it and no container may write it. The cycle's workspace: it is removed before every cycle |
| Whose name on commits | The developer's, given once with `--author` and stored on the host | A token per developer, so that the push and the pull request are theirs too: that is a secret per developer on a shared account, and more than a cycle's container is given |
| The running factory | Sessions and cycles run side by side. The command says so when a cycle is running | Taking the dispatcher's lock: a forgotten session would stall the queue |
| The command's name | `tehas-dev`, like `tehas-work` | A `tehas` front command with subcommands: one subcommand does not justify it |

## The command

```
tehas-dev [<name>] [--author "Name <email>"] [-- <pi arguments>]
tehas-dev --help
```

- `<name>` names the clone, `~/tehas/dev/<name>`. Letters, digits, `_` and
  `-`, starting with a letter or digit. Without it the name is `main`.
- `--author` stores the identity for that clone and uses it from then on.
- Anything after `--` is passed to `pi`, for example `-- -r` to resume.
- Arguments are read before the settings. An argument the command does not
  know stops it with exit 64 and the usage.

| Exit | Meaning |
| --- | --- |
| the session's | Pi's own exit status, as Docker reports it |
| 64 | A wrong argument, a malformed author, no bot token, or no git identity. No container was started |
| 78 | The instance settings are invalid, or `~/tehas/dev/<name>` exists and is not a clone. No container was started |

## The clone

Made on first use from the product checkout, the way a cycle's workspace is
made: `origin` is the product's address, the branch is the one work lands on,
at the tip the product checkout last fetched. The developer pulls inside the
session if that is behind.

It is made beside its place, as `~/tehas/dev/.<name>.making`, and moved there
whole, so a clone that stopped halfway is never taken for a finished one.

tehas never removes or resets it. Work in progress stays between sessions.

The host runs git in it once, to make it. After that the container has written
it, so the host runs no git command there again, not even to read its
configuration. An existing clone is recognised by its `.git` directory and
nothing else. This is the rule a cycle's workspace follows, kept for a tree
that lives longer.

A directory that exists, is not empty and has no `.git` is left alone: exit 78.

## Identity

`--author "Alice Example <alice@example.com>"` writes that line to
`~/tehas/dev/<name>.author`. The file is next to the clone, not in it, so no
container can rewrite it. Later runs read it. A stored line that does not have
the shape `Name <email>` stops the command with exit 64.

The name and email go into the container as git's `user.name` and
`user.email`, at environment level, where a cycle gets the bot's. Every commit
made in the session, by the person or by an agent, is authored and committed
under them.

A clone with no stored author uses the bot's identity, as a cycle does, and
the command says so in one line.

What this is not:

- It is not authentication. Anyone on the tehas account can give any name.
- It does not change who pushes. The push and the pull request go through the
  bot's token, so GitHub shows the bot as the pusher and as the author of the
  pull request. The commits are unsigned.
- A rule that a pull request needs a review from somebody other than its
  author looks at the bot. A person can therefore approve a pull request made
  of their own commits. Reviewers should read the commit authors.

## The container

Exactly what a cycle's container is given, with four differences:

| | A cycle (`tehas-work`) | A session (`tehas-dev`) |
| --- | --- | --- |
| The tree | `~/tehas/work/<name>`, fresh each time | `~/tehas/dev/<name>`, kept |
| git identity | The bot's | The stored author's, else the bot's |
| Terminal | None: `-i`, `pi --mode rpc --approve` | `-it`, `pi` and the arguments after `--`, plus `TERM` and `COLORTERM` |
| Container name | `tehas-work-<issue>` | `tehas-dev-<name>` |

The same: the image, `--cpus` and `--memory`, the bot token by name, the
`PI_ENSEMBLE_*` settings, the credential helper, the host aliases, and the
mounts (`~/.vipune`, Pi's `ensemble-runs` and `sessions`, `models.json` and
`mcp.json` read-only, the two caches). Not given: the Docker socket, SSH keys,
`~/.config/tehas`, `~/.config/gh`, the product checkout, the platform checkout,
the rest of the host environment.

One session per clone: the container name is fixed, so Docker refuses a
second one. A second clone gives a second session.

The command needs a terminal. It does not check for one; Docker refuses `-it`
without it and says so.

## The factory beside it

- Energy and the token meter count a session with no extra work: the sampler
  reads the whole mesh for the models the factory uses, and a session uses
  those models.
- A session's runs and transcripts land in the same `~/.pi/agent` directories
  as a cycle's. It gets no door on the factory floor and writes nothing under
  `~/tehas/live`.
- A session and a cycle share the model endpoint. When `live/running.json`
  says a cycle is running, the command prints one line with the issue number
  and starts anyway.
- Each container has the cycle's memory limit, by default half the host. A
  session beside a cycle can use the whole host between them.

## Code

`bin/tehas-work` builds the container's variables, mounts and host aliases,
and makes the workspace. Those four pieces move to `lib/sandbox.sh`, and both
commands call them, so the two containers cannot drift apart.
`test/work_test.sh` is not changed: it pins that the move altered nothing.

| File | Change |
| --- | --- |
| `lib/sandbox.sh` | New. `tehas_sandbox_env`, `tehas_sandbox_mounts`, `tehas_sandbox_hosts`, `tehas_sandbox_clone` |
| `bin/tehas-work` | Uses them. No change in what it passes to Docker |
| `bin/tehas-dev` | New |
| `install.sh` | Installs both new files |
| `test/dev_test.sh` | New: the session's `docker run` is pinned option by option, as the cycle's is |
| `test/install_test.sh` | The two new files in the expected list |
| `host/docs/` | `operating.md`, `tools.md`, `host.md`, `features.md` |

## Tests

`test/dev_test.sh`, with a stub `docker` that records its arguments:

- a wrong argument, a bad name or a malformed author starts no container and
  makes no clone
- invalid settings, a missing token, a checkout of another repository: no
  container
- the first run makes the clone at the branch's tip with the product's origin
- a later run keeps what is in the clone and runs nothing from it: a planted
  hook and a planted `core.fsmonitor` do not fire
- a directory that is not a clone is left alone
- a clone that fails halfway leaves nothing behind, and the next run makes it
- exactly the cycle's mounts, with the clone in place of the workspace
- exactly the cycle's variables plus `TERM` and `COLORTERM`
- no option beyond `--rm -it --name --cpus --memory -w -v -e`
- the product checkout, the Docker socket, `.ssh`, `.config/tehas` and
  `.config/gh` appear nowhere, and the token's value is not in the arguments
- `--author` is stored outside the clone and used on the next run without the
  option; without one the bot's identity is used and the command says so
- the arguments after `--` reach `pi`
- a running cycle is announced
- the session's exit status is passed on

## Security

This adds a second way to start a container, so it is a security change. It
widens nothing: the session's container is a cycle's container with a
terminal. What is new is exposure over time. A cycle's tree is thrown away;
a session's clone stays and has been written by agents. The host therefore
never runs git in it after making it, and a test holds that.

The bot token is in the session, as it is in a cycle and in the shell of
anyone logged in as the tehas user.

## Not in this version

- A developer's own GitHub token.
- Sessions on the dashboard.
- Running as another Unix account.
- A push check before the session, as `tehas-work` has. A person sees a failed
  push at once.

## From another account (2026-10-11)

The first version needed a login as the tehas user and a typed `--author`.
What was wanted is the usual way to work on a shared machine: log in as
yourself, type `tehas dev`, and have your own git name on the commits.

The session still runs as the tehas user. What changes is how one gets there.

| Piece | What it does |
| --- | --- |
| `host/login/tehas` | Installed as `/usr/local/bin/tehas`. Reads `user.name` and `user.email` of the calling account and asks `sudo` to run `dev-login` as the tehas user. Knows `dev` and `help` only |
| `libexec/dev-login` | Run by `sudo`. Takes the clone's name from `SUDO_USER`, the author from its one argument, loads the tehas user's environment and starts `libexec/dev` |
| `bootstrap.sh dev <user> [<login>...]` | As root: the group `tehas`, its members, the `sudo` rule, `/etc/tehas/manager` and the command for everyone |

Decisions:

- **Through `sudo`, not by sharing files.** The alternative was a readable
  copy of the settings, an image per user id and the `docker` group for every
  developer. The `docker` group is root on the host. One rule for one script
  gives a session and nothing else.
- **A group, not every account.** Whoever is in a session holds the bot's
  token. Being let in is a decision an administrator makes once per account.
- **The clone is the login's.** `sudo` sets `SUDO_USER`; the caller cannot. So
  the name of the clone is not an argument and nobody enters another's.
- **Only the name and the email.** The rest of a person's git configuration
  is not carried in: the tehas user cannot read it, and aliases, helpers and
  signing keys from one account have no place in a container that holds
  another's token.
- **The author is still a label.** It comes from a file the person controls.

Not changed: the container. A session started this way is given exactly what
`test/dev_test.sh` pins.

Not done: showing a person's clone to their own shell. It is in the tehas
user's home and is reached through a session.
