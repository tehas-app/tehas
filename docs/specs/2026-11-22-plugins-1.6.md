# Plugin revision 1.6: the reader's gaps, and surfaces from four plugins

**Version**: plugin specification revision 1.6.0, 2026-11-22, with 1.6.1 (2026-11-23: `spec` is the approved body) (the number is
fixed when it merges, in `2026-11-21-plugins-1.0.0.md`). Built after
tehas 2.0.0, with the rest of plugins (2.1). Nothing here is built.

## Why

The plugins lead ran every plugin's manifest through the reader
(`console/core/src/plugin/manifest.rs`, `read`). Some examples in the
specification do not pass it, and one rule of the reader is tighter than
the specification. Four plugin repositories, built against 1.5.3, also
found surfaces they need and the specification lacks: `console`, `voice`,
`tutor` and `goldfish`.

This file lists the corrections, which are made in the files they correct,
and holds the new surfaces.

| Plugin | What it needs that is new here |
| --- | --- |
| `console` | A `full` view framed by a chat host (1), the console's route (2) |
| `voice` | A `full` view framed by a chat host (1). Its corrections to 1.1.0 are in the voice part |
| `tutor` | A skill's `entry` (3) |
| `goldfish` | `spec` (4), `model` in the hook after a cycle (5), `counts` and `plugin.verdict` (6), the report (7), a pull request's range (8), the tokens left (9) |

## Corrections

Each is an edit to the file it corrects. None adds a surface.

| Where | Was | Now |
| --- | --- | --- |
| v3, the page ticket's manifest | The view's `path` was `index.html`, and the ask was `view` | `"path": "/"` and `view:pages`. A view's path is a folder of `/out`, and each view of `views` needs `view:<id>` (v2 menu part) |
| v3 and v2 menu part, `views[].open` | "`dock` (default)" | `open` is required. The reader has no default |
| v2 menu part and 1.5.0's `frame` | A manifest with `menu` and no build was refused: "menu needs a build" | The rule of `menu` and a build, in the v2 menu part. `panels` passes it |
| v1, security part and hooks part | The ask `hook:after:work`, `at` `after:work` | The names of T9: the ask `hook:after:change.offered`, `at` `after:change.offered`, as T11's events spec (#2878) names them. The rule "a hook needs its ask" is written for any event |
| Hooks part and security part, the context | A hook's context held no issue | `issue`, the cycle's issue number, and `at`, as 1.5.3 gives the hook before a cycle |
| Voice part | 1.1.0 as written before Haru's server was read | C1 to C12 of the voice plugin's spec, each in place |

## What the platform adds

Each addition is an ask in the manifest and a grant in the instance, or a
setting of the instance. `tehas plugin review` lists it, and a person
writes it. Nothing on this list is given by default. Until the code that
enforces a word has merged, the reader refuses it by name.

### 1. A `full` view in a chat host: `TEHAS_PLUGIN_FRAMERS`

v3 has `open: full`, a view over the whole dashboard. 1.1.0 opens a `full`
view from a button in a chat session, and the console opens one in Obeya's
modal. Obeya, the wizard and the assistant are pages of industry, on
another origin than the dashboard. A view's policy is `frame-ancestors
'self' <dashboard origin>`, so those pages cannot frame it.

```
TEHAS_PLUGIN_FRAMERS="https://obeya.example.org"
```

- Space-separated origins: `https://`, a host name, an optional port, and
  nothing else. No path, user, query or wildcard. Unique. At most 4. A
  malformed line is 78 at load.
- Industry writes the line into the `instance.env` it pushes, with the
  origins of its own chat hosts. No plugin names an origin, in its manifest
  or its grant.
- The gate adds those origins to `frame-ancestors` on the documents of a
  view whose `open` is `full`, and on no other answer. A `dock` or `page`
  view, `/_frame`, `/_page`, `/_outside` and the gate's own pages keep
  their policy.
- With the line unset, a `full` view is framed by the dashboard only, as
  v3 says.
- Each origin must be the same site as the plugins' names (the same
  registrable domain, by the public suffix list; a tailnet's
  `<tailnet>.ts.net` counts as one site). An origin on another site is 78
  at load, and that chat host opens the view in a new tab instead: its frame
  would get no session, since the gate's cookie is `SameSite=Lax`. A host
  on its own domain is served later by a single-use, 60-second token as
  `/_page` has, swapped with a `303` for a partitioned cookie scoped to the
  view; until that is built, the rule above refuses it.

What a person should weigh: a page of a named origin can frame the view
and draw over it. The origins are industry's own pages, named by the
operator.

What reaches the container: nothing. A security change: the browser's
policy of a `full` view names origins outside the factory's domain.

### 2. `/_console/<id>`: the console's route

The console (`tehas-app/tehas-plugin-console`) is a person's `tehas dev`
session on the host, drawn in the browser. No plugin capability gives a
host session, in any version, so the console is a tehas feature. Its
plugin is a static view: a terminal emulator and its controls. This
revision holds the parts that touch plugin rules: the `full` view (1) and
the gate's route. The rest of the feature is not specified here (see
"Open points").

- The gate answers `/_console/<id>` only on the origin of the plugin that
  `TEHAS_CONSOLE_VIEW` names, only while that plugin is ready with its view
  granted, and only for a login on `TEHAS_CONSOLE_LOGINS`. With the
  console feature off, the path is 404. It is a setting, not a grant in
  the plugin's line: nothing of the plugin's own runs on the host.
- It is a WebSocket on the one upgrade path the relay brings (1.1.0), with
  the relay's rules: the session, the `Origin` and `Sec-Fetch` rules on
  the upgrade, and nothing of the browser crossing. `<id>` is a console's
  name, and the gate checks it is one of the person's own before the
  upgrade. Anything else is 403 with no body.
- Binary frames are terminal bytes, both ways. Text frames are control,
  one JSON object each:

  | From | Frame | Meaning |
  | --- | --- | --- |
  | view | `{"resize": [cols, rows]}` | The terminal's size |
  | view | `{"window": "pi"}` or `{"window": "shell"}` | Which of the console's two windows to draw |
  | view | `{"lost": true}` | Asks what End would lose |
  | view | `{"end": true}` | End the console |
  | gate | `{"lost": {"files": n, "commits": n}}` | The answer: files not committed and commits not pushed, as counts |
  | gate | `{"ended": true}` | The console has ended, by this view's End or any other way |

  Any other text frame closes the socket, on either side. The two frames
  from the gate hold counts and a flag, never a path, a name or terminal
  text.
- At most 1 MiB a second each way and 64 KiB a frame. A socket with no
  frame for 60 seconds gets a ping, and one that does not answer is
  closed.
- Kept: counts, not content. The start, the end, the login and the byte
  counts, as the relay keeps them.

What reaches a plugin's container: nothing. The view's build only fills
`/out`. A security change: a gate route that reaches a session on the
host.

### 3. A skill's `entry`

v2 gives a granted skill to every chat of the hosts it names. The tutor's
course must reach only a chat the person opened for it.

- A skill may have `entry`: a label of 1 to 32 characters, one line,
  control characters refused. Skills of one plugin with the same `entry`
  are one entry.
- `tehas plugin skills --chat <host> --entries --json` gives the entry
  skills too, each with its `entry`. Without `--entries` they are left
  out. So a host that does not know `entry` never puts such a skill into
  every chat.
- A host that asks with `--entries` draws each entry's label where a
  person starts a chat, as text, beside the plugin's label. It gives an
  entry's skills only to a chat opened from that entry, and to no other.
  A host that does not draw entries asks without the flag.
- `TEHAS_PLUGIN_SKILLS_MAX` counts the skills with no entry together, as
  today, and each entry's skills on their own. An entry's skills never
  share a chat with another entry's.
- `tehas plugin review` prints each skill's `entry`, so the person who
  grants it sees where it shows. `api/plugin-skills.schema.json` gains
  `entry`.

What reaches a container: nothing; a skill is text. The rules of the v2
chats part hold in an entry's chat: the host's rules first, a shaped turn,
no write a host lacks. Not a security change. An entry skill reaches fewer
chats than a skill without one.

### 4. `spec`: the approved body, for the hook after a cycle

The goldfish checks a pull request against what a person approved. In 2.0
that is the issue's body: the approval keeps its hash
(`start.approval.bodySha256`), and a start refuses a body that no longer
matches it. When the body holds lean's `pi-spec v1` block, the block is
the spec pi-rukas plans from, and its `criteria`, each with an id, are the
requirements. (An earlier draft of this part read a linked file pinned by
the feature `spec-pipe`. 2.0 drops that feature and the spec mark, #2892,
so the spec is the approved body.) A plugin has no network, and only tehas
has checked the body against the approval.

- The manifest asks `spec`. It needs the hook after a cycle
  (`hook:after:change.offered`). The ask and the grant are the same
  word.
- In that hook, for a change whose cycle started on an approval, the host
  mounts `/given/<issue>/spec/` read-only. It holds:

  | File | Holds |
  | --- | --- |
  | `body.md` | The issue's body as the cycle's start checked it against `bodySha256`, UTF-8 |
  | `block.json` | That body's `pi-spec v1` block, as core's `plan::spec_block` reads it: the JSON inside the fence. Absent when the body has none |
  | `manifest.json` | `{"api": 1, "issue": 7, "bodySha256": "<hex>", "bytes": 5120, "block": true}` |

- The body is the copy the start checked, kept by the host with the
  cycle's record until the hook has run. The host never fetches the body
  again, so an edit after the start changes nothing the hook sees. It
  checks the copy against `bodySha256` once more before the mount. A copy
  that does not match is not handed over: the hook does not run, and the
  status is `error` with "the approved body could not be read".
- A change whose cycle started with no approval, such as a run by hand,
  gets no folder. The hook still runs.
- The body is written by a person and approved by an allowed account. To
  the plugin it is data, as an issue's text is. `block.json` is that same
  text, read by the one function the dispatcher and lean use, so the
  plugin and the planner cannot disagree on what the block is.

What a person should weigh: the plugin reads the approved issue body, and
with `model` the body goes to the model.

What reaches the container: one read-only mount, `/given/<issue>/spec/`,
in a hook run. Pinned in `sandbox.rs` and `test/fixtures/argv/plugin-spec`.
**A security change.**

### 5. `model` in the hook after a cycle

v1 has no `model` in a hook. 1.5.0 lifts that for the hook before a cycle.
The goldfish's readers are model requests, so this lifts it for the hook
after a cycle too.

- With `model:<tokens>` granted, a `after:change.offered` hook gets the model
  socket. The grant's number is per run. The runs count against
  `TEHAS_PLUGIN_MODEL_DAY`.
- When the day budget is used up, the socket answers 429 and the hook goes
  on without the model. It still leaves a verdict.
- Each model request in this hook is bounded at 60 seconds. `model:images`
  is not given in this hook.
- The hook's `timeout` stays 60 to 1800 seconds, with at most one hook of
  a plugin at a time and two in all, as the hooks part says.
- The context's `model` is allowed in a hook at either event. The schema
  allows it there and in a refresh, and nowhere else.

What a person should weigh: the hook runs at the end of every cycle that
leaves a pull request, refreshes included, so each one may spend the
grant. The pull request's code goes to the model. What the model writes
could reach the status's summary, where every reader of the repository
sees it, a cycle's agents included. So a plugin builds its status summary
from its own counts, not from the model's text: the summary is cleaned and
cut at 140 characters, and holds no prose the model wrote.

What reaches the container: the model socket's directory, in a hook run.
The argument list of a hook with `model` is new in `test/fixtures/argv/`.
A security change: text a model made from a pull request's code now
reaches the commit status.

### 6. `counts` and the event `plugin.verdict`

Industry stores how a pull request matched its spec, and Obeya shows it.
The verdict's schema is closed, so counts cannot ride on `verdict.json`.

**Decided: a file of their own, `/out/_tehas/counts.json`.** The verdict
is what tehas posts and shows, and its schema stays closed and as it is.
Counts have another reader, the event, and their own check against the
manifest. A bad counts file then costs the counts and not the verdict.

- The manifest may have `counts`: the names of a hook's counts, at most
  16, each 1 to 16 characters of `a-z` and `-`, unique. It needs a hook.

  ```json
  "counts": ["requirements", "met", "not-met", "unclear", "blockers", "not-run"]
  ```

- A hook may write `/out/_tehas/counts.json`, read through the tar reader,
  at most 4 KiB:

  ```json
  {"api": 1, "counts": {"requirements": 12, "met": 11, "not-met": 0, "unclear": 1, "blockers": 0, "not-run": 0}}
  ```

  Each name must be one the manifest lists. Each value is an integer from
  0 to 1000000. A name may be left out.
- A counts file that breaks a rule is dropped whole. The run's log says
  why, the verdict stands, and the event carries no counts.
- When a hook ends, tehas raises the event `plugin.verdict`, a notify
  event of T11's kind, with:

  | Field | Holds |
  | --- | --- |
  | `plugin`, `commit` | The plugin's name and pin |
  | `pr`, `head` | The pull request's number and the head commit the hook read |
  | `issue` | The cycle's issue |
  | `verdict` | `pass`, `note`, or `error` when the hook did not finish |
  | `spec` | With `spec` granted and an approved body: `{"bodySha256": "<hex>"}`, from the approval, not from the plugin |
  | `counts` | The counts read, when there are any |

  No text of the plugin's: not the summary, not a finding. Its schema is
  in `api/` with T11's other events (#2878).
- No plugin can listen to this event in this revision. It is for the
  programs that read the factory's events, industry first.

What reaches the container: nothing. Not a security change: integers
under names a person reviewed leave the host, and no text.

### 7. The hook's report

The findings page `/_hooks/<pr>` shows the verdict: a summary and at most
20 findings of 300 characters. The goldfish's whole report does not fit.

- A hook may write `/out/_tehas/report.md`: UTF-8, at most 256 KiB, no
  control character but newline and tab. It is read through the tar
  reader and kept as `~/tehas/plugins/<name>/hooks/<pr>.report.md` beside
  the verdict, and removed with it.
- The gate shows it on `/_hooks/<pr>`, under the findings, in the page
  tehas makes. It is untrusted text, under the rules of the plugin's other
  text:
  - It is rendered as safe Markdown: headings, paragraphs, lists,
    emphasis, block quotes, code and tables. Raw HTML is shown as text.
  - A link is shown as its text and its address, never as a link. An
    image is shown as its alternative text and loads nothing.
  - Secret-looking text is masked, as in the status's summary.
  - The page runs no script and loads nothing from another site, as
    today.
- A report that breaks a rule is left out. The page says "The report
  could not be shown", and the verdict stands.
- It needs no ask of its own. It is part of what the hook's grant gives,
  behind the same sign-in.
- Nothing of the report goes to GitHub. The status and its summary are as
  the hooks part says.

What reaches the container: nothing. A small security change: more of a
plugin's text on a page of the gate, rendered and not only escaped.

### 8. A pull request's range under `history:`

`history:` gives the commits since the plugin's last good run. In a hook
on a pull request that range means nothing: the plugin needs the change,
from the pull request's base to its head.

**Decided: the host mounts the pull request's range, as `history:` mounts
a refresh's.** The host already knows the base, the secret check on what
it hands over stays in one place, and the plugin does not depend on the
clone's depth.

- In a `after:change.offered` hook with `history:` granted, the range is from
  the merge base of the pull request's base and head to its head.
- `/run/history/` holds that range, with the five files of 1.5.0.
  `changed.json` is `{"from": "<merge base>", "paths": [...]}`: the paths
  the pull request changes.
- The clone at `/product` holds the range's commits and the merge base, so
  `git diff <from> <head>` works. The merge base is there also when the
  log is cut at the grant's number; `head.json` then has `"cut": true`.
- The context's `pr.base` stays the base branch's commit as GitHub gave
  it. The merge base is `changed.json`'s `from`.
- A hook without `history:` gets the depth-200 clone, as today. It may
  diff from its clone when the base is within that depth, and must not
  count on it.

What reaches the container: `/run/history/` in a hook run, and the merge
base in the clone. Pinned in `test/fixtures/argv/plugin-history-hook`. A
security change, as 1.5.0's mount is.

### 9. The tokens left, on the model socket

A run does not know how much of its budget is left. The context gives the
grant's number once, and the day budget is shared.

**Decided: a header on the socket's answers.** The number changes with
every request and with other plugins' use of the day. The context is
written once, before the run.

- Every answer of the model socket carries `Tehas-Tokens-Left: <n>`, a
  whole number, 0 or more. That includes `GET /v1/models`, an error and a
  429.
- `n` is the lesser of what the run's grant has left and what
  `TEHAS_PLUGIN_MODEL_DAY` has left, after this answer's `usage` replaced
  its reserve.
- A request reserves its body's bytes divided by 3 plus `max_tokens`, as
  the security part says. A request whose reserve is over `n` gets 429.
- `GET /v1/models` spends nothing, so a run can ask before its first
  request.
- The context's `model.tokens` stays the grant's number.

What a person should weigh: when the day budget is the lesser, a plugin
sees how much all plugins together have left. It is one number.

What reaches the container: one header on a socket the run already has.
Not a security change.

## The plugins

Each grant line is for the tehas-tehas instance. Each manifest follows the
reader's rules for the fields the reader has today. The fields and asks of
this and earlier revisions are refused by name until they are built.

### console

```json
{
  "plugin": 1,
  "kind": "batch",
  "name": "console",
  "label": "Console",
  "license": "Apache-2.0",
  "build": "Dockerfile",
  "timeout": 60,
  "asks": ["view:term"],
  "views": [{"id": "term", "label": "Console", "path": "/", "open": "full"}]
}
```

```
TEHAS_PLUGIN_GRANTS_CONSOLE="<commit> view:term"
TEHAS_PLUGIN_FRAMERS="https://obeya.example.org"
```

A refresh copies the view's files to `/out`. The view opens
`/_console/<id>` and draws the terminal, two tabs and End. End asks first
with `{"lost": true}` and shows the counts. The view closes on
`{"ended": true}`.

### voice

The voice part holds its manifest and its rules, as corrected. It needs
`TEHAS_PLUGIN_FRAMERS` too: its `full` view is framed by the chat host the
person pressed in.

### tutor

Text alone: no build, so no `kind`, `build` or `timeout`.

```json
{
  "plugin": 1,
  "name": "tutor",
  "label": "Course",
  "license": "Apache-2.0",
  "asks": ["skill:course", "skill:levels"],
  "skills": [
    {"id": "course", "about": "Teach how the factory decides, by asking, on its own tickets", "path": "skills/course.md", "chats": ["obeya"], "entry": "Take the course"},
    {"id": "levels", "about": "Levels per part, the target, saving progress, the final check", "path": "skills/levels.md", "chats": ["obeya"], "entry": "Take the course"}
  ]
}
```

```
TEHAS_PLUGIN_GRANTS_TUTOR="<commit> skill:course skill:levels"
```

Obeya draws "Take the course" and opens a chat with the two skills. No
other chat gets them. The facts, the person's progress and the chat's
tools are Obeya's.

### goldfish

```json
{
  "plugin": 1,
  "kind": "batch",
  "name": "goldfish",
  "label": "Goldfish",
  "license": "Apache-2.0",
  "build": "Dockerfile",
  "timeout": 1800,
  "asks": ["product", "history", "model", "spec", "hook:after:change.offered"],
  "hooks": [{"at": "after:change.offered", "timeout": 1800}],
  "counts": ["requirements", "met", "not-met", "unclear", "blockers", "not-run"]
}
```

```
TEHAS_PLUGIN_GRANTS_GOLDFISH="<commit> product history:500 model:400000 spec hook:after:change.offered"
```

The hook reads the context's `issue`, the approved body and its
`pi-spec v1` block from `/given/<issue>/spec/`
and the change from `/run/history/` and the clone. It asks its readers
through the model socket, each request with a fresh message list, and
watches `Tehas-Tokens-Left`. It writes the verdict, `counts.json` and
`report.md`. A change with no approved body gets `pass` with "No approved
spec" and no model call. With `block.json`, its `criteria` are the
requirements and the requirements reader is not asked.

## Work

After plugins are on in a release (2.1), after T9 has named the events,
and after the work each item builds on: the voice part's Work 3 (the
relay), 1.5.0's Work 5 (`history:`) and v3's Work 3 (`open: full`). Each
is a pull request; a security change says so.

1. **The reader.** `menu` with `frame` and no build. The hook rule for any
   event, with T9's names and no alias. `open` required, with `full`.
   `counts`, `entry`, the relay's `setup` and `query`. The samples in
   `api/` and the examples of the specification run through the reader in
   a test.
2. **The context.** `issue` and `at` in a hook, `model` in a hook at
   either event, `api/plugin-context.schema.json` and its samples.
3. **Framers.** `TEHAS_PLUGIN_FRAMERS`, its rule, `frame-ancestors` on a
   `full` view. Security change.
4. **The console's route.** `/_console/<id>` and its frames, against a
   stub of the console. It starts only after the console's feature spec is
   in `docs/specs/`. Security change.
5. **Entry skills.** `--entries`, the cap for each entry, `review`, the
   schema.
6. **The spec mount.** `spec`, the kept body and its hash check,
   `/given/<issue>/spec/` with `block.json` from `plan::spec_block`.
   **Security change**: a new read-only mount, `sandbox.rs` and the
   argument lists. It needs no feature of its own: the approval's `bodySha256` is in 2.0.
7. **The model in the hook after a cycle.** The socket in a hook run, the
   60-second bound, the day budget. Security change: the argument list of
   a hook with `model`, and model-made text in the status.
8. **Tokens left.** The header on every answer of the socket, tested
   against the stub endpoint.
9. **The pull request's range.** The collector's range in a hook, the
   merge base in the clone. Security change: the mount in a hook run.
10. **Counts and the event.** `counts.json`, its check, `plugin.verdict`

## Decided

- **Counts ride on a file of their own**, not on the verdict (6).
- **A hook on a pull request gets the pull request's range mounted** (8).
- **The tokens left are a header on the socket's answers**, not a field of
  the context (9).
- **The hook's `<when>` is `after`.** T11 names two kinds of event, notify
  and gate; a notify event's grant is `hook:after:<event>`. The goldfish's
  draft wrote `hook:report:`; it becomes `hook:after:change.offered`.
- **Who names a framer.** The instance, through industry's push. A plugin
  never names the page that frames it.

## Open points

- **A chat host on its own domain.** Settled in this revision as a rule:
  a framer must be same-site (a tailnet is one site), else 78 at load. The
  token swapped for a partitioned cookie is the later way for a host on
  another domain, and needs its own revision before it is built.
- **The console's feature spec.** The holder, the purge, tombstones, the
  gate's SSH key, `TEHAS_CONSOLE_LOGINS`, `TEHAS_CONSOLE_VIEW` and the
  `tehas console` commands are in the plugin's repository, `docs/spec.md`.
  They are a tehas feature, not plugin rules, and need a spec of their own
  in `docs/specs/` before Work 4.
- **The goldfish's label.** Its full review is asked for by the label
  `goldfish:full`, by 1.4.0's rule (the plugin renamed it from
  `goldfish-full`). The issue feed in the hook after a cycle, which the
  label needs, is not in this revision.
- **The event after a plan is written.** The goldfish's second hook point.
  Not in this revision; it waits for T9's list and for the first hook to
  prove useful.
- **The approved body's size.** GitHub's limit on an issue body (65,536
  characters) bounds it. This revision adds none.
- **The 60 seconds of a model request in the hook after a cycle.** Taken
  from the goldfish's own bound. To check against the measured trial
  before Work 7.
