# What tehas does

Tehas turns GitHub issues into reviewed pull requests, using the Pi coding
agent and [pi-rukas](https://github.com/trail-openers/pi-rukas) on self-hosted
models. A person writes the issue, applies one label, and later reviews and
merges. Everything in between is tehas.

It is a set of shell scripts, one small Rust program and a few containers on
one host. There is no server process of its own and no database for its state:
state lives in GitHub labels, in pi-rukas's state files and in plain files under
`~/tehas`. 365 days of measurements are kept in one SQLite file, see
[Analytics](/analytics).

Each feature below says how far it has been proven. "Verified" means it was run
on a tehas host and the result checked. Rows with a date were checked on the
example instance. Rows without one were checked on another instance, before
settings moved into an instance directory. Nothing here has run for longer than
a day.

## Queue and dispatch

| Feature                                 | Detail                                                                                                                                      | Status                                                                                  |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| GitHub issues as the only control plane | Labels are the state machine: `tehas:ready`, `tehas:running`, `tehas:awaiting-merge`, `needs-human-attention`                               | Verified                                                                                |
| Authorization by label                  | A cycle starts only if `tehas:ready` was applied by an allowlisted account, and the text has not been changed by anyone else since. A `tehas:ready` applied by the bot or anyone else is taken off the issue, said once on the issue, and logged. `tehas:plan` is checked the same way before a planning session starts, and taken off the same way. `tehas:urgent` moves an issue ahead only when applied by an allowlisted account; otherwise it is ignored and logged. A ticked box or a reply counts only from an allowlisted account, and only on the question whose comment id the host has on record | The labeller check is verified. Taking a `tehas:ready` or a `tehas:plan` that came from another account off the issue, the rule about changed text, the checks of `tehas:plan`, `tehas:urgent`, a tick and a reply are tested, not yet seen on a host |
| Open issues only                        | A closed issue is never taken, and a pull request is never taken, open, merged or closed. The poll asks GitHub what a number is before it marks an issue `tehas:running`; `tehasbot cycle` asks again before a label, a comment or a container, and exits 65. A closed issue that still carries a factory label is not counted in line or as being worked on. An issue that an open pull request closes is not taken: its `tehas:ready` comes off with a comment naming the pull request | Tested, not yet seen on a host |
| Closed issues lose state labels | Once a poll, after the rest of it, `libexec/tidy` takes `tehas:running`, `tehas:awaiting-merge`, `tehas:question`, `tehas:planning`, `tehas:refreshing`, `tehas:blocked`, `tehas:ready` and `tehas:plan` off closed issues, with one search of up to 100 issues and a 60-second timeout. `tehas:shipped`, `needs-human-attention` and the labels a person chooses stay. An open issue is never touched, nor a closed one whose cycle still holds its lock. A dry run says what it would remove. A failed search is logged and the poll goes on | Tested, not yet seen on a host |
| Polling                                 | A systemd user timer runs one poll two minutes after the previous one ended. A poll is a few GitHub calls and no model call                 | Verified                                                                                |
| Two commands                            | `tehas` is what a person types (`dispatch`, `work`, `plan`, `dev`, `index`, `update`, `labels`, `status`, `top`, `pause`, `resume`); `tehasbot` is what the units run. The scripts behind them are in `~/tehas/libexec`. `install.sh` removes the one-file-per-command layout that came before | Covered by the shell tests. Installed on the tehas-tehas host, where `tehas update` ran on 2026-10-15; the other commands are not recorded here as seen |
| Ticket concurrency                      | At most `TEHAS_TICKET_CONCURRENCY` cycles side by side, the host's CPUs minus one by default, each in its own unit, container and workspace. A ceiling: the slice's room decides below it, and at most four containers are in the slice. Urgent first (`tehas:urgent`), then lowest issue number | Seen on the tehas-tehas host, 2026-10-11, on the version before the slice. At 1: a poll started a cycle through its unit, and the cycle ended with its lock released. At 2: two cycles ran side by side, the second container with half the CPUs and memory of that version's budget, and stopping that cycle's unit ended it in 14 seconds with the container removed, the lock released and the issue labelled `needs-human-attention`. Not yet seen: two cycles that both ran to their end. The default of CPUs minus one is tested, not yet seen on a host |
| Stalled cycles                          | A cycle none of whose logs change for `TEHAS_WORK_STALL` seconds, an hour by default, is stopped as `stalled` and parked, with how long nothing moved and at which step | Covered by the shell tests, not yet seen on a host |
| Retry after a provider outage           | A cycle whose result says its failure is of kind `provider` (an image without `failure` in its result: a provider-class cap) is said as parked by a provider outage, and the dispatcher starts it again once, without a tick, when the model endpoint answers; a second such park waits for a person | Covered by the shell tests, not yet seen on a host |
| Full slots                              | A new pi-rukas commit runs at full concurrency from its first cycle. Each poll stops a running cycle whose issue is closed, or whose pull request (the bot's, opened since the cycle began) is merged or closed, and fills its slot on the same poll. A cycle that ends starts a poll at once, also when a poll is running then (`tehas-dispatch.path`). A poll that starts fewer cycles than there are free slots and issues waiting logs the one reason on every such poll, and `tehas status` shows it | Covered by the shell tests. Seen on tehas-tehas: a cycle that ended started a poll 5 s later, and its slot was filled 31 s after it ended; with `tehas-dispatch.path` on, a cycle that ended while a poll ran got the next poll 4 to 18 s later, four times on 2026-10-16 and 17, and the poll stopped #261 as `its issue is closed` on 2026-10-16. A stop for a merged or closed pull request has not been seen |
| Pause switch                            | Two switches, either enough: the flag `~/tehas/state/pause.json` that `tehas pause` writes on the host and `tehas resume` removes, and `tehas:pause` on the control issue, which anyone who may label applies and only an account in `TEHAS_ALLOWED_LABELERS` lifts. A running cycle finishes. The control issue is never worked on: a `tehas:ready`, a `tehas:plan` or a retry tick on it starts nothing, whatever account applied it, the poll changes no label of it and logs one line, and it is not counted in line | Tested against a stub GitHub. Not yet seen on a host, and not proven that a cycle finishes while the factory is paused                 |
| All hands                               | `tehas:all-hands` on the control issue, applied by an allowed account, is reported in `tehas status`, its JSON and the dashboard. It changes nothing in the factory; one applied by anyone else is ignored and said once | Covered by the tests, not yet seen on a host |
| Limit and drain                         | `tehas limit` caps the cycles running at once and may hold planning and improvement runs, until it expires or is cleared; one that expired or cannot be read holds every start. `tehas drain` sets a limit of nothing new and waits for the running cycles. Running cycles are never stopped | Covered by the tests, not yet seen on a host |
| History and export                      | `tehas history` lists what ended, oldest first, one line per cycle and per planning turn with `kind` telling them apart, after a cursor, for a program; it reads the files the units write and writes nothing. `tehas export` copies a cycle's result, logs, transcripts and Protolab page into a directory, every text file through the console's mask | Covered by the tests, not yet seen on a host |
| Red branch                              | With `TEHAS_BRANCH_CHECK` set, each poll asks GitHub once for that check on the branch's head commit. While it failed, no cycle, retry or refresh starts and the poll says `holding: main is red at <sha>`, which `tehas status` shows. Running cycles and planning turns go on. Pending, missing or unreadable holds nothing | Covered by the shell tests, not yet seen on a host |
| Review backpressure                     | No new cycle while the cycles side by side plus 2 issues await merge or are being worked on                                                                            | Built, not yet reached                                                                  |
| Model endpoint check                    | The queue is held, not burned, while the model endpoint does not list the configured model                                                  | Built after a real failure; the hold path itself is untested                            |
| Backup model endpoint | A provider in `models.json` may name a `backupBaseUrl` serving the same models. A cycle starts on the backup when the main endpoint does not answer or does not offer a model; each endpoint has its own token from `~/.config/tehas/env` | Tested with fake endpoints only |
| Retry                                   | `tehas:ready` from an allowlisted account starts a fresh cycle on a stopped issue, and on one that awaits a merge; tehas's labels of the earlier outcome go with the start, and `needs-human-attention` goes through the cycle's `--restart`, which pi-rukas answers by taking it off. Applied while the cycle runs, it waits for that cycle to end. The stopped cycle's workspace is kept beside the new one as `<name>-<issue>.before-retry` | A retry with `needs-human-attention` removed by hand first is verified, and the kept workspace was seen on the tehas-tehas host, 2026-10-11. The retry by the one label, on a stopped issue or one that awaits a merge, and the wait behind a running cycle are tested, not yet seen on a host |
| Admission by room in the slice          | The dispatcher starts a cycle only while `tehas.slice` has room for one more `TEHAS_CYCLE_RESERVE`, holds fewer than the four containers whose ceilings fit it, and is not under full memory pressure while more than half of it is promised. Every container in the slice counts at its reserve or its use, whichever is more. A slice that is missing or cannot be read holds cycles and planning turns, with one line in the log | Tested, not yet seen on a host |
| A cycle that left no report             | A poll finds an open issue marked `tehas:running` with no cycle behind it on the host, labels it `needs-human-attention` and says so on the issue. It starts nothing | Tested, not yet seen on a host                                                          |
| An epic is never started                | An issue whose `sub_issues_summary` says it has open sub-issues is a plan, not a change: `tehas:ready` comes off it with one comment naming the count and asking for a label on a sub-issue, a retry ticked on one starts nothing, and the log says so. The field is read from the issue call the poll already makes, so a GitHub without sub-issues, or an answer without the field or whose counts are not numbers, starts as any other issue. A `tehas:plan` session on an epic is allowed | Tested, not yet seen on a host |
| Planning on an issue                    | `tehas:plan` from an allowlisted account starts a planning session. Each turn is one run of pi-rukas's headless planner (`pi-rukas-headless plan`, pi-rukas v0.14.0 or later, `features.planTurns`) and ends in a comment: the planner's questions, or a drafted plan with its open points and one box, **File this plan**, which files it as shown. A ticked box or a reply from an allowlisted account continues it. Every turn works on the session's first commit, with the approved text and pi-rukas's record of the session carried between turns. The ceiling of a turn, 7200 seconds, is [the host manual's time limits](/host#time-limits). A turn runs as its own unit, `tehas-plan-<issue>.service`, which holds `state/plan-<issue>.json.lock` while it runs: the poll that starts it returns at once, a later poll starts no second turn, the turn's end asks for a poll that posts its outcome, and `tehas status` shows it with a `plan` line | Built, not proven: the headless turn, the confirm and the session carry are covered by the shell tests with the runner stubbed. No headless planning session has run on a host yet. The earlier Pi RPC path was seen on a host on 2026-10-14 (issue 109) and is gone |
| Refining a request                      | `tehas:refine` from an allowlisted account starts a planning session whose brief adds `lib/refine-brief.md` after the issue's text: read the code, then plan one issue a single `/work` cycle finishes, with exact paths, named test files and later parts listed. A confirm files that part; the label again plans the next | Built, not proven: covered by the shell tests. No refining session has run on a host |
| Retry by a tick                         | The comment of a cycle that stopped has two boxes. `Retry from a clean start`, ticked by an allowlisted account on a parked issue, starts a fresh cycle | Tested. The comment with its two boxes was seen on the tehas-tehas host, 2026-10-11; a tick has not been |
| Reporting                               | Start and outcome comments on the issue; token usage per agent role on the pull request                                                     | Issue comments verified; the pull request comment awaits the first cycle that opens one |

## The work cycle

| Feature                 | Detail                                                                                                                                   | Status                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Headless pi-rukas       | The container runs pi-rukas's one-shot runner, `pi-rukas-headless work <issue> --json`; the outcome is its result and its exit status, the console reads its stable NDJSON kinds. tehas reads result schema 5 only. Before a cycle the image is asked `--capabilities`, and a contract version, flag or `PI_ENSEMBLE_*` input it does not list, a role among them, stops the cycle with 78. `sandbox/build.sh` asks the base the same before it builds, and builds nothing on a base whose contract `tehas work` cannot use | Covered by the shell tests. The v0.12.80 runner was run by hand in a throwaway container on 2026-10-15 with no model: `--capabilities` answered, and `work` ended in a handoff with exit 10, a schema 3 result and NDJSON progress. Seen in cycles on tehas-tehas from 2026-10-16: schema 3 results with exits 10, 11 and 20, and handoffs that named their pull requests. The runner of pi-rukas main at 316134e, the first on schema 4, was run by hand the same way on 2026-10-18: a schema 4 result with exit 10. No cycle on a schema 4 image has been seen on a host yet, nor a refusal for a contract the image does not list. The v0.14.0 runner, the first on schema 5, has not been run yet |
| One comment per handoff | The runner is given `PI_ENSEMBLE_HANDOFF_CHANNEL=host`: pi-rukas posts no handoff and applies no label, and `tehasbot cycle` posts its handoff in the one comment of the park, or with the usage on the pull request. `tehas:awaiting-merge` only for the cap `awaiting-human-merge` with no review held on its round cap and no `needs-human-attention` on the issue; any other handoff with a pull request is parked and names the cap. A parked issue restarts with `--restart`, and nothing in tehas removes `needs-human-attention` | Covered by the shell tests, against the v0.12.80 result fixture. Not yet seen on a host |
| Cycle deadline | The runner is given `PI_ENSEMBLE_CYCLE_DEADLINE`, a quarter of `TEHAS_WORK_TIMEOUT` (at least a gate run and the handoff allowance, 8 minutes, given as `PI_ENSEMBLE_HANDOFF_TIMEOUT_MS`) before the end, or the allowance alone for an image with the feature `cycleDeadlineHandoffAllowance`: no step starts after it, and the cycle parks with the cap `deadline` | Covered by the shell tests. Not yet seen on a host |
| Time limit cap | A cycle that ends at `TEHAS_WORK_TIMEOUT` with no cap from the runner, whether the runner stopped itself or tehas stopped its container, is `timeout` and goes on record with tehas's cap `wall-clock`, the step it was in and a `capReason` | Covered by the shell tests. Not yet seen on a host |
| Gate runs per container | The runner is given `PI_ENSEMBLE_VERIFY_CONCURRENCY` from the container's CPU quota and memory ceiling | Covered by the shell tests. Not yet seen on a host |
| Workarounds that expire | `TEHAS_RUKAS_WORKAROUNDS` lists the settings that work around a pi-rukas defect with the release that fixes it; a cycle on an image of that release or later stops with 78 | Covered by the shell tests |
| Sandbox                 | Agents run in a container with CPU and memory limits, a fresh clone to work in and the bot token: no Docker socket, no SSH keys, no host environment. Every capability of Docker's default list is dropped and only `CHOWN` and `FOWNER` are given back, and no process gains rights through its mode or file capabilities; the same options for a cycle, a planning turn, a `tehas dev` session and the push check, from one function in `lib/sandbox.sh`. Each starts as the tehas user, not as root. The network is not restricted | Covered by the shell tests, which pin each option on all four `docker run` lines. On tehas-tehas on 2026-10-19 every container started as root with these options died in its entrypoint (`setpriv: setresuid failed`, issue #420); the image started by hand with them and `--user` ran as its own user. Not proven: no whole cycle has been seen to build, test and drive a headless browser with the capabilities dropped; that is owner work on a host |
| Project gates           | The cycle runs the project's own `.pi/verify-cmd`, `.pi/verify-cmd-full` and `.pi/smoke-cmd`                                             | Gates verified in the sandbox; first full cycle in progress at the time of writing |
| Protected gates         | pi-rukas halts a cycle whose patch touches `.pi/`, `.github/`, `CODEOWNERS` or `agents.json`. An edit to `AGENTS.md` or `CLAUDE.md` is not halted: it ships and you see it in the diff, but the cycle is judged against the doctrine at its own base commit, so its own edit changes nothing for it | pi-rukas feature, not exercised here. The list is pi-rukas's own, behind its `PI_ENSEMBLE_PROTECTED_PATHS` |
| Review severity bar     | A review finding blocks the change at the severity the product states, and starts a fix round. Here that bar is MEDIUM and above: LOW findings are notes on the pull request, a CRITICAL finding blocks whatever the bar says, and pi-rukas reads the bar from the product's doctrine (`AGENTS.md`, or `CLAUDE.md` when it has one) at the cycle's base commit, or from `PI_ENSEMBLE_REVIEW_THRESHOLD` on the instance. Three rounds at most | pi-rukas feature. Its MEDIUM default was seen in the log of cycle 97-261013-125428, 2026-10-13, where the verdict was recorded as unstated because this repository states no bar. A bar read from doctrine has not been seen on a host |
| Human merge             | Nothing merges on its own                                                                                                                | By configuration (no merge grant in `AGENTS.md`)                                   |
| Self-hosted models only | One model for every role, set in the instance's `instance.env`                                                                           | Verified                                                                           |
| A model per role        | `PI_ENSEMBLE_MODEL_<ROLE>` gives one of the five roles the pinned pi-rukas reads its own model; the provider defaults to the subagent one. An unknown role is refused with exit 78 | Covered by the shell tests. Not yet seen on a host                                 |
| Work by hand            | `tehas dev` gives a person an interactive pi-rukas session on the host: the cycle's sandbox with a terminal, a clone that is kept, and the person's name on the commits. The push and the pull request are still the bot's | Seen on the tehas-tehas host through the own-account entry below, which runs this command. Started directly as the tehas user: covered by the shell tests only |
| Work by hand, own account | An account in the group `tehas` types `tehas dev` and gets its session in a clone named after it, with the name and email of its own git configuration on the commits. One `sudo` rule, written by `bootstrap.sh dev`, runs it as the tehas user | Seen on the tehas-tehas host: the root step, the clone, a session that reached the model, and the account's own name and email as author and committer inside it. A push and a pull request from a session are not yet seen |
| Concurrency knob        | `TEHAS_CONCURRENCY` sets how many workstreams a cycle runs side by side; 1 by default, above 1 only with one cycle at a time (`TEHAS_TICKET_CONCURRENCY=1`), else every command stops with 78 | Setting reaches the sandbox; its effect on a cycle is not yet observed             |
| Code index              | `tehas index` builds the index behind the agents' code search, in the sandbox image; `install.sh` runs it once. The dispatcher refreshes it as its own unit, `tehas-index.service`, before it starts cycles while none is running and the branch has moved, and starts them on the poll after it; a cycle started while another runs gets the index as it is, so on a host that is never idle it falls behind the branch | Covered by the shell tests; run against the upstream image on a development machine, not yet on a tehas host |

What the five attempts showed, none of it a fault of the instance's setup:

- **A cycle needs two model conversations served at once.** pi-rukas's
  driving session takes turns of its own while a step's agent works. With one
  free slot, or with other agents using the model, calls are refused
  (`no free slot`) and the cycle stops after three retries. Attempts 1 to 3
  ended that way. The dispatcher only checks that the model is listed.
- **A renamed repository empties the queue without an error.** Fixed: the
  dispatcher now checks the name at every poll.
- **pi-rukas can lose a file an agent left uncommitted** (reported upstream as
  pi-rukas issue 1049). Attempt 4 did the work and failed its gate for that
  reason. Attempt 5 passed after `AGENTS.md` told agents to commit their own
  work. pi-rukas fixed it in v0.12.80, and the rule was dropped.
- **The pull request was opened against `main`**, not the branch the cycle
  started from, so its review read the whole difference between the two. The
  lens review ended incomplete and the issue carries `needs-human-attention`
  next to `tehas:awaiting-merge`. On an instance whose work branch is the
  default branch this does not arise.

One cycle is one cycle. It used about 8.5 million tokens for a 172-line change.

The local line: a cycle starts from the product's default branch, and this
repository's contract files were on a work branch when the instance was set up.
`TEHAS_BRANCH` named that branch on the host until it was merged.

## Not built

- Monitoring: availability probes, incident issues, weekly report.
- Electricity price command (#410). The gate for the lowest issues exists:
  `TEHAS_LOW_GATE` names a command the dispatcher asks before it starts an issue
  it puts on neither the urgent list nor the `tehas:next` list, and only exit 0
  lets them start (see [tehas dispatch](/tools#tehas-dispatch)). Nothing on a host
  fills it yet, and no command reads prices yet. `tehas:urgent` and `tehas:next`
  change ordering only.
- Model evaluation; every role uses the same model by default, by decision,
  not by measurement.
- Watching tehas itself: a failed refresh. A full disk is seen where previews
  are on, and stops previews only. A cycle that holds its lock and is not
  heard from for 20 minutes is stopped by the dispatcher; tested, not yet
  seen on a host.
- More than one project per host. See [A new project](/new-project).
- A private database copy per cycle or per preview.

## Known limits

- One host, one project. Cycles that run side by side do not know of each other: two issues that touch the same files give conflicting pull requests.
- The cycle's container holds the bot's token, so agent code can do what that
  token can. Give each instance its own bot account. See [The host](/host).
- Logs are removed only where the improvement loop is on: each of its runs
  deletes the per-cycle files in `~/tehas/logs/` that are older than seven
  days. Without the loop they stay until a person removes them.
- The improvement loop's analyst is one more conversation with the model, for
  up to 60 minutes every three hours. On an endpoint with few slots it can
  take one a running cycle needs.
- A pull request closed without merging leaves `tehas:awaiting-merge` on its
  issue until someone removes it.
- The cleaner frees build output, Docker's build cache and host scratch, and no
  image. Dated sandbox tags and the pulled base image stay until a person prunes
  them, because an image is not made again cheaply. That is #411.
- A preview is public, and it is built from a pull request nobody has reviewed
  yet. Only a branch in the product repository gets one, and only when an
  owner, member or collaborator opened the pull request. See
  [Previews](/edge).
