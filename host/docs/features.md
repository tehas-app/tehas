# What tehas does

Tehas turns GitHub issues into reviewed pull requests, using the Pi coding
agent and [pi-rukas](https://github.com/trail-openers/pi-rukas) on self-hosted
models. A person writes the issue, applies one label, and later reviews and
merges. Everything in between is tehas.

It is a set of shell scripts, a few Rust programs and a few containers on one
host. The queue lives in GitHub labels. The host's own records are in the state
store, `~/tehas/state/tehas.db`, and locks, logs and container files stay plain
files under `~/tehas`. 365 days of measurements are kept in a second SQLite
file, see [Analytics](/analytics).

Each feature below says how far it has been proven. "Verified" means it was run
on a tehas host and the result checked. Rows with a date were checked on the
example instance. Rows without one were checked on another instance, before
settings moved into an instance directory. "Tested" or "covered by the tests"
means only the tests: nobody has seen it on a host. A feature still being built
is off in every release, and its status says so first.

What the five attempts showed, none of it a fault of the instance's setup:

- **A cycle needs two model conversations served at once.** pi-rukas's
  driving session takes turns of its own while a step's agent works. With one
  free slot, or with other agents using the model, calls are refused
  (`no free slot`) and the cycle stops after three retries. Attempts 1 to 3
  ended that way. The dispatcher only checks that the model is listed.
- **A renamed repository empties the queue without an error.** Fixed: the
  dispatcher now checks the name at every poll.
- **pi-rukas can lose a file an agent left uncommitted** (reported upstream as
  pi-rukas issue 1049). Attempt 4 did the work and failed its gate for that
  reason. Attempt 5 passed after `AGENTS.md` told agents to commit their own
  work. pi-rukas fixed it in v0.12.80, and the rule was dropped.
- **The pull request was opened against `main`**, not the branch the cycle
  started from, so its review read the whole difference between the two. The
  lens review ended incomplete and the issue carries `needs-human-attention`
  next to `tehas:awaiting-merge`. On an instance whose work branch is the
  default branch this does not arise.

repository's contract files were on a work branch when the instance was set up.

## Not built

- Monitoring: availability probes, incident issues, weekly report.
- Electricity price command (#410). No command reads prices. A program that
  runs the factory can hold starts back with `tehas limit` and choose which
  ready issues start first with `tehas order`; nothing on the host does that
  by itself.
- Model evaluation; every role uses the same model by default, by decision,
  not by measurement.
- Watching tehas itself: a failed refresh. A full disk is seen where previews
  are on, and stops previews only. A cycle that holds its lock and is not
  heard from for 20 minutes is stopped by the dispatcher; tested, not yet
  seen on a host.
- More than one project per host. See [A new project](/new-project).
- A private database copy per cycle or per preview.

## Known limits

- One host, one project. Cycles that run side by side do not know of each other: two issues that touch the same files give conflicting pull requests.
- The cycle's container holds a GitHub token for its repository, so agent code
  can do what that token can, and its network is open unless `TEHAS_EGRESS=on`
  (tehas#51). The factory acts as [a GitHub App](/github-app), and the
  cycle's token reaches the product repository only and lasts an hour. Give
  each instance its own App. Turn on the egress limit to keep the container to
  GitHub, the registries and the model endpoints: see
  [Where a container may connect](/host#where-a-container-may-connect).
- The cycle's container holds the model key, as `$TEHAS_MODEL_KEY_<NAME>`. Give
  the factory a key of its own, with its own spending limit, so that you can
  revoke it without stopping anything else.
- The cycle's token can comment on any pull request of the repository, not only
  the one its cycle opens: pull requests take one write permission for both.
  Keep the factory on a repository whose pull requests it may write to.
- GitHub's bad minutes cost more than the step they hit (tehas#823). A poll
  that cannot read the queue after its retries does nothing, and the next poll
  tries again; one that cannot read the issues to plan starts nothing either
  (tehas#1702). A cycle whose push or pull request failed on GitHub's side is
  finished by a later poll, three tries within the hour. Its other last steps,
  such as the handoff comment, are not tried again: read the run log, and use
  [`tehas:finish`](/operating#finishing-a-stopped-cycle) for a cycle left
  without its pull request.
- tehas checks the issue's title and body against the approval when it starts a
  cycle, and the cycle then reads the issue from GitHub again. An edit made in
  between reaches the cycle. Until pi-rukas reads the text tehas hands over, let
  only people you trust edit the product's issues.
- The lean driver is still being built, and a host has not yet been seen to run
  it to a merged change. A release refuses it; it is planned for 1.1. See the
  lean rows above.
- The review loop is still being built: no run has been seen on a host. A
  release refuses `TEHAS_REVIEW=on`: see the review loop row above.
- Files under `live/` are for the dashboard, not for programs, and may change in
  any release. A program reads the commands' `--json` instead: see
  [the factory API](/api).
- A host is assumed to sit on a private network. The MCP server is not
  hardened for the open internet: reach it over the private network or through
  your own proxy with TLS, and give out keys only to clients you trust.
- A kept installation token is used until it runs out, up to an hour, after it
  stops reaching the repository, for example when the App is taken off it.
  `tehas github check` says whether the token reaches the repository.
- A pull request closed without merging leaves `tehas:awaiting-merge` on its
  issue until someone removes it.
- A parked issue is held until its body changes or Retry is ticked, also when
  the host caused the park (tehas#1742). A gate on the base branch killed for
  memory can park as `verify-baseline-red`, and the issue stays held after the
  base is green again. Read the run log; when the base was not
  red, tick Retry in the park comment.
- Nothing deletes a branch a cycle pushed (tehas#1791). Each
  `feature/issue-<n>` and `finish/issue-<n>` stays on GitHub after its issue
  closes, and every product checkout fetches it. Turn on "Automatically delete
  head branches" in the repository's settings, and delete the branches of
  closed issues by hand.
- The cleaner frees build output, Docker's build cache, host scratch, the
  sandbox image's dated tags past the age except the newest and except any a
  container or a `uid` tag holds, and the pulled base image of that age, removed
  by its own name. No volume is removed, no image a container was made from, and
  no image that has lost its tag.
- A preview is public, and it is built from a pull request nobody has reviewed
  yet. Only a branch in the product repository gets one, and only when an
  owner, member or collaborator opened the pull request. See
  [Previews](/edge).
